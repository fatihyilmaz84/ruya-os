# T-224 — Telemetry: hardware information, consent, settings and a service that sends it

Status: todo · Phase: 3 · Depends: T-220 · Area: api, services, shell, docs · Size: M · Owner: lead

**Plan audit 2026-11-10 (lead; where this differs from the text below, this wins):** Follows T-220 (it adds rows to that pane and changes its "no telemetry" text). Split in three before dispatch (contract and service; wizard step and pane rows; reference receiver and protocol document).

## Goal
The project learns what hardware its users have, so it knows what to support and optimise, and the user is in charge: nothing is sent until they have chosen, every category can be turned off at any time, they can see exactly what would be sent, and turning it off deletes what is queued. Owner request, 2026-11-06: "add telemetry support: I want to know what the specs of the users are, which crashes occur, and report them; the user can turn them all off." Crash reporting is T-225 and uses this task's service, consent and settings.

## Decisions (consent model decided; the rest still the owner's, later)
- **Consent model: DECIDED (owner, 2026-11-08).** An **explicit first-boot choice, Share / Don't share** (two equal buttons per category, no pre-ticked box), **nothing collected or sent before the answer**, and **everything switchable off later** in Settings -> Privacy (turning a category off deletes its queued data). Build exactly this; "on unless turned off" is not planned. The reasoning that led to it follows. The owner is in the EU (Netherlands): the GDPR/ePrivacy rules treat device identifiers and diagnostic data as personal data unless truly anonymous, and valid consent is an explicit, unambiguous choice (no pre-ticked box). **Design:** a first-boot screen "Help improve RuyaOS" with two categories (**Hardware information**, **Crash reports**), each with a short plain explanation and **two equal buttons, Share / Don't share**; nothing is collected or sent before the answer; the same switches live in Settings -> Privacy; an installation that never saw the screen (an update) shows it once to the next admin sign-in and sends nothing until answered. Opt-out-by-default ("on unless you turn it off") is possible only if the data is anonymous in the legal sense; the owner decides with legal advice. The task builds the *explicit choice* flow; flipping the default later is one constant.
- **Backend and cost: still open, the owner's, later.** Where the data goes (a self-hosted open-source receiver, a hosted service) and who pays is an owner decision (spending, a data-processing agreement, retention). This task defines an open, minimal HTTPS protocol and ships a **reference receiver for development** (so nothing here depends on a vendor); the production endpoint is a configuration value.
- **Retention (proposed, still open with the privacy notice, the owner's, later):** hardware reports 13 months; crash reports 90 days; the server never stores IP addresses. A published **privacy notice** (short text in the console, full page on the project site) is part of the release (owner).

## Scope
1. **What may be collected (a closed schema, version 1; anything else is a bug):** *Hardware report*, at most once a week and on a change: CPU model and logical core count, RAM size (rounded to 1 GiB), GPU vendor, model and driver (kernel and Mesa/NVIDIA versions), display resolution and refresh rate (no EDID serial or name), storage type (SSD/NVMe/HDD/eMMC) and total size rounded to 10 GiB, firmware type (UEFI/BIOS, Secure Boot yes/no), network type (Ethernet/Wi-Fi, Wi-Fi chipset vendor), Bluetooth adapter vendor and chipset, connected controller **models** (vendor:product ids of gamepads), audio output type (HDMI/analog/USB/Bluetooth), RuyaOS version and update channel, kernel version, UI language, time-zone **region** (not city), month of installation. **Never:** serial numbers, MAC addresses, IP addresses, Wi-Fi names, user or profile names, avatars, the list of installed or played apps (an opt-in third category "App usage" is a later decision, Inbox), file names, paths, hostnames, anything from a profile's home.
2. **Identity:** a random installation ID (UUIDv4, generated at first consent, stored under `/var/lib/ruya-telemetry/`, not derived from hardware); "Reset my ID" in Settings makes a new one; no ID exists before consent and it is deleted when everything is turned off.
3. **Contract first: `org.ruyaos.Telemetry1`** (system bus, `ruya-shell` and root only): properties/methods `GetSettings() -> a{sv}` (`hardware` b, `crashes` b, `answered` b, `install_id_present` b, `endpoint_configured` b), `SetSettings(admin_id, admin_pin, a{sv}) -> status` (admin only; turning anything off deletes the queued data of that category at once), `GetPreview() -> s` (the exact JSON the next hardware report would contain, built now, so the user can read it), `GetPending() -> aa{sv}` (queued items with size and kind) and `DeletePending()`, `ResetId()`, signals `SettingsChanged`, `Sent(kind, ok)`.
4. **Service `ruya-telemetry` (Rust, new crate; pure core + traits, as `ruya-update`):** collects the hardware facts through a trait (fake in tests), builds the schema-validated report, queues to a size-capped state directory (atomic files, 0600, at most a few MB), sends over HTTPS with the system trust store (no custom TLS roots), batching, retry with exponential back-off, a 30 s timeout, never while a connection is metered (T-216, until it exists: never on Wi-Fi marked metered by NetworkManager), never before consent, rate-limited, jittered, no retries storm after an outage; the endpoint and a `RUYA_TELEMETRY=off` build/runtime kill switch come from `/usr/lib/ruyaos/telemetry.toml`. Unit with the usual hardening (no new privileges, `AF_INET`/`AF_UNIX` only, read-only except its state dir); the D-Bus policy lets only `ruya-shell` and root call it.
5. **Settings -> Privacy (shell):** a "Help improve RuyaOS" group: the two switches, **View what is shared** (shows the preview JSON as readable rows and the pending crash reports with their text), **Delete pending data**, **Reset my ID**, a plain statement of what is and is never collected and a link text to the privacy notice; admin only to change, readable by everyone. **First-boot step and the one-time prompt** per the consent model above (controller-first, the two equal buttons, Back works, no dark patterns), Turkish.
6. **Reference receiver for development** (`tools/telemetry-receiver/`, small, dependency-light): accepts the schema over HTTPS or HTTP on localhost, validates it against the schema (rejects unknown fields), stores nothing but a JSON line per report in a local file, never logs IPs; used by the VM check and as a protocol specification.
7. **Docs:** `docs/specs/01-platform.md` "Telemetry" section (the schema table, the consent flow, retention, the kill switch), the protocol in `docs/telemetry-protocol.md`, the privacy statement text; `docs/developers/` mentions that app crashes of third-party apps are never reported with data beyond the app id and exit reason (T-225).
