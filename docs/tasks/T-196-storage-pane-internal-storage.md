# T-196 — Settings → Storage shows the console's own storage

Status: in-progress · Phase: 2 · Depends: — · Area: api, services, shell · Size: M · Owner: builder

## Goal
Settings → Storage shows the internal storage first (how much is free, and how much the apps and games take), then the removable drives as today. Owner, 2026-11-06, after the first run on real hardware: with no USB stick the pane showed nothing, and a console needs to know how full it is. Today's pane skips every internal disk on purpose (T-174: the OS is not a "drive").

## Scope
1. **Contract first (`Devices1.Storage`):** add a method `GetSystemUsage() -> a{sv}` and a signal `SystemUsageChanged`. Keys: `total_bytes` x and `free_bytes` x (the filesystem that holds `/var`, where apps, games and profile data live), `apps_bytes` x (the system Flatpak installation, `/var/lib/flatpak`), `data_bytes` x (profile homes, `/var/home`), `system_bytes` x (the rest of what is used: `total - free - apps - data`, never negative). Unknown parts are `-1`. Document it in the XML header; the existing `ListVolumes` stays as it is (the OS is still not a volume).
2. **Service (`ruya-devices`):** a pure core for the numbers (unit-tested with a fake filesystem source) and a Linux source: `statvfs` for total/free (cheap), directory sizes for `apps_bytes` and `data_bytes` computed **on the blocking pool, cached** (for example 60 s) and recomputed after a change signal from the Store (`InstalledChanged`) or on request when the cache is older than that. It must never block the D-Bus executor (T-192 lesson) and never follow symlinks out of the tree. No new privilege: read-only, the unit's hardening stays (check `systemd-analyze --user security ruya-devices` before/after). A prefer-std solution; a new crate needs a one-line justification.
3. **Shell:** `Storage` facade gets `internal` (a map with the five numbers, `valid` false until the first reply); the D-Bus backend and the mock follow the contract; the guard against late replies applies (`RequestSequence`, T-191). The mock has a believable internal disk (for example 464 GB, 450 GB free) and a low-space variant for the screenshot.
4. **Pane:** a first section "This console": one row with the free space ("450 GB free of 464 GB") and a usage bar, then rows for "Apps and games", "Profile data" and "System" with sizes (use the existing row/progress components; text uses `qsTr`, Turkish translated). Below it, the existing removable-drive rows unchanged. With less than 10 % free the bar uses the warning colour token (no new tokens). Focus order: the section's rows are focusable like the others, eject rows keep their behaviour and focus stays on a row when numbers update.
5. **Docs:** the XML, `03` (the Storage "As built" paragraphs: internal usage; the "OS is not listed as a volume" rule stays), `04` §8 if a component is used in a new way, `dev-setup.md` (what the devices check prints).

## Out of scope
- Per-app sizes and uninstall/clear-data from this pane (the Store has them; a later task), a low-space toast, blocking an install when the disk is full, formatting or partitioning, other internal disks (the second data disk case: list it as a volume only if it is mounted outside the system paths, as today).

**Built.**
- **Contract** (`api/dbus/org.ruyaos.Devices1.xml`): `Devices1.Storage.GetSystemUsage() -> a{sv}` with `total_bytes`, `free_bytes`, `apps_bytes`, `data_bytes`, `system_bytes` (all `x`, `-1` unknown) and the signal `SystemUsageChanged` (sent when `apps_bytes` or `data_bytes` change after a measurement, not for free space alone). `ListVolumes` is unchanged.
- **Service** (`services/ruya-devices/src/sysusage.rs`, new; `dbus.rs`, `main.rs`): a pure core `SystemUsage<S: SystemSource, C: Clock>` with a fake source and clock for tests; `LinuxSource` (`statvfs` through the `libc` the crate already has; walk with std only, no new crate). The call never waits for a walk: total and free are read fresh (on the blocking pool), apps and data come from the cache (`-1` until the first measurement; a walk that could not read everything it walked is `-1` too, see below), a stale cache (60 s) starts a measurement on the blocking pool from the call (spawned on zbus's executor, detached) and it ends in `SystemUsageChanged`. A measurement also runs once at start and after the Store's `InstalledChanged` (`watch_installed`, a match rule on `org.ruyaos.Store1`, debounced like the udisks watcher). A change signal during a walk makes the result stale again (tested), only one walk runs at a time. The walk counts `st_blocks * 512`, counts hard-linked files once (a Flatpak deployment is hard links into the OSTree repo, so without this the apps would be counted about twice), never follows symlinks and stays on the device of its root.
- **Profile data is unknown today (`data_bytes` is `-1`), round 2.** Every profile is a Unix user (`ruya-p<N>`) with a 0700 home in `/var/home` and `ruya-devices` runs as `ruya-shell`, so the walk of `/var/home` sees the home directories and none of their files: a number would be a few kB and every save and `~/.var/app` would show as "System". Round 1 wrongly called this a "lower bound"; that wording is removed everywhere (XML, `03`, comments, this file). Now a walk with `TreeSize.partial` (anything unreadable) is reported as `-1`, for `data_bytes` and for `apps_bytes` alike, never as a partial number. `system_bytes` is the remainder of the known parts: `total - free - apps - data` when the data is known, `total - free - apps` while it is `-1` (everything used that is not apps), never negative, `-1` while total, free or apps is unknown. Exact per-profile sizes need a root source (`ruya-profiles` reporting them): a follow-up, no new privilege here. "Apps and games" counts only `/var/lib/flatpak`; game libraries and app data under a profile's home (`~/.var/app`, `~/.local/share/Steam`) are not in it until per-profile sizes exist.
- **Shell:** `StorageBackend` has `refreshUsage()`/`usageListed(SystemUsage)` with its own `RequestSequence` (`beginUsageRequest`/`deliverUsage`/`acceptUsage`); the D-Bus backend calls `GetSystemUsage` on start, when the name appears and on `SystemUsageChanged`, counting a failed call as an outcome; the mock has a 464 GB disk as the real service reports it today (450 GB free, apps 6.5, data `-1`, system 7.5; `mockSetInternal` can give the data a number) and test hooks (`mockSetInternal`, `mockLowSpace`, `mockRefreshInternalDelayed`) that go through the same guard. `Storage.internal` = `{ valid, totalBytes, freeBytes, appsBytes, dataBytes, systemBytes }`, `Storage.refreshInternal()` (the pane calls it when it becomes visible, not when Settings opens: free space has no signal).
- **Pane:** heading "This console", a `UsageRow` (a `SettingControl` with the existing progress-bar look inline: pill track `glass` + `glassBorder`, fill `text`, `warningText` below 10 % free), then "Apps and games" and, while `dataBytes` is `-1`, one row "Other" with `systemBytes` (Turkish "Diğer"); with the data known the "Profile data" row appears and the last row is "System". A "Drives" heading and the volume rows as before. Unknown numbers show an em dash. Strings translated (Turkish, English copy).
- **VM check:** `scripts/vm-devices-check.sh` has a storage part (`storage_usage_check`, in `check`, or `vm-devices-check.sh storage`): five keys; `total_bytes`/`free_bytes` against `stat -f /var` within 1 %; waits for the first measurement of `apps_bytes`; expects `data_bytes` to be -1 (a number passes too); the parts add up; `apps_bytes` close to `du -sx /var/lib/flatpak`; `nobody` refused; then a signed 80 MB test app is built, added and installed through `ruya-store`, and `apps_bytes` must grow by more than 40 MB and `SystemUsageChanged` must be sent (`SKIP_APPS_GROWTH=1` skips the install; everything it makes is removed). Written, `bash -n` clean, not run (no image built here). Hardware: the Dell should show about 450 GB (lead check).
- **Unit hardening:** no unit change, nothing new is needed (`statvfs` and reads are in `@system-service`; `ProtectHome=read-only` still lets it read `/var/home`); `systemd-analyze --user security ruya-devices` before/after was not run (Linux only), `vm-devices-check.sh security` prints it.

**Tests and the revert test.** Rust (`sysusage.rs`, 17): five keys from a fake statvfs and fake sizes, system as remainder and never negative, a partial `/var/home` walk gives `data_bytes` -1 and system = total - free - apps, a fully readable one gives the sum, a partial apps walk is -1, free capped at total, a failing walk is `-1` and not an error (and a failing statvfs leaves the walks), cache reuse then recompute with a fake clock, a change signal making the cache stale (also during a walk), one walk at a time, plus the real walk on a scratch tree. `tst_storage.qml`: numbers from the mock, the section and its order and text, rows updated in place with focus kept (same row objects, Down still moves), the warning colour token at the 10 % boundary and back, unknown parts as a dash, no "Profile data" row and "Other" while the data is unknown (the mock default), the known case (its own row, "System", Down reaches both, the row going again), the numbers asked for again when the pane is shown (and not when it is hidden), a late reply dropped.
