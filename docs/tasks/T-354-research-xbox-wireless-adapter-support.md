## Goal
A written recommendation, **without building anything**, for how RuyaOS could support the Xbox Wireless Adapter (the USB dongle for Xbox One/Series pads) and Xbox pads in general, ending in a ready list of follow-up tasks the lead can plan. Owner decision, 2026-11-08: RuyaOS does **not** ship "no support" for the adapter; it is **investigated**. The owner's idea to evaluate: a **"Download firmware" button** in Settings where the *user* (not RuyaOS) fetches the dongle firmware from Microsoft's own source at run time, as `xone`'s firmware script does; RuyaOS redistributes nothing; the file lands under `/var` and the driver loads it. Part of T-261 (controller families audit); T-261's own scope no longer adds or rules out the driver, it links to this task's result.

## Scope (research and writing only)
1. **The driver on an immutable image.** Compare for the dongle, with evidence from the Fedora 44 kernel (check what the image's kernel is; the owner expects 7.x) and each project's current state: (a) `xone` built at image-build time as a kernel module (akmod/DKMS inside the Containerfile, like NVIDIA, `image/build/40-nvidia.sh`) versus a prebuilt kmod RPM from a third-party repo; (b) **Secure Boot** (the Dell runs with it on): what the module is signed with, whether the project MOK key of §2.3 exists yet (today the NVIDIA key is ephemeral per build), the one-time MOK screen on a controller-only console (a keyboard-less player cannot answer it: say what the UX would be), and a **userspace alternative** (an `xow`-style libusb + `uinput` daemon needs no module, no MOK; its maintenance state and a hardened unit would be ours); (c) kernel API breakage rate across 6.x to 7.x for each project and who fixes it, what a failed module build does to an image build (must never fail the image: optional layer), image size, update path through `bootc upgrade` (module rebuilt per kernel); (d) what the project would own: security fixes, a fork or not.
2. **The firmware.** Facts to establish and quote with source and date: what exactly the adapter needs (file names, which hardware revisions and USB ids), where `xone`'s script gets it (Microsoft's update catalogue driver package, extracted with `bsdtar`/`cabextract`), its size and a **SHA-256 of each accepted blob**; the licence terms that apply to that file and to the download (Microsoft Update Catalog terms of use, the driver package's licence, and whether use outside Windows is restricted); whether xone's README or Fedora/RPM Fusion say anything about redistribution (they do not ship it). Do **not** download or store the blob in the repository; hashes and URLs are enough. If a download is attempted on this host to learn the hash, delete it afterwards and say so.
3. **The "user downloads it" design** (a design, not code): Settings > Controllers shows, only when a dongle is present and the firmware is missing, a row "Xbox adapter needs a one-time firmware download" with a **Download** button and a plain note on what is fetched, from whom and that RuyaOS does not host it. Specify: the states (not needed, needed, downloading with progress, done, failed with a reason and Retry, checksum mismatch, offline); the **offline case** (a second button "Install from a USB stick" that takes the file the user copied there: explicit action only, nothing auto-runs from removable media; or a plain "connect to the internet" message); a "Remove firmware" action; Back leaves every state; Turkish text; which profile may do it (admin, as other system changes). **Security design:** TLS to a pinned host name with the system trust store, a size cap, the SHA-256 of the extracted blob compared with a list shipped in the image (an unknown hash is refused, never installed), the download and extraction done by an **unprivileged, sandboxed helper** (`DynamicUser`, no access to profile data, extraction of the archive in a namespace with no network), a separate small root step that copies the verified file to a root-owned directory under `/var/lib` and tells the driver (kernel `firmware_class.path`, `/var/lib/firmware`, or a path the userspace driver reads: find which the image's kernel supports); the file is data uploaded to the dongle, **never executed on the host**; no telemetry; the Outcome says what a hostile mirror or archive could do.
4. **Legal and terms-of-service risk, stated honestly.** Compare: RuyaOS redistributing the file (not an option), RuyaOS scripting a download the user triggers from Microsoft's own server, and the user doing it by hand. Say what is known, what is not, and what a lawyer must answer. **This is an owner-level question: the planner already put a short Proposed line under "Open owner decisions" in `docs/STATUS.md`; refine it there (and write the long form in `docs/STATUS-parked.md`) with your findings and a recommendation, and do not decide it.** The research and the recommendation do not depend on the answer, except that the download button is never built before it.
5. **The alternative that needs none of this.** Verify what already works without the dongle and without out-of-tree code: an Xbox One/Series pad **over a USB cable** (`xpad`) and **over Bluetooth** (BlueZ with the kernel's `hid-microsoft` / generic HID path; `xpadneo` only adds rumble modes, battery detail and mappings). Check the image: kernel config and modules (`CONFIG_JOYSTICK_XPAD`, `CONFIG_HID_MICROSOFT`, `uinput`; `modinfo` in the VM or WSL kernel package of Fedora 44), what `ruya-inputd` and `families.rs` do with them, and what a VM can fake (`umockdev` fixtures, QEMU USB passthrough of a real pad on the host if the owner has one). Mark every cell `host`, `vm`, `hw` or `unverified` honestly; known caveats (Series pad firmware revisions that break Bluetooth bonding, the pad's pairing button) go into the family table of T-261 and the guidance text of T-260. State plainly what the dongle adds over this (lower latency, no Bluetooth stack, up to 8 pads, headset audio pass-through) so the owner can judge whether it is worth the cost.
6. **Recommendation and the task list.** One recommendation among: do nothing beyond cable and Bluetooth; userspace driver; in-image kernel module; optional layered module installed from the Store later; each with cost, risk and what the owner must decide. Then a **draft list of follow-up tasks** (title, Area, Size, Owner, dependencies, `Developer surface`, which need a "VM (this task)" check, which need hardware) written as a table in the Outcome and as ready-to-copy task headers, **not created** as files: the lead plans them after reading the recommendation. Include the cost of each in lines of code and image megabytes where known.
