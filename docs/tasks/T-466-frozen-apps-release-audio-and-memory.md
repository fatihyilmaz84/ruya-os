# T-466 — Frozen apps release their audio stream and, after a while, their memory

Status: done · Phase: 2 · Depends: T-465 · Area: services (ruya-session) · Size: M · Owner: builder · Complexity: complex · Developer surface: public-format

## Goal
A frozen game costs no CPU or GPU, but it still keeps the audio graph busy and holds all its memory. Make a frozen app as cheap as it can be without making Resume slow or noisy.

## Found (lead-11 study on the Dell, 0.0.64, 2026-11-11)
- PipeWire keeps a frozen app's stream and the ALSA sink `running`: about 1.4 % of a core, about 1000 more context switches and 300 interrupts per second, +0.15 W at idle (0.79 -> 0.95 W). The sound itself is silent.
- With zram (T-465), `memory.reclaim` on a frozen STK race moved 261 MB of anon into 77 MB, at about 1.8 s of kernel CPU; Thaw then took 198 ms and the game resumed at once. Without swap it only drops clean cache (no gain).

## Scope
1. **Audio:** on Freeze, ruya-session detaches the app's playback streams so the sink can suspend (unlink its output links, or move them to a null sink); on Thaw it restores them to where they were. No click or burst on Resume; nothing changes for an app that is not frozen.
2. **Memory:** an app frozen for about 30 s while not under the Hub gets `memory.reclaim` on its cgroups (an amount that leaves Resume fast; measure). Never when the Hub opens (the Hub must stay instant). Only when swap exists.
3. Contract: if the shell needs to know (e.g. a "Paused" state that now also means "memory released"), extend `Session1` first (CLAUDE.md); otherwise say why not.

## Outcome

**What was built.**
- **Sound (ruya-devices `park.rs`, new; `main.rs` `--park-audio`; `pipewire.rs`).** `ruya-devices --park-audio ruya-<id> --frozen=<ids> --running=<ids>` reconciles one profile's streams from one `pw-dump`: the profile's streams are the `Stream/Output/Audio` nodes whose client's `pipewire.sec.pid` is the main process of `ruya-pulse@<user>.service` (asked of `ruya-shell`'s own manager). A stream whose client names a running app (`pipewire.access.portal.app_id`) is parked when that app is frozen; any other stream of the profile only while every running app of the profile is frozen (today every stream falls here, see Decisions). Park = save the old `target.object` under `ruya.parked` in the `default` metadata (JSON), then point `target.object` at the null sink `ruya-parked` (created on the first park with `pw-cli create-node adapter` of `support.null-audio-sink`, `object.linger`, `priority.session 0`; destroyed when no stream is parked any more, a stale one too). Restore = put the saved target back with its type (or delete `target.object` so the stream follows the default), then delete `ruya.parked`. Every run is a full reconcile, idempotent, nothing remembered between runs. `pipewire::parse_dump` never offers `ruya-parked` as an output or as the default.
- **ruya-session core (`session.rs`).** `Instance` now knows its Unix user, when its freeze began (`frozen_at`) and its reclaim state. `sync_audio(user)` sends `Spawner::app_audio(user, frozen, running)` (the whole state of that user) after every change while the user has or had a frozen app: Freeze, Thaw, Stop, a launch, an end; `adopt` sends one per profile user with apps (a restart does not know what is parked). `tick` starts `Spawner::reclaim(unit)` once per freeze for an app frozen for `RECLAIM_AFTER` (30 s), only when `Spawner::swap_active()`; never at the Freeze itself (the Hub opening). A Thaw or Stop of an app whose reclaim was started first calls `cancel_reclaim` (before the thaw), so a reclaim still running does not page out a playing game. **Grace fix (the review finding):** `stop` takes a `Clock` (an `Instant`, or `Instant::now` from the adapter) and reads it after the thaw, so `STOP_GRACE` counts from the SIGTERM. `freeze` takes `now`.
- **ruya-session spawner (`spawner.rs`, pure, tested; `systemd.rs`, Linux).** `park_audio_command` (`systemd-run --machine=ruya-shell@.host --user --wait --collect -p RuntimeMaxSec=15 -- /usr/bin/ruya-devices --park-audio ...`), run by one worker thread in order (`AudioQueue`: a newer request of a user replaces its queued one; round 2: a failed run is tried again 2 s later, 3 tries in all, unless a newer request of that user came in), bounded to 20 s, logged `park-audio <user> frozen=[..] running=[..]: done in N ms (try K)`. `reclaim_command` (`systemd-run --machine=<user>@.host --user --wait --collect --unit=ruya-reclaim-<app>.service -p RuntimeMaxSec=30 -- /usr/bin/sh -c <loop> ...`, writing `reclaim_amount` = `RECLAIM_PERCENT` (50 %) of each cgroup's `memory.current` to its `memory.reclaim`; cgroups from `systemctl show -p ControlGroup` of the unit and the app's active scopes, validated by `valid_user_cgroup`), on its own thread, logged `<unit>: memory reclaim done in N ms: asked X MiB of K cgroups, memory.current A -> B MiB`. `cancel_reclaim_command` (`stop --no-block ruya-reclaim-<app>.service`, its own thread). `SWAP_COMMAND`/`any_swap` (`systemctl list-units --type=swap --state=active`; `ProcSubset=pid` hides `/proc/swaps`). `FakeSpawner` records `audio_calls()`, `reclaim`/`cancel-reclaim` calls, `with_swap()`, and `observer()` (shares its state, for the clock test).
- **Contract:** no `Session1` change. The shell needs to know nothing new: `frozen` and "Paused" mean what they meant; the parking and the reclaim are invisible to it. Only the XML comments of Freeze and Thaw say what now happens.

Missing pw-dump/python3/libpulse or a PipeWire that does not answer with the shell stopped print UNVERIFIED, not PASS.

**Decisions.**
- **The parking runs in ruya-devices, started by ruya-session** (the task says "ruya-session detaches"). ruya-session runs as root with an empty capability set, `ProtectHome`, `PrivateDevices`, and cannot reach `ruya-shell`'s PipeWire (`/run/user/<uid>` is the user's, and a `--machine=` call cannot pass a pipe back); ruya-devices already lives in that manager for exactly this (ADR-010) and parses `pw-dump`. ruya-session decides when and for whom; ruya-devices decides which streams and how. No new D-Bus method, no hardening change.
- **Moving to a null sink, not unlinking.** WirePlumber relinks an unlinked stream at its next rescan; a `target.object` in the `default` metadata is what it honours (it is how pulse moves work), and the null sink takes the stream off the card's graph so WirePlumber suspends the card.
- **Which app a stream is.** The per-profile pulse server runs as `ruya-shell` and cannot read another user's `/proc/<pid>/root/.flatpak-info`, so it most likely sets no `pipewire.access.portal.app_id` (not seen in a VM yet). The rule therefore parks a profile's unidentified streams only while every running app of that profile is frozen; a game that plays is never silenced by a frozen one (unit-tested), at the cost of not parking a frozen game's stream while another game of the same profile runs (the card runs for that one anyway).
- **Thaw first, restore after.** The thaw is not delayed by the park-audio run (a `systemd-run` plus `pw-dump`, a few hundred ms expected); the first moment of sound after the thaw goes to the null sink. No burst: nothing is buffered while parked. Measuring the gap is a Dell item.
- **"While not under the Hub":** the service cannot see the Hub (presence reports say "" for both the Hub and Home), so the reclaim comes 30 s after the Freeze whether the Hub is still open or not; never at the Freeze. Getting this exact needs a shell hint (Inbox), only worth it if the Dell shows the Hub stuttering during a reclaim.
- **The amount:** 50 % of each cgroup's `memory.current` (`RECLAIM_PERCENT`, one constant), the kernel picking the coldest pages; a starting value for the Dell numbers (criterion "Dell numbers in the Outcome later (lead)").
- **The reclaim runs as the profile user** in its own manager: it owns its delegated app cgroups; ruya-session may not write the cgroup tree (`ProtectControlGroups=yes`, no `CAP_DAC_OVERRIDE`), and the hardening stays as it is. No oomd policy (vm-swap-check requires none).

**Round 2 (review).**
- Blocker, a failed restore was never retried: `park::apply` now returns an error (exit 1) when any `pw-metadata`/`pw-cli` step failed, and `park_audio_worker` retries a failed job through the pure `spawner::AudioQueue` (`PARK_TRIES` 3 in all, `PARK_RETRY` 2 s apart; the pause still takes in new requests, and a newer request of the same user replaces the retry). Tests: `a_newer_sound_request_of_a_user_replaces_the_queued_one`, `a_failed_sound_request_is_tried_three_times_in_all`, `a_retry_gives_way_to_a_newer_request_of_its_user`.
- `pw-metadata` gets `--` before its positional arguments (`-d` stays before it).
- `swap_active` no longer runs `systemctl` under the session lock: the real spawner reads the swap state on its own thread every 60 s (`watch_swap`, an `AtomicBool`) and answers from the last reading; it is cached, so swap switched on or off is seen within a minute.
- Developer docs: the `ruya-parked` sink is not an API (do not enumerate, select or rely on it; do not move your stream by hand), in the lifecycle Sound row and audio-and-video rule 6; "about half" and the 30 s are tuning values that may change.
- New test `an_app_that_moved_itself_onto_the_parked_sink_is_neither_restored_nor_left_silent`: a stream with `target.object` ruya-parked set by the app (no `ruya.parked`) is not "restored", the sink holding none of ours is dropped, and when it is frozen it is parked with no saved target, so the thaw removes the target.
