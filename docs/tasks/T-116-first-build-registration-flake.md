# T-116 — Fix the "type X is not defined" failure on the first build after adding a C++ QML type

Status: todo · Phase: 1 · Depends: — · Area: shell (build) · Size: M

## Goal
After a builder adds a new `QML_ELEMENT` C++ class (new `.h`/`.cpp` in the CMake `SOURCES`), the **first** `.\scripts\dev.ps1 test` run is green. Today it fails ("`DeviceSettings` / `Audio` / `SystemInfo` is not defined", qmllint "Member not found") and passes on the second run. It has cost a rerun in T-102, T-103, T-105 and T-108, and each time the cause was a guess.

## Read first
- `shell/CMakeLists.txt` (the static `ruyashell` QML module, `ruyashellplugin`, `tst_ruyashell`, `ruya-shell`)
- `scripts/dev.ps1` (`Do-Build`, the qmllint step that reads `.rcc\qmllint\ruyashell.rsp`)
- `shell/CLAUDE.md`, "Build pitfall" (the current workaround)
- Qt docs: `qt_add_qml_module`, static QML plugins and `Q_IMPORT_QML_PLUGIN`, `qmltyperegistrar`

## Scope
1. **Reproduce it deterministically.** Write the exact steps (in the Outcome, and as a small script `scripts/repro-first-build.ps1` if that makes them repeatable): add a scratch singleton class `Probe` with a property, list it in `SOURCES`, reference `Probe` from a scratch QML file or test, run `dev.ps1 test` once, record the failure, run it again, record the pass.
2. **Find the root cause.** Candidates to check, with evidence (file timestamps, build log with `-v:normal`, which target generated what):
   - CMake re-configures because `CMakeLists.txt` changed, and `qmltyperegistrar`/`moc --collect-json` output is produced after the exe targets already linked against the old registration;
   - the generated `ruyashell.rsp` for qmllint is read before the build refreshed it (it is read after `Do-Build`, so check whether the file is actually regenerated by that build);
   - a missing target dependency between `tst_ruyashell`/`ruya-shell` and the type-registration object files;
   - a Visual Studio generator parallelism race (`-m`).
3. **Fix the cause** in CMake or `dev.ps1`. Prefer a real dependency fix. A "build twice" fallback in `dev.ps1` is acceptable only if the cause is outside our control; then document why in the Outcome and in `dev-setup.md`.
4. Remove the "Build pitfall" section from `shell/CLAUDE.md` once the fix is proven.

## Out of scope
- Linux/CI builds (they use Ninja and a fresh build dir; check them only to say whether they are affected).
- Upgrading Qt or CMake.

## Acceptance criteria
- [ ] The Outcome contains the reproduction, the evidence for the root cause, and the fix.
- [ ] With the fix, adding the scratch `Probe` type and running `dev.ps1 test` **once** ends `ALL GREEN`; repeated three times with three different scratch class names (each time reverting the probe). No test is edited.
- [ ] `dev.ps1 test` on an unchanged tree is still green and not noticeably slower (note both timings).
- [ ] The scratch files are gone from the commit, and `shell/CLAUDE.md` no longer lists the pitfall (or says what remains, if a fallback was needed).
