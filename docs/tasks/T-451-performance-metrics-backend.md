# T-451 — Performance metrics: FPS and frame time from the compositor, CPU, RAM, temperatures, GPU from `Devices1`

Status: in-progress · Phase: 2 · Depends: — · Area: api, services (ruya-devices), shell (compositor, client, mock) · Size: M · Owner: builder · Complexity: complex · Developer surface: internal

## Goal
The shell can show honest performance numbers for the game in front: FPS and frame time, CPU and GPU load, RAM and VRAM, CPU and GPU temperature and power, each with a state that says whether it is supported, and no cost while nobody looks.

## Read first
- ADR-033 point 4; `07-hub-requirements.md` §5.3, §8; `api/dbus/org.ruyaos.Devices1.xml` (`System`, `Thermal.ListSensors`)
- `shell/qml/compositor/` and the shell's frame timing; T-421's Outcome (drm fdinfo as a GPU measure on the Dell); `services/CLAUDE.md`

## Scope
1. Compositor: count the app surface's commits and the shell's presented frames for the app in front; expose FPS and frame time (mean and 99th percentile over the last second) to QML; zero cost while no one subscribes.
2. Contract first, `Devices1.System`: `GetPerformance` returning a map of metrics (`cpu_percent`, `ram_used`, `ram_total`, `gpu_percent`, `vram_used`, `vram_total`, `cpu_temp`, `gpu_temp`, `power_w`), each value with a state `supported | unsupported | unavailable | stale`; read from `/proc`, hwmon, the DRM driver's sysfs and fdinfo where the kernel offers them; never an estimate.
3. Shell client and mock (the mock offers each state); the shell polls only while a consumer is open, interval a setting (default 1 s, bounded 0.5-5 s).

## Out of scope
- The panel UI (T-452); per-process GPU of another profile's game where the kernel needs root (state `unsupported`, an Inbox line if it matters); FPS limiting, overlays inside games.

Built the performance backend; no panel UI (T-452).

- **Contract** (`api/dbus/org.ruyaos.Devices1.xml`, `Devices1.System`): `GetPerformance() -> a{s(sd)}`, metric -> (state, value) for `cpu_percent`, `ram_used`, `ram_total`, `gpu_percent`, `vram_used`, `vram_total`, `cpu_temp`, `gpu_temp`, `power_w`; states `supported | unsupported | unavailable | stale`, their meaning, units and sources in the header. Every name is always present. Internal (shell and root by the bus policy), no stability tag.
- **Service** (`services/ruya-devices/src/performance.rs`, pure, reads through `ruya_sysinfo::Source`, time passed in; `dbus.rs` `SystemIface::get_performance` on the blocking pool; `main.rs`): `/proc/stat` busy share since the reading before; `/proc/meminfo` MemTotal - MemAvailable; the processor package temperature from hwmon coretemp/k10temp/zenpower (Thermal's `pick`, now `pub(crate)`, as is `parse_cpu_jiffies`) else the `x86_pkg_temp` zone, the hottest package; the boot GPU (`boot_vga`, else the first PCI card): amdgpu `gpu_busy_percent`, `mem_info_vram_*` and its own hwmon temperature; else the DRM clients' `drm-engine-<class>` ns in `/proc/*/fdinfo` (busiest class, each `drm-client-id` once, divided by `drm-engine-capacity-*`, other `drm-pdev` ignored); RAPL `intel-rapl:N` `package-*` energy, unwrapped at `max_energy_range_uj`. Rules: a rate needs the reading before, kept 10 s (else `unavailable`); a failed reading keeps the last good value 10 s as `stale`; a temperature outside -20..125 is a failed reading; calls inside 250 ms get the same answer; the layout is found again every 60 s. No timer. `--session` reads the Dell capture.
- **Which GPU measure (the Hint):** the service runs as `ruya-shell` (ADR-010, a user unit), not as root. RAPL `energy_uj` is root-only (checked on the Dell), so `power_w` is `unsupported`. The fdinfo engine times are used only when the service may read every process (`reads_all_processes()`: euid 0): a profile's game runs as `ruya-p1` and its fdinfo is unreadable to `ruya-shell` (checked), and counting only the shell's own client would understate the GPU. The i915 PMU (perf) needs CAP_PERFMON (`perf_event_paranoid` is 2 on the Dell) and is not used. So on the Dell today GPU load, VRAM (integrated: no numbers), GPU temperature (no hwmon for the iGPU) and power are `unsupported`; amdgpu machines get load, VRAM and temperature from sysfs. Inbox line for a root-side reader.
- **Shell** (`shell/src/performance/`): `PerformanceBackend` (with a `RequestSequence`), `MockPerformanceBackend` (an answer holding every state: the rates `unavailable` in the first reply, VRAM and GPU temperature `unsupported`, power `stale`, the rest `supported`; `setMetric`, `reset`, reply delay), `DBusPerformanceBackend` (parses `a{s(sd)}`), `FrameMeter` (FPS and frame time from the front surface's `redraw()` commits and the window's `frameSwapped()`; a presented frame counts when the app committed since the frame before; mean and nearest-rank 99th percentile of the intervals in the last second; `frameSwapped` is connected directly and only stamps a time under a mutex, so the render thread is safe), the `Performance` singleton (`metrics`, `stateOf`, `valueOf`, `fps`, `frameTimeMs`, `frameTimeP99Ms`, `commitsPerSecond`, `frameState`, `counting`, `commitsSeen`, `polling`, `pollCount`, `intervalMs`, `acquire`/`release`, `refresh`, mock and test-clock hooks) and `PerformanceConsumer { active }`. Polling (at once, then every `intervalMs`) and the frame meter's connections exist only while a consumer is open. `DeviceSettings.performanceIntervalMs` (500-5000 ms, default 1000, key `hub/performanceIntervalMs`). `compositor/Compositor.qml` sets `frameWindow` (the shell's window) and `frameSource` (the surface of `Shell.focusedApp` while an app is open, also under the quick menu).

Deviations / notes:
- `power_w` is the processor packages' power (RAPL), not a discrete GPU's or the whole console's: the one honest number for a single key (Inbox: `gpu_power_w`).
- The frame meter takes `QWaylandSurface::redraw()` as the commit signal (it is in the signal table of the Dell's `libQt6WaylandCompositor`; that Qt emits it once per commit is as read from Qt, not tested here: the Windows kit has no QtWaylandCompositor). **Unverified:** the meter with a real Wayland client (VM or Dell), `DBusPerformanceBackend` against the service (compiled only), `Compositor.qml` (built only in the image).
- `PerformanceConsumer` and `Performance.refresh()` (a no-op without a consumer) are additions for T-452 and the late-reply test.
