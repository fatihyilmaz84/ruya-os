# T-199 — Device icons: a controller, a headset, a keyboard... shown next to each device

Status: in-progress · Phase: 2 · Depends: — · Area: shell, services, api · Size: M · Owner: builder

## Goal
Every Bluetooth device in Settings → Bluetooth (and the "controller connected" toasts and the battery rows that name a device) shows an icon that says what it is: a gamepad, a headset, a speaker, a keyboard, a mouse. Where we can tell the controller family (PlayStation, Xbox, Nintendo), the icon is that family's pad; where we cannot, the generic gamepad icon is fine. Owner request, 2026-11-06 (first Dell run: the list is text only).

## Read first
- `docs/specs/04-design-system.md` §3.7 (icons: Material Symbols Rounded subset, ADR-013), §5 components, §8 (a missing token or component is an Inbox line / a spec change in the same commit)
- `shell/fonts/icons.txt`, `shell/qml/Icon.qml`, `scripts/subset-icons.sh`, `scripts/lint-icons.ps1`, `docs/dev-setup.md` "Adding an icon (T-157)"
- `api/dbus/org.ruyaos.Devices1.xml` (`Bluetooth.ListDevices` records; today `kind` is `controller | headset | audio | other` and comes from BlueZ's `Icon`), `services/ruya-devices/src/bluetooth.rs` (`kind_of`), `shell/qml/BluetoothPane.qml`, `shell/qml/` toast code for devices

## Scope
1. **Kinds -> generic icons (always):** extend `kind` to cover what BlueZ's `Icon` says (`input-gaming` -> `controller`, `audio-headset`/`audio-headphones` -> `headset`, `audio-card`/speaker -> `speaker`, `input-keyboard` -> `keyboard`, `input-mouse` -> `mouse`, phone, other) in the contract and `kind_of`, with tests; add the matching Material Symbols to the subset font (`sports_esports`, `headphones`, `speaker`, `keyboard`, `mouse`, `bluetooth`...) per `dev-setup.md`, and show the icon in the Bluetooth pane rows and in the "connected/disconnected" toasts. Accessible names stay the device name plus its kind in words.
2. **Controller family (best effort):** the device record gets a `family` key (`playstation` | `xbox` | `nintendo` | `""`), derived in the service from the `Modalias` BlueZ already reports (`usb:v054Cp0CE6d0100` = Sony 054C; Microsoft 045E; Nintendo 057E; and the name as a fallback). The shell shows a family-specific glyph when it has one and the generic gamepad otherwise.
3. **Family art, without trademarks:** draw our own simple pad silhouettes (PlayStation-like, Xbox-like, Switch-like layouts) as part of the icon font or as small SVGs in the design system, in the same line style as the Material icons. **Do not use Sony/Microsoft/Nintendo logos or button-symbol trademarks** (owner-level: legal); if real brand art is wanted it is an owner decision with a licence answer. Record what was drawn and what is deliberately generic in `04` §3.7.
4. **Mock and tests:** the mock devices cover every kind and family so tests and screenshots show them.

## Out of scope
- Icons for Wi-Fi networks, audio sinks and storage (separate rows exist; reuse the same mechanism later), animated icons, the controller battery art.

## Outcome
Verified: host (hw pending: ListDevices on the Dell)

**Built.** (1) *Kinds.* `kind_of` (`bluetooth.rs`) now maps BlueZ's `Icon` to `controller | headset | speaker | keyboard | mouse | phone | other`; `audio` became `speaker` (the word `Batteries` already uses; only the shell's own tests read the old one). (2) *Family.* `ListDevices` has a new `family` key (`playstation | xbox | nintendo | ""`), set for controllers only, from the vendor id of BlueZ's `Modalias` (`RawDevice.modalias`, read in `bluez.rs`). The classification is **one small table in one file**, `services/ruya-devices/src/families.rs` (`VENDORS`: USB-IF ids 054C, 045E, 057E and the Bluetooth SIG company ids 012D, 0006, 0553; `NAMES`: the fallback for a pad with no usable modalias), which T-261 extends. A vendor that is in the modalias but not in the table (8BitDo) is `""` whatever the pad calls itself; Sony's plain "Wireless Controller" is the last name tried, because "Xbox Wireless Controller" ends the same way (a test found that bug in my first order). The XML change is in the `ListDevices` record only; the T-203 controller-pairing members are untouched. (3) *Icons in the shell.* `DeviceIcons.qml` (a singleton, in `CMakeLists.txt`) is the one place that maps `kind`/`family` to an icon name and to the kind in words (translated, EN/TR); the Bluetooth pane draws the icon before each device (`SettingControl.iconName`, an optional decorative icon like the swatch) and names the row "DualSense, PlayStation controller, Connected"; `BatteryChip` uses the same mapping; the toast gained an optional glyph (`Notifications.show(text, kind, iconText, iconName)`, `ToastLayer` draws an `Icon`), and `Bluetooth.batteryLow` carries `kind` and `family`, so the low-battery toast of a device shows its icon. (4) *Our own pads.* `scripts/add-pad-glyphs.py` draws `pad_playstation`, `pad_xbox`, `pad_switch` (rounded polygons, discs and unions with skia-pathops, outlined and filled variants) into both cuts; `subset-icons.sh` runs it, `icons.txt` marks them with the word `ruya` (private-use code points U+E005 to U+E007, which the script checks upstream does not use), `lint-icons.ps1` accepts the marker. No vendor logo, wordmark or button symbol (the four buttons are plain dots). `smartphone` (phone) came from Material; `sports_esports`, `headphones`, `speaker`, `mouse`, `keyboard`, `bluetooth` were already in the cut (T-223). The fonts were re-cut in WSL from the pinned download. What is drawn and what is generic: `04` §3.7 "Device and controller family icons". (5) *Mock.* `Bluetooth.mockPopulate()` adds a paired, connected device of every kind and family plus a kind no shell knows (`gizmo`); the default mock list is unchanged (existing tests count three devices), and its soundbar is now `speaker`.

**Tests.** Rust (242 in the `ruya-devices` lib): `kinds_and_batteries` (every BlueZ icon, a computer, a tablet, no icon), `families::tests` (Sony 054C/0CE6 and 054C/09CC, Microsoft 045E, Nintendo 057E/2009, the three SIG ids, an unknown vendor with and without a deceptive name, the name fallback, a garbled modalias), `a_controller_carries_its_family_and_nothing_else_does` (the same vendor on a headset, keyboard and phone gives `""`), `family_for_asks_the_table_for_controllers_only`. QML: `tst_bluetooth.qml` (`test_every_kind_and_family_has_its_icon_in_the_pane`: icon name per row, glyph known, accessible name with the kind in words, unknown kind is `bluetooth`, a controller without a family is the generic pad; `test_a_device_toast_carries_the_devices_icon`, with the signal's kind and family; `test_rows_of_the_other_panes_have_no_icon`; `test_a_toast_without_an_icon_name_shows_its_text_glyph`), `tst_icon.qml` (the new names are in the table; `DeviceIcons.iconFor` for every kind x family, an unknown kind and an unknown family). **Revert checks:** removing `phone` from `kind_of` and the `kind == "controller"` guard of `family_for` fail three Rust tests; mapping `xbox` to the PlayStation glyph fails `test_device_icons_answer_known_names`, dropping `iconName` from the pane row fails `test_every_kind_and_family_has_its_icon_in_the_pane`, dropping the icon from the toast fails `test_a_device_toast_carries_the_devices_icon` (one build with all three undone: 3 failures; then restored). `dev.ps1 test`: ALL GREEN, 597 QML passed, 53 skips, 491 Rust passed; lint-icons, font coverage (no coincident contours in the new glyphs) and the translation lint pass.

**Screenshots** (`output/shell-shots/review/bt-icons-1-controllers.png`, `-2-others.png`, `-3-toast.png`; read at half size, the pad rows also at 1:1): the Bluetooth pane with a device of every kind, the DualSense and Xbox pads each with their own silhouette next to the generic gamepad, the Switch-like handheld, headset, speaker, keyboard, mouse and phone, and the headset's battery-low toast with its headphones glyph in the warning colour. At the 40 px of `iconM` the three pads are told apart by their outline (PlayStation: two grips and a bar; Xbox: asymmetric sticks; Switch: a landscape body with a screen) but are small and busy; they read as pads, not as detailed art. **`shots` on this desktop:** the default (threaded) render loop froze animations and layout in real windows: a full `shots` run failed nine screenshot tests in both runs (Glass, Glide x2, GlideSettings, Lockout, Wallpaper, BatteryCluster, Power, Settings; most of them the set T-223 reported), and every `tst_bluetooth` screenshot, the existing ones too, showed the profile picker. With `QSG_RENDER_LOOP=basic` set, the full run was **ALL GREEN (112 passed)** and the screenshots are right. My shot test forces a first grab so a real window lays the pane out; the offscreen `test` is unaffected.

**Deviations / notes.** (a) There is no "connected" or "disconnected" toast for a Bluetooth device today (the only connection message is the screens' own "Controller connected." line, `ControllerPairHint`); I did not invent one. The toasts that name a device are the low-battery ones, which now carry the icon (inbox: connect/disconnect toasts). (b) The status cluster's chips cannot show a family: `Batteries` has no family and no link to the BlueZ address, so a controller chip is the generic gamepad (inbox); the "Controller battery low" toast from `Batteries` is generic for the same reason. (c) The contract change is the `family` key and the `kind` vocabulary of `ListDevices`; `Bluetooth.batteryLow` gained two arguments (kind, family) in the shell.

**Hardware / VM (lead run).** Not run: no adapter in the VM and no Dell. On the Dell: `busctl --system call org.ruyaos.Devices1 /org/ruyaos/Devices1 org.ruyaos.Devices1.Bluetooth ListDevices` should show the DualSense as `kind` `controller`, `family` `playstation` and the WH-1000XM4 as `kind` `headset`, `family` `""` (if the pad shows `family ""`, note its `Modalias` line from `bluetoothctl info`: the table needs its vendor); then look at Settings -> Bluetooth & controllers for the glyphs on the real panel.
