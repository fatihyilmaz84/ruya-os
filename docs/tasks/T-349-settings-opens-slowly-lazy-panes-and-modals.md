# T-349 - Opening Settings is slow (esp. Store to Settings): build panes and modals lazily, measure on the Dell

Status: in-progress · Phase: 2 · Depends: — · Area: shell (SettingsPage, Shell page open/close, GlassSheet, singletons' first use, probe) · Size: M · Owner: builder (Opus recommended: QML refactor with focus risk)

## Goal
Owner report (Dell, 0.0.55, high tier, aurora wallpaper, 1080p): "a small delay when I go from Store to Settings; opening Settings seems demanding". A read-only analysis of the code (no timings yet) found the causes below. Fix them and prove it with numbers from the Dell.

## Causes (ranked, from the analysis; verify each in the code and measure before you cut)
1. `SettingsPage.qml:189-288` creates all ten panes eagerly (MyProfile, ManageProfiles, Display, Network, Bluetooth, Audio, Storage, PowerSaving, System, About), hidden by `visible: false` (comment at `SettingsPage.qml:8` and `StoragePane.qml:137` say by design): about 76 `SettingControl` rows, each with `GlassLayers` (tint, sheen, rim, grain image), roughly 600-900 items built in the key-press frame; `Shell.qml:31-73` `openPage` calls `component.createObject` synchronously and the 300 ms slide starts in the same call.
2. About 11 hidden modal subtrees are built eagerly: `TextEntry` x3 with the keyboard `Repeater`, `PinPad` x3 flows, `ZonePicker`, 2 x `ModePicker`, `WallpaperPicker` (501 lines, a `GlassSheet` each: a `ShaderEffectSource` of `Shell.l0`, a mask layer FBO, `SmoothMask`). Hypothesis (about 40 %): the first-frame shader/FBO creation stalls.
3. Eager refreshes in `Component.onCompleted` of hidden panes: `NetworkPane:54` `syncNetworks`, `AudioPane:49-55` `syncSinks` + `SoundThemes.refresh(usbMounts())`, `BluetoothPane:67` `syncDevices`, `SystemPane:130` `syncSensors`; and lazy C++ singletons (`Wallpapers`, `SystemDetails`, `Display`, `SoundThemes`) constructed on the first Settings open: check their constructors for synchronous IO.
4. The wallpaper blur fade overlaps the transition (shared cost, not Settings-specific).
5. Why Store to Settings is worse: the Store slot is destroyed at 300 ms (`reapIfDone`, `Shell.qml:1058`) in the middle of the glide, so the Store grid teardown and the Settings build collide.

## Scope
A. **Lazy panes:** `Loader { active: current || loadedOnce }` per pane (latching, so the focused-row memory stays, as `SettingsPage.qml:8` wants); instantiate only the pane named by `params.category`, else the first; `currentPane` returns `loader.item`. Keep focus and Accessible behaviour exactly as `tst_settings.qml` asserts.
B. **Lazy modals:** `Loader { active: opened }` for `TextEntry`, `PinPad` flows, `ModePicker`, `ZonePicker`, `WallpaperPicker` and the flow items (a latch where closing must not lose state); `GlassSheet`: `crop.sourceItem: sheet.shown && sheet.blurred ? sheet.source : null`, layer-enable the mask only while shown.
C. **Defer refreshes** to the first time a pane is shown (like `StoragePane`) and behind `Qt.callLater`; warm the C++ singletons in `Shell.Component.onCompleted` (off the transition) or fix a constructor with synchronous IO.
D. **Stagger the Store teardown:** `Qt.callLater(destroy)` in `reapIfDone`, not mid-glide.
E. Prewarm `SettingsPage` idle on Home only if A-D are not enough (say why).

## Measurement (the Dell, standing permission; the lead can help)
Add a permanent cheap probe in `Shell.openPage`/`openSection`: `ruya-shell: page-open <key> create=<ms> firstSwap=<ms> afterAnim=<ms>` (one `qInfo` line via `onFrameSwapped`, behind an env or always). On the Dell also `QSG_RENDER_TIMING=1` via a transient compositor drop-in. A/B 10 runs each, before and after: Home to Settings, Store to Settings, Store to Games; effects performance vs high; first open after boot vs second. Target: Settings `create` under about 30 ms, no frame over 33 ms in the transition. The Outcome carries the table.

## Outcome
Verified: host (hw pending: Dell measurements, lead run)

UX notes: nothing visible changes (the Settings screenshots look as before). States reached in `tst_settings_lazy`: Settings opened from the nav and by deep link, every category, each pane entered and left, each modal family opened and closed. Back leaves a modal to the row that opened it (asserted for the Rename keyboard, the PIN pad, Resolution, Wallpaper, Time zone, the Wi-Fi password and the pairing screen), Back in a pane goes to the category list, Back on the list closes Settings and focus lands on the nav pill. A pane re-entered lands on its remembered row. Doubts: a pane is now built in the key frame that first selects its category, so the first Down onto Display or System costs that pane (once); the sound themes and the USB pictures are looked up a frame after their pane first shows. Found and fixed on the way: `ZoneChooser` started itself while being built (its `onRegionsChanged` ran before `visible` was settled) and took the focus, which a Time zone picker built on its first opening turned into focus lost on close; it now starts only once built.

**What was built.**
- **A. Lazy panes** (`SettingsPage.qml`): each pane sits in a `PaneSlot`, a latching `Loader` (`active: selected || built`, `onLoaded: built = true`) that fills the pane area; the pane keeps `anchors.fill: parent` (tests squeeze a pane through its anchors) and the slot carries `visible`/`enabled` (`selected`). `selected` waits for `ready`, set at the end of `Component.onCompleted` once `params.category` has moved the list, so Settings builds exactly one pane: My profile, or the deep-linked one. `currentPane` returns the slot's `item`. Focus and Accessible are unchanged: the Loader is a focus scope, `forceActiveFocus()` on the pane passes through it, and a pane re-entered lands on its remembered row (`tst_settings_lazy` `test_a_pane_is_built_when_selected_and_kept`).
- **B. Lazy modals**: every modal of the Settings panes is in a `Loader` that sits on the overlay and sizes it, `active: false` until the line that opens it switches it on (then latched). `ProfilePaneBase` builds its PIN pad, delete confirmation and name keyboard together on the first `beginModal()` (`modalsBuilt`: the flows drive them together); `ManageProfilesPane` (name keyboard), `NetworkPane` (password), `BluetoothPane` (pairing screen, rename keyboard, forget confirmation), `DisplayPane` (Resolution, Refresh rate, Wallpaper), `SystemPane` (update PIN pad, restart and rollback confirmations, Time zone) and `AudioPane` (delete confirmation) each per modal. Per-opening data moved from extra modal properties to the pane (`BluetoothPane.forgetId`/`renameId`, `AudioPane.deletingId`). The wallpaper names moved from `WallpaperPicker.nameOf` to `DisplayText.wallpaperName` (the Wallpaper row shows the name without the picker; translations moved with them). The picker no longer scans the USB drives in its `Component.onCompleted` (it is built right before `open()`, which scans; until then `DisplayPane` scans, below). `GlassSheet`: `engaged` is set on the rising edge of `shown` and cleared once the sheet is closed and hidden; `crop.sourceItem` and the mask's `layer.enabled` follow it, so a closed modal holds no crop of L0 and no mask FBO. Deviation: the task says `sheet.shown && sheet.blurred`; with `shown` alone the blur would vanish during the 300 ms fade-out (a visible change), so the texture is kept until the modal is hidden.
- **C. Refreshes**: with lazy panes no pane refresh runs at Settings open. `AudioPane` moves `SoundThemes.refresh` behind `Qt.callLater` (off the frame that builds the pane); `StoragePane` already deferred its refresh to the first show and is unchanged (T-331 works on it). The singleton constructors were read: `Wallpapers` and `SoundThemes` do synchronous file work (`loadBundled`, `loadUser`, `reload`) but are already built at start (`WallpaperLayer`, `Sfx`); `Display`, `Storage`, `Bluetooth`, `Audio`, `TimeZone`, `Update`, `Thermal` are built at start by the shell too; `SystemDetails` is built only by System information; `Network` was the one built by Settings (the eager Network pane), so `Shell.Component.onCompleted` now creates it (`Network.state`): its first list arrives asynchronously and is there when the pane is first shown, so focus still lands on the first network. No constructor needed a fix (none blocks on D-Bus).
- **D. Store teardown**: a popped slot is destroyed only when the page on top has settled (`settled`: shown, opacity 1, slide at 0) and the next frame has been swapped (a `Connections` on `frameSwapped`, with `window.update()` so a still screen draws one); `closingSlots` holds the popped slots until then. With equal durations the old code destroyed the Store page in the very tick in which Settings settled, so its teardown delayed that last frame.
- **E. Prewarm**: not done. A to D remove the eager work found in the code; whether Settings still needs a prewarm on Home is a question for the Dell numbers (Inbox).
- **Probe** (`src/probe/PageProbe.h/.cpp`, `Shell.qml`): one `qInfo` line per page open, `ruya-shell: page-open <key> create=<ms> firstSwap=<ms> afterAnim=<ms> frames=<n> maxFrame=<ms>`, always on. `openSection` starts the clock before it closes the pages below (so Store to Settings counts the Store's close), `openPage` otherwise; `create` after `createObject`, `firstSwap` the first `frameSwapped` after it, `afterAnim` when the slot settles; `frames` and `maxFrame` (longest gap between two swaps, the key press counting as the first) answer "no frame over 33 ms". Swaps are timed when the GUI thread receives them (queued from the render thread). Two extra fields beyond the task's line: `frames`, `maxFrame`.
- **Measurement script** `scripts/page-open-bench.py` (root on the Dell, uinput keys, reads the journal): Home to Settings, Store to Settings, Store to Games, first run apart, median / p90 / max of the rest and the number of runs with a frame over 33 ms; `--label` per image and tier; `--raw` prints the journal lines (with `QSG_RENDER_TIMING=1` in a compositor drop-in, Qt's render times). How to run: `docs/dev-setup.md`. The "before" image needs the probe: it is a commit of its own (the first commit of this branch, probe and script only, nothing else changed), so the lead builds "before" from it and "after" from the branch head.
- **Rows of a late pane**: `PaneSlot.onLoaded` calls `SettingsPane.reflow()`, so a pane built after the page opened lays its rows out at once (T-226 saw a late Column stay unlaid in a real window; `tst_storage` read row positions right after selecting the pane).
- **USB pictures**: until the wallpaper picker is built, `DisplayPane` scans the drives for pictures when it first shows and when the volumes change (what the picker did when it was built with the pane), so "Add from USB drive..." is there on the first opening; once built, the picker does it.
- **Mock counters**: `Network.mockRefreshCalls()`, `Bluetooth.mockRefreshCalls()`, `SoundThemes.mockRefreshCalls()` (Storage already had `mockUsageCalls()`).
