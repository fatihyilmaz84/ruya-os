# T-198 — Display: choose the resolution and refresh rate, and scale the UI to the screen (DPI)

Status: in-progress · Phase: 2 · Depends: — · Area: api, services, shell, image · Size: M · Owner: builder

## Goal
Settings → Display lets the owner pick the resolution and refresh rate the TV or monitor supports, and the UI is sized right for the screen (a 1080p TV, a 4K TV, a 32" monitor) instead of one fixed size. Owner request, 2026-11-06. Today the pane has only effects quality, reduced motion and overscan; the shell is the compositor on KMS (Qt `eglfs_kms`), so there is no desktop tool that could do this.

## Read first
- `docs/specs/02-shell.md` (Settings, Display, text scale), `docs/specs/03-services-and-apps.md` §2.4 Display ("mode list and switching via the compositor (KMS); default is the TV's preferred mode, capped at 4K60"), `docs/specs/04-design-system.md` §1 (read from the sofa: 3 m from a 1080p TV, body text 30 px) and the text-scale rule

- Qt docs: eglfs KMS (`QT_QPA_EGLFS_KMS_CONFIG` JSON: per-output `mode`, `size`/`refresh`, `physicalWidth`/`physicalHeight`), `QT_SCALE_FACTOR`, `QT_FONT_DPI`

## Scope
1. **What is true on the Dell is hardware (lead, later):** the builder works from the DRM sysfs/EDID layout (`/sys/class/drm/*/modes`, `edid`, `status`) with fixtures written from the Linux ABI, and leaves a `dell.dump`-style capture command in the Outcome (like `ruya-sysinfo --example dump`) for the owner to run on the Dell; the lead records the Dell numbers (modes, chosen mode, UI size) in the Outcome afterwards.
2. **Contract + service:** a Display interface (new `org.ruyaos.Devices1.Display` or in `ruya-devices`) that lists the connected outputs with their modes (width, height, refresh, preferred, current), the physical size from EDID, and stores the owner's choice (output, mode, scale) under `/var/lib/…`. The service cannot change the mode of a running eglfs shell: the choice is applied by writing the KMS config JSON the compositor reads at start and restarting `ruya-compositor@tty1` (the shell comes back to the same page).
3. **Safe switching:** after a change the shell asks "Keep this resolution?" with a 15 s countdown and reverts to the previous mode if nobody confirms (a TV that cannot show the new mode must never leave the owner with a black screen); a failed start falls back to the preferred mode automatically (a marker file the compositor unit checks).
4. **UI scale (DPI):** `Theme` derives its unit from the output (physical size and resolution, or an owner override "Auto / 100 / 125 / 150 / 200 %" separate from the accessibility text scale) so 4K gets the same physical sizes as 1080p, and a close monitor gets sensible sizes. Decide whether to use `QT_SCALE_FACTOR` at start or the Theme unit; record why. Keep the 3 m / 1080p design target as the reference.
5. **Pane:** rows for Resolution (list of modes, preferred marked), Refresh rate, UI size, and the confirm/revert dialog; existing components only; Turkish strings; the mock offers three outputs for tests and screenshots.

## Out of scope
- HDR, VRR, refresh-rate matching for video (spec 2.4, later), several outputs at once, rotation.

**Decisions.**
- **UI scale: the Theme unit, not `QT_SCALE_FACTOR`** (recorded in `04` §2): it applies live (no restart, no second confirm) and everything already goes through `u`; `QT_SCALE_FACTOR` is read at start and changes the logical window size.
- **Auto** is from the screen's physical size only (the resolution is already in `height / 1080`): 1 for a TV of 42" or more (watched from farther the bigger it is), smaller for a monitor read from a desk (32" 4K: 0.85, 27": 0.55), never above 1 (the layouts are made for 1080 design px of height), 1 when the size is unknown. 100/125/150/200 % are absolute on the 1080p reference. At 150 % on 1080p the Settings pane shows three rows (`display-5-ui-150.png`): the pages crop or scroll what no longer fits, nothing breaks.
- **The shell restarts itself by exiting** (`Restart=always`), so there is no polkit rule and no `RestartUnit` call; the dialog comes back from the service's marker (`starts >= 1`), so it works after a real restart. The mock plays the restart (`restartShell` counts and marks the first start).
- **Current mode** is the stored choice (if the output still offers it) else the default: sysfs does not say what the screen runs on. The service reads sysfs at each call; no hot-plug signal (Inbox).
- **The new rows come last in the Display pane**, so the focus order of the existing rows did not change; `tst_settings.qml` was updated for it (the last row is now UI size) and `test_scroll_cue_hidden_when_everything_fits` runs with the mock's "none" screen, because with the three new rows the pane no longer fits at 1280x720 and that test is about a pane that fits.
- **A running game or app blocks the change** (toast "Close running games and apps first..."): the restart would kill it. Not in the task text; a restart under a game is data loss.
- No admin-only rule (like Audio and Network): the bus policy already restricts the service to the shell and root.
- Only the first connected output is used; the mock's three screens are scenarios (`Display.mockUseScenario`), not three simultaneous outputs.

### Round 2 (code review: changes requested; UX; design review; lead decisions)

**Blocking, fixed.**
1. **Qt's screen names.** `qt_output_name` (display.rs) maps the kernel's connector name to what Qt's `nameForConnector` gives (`HDMI-A-1` and `HDMI-B-1` -> `HDMI1`, `DVI-I/-D/-A-n` -> `DVIn`, `SVIDEO` -> `TV`, `Component` -> `CTV`, `9PinDIN` -> `DIN`, the rest unchanged, then the dash before the number dropped: `DP1`, `eDP1`, `VGA1`, `Virtual1`). `kms_config` writes the Qt name and, when it differs, the kernel's name as a second entry; golden file updated; spec 03 §2.4 and the XML comment corrected. `vm-display-check.sh check` greps the Qt name; `switch` FAILS (was WARN) when `fb0/virtual_size` does not follow the mode.
2. **Start limit.** `ruya-compositor@.service` now has `StartLimitBurst=10` (was 5), `StartLimitIntervalSec=120`. **How the number was chosen:** a change and its revert are two starts, a reset one, and the lead asked that deliberate restarts fit with room; ten leaves headroom for several attempts in two minutes, and a crash loop (`RestartSec=1`) still reaches ten in about ten seconds, so the protection is kept (the greenboot drill of T-130 that counted five failed starts will now see ten; same outcome, a little later). The guard records every start in `display-starts` (pruned to the window), and `SetMode` and `Reset` answer **`busy`** while eight or more starts are in the last 120 s (`REFUSE_MARGIN` 3: the change, its revert and one to spare); `Keep` and `Revert` are never refused. The shell toasts "Try again in a minute...". `vm-display-check.sh switch` needs about five starts, refuses to run with three or more recent, and checks the recorded count stays under ten and the unit is `active`.
3. **Revert always restarts.** The facade restarts the shell after every Revert answer except `no-pending` (ok or failed); the mock now plays the guard (a second start with a change waiting drops it and queues the fallback note). `test_a_revert_the_service_fails_restarts_the_shell_anyway` uses `mockFailRevertNext()` on the timeout path.
4. **Design:** `04` §5 has rows for **Mode picker** and **Mode confirm**, a **Dialog card** row (width = widest child + 120 u, height = content + 96 u, texts at most 1100 u) shared by PowerConfirm, ThermalNotice and ModeConfirm, and the layer-table line **L5, z 40**, above the volume OSD, accepting every key.
