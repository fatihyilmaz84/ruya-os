# T-457 — Ruya Hub pauses the game: freeze on open, thaw on close

Status: in-progress · Phase: 2 · Depends: — · Area: api, services (ruya-session), shell · Size: M · Owner: builder · Complexity: complex · Developer surface: internal

## Goal
Opening Ruya Hub over a game pauses it (no CPU, no sound, its last frame under the Hub) and closing the Hub returns to gameplay at once; online players can turn it off.

## Read first
- ADR-033 point 3 (owner, 2026-11-10) and ADR-019 (`00-overview.md`); `02` §1.6 "The game pauses"; `03` (Session1, ruya-session scopes, T-363, T-435)
- `api/dbus/org.ruyaos.Session1.xml`; `services/ruya-session/src/` (`scope.rs`, `systemd.rs`: app scopes named exactly since T-435); `shell/qml/QuickMenu.qml`, `Shell.qml` (launch, focusApp)
- T-274 and T-275 (the ADR-019 spike and freeze/Switch tasks): this task builds the freeze primitive they will reuse

## Scope
1. Contract first, `Session1`: `Freeze(instance)` and `Thaw(instance)` for a running app of the signed-in profile, a `Frozen` state in the app's record and a change signal; status strings (`ok`, `not-running`, `failed`). Implementation: `systemctl --user freeze`/`thaw` of the app's unit and every app scope it names exactly (T-435's `app_scopes`), bounded like T-435's calls; idempotent; a stop or kill of a frozen app thaws first.
2. Shell: the Hub freezes the app in front when it opens over it and thaws it on Resume/B/Guide; Home keeps it frozen; Switch to thaws the chosen one; Close thaws then stops. A failed freeze leaves the game running and the Hub open, with no "Paused" shown.
3. The app header shows "Paused" while frozen.
4. Settings -> System: "Pause games when Ruya Hub opens" (on by default), stored like the other device settings.

## Out of scope
- Background policy, memory pressure, snapshots and the switcher (T-275..T-278); per-game opt-outs (later, an Inbox line if wanted).

**Built.**
- **Contract** (`api/dbus/org.ruyaos.Session1.xml`): `Freeze(instance) -> status`, `Thaw(instance) -> status`, signal `FrozenChanged(instance, frozen)`, key `frozen b` in the running record, statuses `not-running` and `not-allowed` (besides `ok`, `invalid`, `failed`). Deviation from the Scope's list: "another profile's app" answers `not-allowed` (an existing status string of the ledger) rather than `not-running`, so the shell can tell a refusal from a gone app; an empty instance is `invalid`.
- **Service** (`services/ruya-session`): `Session::freeze`/`thaw` in the core (signed-in profile check, running only, a second freeze is a no-op without an OS call, a failed freeze is undone by a thaw and answers `failed`, a thaw always asks the OS so a state lost across a service restart is repaired, `take_frozen_changes` for the signal); `Session::stop` thaws a frozen app before the stop. `Spawner::freeze`/`thaw` (fake records the calls; `--session` can fail them with `failing_freeze`); `SystemdSpawner::freezer` lists the app's scopes like T-435 and keeps only the app's own, active ones (`spawner::active_app_scopes`: systemd refuses to freeze an inactive unit, such as a failed scope not swept yet), then `systemctl --user -M <user>@.host freeze|thaw <unit> <scope>...`, each call bounded to 5 s, synchronous under the registry lock (so a Thaw sent right after a Freeze is served after it). The D-Bus adapter reads `Profiles1.ActiveProfile` per call (system mode) and emits `FrozenChanged`; `Stop` became async to emit it too.
- **Shell**: `Session.freeze`/`thaw`, `freezeFinished`/`thawFinished`/`frozenChanged`, records carry `frozen` (updated in place on the signal); D-Bus client and mock follow the contract (mock: signed-in profile check through the Profiles singleton, stop thaws first, `mockFailFreeze`, `mockCalls`). `HubPause.qml` (non-visual, on the spec-lint baseline) freezes the app in front when the Hub opens and thaws an app it froze whenever the Hub is closed and that app is in front again. Close game stays a plain `Stop`: the service thaws a frozen app before it stops it (a shell-side Thaw first was built, then removed: the revert check showed it was redundant with the service's own thaw and untestable apart from it). `QuickMenu` shows "Paused" (`quickMenuPaused`) only from the record's `frozen`; the app header is now as tall as the taller of the art and its text (a two-line title was already taller than the art at 720p and ran into the Resume row; with "Paused" it would more so). `DeviceSettings.pauseGamesInHub` (`hub/pauseGames`, default on) and the Settings -> System toggle "Pause games when Ruya Hub opens" with the note "Online games can lose their connection while paused." (Turkish translated). Switch profile closes the Hub over the app before the lock lands, so the app is thawed (documented in `02` §1.6; freezing a locked profile's apps stays T-165's).

**Round 2 (review findings).**
- *Switch profile left the game frozen* (Thaw refused `not-allowed` once the lock landed, nothing retried). Fixed two ways: the Hub now closes before `Profiles.lock()` (the Thaw goes out while the profile is signed in), and `HubPause` has a **sweep**: every frozen app of the signed-in profile that the shell is neither freezing nor thawing is thawed, on every change of `Session.running` and of the signed-in profile. The profile gate on Thaw stays (one rule for both calls); the sweep is the retry. Test: `test_switch_profile_from_the_hub_then_signing_back_in_thaws_the_game` (behaviour; in the mock the lock is asynchronous, so the refusal itself does not happen there: the sweep's own test is the restart one below).
- *Freeze/Thaw ordering race* (each call awaits `Profiles1` first, so zbus could serve a quick Thaw before its Freeze): an `async_lock::Mutex` (`async-lock`, already in the tree through zbus) is taken before the first await, so calls are served in the order they arrive; the XML says so. The sweep also repairs a Freeze that lands after its Thaw.
- *Shell restart with a frozen game*: the sweep thaws it when its profile signs in to the new shell (Thaw is profile-gated, so not before). Test: `test_a_game_left_frozen_before_a_shell_restart_is_thawed_at_sign_in`.
- *Adoption reads `FreezerState`* (`SHOW_PROPERTIES`, `ShowUnit.freezer_state`, also on the bus probe; `RunningUnit.frozen`): an app left frozen across a ruya-session restart is listed frozen, so Stop thaws it first. Tests: `an_adopted_frozen_unit_is_listed_frozen_and_thawed_before_its_stop`, `systemctl_show_blocks_are_parsed` (FreezerState).
- *Thaw answers*: an instance leaves `thawing` only with the answer; a `failed` Thaw toasts "Could not resume the game. Open Ruya Hub and choose Resume." (`warning`, Turkish translated); the sweep or the next Hub over it retries (its Freeze is a no-op for the service). I first also put the instance back into `asked`; the revert check showed that made no difference (the idempotent Freeze and the close's Thaw do the same), so it was removed. Test: `test_a_failed_thaw_toasts_and_the_next_close_tries_again` (mock `mockFailThaw`).
- `hub/pauseGames` survives a restart: `checkPausePersistence` in `tst_main.cpp`, asserted by `test_the_setting_survives_a_restart`.
- Design text adopted into `04` §5 (Quick menu "Paused", the Hub pause row, the note under a setting row); `HubPause.qml` left the spec-lint baseline. Shots case `hub-6-settings-pause-row.png`.
