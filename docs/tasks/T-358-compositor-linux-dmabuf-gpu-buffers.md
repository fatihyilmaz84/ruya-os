# T-358 — The compositor gives apps GPU buffers: linux-dmabuf-v1

Status: done · Phase: 2 · Depends: T-164 · Area: image (a qtwayland plugin build stage), shell (compositor), scripts · Size: M · Owner: lead · Complexity: hard · Developer surface: none

## Goal
A game started from the shell renders on the GPU. Found on the Dell (T-355, 2026-11-09): SuperTuxKart through the shell (T-164) runs on llvmpipe at 560 % CPU and a low resolution, because the compositor offers clients no GPU device: Mesa 26.2 clients need `linux-dmabuf-v1` (`MESA-EGL: failed to get driver name for fd -1`), and the image's qt6-qtwayland 6.11.2 ships only the old `wayland-egl` server integration (loaded by the shell, but Mesa no longer advertises a device through it). The game's sandbox already has `/dev/dri`. Vulkan games need the same protocol.

## Decision (lead, 2026-11-09, inside ADR-002; owner agreed "take the lead")
Option A: build Qt's own `linux-dmabuf-unstable-v1` compositor client-buffer integration from the qtwayland source of the image's exact Qt version as an image build stage, install it beside Fedora's plugins and select it for the compositor. Rejected for now: our own linux-dmabuf implementation (much more code to maintain), gamescope on the display outside our compositor (changes ADR-002, loses the Guide overlay over games; owner-level).

## Scope
1. **Spike:** does qtwayland 6.11.2 contain the plugin, why does Fedora's build not ship it (spec, feature check, missing build dependency), and the smallest build that produces `libqt-wayland-compositor-linux-dmabuf-unstable-v1.so` against Fedora's Qt (same version, ABI-exact).
2. **Image:** a build stage in the Containerfile (or a small RPM) that compiles only that plugin; `ruya-compositor@.service` selects it (`QT_WAYLAND_CLIENT_BUFFER_INTEGRATION`, keep `wayland-egl` as the fallback if both can be listed); the image lint checks the plugin is present.
3. **Shell:** if the integration needs code in `Compositor.qml` (e.g. `useHardwareIntegrationExtension`), add it; the shell's own rendering must not change.
4. **Checks:** VM (this task): `RUYA_BOOT_OK`, `vm-session-check.sh display` and `check` still pass (software rendering in the VM; the client must still map); the plugin is loaded (journal). Dell (hw): STK's log names the Intel GPU (not llvmpipe), CPU load, resolution and frame feel recorded; the Guide overlay over the game still works.

## Out of scope
- Explicit sync, hardware planes/direct scanout, HDR, VRR, gamescope nesting (B-003 keeps those).

## Acceptance criteria
- [x] The image contains the plugin built from the same qtwayland version as Fedora's Qt; the build is reproducible in `scripts/build.sh` (no network beyond the package mirrors and the source RPM).
- [x] VM (this task): `RUYA_BOOT_OK`; `vm-session-check.sh display` ALL CHECKS PASSED; the compositor journal shows the dmabuf integration loaded.
- [x] Dell (hw): STK reports the UHD 630 as its renderer through the shell; CPU load and frame feel recorded in the Outcome.

## Outcome
Verified: hw (0.0.58 on the Dell, 2026-11-09, lead-6) and vm (0.0.58: `RUYA_BOOT_OK`, `vm-session-check.sh display` and `check` ALL CHECKS PASSED).

**Spike 1 (why it is missing):** qtwayland 6.11.2 has the plugin (`src/plugins/hardwareintegration/compositor/linux-dmabuf-unstable-v1`, feature `wayland-dmabuf-client-buffer`, key `linux-dmabuf-unstable-v1`). Fedora's build lacks it through an upstream CMake ordering bug: `src/compositor/configure.cmake` never finds EGL before the `dmabuf_client_buffer` test (`Failed because EGL::EGL not found`), so the feature is off although the spec has the BuildRequires. Recipe: the SRPM of the exact installed version, `dnf builddep`, configure with `-DTEST_dmabuf_client_buffer=ON -DCMAKE_SKIP_RPATH=ON`, `ninja QWaylandDmabufClientBufferIntegrationPlugin` (about 1 min), 139 KB stripped, resolves against Fedora's Qt. Selected with `QT_WAYLAND_CLIENT_BUFFER_INTEGRATION=linux-dmabuf-unstable-v1;wayland-egl` (all listed keys load); `Compositor.qml` needs no change. Private Qt API: the plugin must be rebuilt for every qt6-qtwayland/qt6-qtbase update (image lint).
**Spike 2 (Dell, transient `bootc usroverlay` and a `/run` drop-in, removed afterwards):** the plugin loads and the shell renders, but STK still renders on llvmpipe (563 % CPU): `WAYLAND_DEBUG` shows Mesa (Flatpak runtime 26.2.5) binding `zwp_linux_dmabuf_v1` **v3** and getting formats, but no device (no `wl_drm` global, no feedback). Also: the stock `wayland-egl` integration does nothing on Mesa 26.2 (`There is no EGL_WL_bind_wayland_display extension`). **Next:** patch the plugin to protocol v4 with default/surface feedback (`format_table` memfd, `main_device` = the render node's dev_t from `EGL_DRM_RENDER_NODE_FILE_EXT`, one tranche), about 150-200 lines, carried as a patch file in the build stage; worth upstreaming.
**Spike 3 (the patch, Dell, transient):** `image/qt/0001-linux-dmabuf-v4-feedback.patch` (306 lines, +183/-6, 5 files): a `LinuxDmabufFeedback` class (sealed memfd format table, default and surface feedback, `main_device` and one tranche), v4 advertised when the EGL device has a render node (`EGL_DRM_RENDER_NODE_FILE_EXT`, fallback `drmGetRenderDeviceNameFromFd`), else v3; no `format`/`modifier` events to v4 clients; the global is created at the end of `initializeHardware` (no global when EGL setup fails; upstream advertised a broken one); the plugin's CMake uses wayland-protocols' v5 XML. STK: UHD 630, 14-17 % CPU, 1080p60, Guide over it.
**Built into the image (lead-6):** stage `qt-dmabuf` in `image/Containerfile` (the SRPM of the installed qt6-qtwayland, `builddep`, the patch, `-DTEST_dmabuf_client_buffer=ON -DCMAKE_SKIP_RPATH=ON`, one ninja target, stripped); the OS stage refuses an image whose qt6-qtwayland/qt6-qtbase differ from `/usr/share/ruyaos/qt-dmabuf-built-against`; `ruya-compositor@.service` sets `QT_WAYLAND_CLIENT_BUFFER_INTEGRATION=linux-dmabuf-unstable-v1;wayland-egl`; `vm-session-check.sh display` asserts the compositor's `linux-dmabuf: zwp_linux_dmabuf_v1 version` line; `lint-text.ps1` allows tabs in `image/qt/*.patch` only; spec `00` (GL clients). Image 0.0.58: build 23 min (the stage about 3 min), qcow2 17 min. VM: `display` all PASS (v3 there: llvmpipe has no render node), `check` all PASS, audio checks of T-322/T-347 PASS. **Dell 0.0.58 from the image (no overlay):** `linux-dmabuf: zwp_linux_dmabuf_v1 version 4 with feedback, main device "e280"`; STK through Session1: `OpenGL renderer: Mesa Intel(R) UHD Graphics 630 (CML GT2)`, 14.5 % CPU, the shell 17.5 %.
**Follow-ups (Inbox):** filter `external_only` modifiers out of the tranche; explicit sync (NVIDIA proprietary); multi-GPU tranches and direct scanout (B-003); offer the patch upstream (Qt bug: the configure test never finds EGL, and the plugin is v3 only); frame times in a real race (T-355 second pass).
