# T-230 — `.play` format: schema, parser and the hostile-package tests

Status: todo · Phase: 7 · Depends: T-228 · Area: services, api · Size: M · Owner: builder · Developer surface: public-format

## Goal
One pure-Rust library that reads a `.play` folder or `.play.zip` and says "valid, with this manifest and file table" or names exactly what is wrong. It is the only parser: the importer, the shell's package page (through the service), `ruya-pack` and the Store all use it.

## Read first
- `docs/specs/05-play-packages.md` §2 to §5, §9.3, §15
- Reference patterns: `services/ruya-store` (pure core + thin adapters, untrusted-input parsing and its tests), `api/dbus/*.xml` (a contract file next to code)

## Scope
1. A library crate in the services workspace (check `services/Cargo.toml` for naming and layout; suggested `ruya-play-format`; MIT OR Apache-2.0) with no D-Bus, no Flatpak, no network, builds on Windows.
2. `api/play/play.schema.json`: the JSON Schema of `play.json` (strict for `permissions`, `run`, `components`; ignoring unknown keys elsewhere), the genre and link-kind vocabularies, the permission vocabulary, the limits as constants in one place.
3. Reader trait over a `Source` (folder, zip) listing entries (name, kind, size) **before** reading content; the zip reader enforces 05 §4.3 (no encryption, no links, no duplicates, central directory only, expansion ratio, declared sizes).
4. Validation: `play.json` rules (ids, localized text, plain-text sanitising, links https only, art slot names, `controller`, `age_rating`), `play.files` rules (05 §4.2: paths, NFC, case-insensitive uniqueness, reserved names, link containment and one-hop rule, counts), the match between table and package (nothing extra, nothing missing, hashes and sizes when content is read), `requirements.installed_mb` within 1 % of the table.
5. A machine-readable error list (code, path, message) the shell and `ruya-pack` can show; messages are user-fixable.

## Out of scope
- Signatures (T-231), image/video decoding (T-232), unpacking to disk (T-237), runner resolution (T-239).

## Acceptance criteria
- [ ] Fixture packages (generated by a test helper, not binary blobs in git) for every rule: `valid_minimal`, `valid_wine_full`, and hostile ones named after what they do: `path_traversal`, `absolute_path`, `backslash`, `case_collision`, `reserved_name`, `symlink_in_zip`, `hardlink`, `device_node`, `link_escapes_tree`, `link_chain`, `duplicate_entry`, `encrypted_entry`, `zip_bomb_ratio`, `declared_size_lies`, `extra_file_not_in_table`, `missing_file`, `hash_mismatch`, `manifest_too_big`, `json_too_deep`, `unknown_permission_key`, `unknown_run_key`, `format_from_the_future`, `http_link`, `name_with_bidi_override`, `reserved_app_name`. Each is rejected with its own error code (test: `tests/hostile.rs`, one test per fixture).
- [ ] Each limit has a boundary test at, one below and one above (`tests/limits.rs`).
- [ ] Reverting any single rule in the validator turns at least one named test red (the Outcome lists the rule-to-test map).
- [ ] The folder and zip forms of `valid_wine_full` give identical results (`tests/forms.rs`).
- [ ] The schema validates `valid_*` and rejects the schema-level hostile fixtures (`tests/schema.rs`).
- [ ] `.\scripts\dev.ps1 test` ALL GREEN; `dev.ps1 rust` clean (clippy/fmt as the other crates).
