# T-463 — A faster Qt Quick test run: shards, a test motion scale, condition waits

Status: done · Phase: 2 · Depends: — · Area: scripts (dev.ps1), shell (tests) · Size: M · Owner: builder · Complexity: normal · Developer surface: none

## Goal
`dev.ps1 test` spends about 330 s in the offscreen Qt Quick tests (1198 tests). Every builder round, review and merge gate waits for it (owner, 2026-11-11: "do we lose time with unnecessary tests?"). Make the same tests, with the same assertions, finish in well under half the wall time.

## Found (lead-11 profile, 2026-11-11; raw data `output\perf-times.xml` on the lead's checkout, not tracked)
- 1265 functions, 329.9 s in total. 59 functions of 1 s or more take 139.9 s (42 %); start-up per file is negligible. The exe runs every `tst_*.qml` in one process.
- Slowest TestCases (s): SoundAmbient 33.5, Wallpaper 32.2, Bluetooth 17.0, Storage 16.5, Settings 15.1, SoundChecker 13.7, Power 13.1, Pages 11.9, Display 9.5, AppFlow 9.0.
- Causes: real animations at full duration (only 4 of about 170 files set `Theme.motionFactor`); 322 literal `wait(N)` calls (18 of 1 s or more, 29 s, e.g. `tst_glide.qml:555` wait(7000), `tst_wallpaper.qml:1001-1136` wait(600..1500)); timer-bound waits (`Theme.guideHoldMs` in `tst_Power.qml:309,328`, three real pairing time-outs in `tst_picker_pairing.qml:83-93`); `SoundThemes.fuzz(60000)` at `tst_sounds.qml:125` is 13.5 s of real CPU work.

## Scope
1. **Shards.** `dev.ps1 test` (and CI's shell job) runs the offscreen Qt Quick tests in N processes (default 3; `-Shards`), each with its own subset of the test files through the runner's `-input`, its own log, balanced by the measured times (a checked-in list or a simple size heuristic), and one combined pass/fail with the totals of all shards. A shard that crashes or hangs is a failure with its log named. `qml tst_x`, `shots` and the green marker work as before.
2. **A test motion scale.** Tests whose subject is not timing run with a short motion scale (e.g. `Theme.motionFactor` 0.05-0.1, set once in a shared place); tests whose subject is a duration (the ambient bed fade at `tst_sound_ui.qml:173`, which asserts reduced motion does not shorten it; glide timing; long press) keep real time and say so in a comment.
3. **Condition waits.** Replace the fixed waits of 1 s or more with `tryVerify`/`tryCompare` on the condition they wait for. A negative check ("nothing happens within X") keeps its wait but may shorten X when X is a tunable time the test sets (hold time, pairing window).
4. Leave `SoundThemes.fuzz` unless a cheap, assertion-preserving cut is obvious (its `cases > 1500` floor stays).

## Out of scope
- Removing, skipping or loosening any test (CLAUDE.md, Hard rules). `shots` speed.

**What was built.**
1. *Shards* (`scripts/dev.ps1`). The runner's `-input` takes one path (the last one wins; checked), and some tests resolve files relative to their own location (`tst_bluetooth`, `tst_sounds`), so copies in shard folders would break them. Instead `Invoke-QmlShards` starts **one `tst_ruyashell` process per test file**, `-Shards N` at a time (default 3), biggest file first (a size heuristic; a process pool balances itself, so no list of timings is checked in). Each file has its own log (`shell\build-win\qmltest\<file>.txt`); the run prints one `Totals:` line summed over all files. A file whose process exits non-zero, ends without a `Totals` line (a crash) or runs longer than 10 minutes (killed) fails the run with `SHARD FAILED: <file>: <why> - log <path>`. A process costs about 0.3 s of start-up, so 65 processes add about 7 s of CPU in 3 lanes. The green marker, `qml tst_x`, `shots` and the rest of `test` are unchanged. QWARN lines are no longer echoed (hundreds of "font directory" lines per run); they stay in the logs. FAIL, XPASS, QCRITICAL and failure locations are printed, with the file name in front.
2. *CI* (`.github/workflows/ci.yml`, shell job): `ctest` is replaced by `scripts/run-qml-tests.sh <exe> 3 <logdir>` (bash, `xargs -P`, `timeout`, `awk`; `findutils gawk` added to the `dnf install` line), the same rules and the same output. Not run on Fedora here; `ctest`'s `qml` test stays for a serial run by hand.
3. *Test motion scale* (`shell/tests/tst_main.cpp`): `windowGuard.ensureActive()`, which every `init()` already calls, sets `Theme.motionFactor` to 0.1 (`windowGuard.testMotion`; not under `shots`, where it stays 1; `RUYA_TEST_MOTION=<f>` overrides it, 1 = as designed). Set per test, not per engine, because several files reset the factor to 1.0 in `cleanup()`. The first run with the scale failed 10 tests in 5 files whose subject is a duration; they set `Theme.motionFactor = 1.0` themselves, with a comment: all of `tst_motion` and `tst_glide` (in `init()`), one test in `tst_appflow` (launch token 400 ms), two in `tst_glass` (pulse, shimmer period), two in `tst_themes` (700 ms cross-fade, mid-fade sample). One more test edit, not an opt-out: `tst_hub_pause` (see Flake below). `tst_pages` keeps its own 0.03. `tst_sound_ui:173` (the ambient bed's 800 ms fade) needed nothing: that fade is an `AmbientLoop` constant, not a Theme token, so the scale does not touch it and the test still asserts the real 800 ms. New `tst_test_motion.qml` asserts the scale is set before the body, a test can change it, and the next test gets it back.
4. *Condition waits.* Every literal `wait(N)` of 1 s or more in `shell/tests` was read. Those at `tst_wallpaper` (1013-1136), `tst_glide:555` (7000), `tst_timezone`, `tst_long_names`, `tst_artglow`, `tst_thermal:403` are inside `test_zz_screenshots*` functions that run only under `shots`, so they cost the gate nothing and are not touched (`shots` is out of scope). The rest are negative checks whose wait is the subject, kept: `tst_picker_pairing` 1500 and 1000 (the mock's pairing window is a fixed 300 ms, not a time the test sets), `tst_performance` 1200 twice and `tst_hub_performance` 1200 ("more than two polling intervals"; the interval's minimum is 500 ms), `tst_power` `Theme.guideHoldMs + 400` (a spec constant, 2000 ms, readonly). No positive fixed wait of 1 s or more was left in a test the gate runs, so nothing was replaced by `tryVerify`; I did not go through the 300 shorter waits. `SoundThemes.fuzz(60000)` untouched (14 s of CPU, `cases > 1500` floor intact).

**Where the time is now.** 292 s of test CPU over 3 lanes. Biggest files: `tst_sound_ui` 33 s (26 tests that each wait for the real 800 ms bed fade), `tst_sounds` 19 s (14 s of it the fuzz), `tst_bluetooth` 17 s, `tst_storage` 16 s, `tst_power` 13 s (`guideHoldMs`), `tst_wallpaper` 13 s (was 32 s). The rest is about 0.14 s per test of shell start-up, which no wait fix touches. Going from 3 to 4 lanes would save roughly another 20 s on this 16-thread machine; the default stays 3 (task text).

**Proofs.**
- Shard failure path (`Test-QmlShardRunner`, in `dev.ps1 shell`/`test`, before the Qt Quick step): stand-in programs for an ok, a failing, a crashing (exit 3, no Totals) and a hanging file; the verdict, the three log names and the sums (8 passed, 1 failed, 2 skipped) are asserted, for the PowerShell runner and again for `scripts/run-qml-tests.sh` (Git's bash). The sh twin's first version used `tee /dev/stderr`, which does not exist under PowerShell: this self-check was red on the first full `test` and caught it.
- Revert checks (`scripts\revert-check.ps1`): `tst_main.cpp` `setProperty("motionFactor", testMotion())` -> `1.0`: CAUGHT, both `tst_test_motion` tests fail. `tst_motion.qml` without its `Theme.motionFactor = 1.0` in `init()`: CAUGHT (`test_defaults`, `test_reduced_motion`). `dev.ps1` `-gt $TimeoutSec` -> `-gt 99999`, and `run-qml-tests.sh` "no Totals line" check -> `false`: revert-check says "NOT CAUGHT" because it counts only failing Qt tests, but in both runs `FAILED: shard runner self-check` / `(sh) self-check` is printed and the run is red, i.e. the self-check caught them.
- **Flake found and fixed.** The first of three back-to-back full runs on the committed code was red: `tst_hub_pause` `test_a_failed_thaw_toasts_and_the_next_close_tries_again`, `verify(find("quickMenuPaused").visible)` straight after `openHub()` (an instant read of a state that arrives with the service's reply). Run 3 at a time, 30 runs of the file: 4 red at the short motion scale, 0 of 30 with `RUYA_TEST_MOTION=1`. The line is now `tryVerify(..., 2000, "the header says Paused again")`: the same condition, waited for (not weakened). After it: 36 of 36 green runs of the file under 3-way load, and 4 full sharded Qt Quick runs in a row, each `1223 passed, 0 failed, 100 skipped` in 109-111 s. Full `dev.ps1 test`: green twice before the fix (runs 2 and 3 of the three: 164 s and 125 s in the Qt step, slowed by the hub_pause polling and the other builder's load), and twice in a row after it, the last one on the committed tree (it wrote `output\last-green-test.txt`; step times in the HANDOFF). Other flake risks in 65 files at 0.1 motion are not excluded by about ten clean full runs; if one shows up, `RUYA_TEST_MOTION=1` tells at once whether the short scale is the cause.

- **Round 2 (review): second flake.** `tst_settings_lazy` `test_a_replaced_page_goes_after_the_glide` (the order of the Store's reap against Settings settling, with a glide of about 28 ms) was red 2 of 21 at 0.1 and 0 of 21 at `RUYA_TEST_MOTION=1`, and once in a full `test`. Its subject is an order relative to a duration, so it keeps real time (`Theme.motionFactor = 1.0` with a comment, added to the `shell/CLAUDE.md` list). I did not establish whether the reap can really precede the settle at short durations (a product race) or only the watch is armed late; see the HANDOFF inbox. After that, a loop of the sharded Qt step 10 times in a row (offscreen, `scripts/run-qml-tests.sh`, 3 at a time): all 10 `1223 passed, 0 failed, 100 skipped` (110-154 s), no file red even once, so there was nothing more to rerun per file; `tst_settings_lazy` alone 21 runs under 3-way load: 0 red. `run-qml-tests.sh` now prints the number of logs it found, not the expected number of files (the self-check expects `in 4 files`: the hanging stand-in writes no log).

**Deviations.** (a) Process-per-file with a pool instead of N fixed subsets: the runner takes one `-input`, copies break relative paths, and a pool needs no timing list. (b) CI is sharded too (3). (c) A new test file, `tst_test_motion.qml`. (d) `shell/CLAUDE.md` gets the rule for the scale; `docs/dev-setup.md` the shard runner.
