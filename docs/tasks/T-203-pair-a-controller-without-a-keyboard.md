# T-203 — Pair a controller on a fresh install, with no keyboard (first boot and login screen)

Status: in-progress · Phase: 2 · Depends: — · Area: services, shell, image · Size: M · Owner: builder

## Goal
A console with no keyboard can be set up and used with a Bluetooth controller alone. Today the first-boot setup (`Setup.qml`) and the profile picker have no way to pair a controller: Settings → Bluetooth exists only after sign-in, and signing in needs input. Owner report, 2026-11-06: "from a cold boot the controller doesn't connect when it is on the login screen". The firmware cause is fixed in the image (T-162 session); this is the other half: a bonded controller must reconnect at the login screen (verify), and a controller that is **not** paired yet must be able to pair itself there.

## Facts (Dell, `0.0.44`)
- Cold boot with the Intel dongle: the adapter had no firmware (`ibt-19-0-4.sfi` missing in the image) -> `No default controller available` -> nothing connects. Fixed by shipping the firmware (`image/build/20-base.sh`); verify on a cold boot of the new image.
- A bonded + trusted DualSense reconnects by itself when its PS button is pressed (BlueZ accepts the connection; `ruya-inputd` creates the navigation device on hot-plug). Needs checking at the picker.
- BlueZ keeps the adapter not pairable; `ruya-devices` opens `Pairable` only for the length of a `Pair` call (T-162 session). An unpaired pad in pairing mode (PS + Create) is therefore ignored, and there is no BlueZ agent to accept an incoming pairing.
- The first-boot wizard has no Bluetooth step; the picker has no hint.

## Scope
1. **Controller pairing window (service):** `ruya-devices` can open a bounded window (default 120 s) in which the adapter is discoverable-for-HID/pairable and a registered BlueZ agent (`NoInputNoOutput`, "just works") **accepts incoming pairings only from input devices** (Class of Device major class Peripheral `0x05`, i.e. gamepad/keyboard/mouse; anything else is rejected), marks them trusted, and lets the HID connection through. The window is opened by a D-Bus call (`Bluetooth.StartControllerPairing(seconds)`, `StopControllerPairing`, a `ControllerPairingState` property/signal) and closes itself on timeout, on success, or when stopped. Contract first in `Devices1.xml`. Security: the window is only opened by `ruya-shell` (existing bus policy), never by default; no PIN/passkey device is accepted here (B-006 owns PIN pairing); the agent must not accept audio or unknown classes.
2. **When the shell offers it:** (a) in the first-boot wizard, as its first step when no HID input device other than the built-in virtual one exists ("No controller or keyboard found. Hold PS + Create (or the pairing button) on your controller"), skipped when any input device is already present; (b) on the profile picker when there is no input device at all, as a hint plus the window opened automatically; (c) Settings → Bluetooth gets a "Pair a controller" row that opens the same window (the current manual scan-and-pair flow stays). Copy in `qsTr` + Turkish; the screens are controller-first, so the wizard step itself must be passable with the newly paired pad.
3. **Reconnect at the picker (verification, no new code if it works):** with a bonded pad and a cold boot, the pad reconnects at the picker within a few seconds of the PS button and navigates; if the shell starts before BlueZ/`ruya-inputd` see the adapter, make the ordering/retry robust (`After=bluetooth.service` on `ruya-inputd` if useful) and record what was needed.
4. **Mock and tests:** the mock offers the window with scripted outcomes (success, timeout, rejected device class).

## Out of scope
- PIN/passkey pairing (B-006), pairing several players' pads in one flow, renaming pads, Wi-Fi onboarding (a later OOBE task), a keyboard-only path (a USB keyboard already works).

**What was built**

- **Contract (`api/dbus/org.ruyaos.Devices1.xml`, Bluetooth part only):** `StartControllerPairing(u seconds) -> s`, `StopControllerPairing() -> s`, properties `ControllerPairingState` (`idle` | `open` | `paired` | `timeout`) and `InputPresent` (b), signal `ControllerPairingRejected`; new statuses `busy` and `refused`. No change to the Batteries part or to the icon font (T-223 lane).
- **Service (`services/ruya-devices`):**
  - `pairing.rs` (new, pure): input-class rule (Class of Device major class Peripheral `0x05`; for a device without a class, a Bluetooth LE appearance in the HID category), HID service UUIDs, `caller_allowed` (root or the service's own user, fails closed), window lengths (default 120 s, at most 300 s), state names, device path to address.
  - `bluetooth.rs`: the window in the core (`start_controller_pairing`, `stop_controller_pairing`, `tick`, `pump`, `window_pair`, `agent`), the `AgentHandler` seam; the `Bluez` trait gets `set_discoverable`, `register_agent`, `unregister_agent`; `RawAdapter` gets `pairable`/`discoverable`, `RawDevice` gets `class`/`appearance`; `FakeBluez` follows (adapter state, agent registration, `bond`, `add_device`).
  - `bluez.rs` (Linux): the `org.bluez.Agent1` object served on the `BluezClient` connection (BlueZ calls an agent on the connection that registered it), `RegisterAgent(path, "NoInputNoOutput")` + `RequestDefaultAgent`, `UnregisterAgent`, `Discoverable`, `Class`/`Appearance` read. PIN and passkey methods always answer `org.bluez.Error.Rejected`.
  - `input.rs` (new): `InputPresent` from `/sys/class/input/input*/capabilities/key` (keyboard = keys 1-31, gamepad = a button in `0x120`-`0x13e`; `RuyaOS Navigation` excluded), polled every 2 s.
  - `dbus.rs`/`main.rs`: methods, properties, signal; caller uid check through `GetConnectionUnixUser`; the watcher also waits on the window's deadline, runs `pump` after each read and pairs a found gamepad off the loop; a notifier announces what happens outside any call (a refused device).
- **Shell:** `Bluetooth` facade (`controllerPairing`, `inputPresent`, `inputKnown`, `startControllerPairing()`, `stopControllerPairing()`, `controllerRejected`), D-Bus client and mock (scripted outcomes `wait`/`success`/`timeout`/`rejected`, `mockSetInputPresent`; the mock has an input device by default so every existing screen is unchanged). New `ControllerPairHint.qml`; `Setup.qml` pairing stage in front of the welcome step (not a numbered step), `ProfilePicker.qml` hint plus automatic window, Settings -> Bluetooth "Pair a controller" row. Turkish and English strings are translated.

**Round 2 (security review, all five blocking items and the non-blocking ones)**

1. **Strangers that bond are removed.** With the agent registered `NoInputNoOutput` the kernel accepts a just-works pairing itself and BlueZ never asks the agent, so a phone could bond. The window now remembers the devices that were paired when it opened (`paired_before`); `pump` (after every read) treats a device that is paired now and was not as the controller that ends the window if it is an input device, and otherwise removes it (`Bluez::remove` = `Adapter1.RemoveDevice`, on every read that shows the stranger paired, no "already removed" memory, round 3), sets `rejected` and so announces `ControllerPairingRejected`. The agent's refusal path removes a refused device that has bonded. A device the user pairs by hand in the window is added to `paired_before`, so it is not swept. Tests: `a_phone_that_bonds_anyway_is_removed_again` (phone, headset, unknown: `remove` + rejected, window goes on; round 3: `a_phone_that_bonds_again_is_removed_again` removes it again after each re-bond), `a_refusing_agent_also_removes_a_device_that_bonded`, `a_controller_that_bonds_without_asking_the_agent_ends_the_window`, `what_was_paired_before_the_window_is_not_a_stranger`, `a_device_the_user_pairs_by_hand_in_the_window_is_kept`. The old test that only asserted the window ignores a bonded phone is replaced. **Residual risk** (written in `Devices1.xml` and 03): Class of Device and LE Appearance are supplied by the remote and trivially spoofed, so any device claiming `0x05xx` in a window can bond, be trusted and act as a keyboard or pad; mitigations are the short window, no Discoverable, the cap on automatic reopening and the sweep.
2. **`set_discoverable(true)` is gone from the window.** Pads in pairing mode advertise and are found by the scan and paired by `window_pair`; a bonded pad pages the console. Pairable stays (our outgoing pair needs it). `Discoverable` is only ever switched off (item below). XML comment, 03 and 02 updated; tests assert `discoverable` stays false and no `discoverable` call is made.
3. **Picker reopen cap.** `ControllerPairHint` counts the windows of a series (`windows`, `maxAutoWindows` = 3, about six minutes); after the third timeout nothing opens by itself, `exhausted` shows the translated "Press A to start pairing.", and A/Return in the picker starts a new series (`newSeries()`) instead of choosing a profile. Test `test_a_timed_out_window_is_opened_again_but_only_three_times` (mock `timeout` script: starts stop at 3 over a 1.5 s wait, Return reopens, again 3, nobody signed in). 02's picker row updated. Answers the lead's question: capped.
4. **VM check.** `scripts/vm-devices-check.sh` (Bluetooth section, runs in `check` and `bluetooth`): `InputPresent` is `b true` (QEMU's keyboard counts, which also proves `/sys/class/input` is readable in the hardened user unit), `StartControllerPairing 0` answers `unavailable`, 301 s answers `invalid`, `ControllerPairingState` stays `idle`, `StopControllerPairing` answers `ok`, `nobody` is refused for both calls (bus policy; the service's own uid check is covered by the unit tests), `ruya-devices` still active. **VM queue item for the lead: `vm-devices-check.sh` (T-203).** Not run here (no image built).
5. **`window_pair` is confined.** It returns at once unless the window is open and the pump handed out exactly that address (`in_flight`); it remembers the window's id, and after a successful pair it trusts and connects only if that same window is still open, otherwise the pad is left bonded but untrusted (a message in the journal). Tests: `a_pairing_handed_out_does_nothing_once_the_window_ended` (stop and timeout between `pump` and `window_pair`, and a stranger address: no pair/trust/connect call) and `a_pairing_that_completes_after_the_window_ended_is_not_trusted` (the window is stopped inside the `pair` call, through a hook in `FakeBluez`).
- **Non-blocking items:** a test for the pump candidate filter (`the_window_only_pairs_a_gamepad_that_claims_an_input_class`: icon `input-gaming` with a phone class, a headset class or no class is not paired). A `starting` flag under the state lock makes a second `StartControllerPairing` that arrives while the first talks to BlueZ `busy` (`a_second_start_while_the_first_is_opening_is_busy`, via the fake's hook). On the first read that shows an adapter (no window open) the service switches `Pairable` and `Discoverable` off (`an_adapter_found_pairable_or_discoverable_is_closed_once`), so a crash inside a window cannot leave the console pairable; `PairableTimeout` in the image's `main.conf` stays an inbox line. The stale-reply race in `ControllerPairHint` is fixed by keying: the shell's `finished("controller-pairing", id, status)` now carries `id` `start` or `stop`, and the hint takes only the answer to its newest start (`test_a_stops_answer_is_not_taken_for_the_starts`: power off, then stop and start at once, the start's `unavailable` must decide). Copy: "(on a DualSense: PS + Create)" next to the generic words, in `ControllerPairHint.message` only (`test_the_text_names_the_dualsense_combination`); Turkish translated, the replaced strings removed.

**Deviations and judgement calls**

- **The window also pairs a found gamepad from our side (round 2: the window is not discoverable; a pad in pairing mode is found by the scan)** (its scan finds a pad in pairing mode: `Icon` `input-gaming` and an input class; three attempts): a pad in pairing mode does not call a host it does not know, so an agent alone would not pair a DualSense. Phones, audio and keyboards are never paired this way (keyboards need a passkey, B-006). The task text says the agent accepts incoming pairings only; this is an addition that stays inside the same class rule.
- **`InputPresent` is a property of the Bluetooth interface**, not a new interface: the shell asks it for the sake of the window, and the XML change stays in the Bluetooth part. It is polled every 2 s (no udev here). It reads sysfs, so it counts keyboards and gamepads over USB too, as the task asks ("any HID input device other than the built-in virtual one"); a mouse alone does not count.
- The task says `ControllerPairingState` "property/signal": it is a property (its `PropertiesChanged` is the signal) plus `ControllerPairingRejected` for the refused-device event.
- The pairing stage is in front of step 0 and not a sixth numbered step, so the progress dots and every existing step index and test are unchanged.
- The window length the shell asks for is the service default (120 s); a longer one has no UI.
- `ruya-devices --session` follows nothing, so a window opened there never ends by itself (documented in `dev-setup.md`).
- `caller_may_pair` (the uid lookup on the bus) is Linux-only wiring and is not unit-tested on the host; the rule it feeds (`caller_allowed`) and the core's `refused` status are.
