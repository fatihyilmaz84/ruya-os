# RuyaOS — Platform, Build & Release

Status: **Draft v1** · Parent: [00-overview](00-overview.md)

## 1. OS image

### 1.1 Base
- `FROM quay.io/fedora/fedora-bootc:<N>`, pinned to a Fedora major release. Track N and N+1 in CI so rebases happen deliberately.
- **One image for all hardware** (ADR-009): RPM Fusion codecs and the NVIDIA driver are always included. Build steps are ordered scripts in `image/build/NN-*.sh` (repos → base → codecs → NVIDIA → slim → services → initramfs → branding → guard → cleanup), bind-mounted at build time so they aren't shipped. Branding (`92-branding.sh`) also writes `RUYA_API_LEVEL=<n>` (starts at `0`) into `/usr/lib/os-release`: the API level apps can ask for with `x-ruya-min-api-level` (RUY-156).
- Every build runs `bootc container lint` and fails if it reports problems.

**What the image really holds** is in [`docs/image-packages.md`](../image-packages.md): every package group and every leaf of the built image with the reason it is there, what the slim step removed and why, and the enabled units. This table is the design intent.

Firmware, GPU drivers, codecs and Bluetooth/Wi-Fi support are not trimmed (ADR-009).

### 1.3 Filesystem semantics (what to rely on)
- `/usr`: read-only, comes from the image.
- `/etc`: **persistent and mutable**. On upgrade, bootc does a 3-way merge (image default, old image default, local edits). Ship defaults in `/usr/lib/…` and `/usr/etc` where possible, and keep local `/etc` edits to a minimum.
- `/var`: persistent, never touched by updates. `/home → /var/home`. Our state lives in `/var/lib/ruyaos/` (0755 root): one directory per service (`library/`, `notifications/`, `platform/`, each 0700), and `profiles/` (0700 root, made by `tmpfiles.d/ruyaos.conf` at boot) holding the PIN store `profiles.toml` (0600), hidden from every other root `ruya-*` unit except the listed ones (§3 item 11).
- `/opt`: in Fedora bootc it points into `/var` by default. Don't install image content there. Use `/usr/lib/ruyaos/`.
- Default root filesystem is XFS on one partition (+ ESP + `/boot`). There is no separate data volume unless the installer creates one (§5).

### 1.4 Swap and memory pressure (T-465)
- **The image has one swap device: a compressed zram device in RAM, no swap file or partition.** `image/rootfs/usr/lib/systemd/zram-generator.conf` (`zram-generator` was installed from the start but had no config, so there was no swap at all) sets `zram-size = min(ram / 2, 4096)` (MiB) and `compression-algorithm = zstd`; `systemd-zram-setup@zram0.service` makes `/dev/zram0` at boot (swap priority 100). An 8 GB console gets 4 GB of zram, a 4 GB VM 2 GB.
- **Why.** A frozen game (T-147) costs no CPU but keeps all its memory (a frozen SuperTuxKart race about 1.0 GB, of which 680 MB i915 GPU buffers); a third or fourth game could only end in the OOM killer. With swap the kernel can push a frozen game's pages out, compressed. Measured on the Dell (8 GB, 0.0.64, a temporary 4 GB zstd zram): `memory.reclaim` on the frozen game moved 261 MB of anon memory into 77 MB (3.1x); under a 5.2 GB memory hog the i915 shrinker released 343 of 697 MB of GPU buffers into swap, with no OOM kill; thawing took 198 ms and 42 MB faulted back within 0.4 s. Asking the kernel to reclaim a frozen app's memory on purpose is built in T-466 (30 s after the Freeze, half of each cgroup's `memory.current`, only with swap active; spec 03 section 4.1, Freeze and Thaw); this swap makes it worth doing.
- **Why not the `zram-generator-defaults` package.** It ships a file at the same path, but with `zram-size = min(ram, 8192)` and the kernel's default algorithm (lzo-rle). Half of RAM is plenty (a full device holds RAM / 2 of pages and, at the measured 3x, costs about RAM / 6), and zstd is what was measured. The image carries its own file, so a package update cannot change the numbers; a machine-local `/etc/systemd/zram-generator.conf` overrides it (an empty one turns zram off).
- **`systemd-oomd`** is enabled (`enabled-units.txt`), but the image has no `systemd-oomd-defaults` and nothing sets `ManagedOOMSwap=` or `ManagedOOMMemoryPressure=` on any unit or slice, so oomd watches no cgroup and never acts: its `SwapUsedLimit` (90 %) cannot make it kill a game for filling zram. The kernel OOM killer stays the last resort. Choosing who dies first is T-464; a cap on frozen apps is an owner decision (STATUS), and T-466 reclaims a frozen app's memory without an oomd policy.
- **Swap settings: swappiness stays at the kernel default 60, `vm.page-cluster` is 0** (RUY-530; `image/rootfs/usr/lib/sysctl.d/61-ruyaos-zram.conf`, apart from the gaming file of §1.5 because the reason is zram). The kernel's page-cluster 3 reads and decompresses 8 pages per swap-in, a readahead that saves disk seeks; zram has none, so 0 (one page, as CachyOS does for zram) avoids the wasted work, mostly when a frozen, reclaimed game is thawed (198 ms measured above, at 3). The Dell thaw numbers at 3 and 0 are in the RUY-530 Outcome. 60 was the swappiness value in the measurements above. Raising it for zram is common advice, but it would also push the running game's pages out, which a console wants least; change it only with a measurement on a running game.
- **Checked on every booted image:** `scripts/vm-swap-check.sh` (device, size, `zstd`, the only swap and on, swappiness 60, `vm.page-cluster` 0, oomd not failed and no `ManagedOOM*` anywhere, and a real `memory.reclaim` of a transient service's 256 MiB into zram at under half the size; the pattern is far more compressible than a game, so this proves the plumbing, not the 3.1x ratio). The System page already lists swap and zram (T-226); before this it had nothing to show.

### 1.5 Gaming kernel settings (RUY-525, RUY-527; audit RUY-522)
Three kernel-side defaults a Windows game under Proton wants, all of which SteamOS sets and Fedora does not, plus the disk scheduler for flash (RUY-531). Files: `image/rootfs/usr/lib/modules-load.d/ruyaos-ntsync.conf`, `image/rootfs/usr/lib/sysctl.d/60-ruyaos-gaming.conf` (sorts after Fedora's `10-map-count.conf`, so it wins) and `image/rootfs/usr/lib/udev/rules.d/61-ruya-block-scheduler.rules` (sorts after systemd's `60-block-scheduler.rules`). No unit, hardening or D-Bus rule changes; the guard and the enabled units are unchanged.
- **`ntsync` is loaded at boot.** The kernel builds the NT synchronisation driver as a module (`CONFIG_NTSYNC=m`) and ships `ntsync.ko`, but nothing loaded it, so `/dev/ntsync` did not exist (Dell, 0.0.75). GE-Proton (the default Windows runner, ADR-025) uses ntsync from 10-9 on when the device exists and falls back to fsync otherwise; SteamOS 3.7.20 loads it by default.
  - *Access.* The driver registers a misc device with mode `0666`, owner `root:root` (kernel source `drivers/misc/ntsync.c`), so every profile user (`ruya-p<N>`) can open it and `ruya-shell` and the services need nothing: **no udev rule is shipped**, and `image/security-baseline.json` needs no entry (`vm-security-check.sh` looks for world-writable files under `/usr` and `/etc` only, not `/dev`). The device is an NT sync-object API (mutexes, semaphores, events) and carries no data of a user. Security note: it is a small kernel driver reachable by every profile user, i.e. added kernel attack surface. The SELinux label is whatever policy gives an unlabelled misc device (expected `device_t`); the VM check prints it. *To be confirmed on the 0.0.82 image (lead): mode, owner, label.*
  - *Flatpak.* `--device=all` exposes the whole host `/dev` and so `/dev/ntsync`; `--device=dri` binds only `/dev/dri`, so **expected: only `device=all` shows `/dev/ntsync`** in Flatpak 1.18.4. *To be confirmed (lead; `vm-gaming-check.sh flatpak <app-id>` records both).* If confirmed, a Windows-game runner (RUY-34, RUY-35) needs `device=all` to get ntsync or accepts the fsync fallback; no app's permissions are widened here.
- **`vm.max_map_count = 2147483642`** (Fedora: 1048576). Some Windows titles map more regions than that; SteamOS, Bazzite and CachyOS use this value.
- **`kernel.split_lock_mitigate = 0`** (kernel: 1; set with a leading `-` so a kernel without the setting is not an error). On CPUs with split-lock detection (Intel Ice Lake / Alder Lake and later) a game that does misaligned atomic accesses is slowed about 10 ms per event while the mitigation is on; SteamOS and Bazzite turn it off. **Security trade (owner decision 2026-11-13):** the mitigation is a local denial-of-service defence, and with it off a process can slow the whole machine with bus locks. That is acceptable on a single-user console, where the only such process is the game in front. The Dell's i5-10500T has no split-lock detection, so the value is a no-op there.
- **I/O scheduler by device type (RUY-531).** `image/rootfs/usr/lib/udev/rules.d/61-ruya-block-scheduler.rules` sorts after systemd's `60-block-scheduler.rules` (bfq for every `sd*`, `mmcblk*`, `sr*`). Flash (`sd*` disks and `mmcblk*` with `queue/rotational` 0: SATA SSD, eMMC, and USB sticks, which follow their flag) gets `mq-deadline`, because bfq costs CPU per request. Rotational disks keep bfq. NVMe keeps `none`; virtio (`vd*`), zram, optical and loop devices are not matched. The Dell fio and game cold-start numbers are in the RUY-531 Outcome.
- **Checked on every booted image:** `scripts/vm-gaming-check.sh` (`lsmod` has `ntsync`; `/dev/ntsync` is a character device with mode 0666, its owner and label printed; a profile user opens it read-write; both sysctl values; the scheduler of every block device (a virtio disk stays `none`, a flash `sd*`/`mmcblk*` is `[mq-deadline]`), and `vm-swap-check.sh` (swappiness still 60, `vm.page-cluster` 0).

### 1.6 System runners: the image prunes what shadows the runtime (ADR-038, RUY-1039)
A system runner is a pinned upstream release unpacked under `/usr/lib/ruyaos/play/runners/<Name>/` (`docs/specs/05-play-packages.md` §6.4). GE-Proton's `proton` script puts its own `files/lib/x86_64-linux-gnu` first in `LD_LIBRARY_PATH`, so a library the release bundles wins over the same soname in `org.freedesktop.Platform`, even when it is older. GE-Proton11-12's libxkbcommon 0.9.2 broke the runtime's libSDL3 (`V_1.10.0` not found; the runtime has 0.13.2): sdl2-compat aborted the winedevice that hosts winebus and no Windows game saw a controller. The fix is made when the image is built, not at launch (Proton rebuilds the path itself): a runner folder may carry a `prune` file, and `install-runners.sh fetch` deletes what it names **before** the runner hash is computed, so the hash, `runner_check` and the file table describe the tree that ships. A library is pruned only when it is proven to break something that loads from the runtime; today that is `libxkbcommon.so*` and `libxkbregistry.so*` of ProtonGE11. The other overlaps are listed in the RUY-1039 Outcome (libav*, libswscale, libswresample, libdav1d, libgraphene, liblzma, libsoup, libxml2 stay: of all 516 runtime libraries that load alone, only libSDL2/libSDL3 and their satellites fail beside the runner's folder, apart from the runtime's own libavcodec and libavfilter, which nothing on a game's path loads; replacing Proton's own ffmpeg by the runtime's is unproven). `vm-play-check.sh launch-windows` loads the libraries a game needs with the runner's folder first and checks that winebus holds the pad.

## 2. Boot & session

### 2.1 Startup chain
`systemd` → `graphical.target` (or `multi-user.target`) → `ruya-compositor@tty1.service` (implemented in `image/rootfs/usr/lib/systemd/system/`). The unit is `WantedBy=graphical.target multi-user.target`, because an Anaconda/ISO install leaves `default.target` at `multi-user.target` and the shell must start regardless (T-178); the image itself sets `graphical.target`. This unit has `User=ruya-shell`, `PAMName=ruya-shell` (dedicated PAM stack: auth denied, account + session only), `TTYPath=/dev/tty1`, `StandardInput=tty`, and `Conflicts=getty@tty1`. It gets a logind session on seat0 with DRM and input access. Since T-198 it also has `QT_QPA_EGLFS_KMS_CONFIG=/var/lib/ruya-shell/.local/state/ruya-devices/kms.json` (the owner's resolution and refresh rate, written by `ruya-devices`; no file means the TV's preferred mode) and `ExecStartPre=-/usr/bin/ruya-devices --display-guard`, which counts a mode change waiting for the owner's confirmation and drops one that was never confirmed (`03` §2.4). A mode change restarts the shell by ending the process (`Restart=always`); there is no polkit rule for it. The Rust services are ordinary system services with `Before=ruya-compositor.service`, except `ruya-devices` (ADR-010): a systemd *user* unit of `ruya-shell` (`/usr/lib/systemd/user/ruya-devices.service`, `ConditionUser=ruya-shell`, after `wireplumber.service`, enabled with `systemctl --global`) that owns `org.ruyaos.Devices1` on the system bus from code (`Type=simple`).

- **As built (T-130):** the unit runs `ruya-shell` itself as the Wayland compositor, directly on KMS (`QT_QPA_PLATFORM=eglfs`, `eglfs_kms`), with no cage (ADR-002 option A). The image compiles the shell with `-DRUYA_COMPOSITOR=ON`, which makes `compositor/Compositor.qml` the entry point: a `WaylandCompositor` whose output window is the ordinary `Main`. The shell's own clients (VM test clients) connect to `/run/user/<ruya-shell uid>/ruya-0` (xdg-shell) and are shown fullscreen in the shell's app layer (02 §1.5). The health check still waits for `ruya-shell: ready` (the first frame of the output window).
- **Per-profile sockets (T-164, ADR-023):** the unit has `RuntimeDirectory=ruya-wayland` (`/run/ruya-wayland`, `ruya-shell`, 0711, emptied at every start and stop). The shell makes one listening socket per profile in it, `ruya-<id>`, mode 0600 with the ACL entry `user:ruya-<id>:rw-` (bound in a private `.staging` directory, then renamed into place), and serves it with `addSocketDescriptor`; the journal says `ruya-compositor: socket /run/ruya-wayland/ruya-<id> for ruya-<id> (uid N): mode 0600, acl user:ruya-<id>:rw-`. `ruya-session` starts every app with `WAYLAND_DISPLAY=/run/ruya-wayland/ruya-<id>` and `SDL_VIDEODRIVER=wayland`; Flatpak binds that one socket into the sandbox as `wayland-0`. A client is accepted when its peer uid is the signed-in profile's user (or `ruya-shell`); any other client is closed at its first surface (`ruya-compositor: refused surface of uid N pid P (other-user|nobody-signed-in)`). Profile apps get input only through the compositor (no `/dev/input` access for profile users). Check: `scripts/vm-session-check.sh display`.
- **GPU buffers for apps (T-358):** the unit sets `QT_WAYLAND_CLIENT_BUFFER_INTEGRATION=linux-dmabuf-unstable-v1;wayland-egl`; the dmabuf plugin is Qt's, built in the image from the installed qt6-qtwayland's source RPM with `image/qt/0001-linux-dmabuf-v4-feedback.patch` (protocol v4, feedback with the render node of the compositor's EGL device as `main_device`). The journal says `linux-dmabuf: zwp_linux_dmabuf_v1 version 4 with feedback, main device "e280"` on a GPU and `version 3` without a render node (the VM). Apps' sandboxes need `--device=dri` for the GPU.
- **Device access (decided, lead, T-130):** eglfs opens DRM and `/dev/input/event*` itself; Qt has no logind `TakeDevice` path. `/usr/lib/udev/rules.d/70-ruya-input.rules` tags input devices `uaccess`, so logind gives the **active seat session** (the shell's) an ACL on them, as it already does for the DRM card (RUY-3: except the virtual pads `ruya-inputd` makes for a profile, phys `ruya-input/pad*`, and a pad's motion and touchpad nodes; `/dev/uinput` is `ruya-input` 0660, and `74-ruya-input-acl.rules` gives the service user `ruya-input` an ACL entry on the physical pads: [06](06-input.md) §3). The shell user can then read every input device, which is acceptable because it is the session's only UI; a session on another VT that becomes active takes the access over. Logind-based opening (a small QPA input plugin) stays an option if this ever needs tightening. VT switching, suspend/resume and DRM-master handover under eglfs are not explored yet.
- **Fallback:** no second session ships. A shell that cannot start fails the health check and greenboot rolls back to the previous deployment (§4); a crash loop also stops at `StartLimitBurst`.
- **Watchdog (RUY-483):** the unit has `WatchdogSec=30s`, `NotifyAccess=main` and `TimeoutAbortSec=10s` (still `Type=simple`: no `READY=1`). The shell (`shell/src/system/SystemdWatchdog`, started from `main.cpp` once the event loop runs) sends `WATCHDOG=1` to `NOTIFY_SOCKET` at once and then every `WATCHDOG_USEC / 2` (15 s) from a timer on its GUI thread, without libsystemd; the journal says `ruya-shell: systemd watchdog every 15000 ms`. A GUI thread that stops (a wedged event loop) misses the pings, and after 30 s systemd sends SIGABRT (a coredump, `coredumpctl info ruya-shell`), then SIGKILL after 10 s if the process is still there, and `Restart=always` starts the shell again; the journal has systemd's `Watchdog timeout (limit 30s)!`. A watchdog restart counts in `NRestarts` and in `StartLimitBurst` like a crash. The render thread is not watched. Without `WATCHDOG_USEC` (run by hand, the mock services, Windows) nothing runs. Every running game loses its Wayland connection with the restart (a wedged shell had already stopped serving it). Check: `scripts/vm-boot-check.sh watchdog` (a SIGSTOPped shell is restarted within 45 s; a stopped process leaves no coredump, as it only dies by the SIGKILL).
- No display manager and no greeter. Profile selection happens inside the shell.
- `Restart=always` with `StartLimitBurst` on the compositor. After N fast failures, start `ruya-safe-mode.service`: a minimal QML screen offering Restart, Roll back OS, or Factory reset.
- **Boot experience (T-269).** From the firmware to the shell the screen shows the firmware's own logo, the RuyaOS splash, then the shell: no boot menu, no kernel or systemd text, no text cursor, no login prompt.
  - **Silent:** `image/rootfs/usr/lib/bootc/kargs.d/10-ruyaos.toml` adds `quiet splash loglevel=0 vt.global_cursor_default=0 systemd.show_status=false rd.systemd.show_status=false rd.udev.log_level=0 udev.log_level=0 rd.plymouth=1 plymouth.enable=1 plymouth.ignore-serial-consoles` (the last keeps a serial console, which the VM has, from turning the splash into text). Nothing is lost: the kernel log and the journal keep everything (`dmesg`, `journalctl -b`). A boot that fails shows no text; you read the journal, and greenboot's rollback (§4) works as before. An installed disk gets the new arguments with the next image update (bootc applies the new image's kargs.d; seen on the first boot of the new deployment). `getty@tty1` never starts (the compositor conflicts with it), so there is no login flash.
  - **Splash:** Plymouth theme `ruyaos` (`image/rootfs/usr/share/plymouth/themes/ruyaos/`, module `script`, package `plymouth-plugin-script`): the Dreamglass backdrop, the wordmark "RuyaOS" in Inter (white "Ruya", the lightened Ruya indigo on "OS"; **there is no logo yet**: a drawn mark is an owner decision) and a faint track with a soft highlight gliding along it. No text, no percentage, no password prompt (there is no disk encryption yet, §3). Everything is scaled by the screen height (1080p design size), so 720p, 1080p and 4K look alike. The same picture shows at reboot and shutdown: `ruya-compositor@.service` is ordered before `plymouth-reboot/poweroff/halt/kexec.service`, so the shell is gone before the splash (seen at a reboot in the VM). The images are drawn by `scripts/make-boot-assets.py` (Pillow; the PNGs are committed). `90-initramfs.sh` selects the theme, puts it into the initramfs and fails the build if it is not in there. The stock `spinner` theme stays installed as a fallback.
  - **No menu:** GRUB boots the default deployment after a hidden 2 s window in which **Esc** shows the menu (tap it once: a second Esc leaves the menu for the `grub>` prompt, as on every Fedora system on UEFI). GRUB cannot read a held Shift on UEFI (not tried here), so Esc is the key. Entries read "RuyaOS &lt;version&gt; (ostree:N)", one per deployment, so the previous one is reachable. When the previous boot did not become healthy (`boot_success=0`, or greenboot's `boot_counter` still set) the menu is shown for 5 s with a countdown, whatever is pressed; greenboot's own countdown to the previous deployment (`08_greenboot.cfg`) is untouched. A disk installed from this image has the policy in its `grub.cfg` (bootupd's static config `/usr/lib/bootupd/grub2-static/configs.d/07_ruyaos-menu.cfg`, which runs before greenboot resets `boot_success`). **A `grub.cfg` already on a disk is not rewritten by an image update**, so `ruya-grub-menu.service` (root, oneshot, every boot) copies `/usr/lib/ruyaos/grub-menu-custom.cfg` to `/boot/grub2/custom.cfg`, which GRUB sources last (`/boot` is read-only and is remounted for the copy; a `custom.cfg` without the file's marker line is never touched; `ruya_menu_policy` stops the two copies of the policy from repeating each other). On such a disk the first boot of the new image still shows the old one-second menu, the following ones do not. Firmware fast boot may skip key detection.
  - **Handover to the shell:** `ruya-compositor@.service` starts after `plymouth-quit-wait` (Plymouth has exited) and `plymouth-quit.service` quits with `--retain-splash` (drop-in `10-ruyaos.conf`). Plymouth has to be gone first because eglfs opens the DRM device as the unprivileged `ruya-shell` and only gets the display (DRM master) when nobody else holds it: with `plymouth deactivate` instead, the shell's page flips failed with "Permission denied" and the screen stayed dark. **Measured in the QEMU VM (virtio-vga, software rendering): the display is dark from the moment Plymouth exits until the shell's first frame, 3.4 s and 4.3 s in two boots (`plymouth-quit` to `ruya-shell: ready` in the journal), and `--retain-splash` does not keep the splash frame there. No text shows in that gap.** Closing it needs a change outside the image (the shell drawing the splash as its first frame, or the compositor getting the display through logind); it is an Inbox item. Not measured on the Dell.
- VT switching is disabled in production builds and enabled in `dev` builds (§6).

### 2.2 Suspend / power
- Idle → screen saver → display off → suspend (s2idle/S3) after configurable timeouts. Apps keep running across suspend. **Built (T-202):** the shell is the compositor and sees every key, button and pointer event, so it keeps the one idle clock (`IdleClock`) and the timeline. Times are minutes without input, per device (`DeviceSettings`, Settings -> Power saving), 0 = off:

  | Step | Default | Choices | What happens |
  |---|---|---|---|
  | Screen saver | 10 min | Off, 5, 10, 15, 30 | full-screen dim art and a small clock that moves every minute; any input wakes and is eaten |
  | Turn the screen off | 30 min | Never, 15, 30, 60 | the display is switched off (DPMS through the platform plugin) under a black frame; the first input switches it on |
  | Sleep | 60 min | Never, 30, 60, 120, 240 | `Power.suspend()` (logind); only where suspend is available **and** verified |
  | Controllers turn off | 15 min | Never, 5, 10, 15, 30 | the shell tells `Devices1.Bluetooth.ReportIdle`; the service disconnects idle bonded pads |

  The steps count from the last input; a step is skipped when it is off, and the deepest one reached is entered. **Nothing idles while something holds the console awake** (`IdleInhibit`; the reasons are logged `ruya-shell: idle inhibit +job`; the saver's own start and end are logged too (RUY-563): `ruya-shell: screen saver on (idle 600 s, stage saver)` once, when the first step away from active is taken (the stage may already be `off`), and `ruya-shell: screen saver off (input|resume, was saver|off|sleep)` once, when input or a resume ends it; nothing in between and listed in Settings -> Power saving): an app's Wayland `zwp_idle_inhibit_manager_v1` inhibitor (video players, games; QtWaylandCompositor has no such extension, `shell/compositor/IdleInhibitManager` implements it from the protocol XML). **An inhibitor counts only while its app is the front app (RUY-561, as the protocol says: only while its surface is visible):** the compositor hands `Shell.addInhibitor(id, surface)` each inhibitor, and `Shell.heldInhibitors` holds `wayland:<id>` only while the surface belongs to the app in front (the window's own surface, or any surface of the same Wayland client, so the `wl_subsurface` a video app draws in counts too, RUY-578; shown to the signed-in profile, so a lock or a profile switch releases it; not behind Home or the picker, and not under the open Hub: an open Hub releases it at once, whether or not the pause has frozen the game yet) and the Session1 record of that app is not frozen (`ListRunning` `frozen`, which includes what ruya-session freezes on a profile switch; not `Shell.appFrozen`, which counts only what the Hub froze). It is released when the app goes behind or freezes, taken again when it is back in front, and released once when the app destroys the inhibitor, its surface dies or the client goes. (Before RUY-561 a game behind Home or frozen held the console awake for hours.), a Store job (install, update, remove), an update being checked or fetched (`Update.state`), audio playing (`Devices1.Audio.Playing`: a PipeWire output *stream* is running and not corked; a paused or corked stream, a sink that is still running after it, or a microphone do not count, T-293; **a parked stream does not count either (RUY-562):** a game the Hub froze keeps its stream, and `parse_playing` leaves out one that `park.rs` moved to `ruya-parked` or marked with `ruya.parked`; a profile that also has an unfrozen app is not told apart, `park.rs` explains why). **Audio holds only the "Turn the screen off" and "Sleep" steps, not the screen saver (RUY-562; owner 2026-11-14: playing music allows the saver; the screen-off part is a lead decision):** sleep would stop the music, and on HDMI/DisplayPort the TV is usually the speaker and many TVs go into standby when the source turns the display off, which cuts the sound; every other holder holds all three steps. The clock counts two idle times, one without audio for the saver (`IdleClock.saverHeld`, `lastSaverBusyMs`) and one with it for screen off and sleep. If the owner wants screen-off allowed for audio too, that is one line in `IdleClock.stageFor`. While held, the countdown starts again from the moment the last holder lets go; a holder that appears after the saver started stops the *next* step, it does not end the saver. **Sleep is offered only when `Power.sleepAllowed`**: logind says `CanSuspend` and the image carries `/usr/share/ruyaos/suspend-verified` (T-166 creates it when suspend is proven under eglfs; `RUYA_SUSPEND_VERIFIED=1` forces it for a test); without it the Sleep row is shown disabled ("Sleep is not available on this console yet") and the step does not exist. **Waking from any suspend counts as activity** (the Guide menu's Suspend as well as the sleep step, and a power-button wake that sends no key): the clock's timer never waits longer than a heartbeat (a minute), the clock is monotonic (`MonotonicClock`, T-293: a wall-clock change moves nothing) and a resume is read from the time the machine has slept (`sleptMs`, CLOCK_BOOTTIME minus CLOCK_MONOTONIC; a clock that counts the sleep shows as two looks more than `gapMs` (90 s) apart), and the next look is treated as input in every stage; otherwise the time asleep would read as idle time and the console would go dark and suspend again at once. With the debug divisor both scale down (heartbeat at least 1 s, gap at least 5 s). A Bluetooth pad that connects (a button press on a bonded pad) is input too. `RUYA_IDLE_DIVISOR=60` divides every time by 60 (10 minutes become 10 seconds) for the VM and the Dell. The update service's idle test (30 minutes without input, no app) is fed by the same clock (`ReportActivity`, below); the play ledger's "idle" (`UsagePresence`) counts held-awake time as presence.
- **What counts as input (RUY-588).** Every key, button and pointer event the shell sees (`KeyRouter.activity`), and one more source: while an app is in front (route `app`, `06-input.md` §5.1) its pad's input goes to the game's virtual pad and the shell sees none of it, so `ruya-inputd` sends `Input1.UserActive` (a press, or a stick or trigger moved past a quarter or a tenth of its range; at most every 30 s; no device, no content) and `IdleClock` takes it like a key. A game played with a pad therefore holds the saver, the dark screen and sleep off with or without a Wayland idle inhibitor. **While the saver or the dark screen is up the signal is ignored:** the route is `overlay` then (the saver covers the app), the pad's press arrives as a navigation key, KeyRouter eats it and that wakes the screen, as for a keyboard; the game is not in the route and gets nothing, so the press does not reach it. Acting on `UserActive` there would wake the screen ahead of the key and let the key through to the page under the saver. The 30 s gate means the saver can start up to 30 s early after play stops (the last announced press may be that old).
- Wake sources: power button, USB controller/keyboard (`/sys/.../power/wakeup`), Bluetooth (adapter-dependent, best effort).
- The Guide button held for 2 s opens the power menu. **Built (T-107):** the shell's Power page and Guide overlay call `org.freedesktop.login1.Manager` (`Suspend`, `Reboot`, `PowerOff`, with `interactive=false`; `CanSuspend`, `CanReboot` and `CanPowerOff` decide what is offered). The image ships `/usr/share/polkit-1/rules.d/50-ruyaos-power.rules`, which lets exactly the user `ruya-shell` do those three actions (and their `-multiple-sessions` variants) without authentication. Idle timers and wake sources are not built yet. UI: 02 §1.4. **Network (T-132):** `/usr/share/polkit-1/rules.d/50-ruyaos-network.rules` lets exactly the user `ruya-shell` (the user `ruya-devices` runs as) do the NetworkManager actions Wi-Fi management needs: `wifi.scan`, `network-control`, `settings.modify.system`, `settings.modify.own` and (T-448, the Quick Hub's Wi-Fi tile: `Devices1.Network.WifiEnabled` sets NetworkManager's `WirelessEnabled`) `enable-disable-wifi`; every other NetworkManager action is refused for that user (`NO`, T-180: no hostname, no enabling or disabling networking, WWAN or the connectivity check, no sharing, no reload or checkpoints, and NetworkManager's own defaults for an active session do not apply). polkit cannot tell connection types apart, so the service itself only touches Wi-Fi connections.

### 2.4 Thermal policy (T-200)
The console watches its own temperatures and fans. Normal use shows nothing; a warm console says so, a hot one protects itself in steps, and a critical one is never a surprise crash. **The service measures and classifies, the shell acts.** `ruya-devices` (`org.ruyaos.Devices1.Thermal`, `services/ruya-devices/src/thermal.rs`) reads sysfs read-only, with no new privilege (the unit is unchanged), every 5 s on the blocking pool (every 1 s while a level above normal holds), and sends `SensorsChanged` and `LevelChanged` only on change. Fans are never controlled: the firmware does that.

- **Sensors.** One for the processor package (`coretemp`, `k10temp`, `zenpower`; the thermal zone `x86_pkg_temp` when none of them exists), one per graphics chip (`amdgpu`, `nouveau`, `nvidia`), one per NVMe drive (`Composite`) and SATA drive (`drivetemp`, which the image loads at boot with `modules-load.d/ruyaos-drivetemp.conf` (RUY-737; the kernel builds it as a module and nothing else loaded it); a USB drive is not listed; an SSD, by the block device's `rotational` flag, is classed with the NVMe drives), and every fan (`fan*_input`). Cores and the board's other temperatures (`acpitz`, `pch_*`, the many `dell_smm` ones) have no threshold and are not listed. Sensors are keyed by chip name, label and device (never `hwmonN`, which renumbers), so a sensor that appears late (a hot-plugged drive) joins the list. A machine without sensors (a VM) has an empty list and level `normal`.
- **Thresholds** (degrees Celsius; `/usr/lib/ruyaos/thermal.toml` ships them, `/etc/ruyaos/thermal.toml` replaces single values, a file with a mistake is ignored whole and the journal says why):

| Class | warm | hot | critical |
|---|---|---|---|
| Processor (`cpu`) | 80 | 90 | the sensor's own `crit` (the zone's critical, else last trip point) minus 5, 100 without one |
| Graphics (`gpu`) | 80 | 90 | the sensor's `crit` minus 5, 100 without one |
| NVMe / SSD (`ssd`) | 70 | 75 | 80 |
| SATA disk (`hdd`) | 50 | 55 | 60 |

  A critical level is never at or under `hot`. A pad's battery is not monitored here (UPower, T-161).
- **Filtering.** A level counts after the reading has been at or above its threshold for 10 s, and clears when it is 5 degrees below that threshold (`hysteresis`, `debounce_seconds`). Readings outside -20..125 degrees are ignored (the `dell_smm` sensor that reads 126), and a sensor not heard from for 30 s leaves the list. A temperature below its warm threshold that does not change at all for 5 minutes while the processor is busy the whole time is a stuck sensor and is ignored. **A fan** that was seen spinning, reads 0 rpm for 30 s while the processor is `warm` or worse is `hot` (a fan that never turned is an unused header, not a fault).
- **What the shell does** (`qml/ThermalPolicy.qml`):
  1. **warm:** nothing changes. Settings -> System shows a mark on the category, a line and the sensor row's mark (02 §1.2).
  2. **hot:** one toast "The console is running hot (Processor). Effects are reduced." (names the sensor); the effects quality drops to `performance` (no blur) for the session (`DeviceSettings.thermalLimited`; the owner's setting is not rewritten, and Settings -> Display shows it) and stays until the level is **normal** again. No second toast within one incident (the level has to return to normal first).
  3. **critical:** a notice (`ThermalNotice`, one "OK" button that hides it) says what is happening and counts down; every running app is asked to stop (`Session.stop`, also an app started meanwhile), the effects are off (as at hot) and the notice opens over the current page (the shell does not navigate to Home: Inbox); if the level still holds **60 s** later, `Power.powerOff()` (logind). If it falls below critical first, the notice goes and nothing is powered off. The kernel's own hard limit still applies underneath.
- **Trying it** (no sensor is hot on demand): `docs/dev-setup.md`, "Fake a hot sensor".

## 3. Security baseline
1. SELinux enforcing. We write custom policy modules for our services when needed.
2. Rust services run with systemd hardening (`ProtectSystem=strict`, `NoNewPrivileges`, `DynamicUser` where possible). A service that must run as root gets a `CapabilityBoundingSet` limited to what it needs, `SystemCallFilter=@system-service` and `UMask=0077`; `ruya-profiles` (root for `useradd`) scores 1.6 OK in `systemd-analyze security` (T-126). `ruya-session` (T-162) is root with an empty `CapabilityBoundingSet` (it only asks systemd to start apps as the profile users), `PrivateNetwork`, `AF_UNIX` only, `ProtectHome=yes`, `RuntimeDirectory=ruya-session`, exposure 1.1 OK. `ruya-library` (T-163) needs no privilege at all: it runs as its own system user `ruya-library` (sysusers), with no capabilities, `ProtectHome=yes`, no network (`PrivateNetwork=yes`, `AF_UNIX` only) and `MemoryDenyWriteExecute`, and only reads the system Flatpak installation.
3. Third-party code runs only in Flatpak sandboxes, as the profile's user, never as root.
4. **Full-disk encryption (Phase 6):** LUKS2 with TPM2 auto-unlock (`systemd-cryptenroll --tpm2-pcrs=7`) as an installer option that's on by default when a TPM2 is present. Without it, profile PINs only protect against casual access.
5. Image signature enforcement via `/etc/containers/policy.json` (`sigstoreSigned` for our registry).
6. No auto-run from removable media, ever. Mount policy (T-174): `ruya-devices` mounts removable volumes through udisks2 with `nosuid,nodev,noexec` (read-write, so saves and screenshots can be copied; these options already stop anything on the stick from running, gaining privileges or acting as a device), only filesystems `ext4`, `btrfs`, `exfat`, `vfat`, `ntfs`, only once per plug-in. polkit (`image/rootfs/usr/share/polkit-1/rules.d/50-ruyaos-storage.rules`) gives `ruya-shell` mounting, media ejecting and drive power-off, and refuses every other udisks2 action for that user (NO, so udisks2's defaults for formatting, unlocking and loop devices do not apply); udisks2 and `exfatprogs`/`ntfs-3g` are in the base packages.
7. Debug features (SSH, VT switching, shell journal over network) exist only in `dev` channel images.
8. **Checked on every booted image (T-424):** `scripts/vm-security-check.sh` compares the running image with `image/security-baseline.json`: the `systemd-analyze security` exposure of every `ruya-*.service` (at or below its baseline value), the listening TCP/UDP ports (a set of `proto:scope:port`, scope `loopback` for 127.0.0.0/8, `::1` or a socket bound to `lo`, else `any`, a wildcard or a network address: a loopback listener that moves to every address fails, RUY-18), `getenforce` = Enforcing and no unnamed `unconfined_service_t` `ruya-*` process, the setuid/setgid files under `/usr` (exact list) and no world-writable file under `/usr` or `/etc`, and the accounts with a login shell or usable password, and for X11 apps (ADR-034, RUY-436) no abstract `@/tmp/.X11-unix/*` listener, only 0700 `X*` sockets owned by a profile user, and every running Xwayland with `-auth` and `-nolisten local` in a baseline domain (`xwayland_domains`: `xserver_t`). Every baseline entry has a reason; a looser value needs one in the same commit. The baseline records the development image as it is (it lists SSH, root login); the release profile (T-425) tightens it.
9. **Who receives a service's signals (RUY-594).** A bus policy that limits only `send_destination` says who may call a service; its signals are broadcasts, which any system-bus client can match unless the policy denies receiving them (Input1's `TestInput` streams the button test's raw input, `ActiveInputChanged` names the pad that pressed last, `UserActive` says someone plays; Session1's `AppStarted` names what runs; Store1's `JobProgress` what is installed). Every `org.ruyaos.*.conf` (Devices1, Input1, Library1, Profiles1, Session1, Store1, Update1; `Notifications1` is a draft with no service and no policy yet, RUY-88: its per-profile `Added`/`Removed`/`Changed` need the rule in the policy RUY-88 adds, and the lint refuses that policy without it) therefore has `<deny receive_sender="<name>" receive_type="signal"/>` in the default context and the matching `allow` in the `root` and `ruya-shell` policies only; a profile user (so an app), `ruya-link` (whose ADR-029 allow-list is about method calls and is untouched), `ruya-input`, `ruya-library` and `nobody` receive none. **The one exception is `Platform1` (ADR-022, RUY-157):** the door for sandboxed apps also allows every user, after its default denies, to call `org.ruyaos.Platform1.Lifecycle` (`send_interface`, method calls only) and to receive that interface's signals (`receive_interface`), which the service sends unicast to an app's own registered connections; `Manage` stays root and `ruya-shell`. Which names and interfaces may do this is data, `image/security-baseline.json` `public_bus_doors` (each listed interface fully tagged `org.ruyaos.Stability`), read by the lint (rule 1) and by `busrecv`; any other default-context allow is refused. The rules name `receive_type="signal"`, so a method reply (which a `ruya-link` call needs) is never dropped. The default deny is only that when it carries no other `receive_*` attribute and no `eavesdrop` (dbus-daemon(1): `receive_member`, `receive_interface`, `receive_path`, `receive_error`, `receive_requested_reply` narrow a rule, so `receive_member="Nothing"` would close nothing), and the `root` and `ruya-shell` policies have no receive `deny` at all (it would cut them off from their own service); the lint (rule 4) and the VM's `busrecv` step refuse both (RUY-616). Every service gets the rule, also those whose signals carry nothing (`Library1.ItemsChanged`, `Update1.StatusChanged`): the shell is their only legitimate listener (ruya-session, as root, listens to Profiles1; ruya-devices, as `ruya-shell`, to Store1 and the system services), and one rule for all keeps `scripts/lint-bus-policies.ps1` (rule 4, with `-SelfTest`) able to refuse a new policy without it. dbus-broker applies the rule per receiving connection, with the user policy over the default one; a root `busctl monitor` is not subject to it. **To be proved in the VM** (not yet run): `vm-security-check.sh` checks the installed files (`busrecv`), and `vm-security-check.sh signals` runs plain bus clients as root and `ruya-shell` (they hear Input1's signals while a pad is pressed) and as `nobody`, a profile user, `ruya-link` and `ruya-library` (they hear none, yet do hear the bus's own `NameOwnerChanged`). **A service user's one declared signal (ADR-045 amendment, RUY-1196, owner 2026-11-25):** dbus-broker checks a broadcast's send rules against each receiver's names, so a signal from a non-root service to a root service is dropped silently by the receiver's default `deny send_destination` (found when `Library1.Rescan` never reached ruya-session; `vm-library-check.sh steam` now passes with the allow). A service user therefore has exactly one more kind of `allow`: an exact `send_destination` + `send_type="signal"` + `send_path` + `send_interface` + `send_member` for an entry of `security-baseline.json` `service_signals`, whose member is a `<signal>` in `api/dbus/<interface>.xml`; the lint (rule 2, with `-SelfTest`) refuses a wildcard, a method call, an undeclared or unlisted signal and any further attribute. Today: `ruya-library` to Session1, `Library1.ProfileScanWanted`.
10. **What listens, what is setuid, who owns a bus name (RUY-18).** The development image listens on `tcp:any:22` (sshd, dev only, T-425), the systemd-resolved stub `tcp:loopback:53` and `udp:loopback:53` (127.0.0.53/127.0.0.54) and chronyd's command port `udp:loopback:323`, nothing else: resolved's LLMNR responder (tcp/udp 5355 on every interface) and its mDNS are off (`/usr/lib/systemd/resolved.conf.d/80-ruyaos.conf`, `LLMNR=no`, `MulticastDNS=no`; an announcement of the console on the home network would be Avahi's, ADR-029). **Setuid policy:** a setuid or setgid file ships only if something on the console uses it, with its reason in the baseline's `setid` list; `sudo` is not in the image (`50-slim.sh` removes it with `sudo-python-plugin`; no account logs in to elevate, the services are root units and support reaches the console as root over SSH), and `pkexec` (polkit) and `pam_timestamp_check` (pam) keep their packages but lose the bit in the Containerfile; `98-guard.sh` fails the build on `sudo` or on either bit. **Bus names:** every `org.ruyaos.*.conf` denies `own` of its name in the default context in writing, next to the default `send_destination` and signal denies (dbus-broker's `system.conf` already denies `own`; the explicit rule holds whatever another policy file says), and `scripts/lint-bus-policies.ps1` (rule 1, with `-SelfTest`) refuses a policy without it. **The three oneshot and session units** (`ruya-boot-marker`, `ruya-flathub-remote`, `ruya-compositor@`) are hardened as far as their work allows: the boot marker is fully sandboxed (no capability, no network, `DevicePolicy=closed` with `/dev/ttyS0` only); the Flathub remote has an empty capability set, `@system-service` and `AF_UNIX AF_INET AF_INET6`; the compositor gets only what cannot take the DRM card, `/dev/input`, the tty or the logind session away (`ProtectKernelModules`, `ProtectKernelLogs`, `ProtectClock`, `ProtectHostname`, `LockPersonality`, `RestrictSUIDSGID`, `RestrictRealtime`; no `ProtectSystem`, `PrivateDevices` or `DevicePolicy`). Their `max_exposure` in the baseline is still the 0.0.61 value until the next `vm-security-check.sh measure` lowers it. **To be proved in the VM** (not yet run): the boot to `RUYA_BOOT_OK`, the Flathub remote, and `vm-security-check.sh check` against this baseline.
11. **The PIN store is ruya-profiles' alone (RUY-1130, ADR-022 decision 4).** Root reads any file whatever its mode, and `ProtectSystem=strict` leaves `/var` readable, so a 0600 file in the shared `/var/lib/ruyaos` was readable by every root service. The store therefore lives in its own directory, `/var/lib/ruyaos/profiles/profiles.toml` (directory 0700 root, file 0600), hidden from every other `ruya-*` unit except the listed ones. **The hiding is one layer, not the boundary** (the open window is in (b); the boundary is ADR-049, ruya-profiles as its own user with a bus-less root accounts helper, a separate ticket). Three parts: (a) every other `ruya-*` system unit that runs as root (or holds `CAP_DAC_OVERRIDE`, `CAP_DAC_READ_SEARCH`, `CAP_SYS_ADMIN` or `CAP_SYS_PTRACE` as ambient capabilities) carries `InaccessiblePaths=/var/lib/ruyaos/profiles /sysroot`: in its mount namespace both are empty, inaccessible nodes. `/sysroot` because on bootc `/var` is a bind of `/sysroot/ostree/deploy/<stateroot>/var`, so the same directory is reachable there too; none of those units uses `/sysroot`. It is the directory that is hidden, not the file: `InaccessiblePaths=` on a file covers that inode, and the store's tmp + rename puts a new, visible one in its place. A unit whose bounding set holds `CAP_DAC_READ_SEARCH` (ruya-play, ruya-store) could open the store by file handle (`open_by_handle_at`) past any mount hiding, so its `SystemCallFilter=` must be an allow list that names neither `@privileged` nor the call (the lint checks the unit as written; whether `@system-service` itself lets the call through is systemd's expansion, which `vm-profiles-check.sh private` reads from `systemctl show`). (b) `ruya-profiles` makes itself non-dumpable at start (`prctl(PR_SET_DUMPABLE, 0)`, `src/process.rs`), so its own `/proc/<pid>/root`, which leads into its namespace, is closed to every process without `CAP_SYS_PTRACE` (a root peer whose capabilities include ruya-profiles' own, such as ruya-play or ruya-store, would otherwise be let in); it also means the kernel writes no core dump of ruya-profiles (systemd-coredump records none). **The open window:** the attribute goes back to dumpable on `execve`, so the children ruya-profiles runs (`useradd`, `userdel`, retried for up to 5 s, `loginctl`, `getent`; `src/accounts.rs`) are dumpable, run in its mount namespace with its five capabilities, and a root peer with a capability superset (ruya-play, ruya-store) can open `/proc/<child>/root` while one runs, keep that directory open after the child exits and read the store through it. That lasts until ADR-049.  (c) **The exceptions** are units that can undo (a) or (b) with `CAP_SYS_ADMIN` (unmount the cover) or `CAP_SYS_PTRACE` (open the non-dumpable process), each named with its reason in `image/security-baseline.json` `private_state` `exceptions`: `ruya-update` (bootc writes `/sysroot` and reads `/proc/1/ns/mnt`), `ruya-platform-identify@` (its job is `CAP_SYS_PTRACE` + `CAP_DAC_READ_SEARCH`, RUY-1129) and `ruya-grub-menu` (`CAP_SYS_ADMIN` and `@mount` for `/boot`); they carry no `InaccessiblePaths=` line for the store, as it would not hold. Non-RuyaOS root services (sshd, NetworkManager, systemd's own and bootc's timers) are not covered. `tmpfiles.d/ruyaos.conf` makes the directory at boot, before any unit starts (a missing `InaccessiblePaths=` path fails the unit); `ruya-profiles` sets it to 0700 at every start and writes the store 0600 (tmp file opened 0600, flushed, renamed, directory flushed). Which directories are private, their aliases, whose they are and the exceptions are data in `private_state`; `scripts/lint-private-state.ps1` (with `-SelfTest`, in `dev.ps1 test` and CI) refuses a root `ruya-*` unit without both paths (drop-ins included; a `-` path, ignored when missing, does not count), a hidden unit with `CAP_DAC_READ_SEARCH` whose filter is missing, a deny list, or names `@privileged` or `open_by_handle_at`, a root unit whose `CapabilityBoundingSet=` (none set = all) holds `CAP_SYS_ADMIN` or `CAP_SYS_PTRACE` and is not an exception, a stale exception, any `BindPaths=`/`BindReadOnlyPaths=` source at, above or below a hidden path, the owner hiding its own directory, and a tmpfiles line that is missing or not `0700 root root`, so a new root unit is covered without a list to edit. Units of their own user (`ruya-library`, `ruya-inputd`, `ruya-compositor@` as `ruya-shell`) are closed out by the 0700 mode. **To be proved in the VM** (not yet run; (a) and (b) are reasoned from mount and ptrace semantics): `vm-profiles-check.sh private` (the modes, no old file, ruya-profiles sees its store, every other root unit but the exceptions lists both paths and, running, sees neither the store nor its `/sysroot/ostree/deploy/*/var` copy through `nsenter -m`, a `CAP_DAC_READ_SEARCH` unit's expanded filter has no `open_by_handle_at`, and a transient root process with ruya-play's capability set answers DENIED for the store through `/proc/<ruya-profiles pid>/root` while the root shell can read it; it does not probe the children) and `vm-profiles-check.sh migrate`. **That the units keep working with `/sysroot` hidden is reasoned only:** flatpak and ostree in ruya-play, ruya-store and ruya-flathub-remote work on `/var/lib/flatpak`, not `/sysroot`; the VM proves it with `vm-store-check.sh check` (an install and uninstall through Store1) and `vm-play-check.sh check` (a `.play` install) on an image with this change.

## 4. Updates & rollback (ADR-006)
`ruya-update` is the only thing that upgrades or reboots for updates: `bootc-fetch-apply-updates.timer` (which would run `bootc upgrade --apply` by itself) is disabled in the image (T-195).

- Images are pushed to an OCI registry at **`registry.ruyaos.org/ruyaos:<channel>`** (owner, 2026-11-21: the name every console has baked in is ours, so the hosting behind it can move without a `bootc switch` on each console; it may front a hosted registry), signed with **cosign** keyless or a project key.
- **Built (T-135 shell side, T-151 service):** the contract `api/dbus/org.ruyaos.Update1.xml` (status record with state `idle|checking|downloading|staged|up-to-date|failed`, `available`/`staged`/`current` versions, `channel`, `last_check`, `progress`, `rollback_available`; methods `Check`, `Download`, `Rollback`, `SetChannel`, `GetStatus`; signal `StatusChanged`), the shell's `Update` singleton with a mock and a D-Bus client, Settings -> System, and the service `services/ruya-update` (root, system bus). Versions come from `bootc status --json` (the image's version label, else its tag); `Check` runs `bootc upgrade --check` and reads `cachedUpdate`; `Download` runs `bootc upgrade` as the image job (below); `Rollback` runs `bootc rollback` and shows the previous image as `staged`. The channel is the image tag: `SetChannel` remembers `stable` or `beta` in `/var/lib/ruya-update/channel` and clears `available`; while the remembered channel differs from the tag the host tracks, a check does not ask the registry (`bootc` cannot look at another tag without staging it) and reports the channel name as `available`, and `Download` runs `bootc switch <repo>:<channel>`. Without a chosen channel the host's own tag is followed (a dev image tracking `ruyaos:0.0.20` simply upgrades). A staged download hides the other channels until the reboot: `bootc` tracks one image, so a switch or a rollback waits for the restart that applies what is staged. If the remembered channel file is unusable (unknown value, unreadable) the service still starts, follows the host's own tag and reports state `failed` with an error naming the file until `SetChannel` writes a good one (`/var` survives an image rollback, so a fatal start would fail every boot through the required check). A check while the tracked image is not known yet reads `bootc status` first and fails with an error if it still does not say; it never switches to a tagless reference. `Rollback` and `SetChannel` answer `forbidden` unless the caller is root, or `ruya-shell` while the active profile is an admin (the admin PIN itself is asked by the shell through `Profiles1.VerifyAdmin`; lead decision 2026-10-30). Unit `ruya-update.service` and its bus policy (root owns, shell and root call); greenboot's required check `51-ruya-update.sh` wants the service active.
- **The download is a job (RUY-29, ADR-026 v2; `bootc.rs` reads the events, `job.rs` maps them, `service.rs` owns pause, resume and cancel; the rate and the per-day ledger come from the shared crate `ruya-jobs`; host-tested on the Dell's recorded 0.0.105 -> 0.0.106 run, `services/ruya-update/tests/fixtures/`; VM check `vm-update-check.sh download`, lead run):** `Download` runs `bootc upgrade` (or `switch`) with `--progress-fd 3` on a pipe (bootc refuses a file) and reads its JSON lines as they come: `ProgressBytes` while layers arrive, `ProgressSteps` for the import and the deploy; another event type is ignored and a line that is no event is skipped. The job is Update1's `Job record` (the Store1 v2 record with source `update`, kind `os`, title `RuyaOS <version>`; `GetDownloadJob`, `JobChanged` at most once a second while it runs and at every state or phase change): `bytes_total` is the first event's `bytesTotal`, fixed for the job; `bytes_done` adds the network bytes of all its runs; `percent` is bytes 0..90, then 90..95 over the import and 95..99 over the deploy, 100 when staged, never decreasing; `rate_bps` is smoothed over 5 s (0 after 10 s without a byte); `eta_s` only while bytes arrive. The status record's `progress` is the job's percent. `PauseDownload` sends bootc SIGTERM (whole layers stay in the OSTree repository and the next run reuses them, also after a reboot; ruya-update logs `download <id>: <n> layers (<b> bytes) here, <m> layers (<b> bytes) to fetch` at each run's first event), the state becomes `idle` with `available` kept, and `ResumeDownload` (or `Download`) runs the same command again. `CancelDownload` stops it for good (`cancelled`, nothing staged, booted and rollback deployments untouched); a paused one ends at once. Once the import has begun both answer `unsupported`; with nothing to act on, `wrong-state`. The job is kept in `/var/lib/ruya-update/download_job` while it runs or is paused, so a service restart (or a reboot) finds it paused. `SetChannel` and `Rollback` end a paused job as cancelled. A download the policy paused (reason `playing`, `policy_pause`, wired by RUY-31) resumes by itself at the next look at the schedule once no app runs. `GetDownloadStats(days)` reads the per-day ledger `/var/lib/ruya-update/downloads.json` (bytes, finished and failed jobs per local day, 90 days; a run's bytes count on the day it ends; a corrupt ledger answers `failed` and is never overwritten).
- **Schedule (T-154, pure rules in `schedule.rs`, driven by a thread in `main.rs` once a minute):** `ruya-update` checks when it starts if the last finished check (`last_check`, kept in `/var/lib/ruya-update/last_check`) is a day old, then every 24 h; a failed scheduled check is retried after an hour, and so is a failed scheduled download (T-159: the schedule notes the failure and, an hour later, starts the download again if the state is still `failed` with an update found; a download the user started with `Download` is never retried, and starting one takes over a noted failure); no scheduled check runs while a job runs or an image is already staged. A check the schedule started that finds an update also downloads it; a check the user started (`Check`) does not (the user gets the Download button). When an image is staged the service restarts the console itself (`systemctl reboot`) if the setting `auto_restart` is on (default; `SetAutoRestart`, admin only, stored in `/var/lib/ruya-update/auto_restart`), the local time is in [03:00, 05:00), no input arrived for 30 minutes and no app runs. **Local time is the console's time zone (T-213):** the service reads it from libc (`localtime_r`, i.e. `/etc/localtime`), and calls `tzset()` before each read, because glibc's `localtime_r` alone reads the zone once and a zone the owner chose while the service runs (timedated relinks `/etc/localtime`) would not count until the next start (a Linux-only test sets `TZ` between reads and fails without the call). The arithmetic is `local_minute_of_day(now, utc_offset)`; tests put a `ZonedClock` in Tokyo and show the window opening at 18:00 UTC and not at 03:00 UTC, and moving the moment the zone changes. The zone itself is `org.ruyaos.Devices1.Time` (`03` §2.3): chosen in the first-boot setup and in Settings -> System, kept by systemd-timedated. **The restart is announced first (T-159):** when those rules first hold the service sets `restart_at` (unix seconds, a key of the status record, 0 = none) to now + 120 s and emits `StatusChanged`; at the next look (once a minute, so the reboot lands 120 to 180 s after the notice) at or after that time it reboots if the rules still hold. `ReportActivity` (any input, an app starting or closing), `SetAutoRestart(false)`, the image no longer being staged or the window ending clears `restart_at` at once (`StatusChanged`), and the 30 idle minutes start over. The decision is `Schedule::restart_step` (pure, fake-clock tests); the record shows `restart_at` only while the state is `staged` and the setting is on. The shell shows a sticky warning toast while `restart_at` is set (`02` §5.1). Idle time and "app running" come from the shell through `ReportActivity(app_running)`, which the shell sends when input arrives, at most once a minute, and at once when the first app starts or the last one closes (an app left running behind Home counts); with no report since the service started, idle time counts from the start. A `last_check` or activity time later than the clock (a wrong clock before NTP) counts as long ago, so it never stops the schedule. "No app running" is the shell's own view until `ruya-session` reports apps. A staged rollback is restarted into the same way.
- `ruya-update` checks daily (or on demand) with `bootc upgrade --check`. Then it downloads with `bootc upgrade` (a job that can be paused, resumed and cancelled), stages, notifies, and reboots when idle or when the user accepts.
- **Automatic rollback:** greenboot runs required health checks on boot (compositor starts, `ruya-*` services are active, the shell reports "home rendered" over D-Bus within 60 s). After 3 failed boots, greenboot rolls back with `bootc rollback` and records the event, which the shell displays. Of the stock checks in `greenboot-default-health-checks` only `02_watchdog.sh` (required) runs: `01_repository_dns_check.sh` (required) and `01_update_platforms_check.sh` (wanted, it curls the ostree remotes of `/etc/ostree/remotes.d`, which a bootc console does not have) are listed in `DISABLED_HEALTHCHECKS` in `/etc/greenboot/greenboot.conf` (T-160), so a healthy boot logs no failing check.
- **A rollback across the PIN store move (RUY-1130).** The first start of an image with RUY-1130 renames `/var/lib/ruyaos/profiles.toml` to `/var/lib/ruyaos/profiles/profiles.toml` (no copy stays at the old path: it would be readable by every root service again, §3 item 11). An older image's `ruya-profiles` reads only the old path, and a missing store is an empty store to it, so after a rollback to such an image: the shell shows the first-run profile setup (no profile is listed, so nobody can sign in; the profile users, their homes and `profiles/profiles.toml` are untouched and no PIN is bypassed), and the admin PIN gate is gone until the console runs the newer image again: the first profile created takes the id `p1`, so when `ruya-p1` is still a user (`p1` never deleted) `useradd` refuses it and every attempt answers `failed`, but when `p1` was deleted earlier, anyone at the controller creates a new admin `p1`. **While the older image runs, its units do not hide `profiles/` either**, so every root unit can read the store again (`profiles/profiles.toml` and any `.rollback`) until the console runs the newer image. Rolling forward (the GRUB menu, §2.1) brings every profile back. If the older image wrote a store of its own at the old path, the newer one keeps its own store (changes made after the rollback are not merged) and moves the older one, when it differs, to `profiles/profiles.toml.rollback` (hidden like the store, logged by ruya-profiles). Whether an older console should refuse to run instead is an open availability-versus-security question for the architect.
- Manual rollback is available in Settings → System (admin only) and in the GRUB menu (tap Esc at power-on, §2.1; the menu also appears by itself after a boot that failed).
- Channel switching uses `bootc switch registry.ruyaos.org/ruyaos:<channel>`.
- Use chunked images (`rpm-ostree compose build-chunked-oci` or an equivalent rechunker) to keep update downloads small. Measure the delta size per release.
- App (Flatpak) updates are independent of OS updates and never need a reboot.

## 5. Installer, first boot, recovery

### 5.1 Installer
- Phase 0–5: `bootc-image-builder` outputs (`qcow2`, `raw`, `anaconda-iso`) with a kickstart that does an unattended install to the largest disk. No user creation in Anaconda.
- Phase 6: a **controller-driven installer**. A live ISO boots the RuyaOS shell in "installer mode", where you pick a disk, encryption on or off, confirm, and the installer runs `bootc install to-disk`. This replaces the keyboard/mouse Anaconda UI.

### 5.2 First-boot setup (OOBE), run by the shell
Language/region → controller pairing (if no wired pad) → network → time zone → create the admin profile + PIN → optional extra profiles → updates check → home.

**Built so far (T-106, `shell/qml/Setup.qml`)**, shown instead of the profile picker whenever the profiles service reports no profile: welcome → **language** (English/Türkçe; stored in `DeviceSettings.language`, translation itself is T-109) → **network** (placeholder text only) → **create the admin** (name via the on-screen keyboard, PIN entered twice, `CreateProfile` with no admin credentials) → done → profile picker. Not built yet: controller pairing, time zone, region, extra profiles, update check. Setup does not sign the new admin in; they pick their profile and enter the PIN like any later boot.

### 5.3 Factory reset
Because `/etc` and `/var` persist, reset is explicit. It removes `/var/home/*`, `/var/lib/ruyaos`, `/var/lib/flatpak` (optionally keeping system apps), and local `/etc` diffs (restored from `/usr/etc`), then deletes profile users and reboots into OOBE. It requires the admin PIN and a confirmation hold. **Open:** whether to implement this as a fresh `bootc install` re-deploy from the currently booted image, which is cleaner. Spike in Phase 6.

### 5.4 Recovery
- GRUB menu: previous deployment (rollback). Hidden on a normal boot; tap Esc at power-on, or it shows by itself after a failed boot (§2.1).
- Safe mode (§2.1).
- The USB installer has a "Repair" option that re-deploys the image while keeping `/var` (`bootc install to-existing-root`).

## 6. Development workflow

### 6.1 Hosts
Developers edit on **Windows** (VS Code). Builds and VMs need Linux. Supported setups, in order of preference:

| Setup | Builds | VM tests | GPU/KPI tests |
|---|---|---|---|
| **A. Windows + dedicated test mini-PC** (recommended) | Podman Machine | QEMU (WHPX) for smoke tests | Real hardware over SSH, flashing via USB or `bootc switch` |
| B. Windows + Hyper-V Fedora VM (nested virtualization on) | Podman inside the VM | QEMU/KVM inside the VM | ✗ |
| C. Podman Machine only (WSL2 backend, rootful, ≥ 6 GB RAM) | ✓ | Limited (needs nested KVM in WSL2) | ✗ |

QEMU on Windows has no KVM (WHPX only), and virgl/GL acceleration there is limited. The shell will fall back to llvmpipe. That's fine for functional tests and **invalid for performance numbers.** GPU KPIs are measured only on real hardware.

### 6.2 Commands (to be scripted in `scripts/`)
```bash
# inside Podman Machine / Linux VM
podman build -t localhost/ruyaos:dev -f image/Containerfile .
podman run --rm localhost/ruyaos:dev bootc container lint

# disk image for QEMU (never `bootc install to-disk /dev/vda` inside the build VM — that is the VM's own disk)
sudo podman run --rm -it --privileged --pull=newer \
  --security-opt label=type:unconfined_t \
  -v ./output:/output -v /var/lib/containers/storage:/var/lib/containers/storage \
  quay.io/centos-bootc/bootc-image-builder:latest \
  --type qcow2 --rootfs xfs --local localhost/ruyaos:dev
```
For quick iteration on a running test box: push to a local registry, then run `bootc switch --transport registry <host>:5000/ruyaos:dev` and reboot. During shell-only work, run the shell nested on the dev machine (Linux VM with a desktop) to avoid reflashing.
