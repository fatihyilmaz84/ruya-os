# 06 — Ruya Input (design)

**Status.** Design, from the spike T-366 / RUY-2 (lead, 2026-11-12). Built: `ruya-inputd`'s Phase 0 bridge (pads to navigation keys, ADR-003) and, since RUY-3 (T-367), the service half of §3, §4.1, §5.1-5.2 and §8.1, marked *(built, RUY-3)*: the service, its user and udev rules, the virtual pads, the routing core and `Input1`'s Devices and Routing members. Since RUY-409 the shell calls `SetRoute` on every change (§5.1, "The shell's side"), so a game in front gets its profile's virtual pads (verified on the host with the mock; the VM run of `vm-input-check.sh shell` and the Dell race are pending). Everything else here is the **target** that the tasks T-367..T-374 build, each marked *(planned, T-nnn)*. The owner's requirements are the appendix [`06-input-requirements.md`](06-input-requirements.md); where this file and an *Accepted* ADR differ, the ADR wins. Contract draft: [`api/dbus/org.ruyaos.Input1.xml`](../../api/dbus/org.ruyaos.Input1.xml); profile format: [`schemas/input-profile-v1.json`](schemas/input-profile-v1.json).

## 2. Engine decision (ADR-003, ADR-024)

**`ruya-inputd` grows into the Ruya Input service; InputPlumber is not used** (ADR-003's named fallback). Reasons, in order:
1. **Least privilege.** The requirement is "not the whole engine as root" (§2.3 of the requirements; the hardening invariant in `CLAUDE.md`). The spike shows the whole service can run as an unprivileged system user with udev ACLs; InputPlumber runs as root with almost no hardening, and its design (moving device nodes) needs it.
2. **The profile boundary is ours anyway.** ADR-024's core rule, "a virtual node has one ACL entry, for the signed-in profile, re-made at every lock and switch", has no place in InputPlumber; we would write that layer next to it and keep a root daemon we do not control between the pads and the games.
3. **Packaging.** A COPR in a signed image is a third-party repository in the supply chain (01 §4); a source build is a new Rust stack in our image build, for one daemon.
4. **Cost of ours.** It already reads every pad, survives pads vanishing (T-337) and adds 88 µs median. What it lacks (virtual pads, routing, profiles) is the work T-367..T-374 plan either way.

What we take from InputPlumber: an intercept mode for overlays (our route `overlay`), a device database separate from user profiles, the generic-gamepad fallback, and its list of virtual targets as the long-term goal for §7 of the requirements. Revisit only if handheld-specific hardware (built-in pads exposed as keyboards, vendor HID buttons) becomes a target: InputPlumber's device configs are its real value there.

## 3. Process, privilege and device access *(built, RUY-3)*

- **User.** `ruya-inputd` runs as the system user `ruya-input` (sysusers, no home, no login shell), not root. Unit hardening stays as today plus `User=ruya-input`, `DeviceAllow=char-input rw`, `DeviceAllow=/dev/uinput rw`, `DeviceAllow=char-hidraw rw` (T-373 only), `RestrictAddressFamilies=AF_UNIX AF_NETLINK` (the udev monitor). **As built:** `PrivateNetwork=` is off, because udevd broadcasts its monitor messages in the host's network namespace only; `IPAddressDeny=any` and the address families leave the service no IP at all. Its state (the id salt, §4.1) is the unit's `StateDirectory` `/var/lib/ruya-input` (0700).
- **udev rules** (`70-ruya-input.rules`, replacing the old single line, and, as built, `74-ruya-input-acl.rules` for the `RUN` entries of rule 2: after `73-seat-late.rules`, whose uaccess builtin flushes named ACL entries, so `ruya-input`'s entry must be added after it on every event):
  1. `/dev/uinput`: `GROUP="ruya-input", MODE="0660"`. Only root and `ruya-input` can create input devices, so only they can claim the `ruya-input/` phys prefix below.
  2. **Physical pads** (`ENV{ID_INPUT_JOYSTICK}=="1"` and not ours): `RUN+="/usr/bin/setfacl -m u:ruya-input:rw $devnode"` (after logind's builtin, so both entries stay). The pad's **motion and touchpad nodes** (same HID parent, `ID_INPUT_ACCELEROMETER` / `ID_INPUT_TOUCHPAD` on a joystick's parent) get the same entry and **lose `uaccess`** (no ACL for the shell): the service reads them (T-373), libinput in the shell no longer does.
  3. **Virtual pads** (`ATTRS{phys}=="ruya-input/pad*"`; a pad's phys is `ruya-input/pad<n>`): `OWNER="ruya-input", MODE="0600"`, and no uaccess tag. systemd's `70-uaccess.rules` sorts after `70-ruya-input.rules` and tags the virtual pads as joysticks (RUY-446: node 0660 with a `ruya-shell` ACL entry, the group bits being the ACL mask), so `71-ruya-input-pad.rules` (after 70-uaccess, before `73-seat-late`) removes the tag with `TAG-="uaccess"` and asserts owner and mode again. The node is `ruya-input` user rw, group and other nothing, plus the one ACL entry of the profile user (`vm-input-check.sh nodes`, which runs with the shell up: with it stopped, logind has no session to give an entry and "no `ruya-shell` entry" could not fail). The service **re-asserts that entry after every udev event on its own node** (it watches the udev monitor for its phys prefix) and only then announces the device as ready, because a `change` event (or a seat change) makes udev / logind rewrite the node's ACL: the spike showed an ACL set after the `add` event holds and a `change` event wipes it. Other `ruya-input/` devices (the keyboard and mouse of T-372 / RUY-45, which the compositor reads, not a profile user) keep uaccess; the service never reads any `ruya-input/` device back as a physical pad. This rule is for **virtual pads** (`ruya-input/pad*`). **Virtual keyboards and mice** (`ruya-input/kbm*`, T-372) are different: a Wayland game (and Xwayland or Wine through it) never reads keyboard or pointer nodes; it gets keys and motion from the compositor's seat. So those nodes keep `uaccess` (the shell's libinput reads them) and never get a profile ACL. The service emits on them only while the route is `app`, and the compositor delivers them to the focused app through `KeyRouter` like a real keyboard, Guide keys included.
  4. **hidraw** of a known pad family (T-373: adaptive triggers, lightbar, gyro calibration): `ruya-input` only. Never a profile user, except in `steam` mode (§5.3) for the running app's user, and only for that run.
  5. **No legacy joystick API** *(built, RUY-3 round 2)*: `joydev` is blacklisted (`/usr/lib/modprobe.d/ruya-no-joydev.conf`: `blacklist joydev`, `install joydev /bin/false`), so no `/dev/input/js*` node exists. Fedora's stock rule makes every `js` node `0664` (world-readable, seen on the Dell): with joydev loaded, any user could read any pad, a physical one or another profile's virtual pad, past every ACL above. SDL, Wine and Proton read evdev, so nothing supported needs `js`. `vm-input-check.sh` asserts that joydev is not loaded, that no `js` node exists with a virtual pad up, and that a profile user opens none.
- **The shell keeps its own path**: the physical pad nodes keep logind's `ruya-shell` entry (uaccess), so the emergency reader (§8) can open them without the service.
- **Every app gets `/dev/input` in its sandbox** *(built, RUY-837; host-tested, vm and hw pending)*. `ruya-session` runs every app as `flatpak run --device=input <id>` (Wayland mode, `spawner::launch_command_in`, and the X11 helper's `x11::app_argv`; `spawner::DEVICE_INPUT`), whatever its manifest asks: a game packaged with `devices=dri` only (Neverball) otherwise has no `/dev/input` and no pad at all (§1). Why that is safe: the grant only makes the directory visible; what a profile user can open there is still decided by the node permissions above. Physical pads, their motion and touchpad nodes, the navigation keyboard and every other profile's virtual pads have no entry for the profile users (rules 2 and 3), and a profile's own virtual pads carry exactly one ACL entry, that profile's user. So a sandboxed app opens its own player pads and nothing else, as it did with `--device=input` or `all` from its manifest (the §1 rows "A virtual pad reaches a game" and "Another user"). The Store still shows the permissions of the manifest; the grant adds no other device class (`dri` and `all` stay what the manifest says). Needs Flatpak 1.15.6 or newer (the image has 1.18).

## 4. Device model

### 4.1 Identity *(stable and instance ids built, RUY-3; matching like pads is T-264)*
- **Stable id**, `<bus>-<vid>-<pid>-<key>`, where `<key>` is a 12-hex-digit hash (SHA-256 of a machine salt kept in `/var/lib/ruya-input/salt` plus the identifying string): Bluetooth → the device address (`uniq`, measured on the Dell: the DualSense's MAC); USB with a serial (`ID_SERIAL_SHORT`) → the serial; USB without one → the USB port path (`ID_PATH`), so two identical serial-less pads are told apart by socket. Never `eventN`. The hash keeps MAC addresses and serials off the bus.
- **Instance id**: a counter per connection (`<stable id>#<n>`). Signals carry both; the shell keys rows by the stable id.
- **Like pads (ADR-017; for held seats built, RUY-627).** A serial-less USB pad plugged into another socket is a new stable id (`identity::port_bound`: a USB pad without a serial, whose id names its port). A pad that reconnects within 60 s with the **same** stable id gets its seat back (§11.3). A port-bound pad with a **new** id takes a held seat only when exactly one held seat's pad was port-bound with the same `vid:pid` (the id's `usb-<vid>-<pid>` part); the seat's `device_id` becomes the new id, and its virtual pad is bound to it. With two or more such seats it takes none: it is an unseated pad, and "Who's playing?" asks (RUY-38/122). A pad with a serial, a Bluetooth pad or another model never takes another id's seat. Matching like pads that are not in a held seat (the registry, T-264) is not built. **Twins** (two connections with one stable id, e.g. two serial-less pads behind one hub port path): only one of them is the seat's pad (the one with the seat's virtual pad, else the first connected; RUY-642), the other is unseated; when the seat's one goes and the twin stays, the twin is the seat's pad at once, on the same virtual pad, without a hold.
- **As built** (`identity.rs`): the salt is 32 random bytes, made once (a salt of the wrong size is reported and never overwritten: ids are then unstable until it is fixed); `<bus>` is `usb`, `bluetooth` or `virtual`; the identifying string is the address for Bluetooth, else the serial, else `ID_PATH`, else `uniq` or `phys`; the family goes by vendor (Microsoft, Sony, Nintendo), then by driver (`xpad`, `playstation`/`sony`, `nintendo`).
- **Owner (RUY-124, ADR-017 amendment 1; `owners.rs`).** Per stable pad id, `ruya-inputd` remembers the last non-guest profile seated on it: seat 1 at a pad sign-in (a keyboard sign-in has no pad) or a `JoinPlayer` that seats it. A temporary guest (passwd comment "RuyaOS profile (guest)", `Accounts::is_guest`) is never recorded. It is kept in `/var/lib/ruya-input/owners.json` (0600, owner `ruya-input`), written whole and atomically (temp file and rename), at most 64 pads (the oldest dropped). An entry whose profile is no longer a profile account is dropped at the next write and reads "" meanwhile (ids are never reused). A missing file means no owners; an unreadable one is journaled, means no owners and is never overwritten. The device record's `owner` carries it. A like pad (above) has another stable id and so no owner.
- **Family** (`xbox`, `playstation`, `nintendo`, `generic`): a behaviour class (navigation, the Confirm button, glyphs, profile slots), from **one** table, `ruya_pads::family_of(vendor, product, driver, name)`, used by `ruya-inputd` and by `ruya-devices` (`Devices1`) alike (RUY-692): the USB vendor id (`045e` xbox, `054c` playstation, `057e` nintendo; `ruya-devices` translates the Bluetooth SIG company ids of a `bluetooth:` Modalias to them), then the kernel driver (`xpad`; `playstation`/`sony`; `nintendo`), then, only where no vendor id is known, the name, else `generic`. A pad of another maker is `generic` whatever it calls itself. **8BitDo is a model, not a family** (`model`, e.g. `8bitdo_pro2`, draws the silhouette): its family follows its mode, X-input reports Microsoft's id (`xbox`), Switch mode Nintendo's (`nintendo`), D-input `2dc8` is `generic`. T-261's audit and RUY-154's 360 receiver add entries. SDL's mapping database is a separate data file the service reads for unknown pads (requirements §4.2); it never decides capabilities.

### 4.2 Normalised input
Buttons: `south east west north l1 r1 l3 r3 start select guide dpad_up dpad_down dpad_left dpad_right` plus `paddle1..4`, `misc1` (share/capture) and `touchpad_click`. Axes: `left_x left_y right_x right_y` as i16 (-32768..32767, up negative) and `left_trigger right_trigger` as 0..32767. Motion: `gyro_{x,y,z}` in deg/s ×16, `accel_{x,y,z}` in mg; touchpad contacts as (id, x, y) in 0..65535 of the pad's surface; `touchpad` names the surface as a whole (for touchpad-as-mouse). Every event keeps its **raw source** (`<node kind>:<evtype>:<code>`) so a profile can map an input that has no normal name. Buttons are named by **position**, not label: Nintendo's A is `east` (the family's confirm button, ADR-027, is a mapping on top: T-398).

**Model mappings (RUY-826).** A pad whose driver does not report a gamepad's codes gets its own key table, chosen by `identity::model` (`pad::model_keys`, the one table) and tried before the generic one; every other model has none and maps exactly as above. The bare **Wii Remote** (`wii_remote`, hid-wiimote) is held **sideways**: the D-pad under the left thumb, 1 and 2 under the right, the IR end pointing left. It feeds the shell's navigation keys and, in route `app`, the virtual pad, so a game sees a normal pad with a D-pad and four face buttons. The `nintendo` family confirms with east, so 2 confirms and 1 goes back.

| Wii Remote | Pad button |
|---|---|
| D-pad up / down / left / right (`KEY_UP/DOWN/LEFT/RIGHT`) | `dpad_left` / `dpad_right` / `dpad_down` / `dpad_up` (a quarter turn) |
| 2 (`BTN_2`) | `east` |
| 1 (`BTN_1`) | `south` |
| A (`BTN_A`) | `north` |
| B (`BTN_B`, trigger) | `west` |
| + (`KEY_NEXT`) / - (`KEY_PREVIOUS`) | `start` / `select` |
| Home (`BTN_MODE`) | `guide` |

**A pad without a left stick** (its probe found no `ABS_X`/`ABS_Y`, capability `sticks` with `driver` false; today the bare Wii Remote) also sends its D-pad in route `app` as the virtual pad's left stick at full deflection (RUY-832), besides the hat, so a game that steers or navigates with the stick can be played; it is centred with the same diff on release, neutral and a pad leaving. Pads with a stick are unchanged. A per-game choice belongs to the controller profiles (RUY-43).

The Nunchuk, the accelerometer and the IR camera are separate evdev nodes and are not mapped (the Nunchuk and an upright layout are planned; motion is RUY-46).

### 4.3 Capability descriptor *(built, RUY-39)*
Per device, per capability (`buttons`, `sticks`, `analog_triggers`, `dpad`, `gyro`, `accelerometer`, `touchpad`, `rumble`, `trigger_rumble`, `adaptive_triggers`, `lightbar`, `player_leds`, `speaker`, `microphone`, `battery`), four booleans:
- `hardware` — the model has it (device table);
- `driver` — the kernel exposes it here (a motion node exists, `EV_FF` with `FF_RUMBLE` on the node, a power-supply entry);
- `available` — usable now (the node opened, the battery reports, Bluetooth rumble acknowledged);
- `output` — the virtual device the pad is routed to can carry it (an Xbox 360 virtual pad: rumble yes, gyro no).
Only what is detected is reported (`rumble` never implies `adaptive_triggers`). `GetCapabilities` returns them as `a(sbbbb)`.

**As built** (`caps.rs`, filled when the pad connects): every name is listed, in the order above, and `hardware` false means the model has no such part. `hardware` is the device table's entry (by `vid:pid`: DualSense and Edge, DualShock 4, Xbox 360 wired and receivers, Xbox One and Series, Switch Pro) or, for a model it does not know, only what the kernel shows; a part the kernel exposes counts even when the table lacks it. `driver` comes from the pad's own node (`BTN_SOUTH`; `ABS_X`/`ABS_Y`; `ABS_Z` or `ABS_RZ`; a hat or `BTN_DPAD_*`; `FF_RUMBLE`), its sibling nodes under the same HID parent (`ID_INPUT_ACCELEROMETER` for gyro and accelerometer, `ID_INPUT_TOUCHPAD`) and the parent's `power_supply/` entry. `available` needs that node to open (the ACL of §3 rule 2) or the battery to report a capacity: a node that is missing is neither `driver` nor `available`, one that does not open is `driver` only. The service has no kernel path yet for `trigger_rumble`, `adaptive_triggers`, `lightbar`, `player_leds`, `speaker` and `microphone` (hidraw, T-373): never `driver`. `output` is the Xbox 360-style virtual pad's set: buttons, sticks, analog triggers, D-pad and rumble. The descriptor is not refreshed while the pad stays connected (a battery that starts reporting later shows at the next connection).

### 4.4 Button test *(built, RUY-39)*
`StartTest(device_id, hold_left_stick)` streams one pad's input to the shell as `TestInput(device_id, input, value, source)`: `input` is the normalised name of §4.2, or the raw source for an input without one; `value` is 1/0 for a button, the normalised value for an axis, the kernel's value for a raw input; `source` is the raw source (`raw:pad:<type>:<code>`, `pad` being the pad's main node). Buttons go out at once; each axis at most 30 times a second, its newest value never lost (held back at most 1/30 s; the service then ticks every 16 ms instead of 500). A digital trigger next to its analog axis, a hat that did not move and key autorepeat send nothing. Only in the routes `shell` and `overlay` (`not-allowed` otherwise; `overlay` since RUY-611: a game held behind Home), one test per device (`busy`). A test ends by `StopTest`, the route `app` or `locked`, the pad disconnecting, its caller leaving the bus, or 120 s after the pad's last input; every end is one `TestEnded(device_id, reason)` with `stopped`, `route`, `gone`, `caller` or `idle`. The navigation keys and the virtual pads are not touched by a test, except by `hold_left_stick` (RUY-479): with `true` the router sends no arrow key for that pad's left stick while the test runs (the D-pad and the buttons keep navigating; `TestInput` still reports the stick), releases a direction the stick holds when the test starts (once), and, when the test ends with the stick still pushed, sends no key for it until it has been near neutral (a quarter of its travel; the same `axis_held` rule as the held-at-entry mask) and moves again. `false` changes nothing. Only the stick editor of the left stick sets it (Controls in games > Left stick, 02 §1.2): trying the stick must not move the page's focus or slider. The shell's mock plays the same path when a test asks (`Input.mockStickNavigates(true)`). Settings > Controllers > a controller > Button test is the client (02 §1.2).

## 5. Routing *(built: the service RUY-3, the shell's calls RUY-409; ownership modes T-371)*

### 5.1 States
| Route | Set when | Pads produce |
|---|---|---|
| `shell` | the shell (or the Hub, a page, the picker's pre-session state) is in front | navigation keys on "RuyaOS Navigation" (today's behaviour); no virtual pad exists (a game frozen or closing behind Home is held under `overlay`, §5.2), except the pads prepared for a game about to start (`PreparePads`, below; neutral) |
| `app` | an app has the focus | the app's profile's virtual pads only; navigation keys stop, except **Guide**, which always goes to the shell as `KEY_HOMEPAGE` and is never forwarded to the virtual pad |
| `overlay` | an overlay over the app in front, running or frozen by the Hub (Hub, Guide menu, a system dialog: ADR-033), or a game frozen or closing behind Home *(RUY-611)* | navigation keys; the app's virtual pads stay and are held in neutral (sticks centred, nothing pressed; RUY-541 for the frozen app) |
| `locked` | the picker or the PIN pad after Lock, or no profile signed in | navigation keys; **no virtual pad exists** |

Every transition releases on the side being left whatever is held (the `KeyBoard` count of T-337, extended to pad buttons and axes), then switches: no stuck button and no double input. The shell is the only source of the route: the compositor knows the focus first (`KeyRouter`), and the shell calls `Input1.SetRoute(route, instance, app_id, profile)` on every change (`app_id`: the Flatpak id of the app in front, which lets the service pick a game or platform profile, RUY-43; `instance` stays opaque), exactly as it reports presence to `Session1` today. The service trusts the shell's argument (the bus policy lets only `ruya-shell` and root call it, like `Session1.Launch`, and only they receive its signals: `TestInput`, `ActiveInputChanged`, `ForeignInput`, `UserActive` and the rest are broadcasts that carry raw input, the last pad and the profile, so `org.ruyaos.Input1.conf` denies receiving them in the default context and allows root and `ruya-shell`; a game's user, `ruya-link` and every other user hear none, RUY-594, 01 section 3 item 9), refuses profiles that are not profile accounts, and **falls back to `locked` when the caller that set the route leaves the bus** (`NameOwnerChanged`), so a dead shell never leaves a game owning the pads.

**As built (RUY-3, `routing.rs`).** The service starts in `shell` with no profile. Only a **seated** pad (§11.3, *built RUY-121*) has a virtual pad; an unseated pad's input reaches no app. **The seat gate is on** since RUY-122 (the flag `SEAT_GATE` is gone; RUY-121 had shipped it off, with unseated pads numbered after the seats): a pad gets a seat, and so a virtual pad, only through `JoinPlayer`, which the shell's "Who's playing?" calls (02 §1.9). Virtual pads (`Ruya Xbox 360 Pad`, `045e:028e` version `0x0114`, the 11 xpad keys with `BTN_MODE` declared so that SDL's "Xbox 360 Controller" mapping applies, sticks, 0..255 triggers, the hat, `FF_RUMBLE` when the physical pad has it) exist only while the route is `app`, and stay, held in neutral once, for `overlay` with the same instance and profile, whether the app is frozen or not *(RUY-541)*, and for the `app` that follows it: the same devices and event nodes, so a game sees no removal across the Hub; `shell`, `locked`, an `overlay` with another or no instance (the shell no longer sends one with none) and an `app` with another instance or profile destroy them. Entering `app`, every navigation key but Guide is released, and a button or axis already held (a quarter of its range or more) is not forwarded until it is let go, so the press that closed an overlay never reaches the game. **Numbering *(built, RUY-540; seat numbers RUY-121; ADR-017 amendment 6)*:** a virtual pad's number is its pad's **seat** (§11.3): phys `ruya-input/pad<slot>`, so `pad1` is always player 1 and pad *n* is seat *n*. A profile's **active controller**, seat 1's pad, is the pad that gave the last input when the route first went to the profile (the sign-in); the service keeps it until the profile changes or is locked, however other pads press later, or until `JoinPlayer` moves player 1 to another pad. Only a pad that pressed after the profile last changed (lock, sign-out, picker, or a Hub switch) can become the next profile's active controller, so a keyboard or touch sign-in never inherits the previous profile's pad and the order is the connection order *(RUY-551)*. On entry to `app` for a new owner **every seated pad's virtual pad is made at once** *(RUY-681: before, the others were made only once `pad1` was ready)*, in seat order, so the active controller is created **first**: it is `pad1`, the lowest event node and SDL index 0. The others' first ACL, the moment an app can open them, waits until an app can open `pad1` *(RUY-541)*: when its ACL is set (after udev's event on it) or its 2 s udev fallback ran, also if that failed; a udev event or fallback of `pad2`..`pad4` before then is remembered and answered right after `pad1`'s, in seat order. A game that follows hot-plug and opens the first pad it can open (ironwail/LibreQuake opens one) thus gets the pad in the player's hands, not an idle one whose ACL happened to be set first (seen on the Dell, 0.0.79: `pad2 ready` was logged before `pad1 ready` and the game took pad2). With no active controller (a keyboard sign-in, or its pad's 60 s hold ran out) there is no `pad1` to wait for, and the others are opened as their own events come; a held seat 1 does not hold them back either. A pad that connects is not seated and gets no virtual pad; one that joins while an app is in front gets its virtual pad at once with its seat's number (while `pad1` is not ready yet its ACL waits with the others'; one that joins under an overlay gets its pad when the app is back in front). A move (`JoinPlayer` of a seated profile on another pad) **binds** the seat's virtual pad to the new pad *(RUY-627)*: the same device and node, no `create_virtual` or `destroy_virtual`, what the new pad holds is masked until let go, and the app's rumble effects are uploaded to it again; `LeavePlayer` destroys it; live pads are never renumbered (the game would see its pad vanish). **A virtual pad keeps its number for the owner's whole life** *(RUY-681)*: a seat that has no pad any more (its hold ran out, its pad was unseated by a join, seat 1 after Join case c) leaves its virtual pad **quiet** (`Router::idle`: one neutral frame, rumble erased on the pad, the app's uploads kept, journal `virtual pad ruya-input/pad<n> stays quiet: its seat has no pad`), and the next pad seated in that number binds it, also another player's (its engine is compiled for that player: a pad joined as another profile, Join case c, keeps its device too, where before it was a new one). It is destroyed only with the owner (lock, switch, run end, another instance) or by `LeavePlayer` of its number (also when the seat is already empty). A join that takes a seat of 2-4 (Join case d) takes, in this order, the free seat whose quiet pad was that player's in this game, the lowest free seat the game has no virtual pad for (a new pad: one hotplug), else the lowest free seat (taking its quiet pad over). SuperTuxKart, seen on the Dell (0.0.84, owner report 2026-11-15), does not survive a pad removed and made again (`Error in handleJoystick() map::at`), and two Bluetooth pads that powered off for 10 minutes ran their holds out mid-game. **A seated pad that disconnects** keeps its seat for 60 s and its virtual pad stays (one neutral frame, then nothing; §11.3, RUY-627); the pad that comes back within the hold is bound to it the same way, and after the hold the pad stays quiet as above. If `pad1` is unplugged before it was ready, the ACLs that waited for it are set at once.

**The pads before the game (RUY-837, built; host-tested, vm and hw pending).** A game that opens its pad **once at start-up** and ignores hot-plug finds no pad if the pad, or its ACL, comes after its first look: on the Dell (0.0.90) Neverball 1.6.0 (SDL2 through sdl2-compat on SDL3, "Container detected, disabling udev integration") opened joystick 0 at 13:11:48.614, the route `app` came with its window and `pad1` was ready at .870, so the game had no controller for the whole session; a pad present but with its ACL set 6 s late was never opened either. So the order of a launch is: **pads made and ACL'd, then the game starts.** The shell (`Shell.qml` `launchApp`) calls `Input1.PreparePads(app_id, profile)` before `Session1.Launch` and launches on its answer (`Input.preparePads`, `padsPrepared`); `Input` bounds the wait to 1 s (`prepareWaitMs`: then `ruya-shell: Input1 PreparePads <app> did not answer in 1000 ms; the app starts anyway`), and any other answer (`failed`, `not-allowed`, no service) starts the game too, with a log line: a launch never hangs on Ruya Input. The service (`Router::prepare_pads`) makes the virtual pads of every seated pad for the profile exactly as on `app` (pad1 first, the others' ACLs after pad1's), without changing the route: pad input keeps navigating the shell and the pads stay neutral. It answers when each pad is ready (the `virtual pad ... ready` point) or its 2 s udev fallback ran (`failed` if an ACL could not be set), at once with no seated pad. The first `SetRoute` `app` or `overlay` with that app id and profile binds the prepared pads to its instance (journal `prepared pads for <app> bound to instance '<i>'`: the shell did not know the instance before the launch), so the window's `app` makes nothing new and the game keeps the descriptors it opened. While they wait, `shell` and `overlay` (any instance) of the profile keep them; `locked`, a profile change, `app` for another app, a preparation for another app and 60 s with no such route (`PREPARE_TTL`, journal `prepared pads for <app> were not used in 60 s`) destroy them. One owner at a time: preparing a game ends the pads of a game held behind Home (it would lose them anyway when the new game comes to the front). **Residual cases:** a game whose window takes more than 60 s to appear loses its prepared pads; and a game that never re-scans keeps a dead descriptor whenever its pad is destroyed and made again while it runs (Lock, a switch, Home over a game that is not frozen, an app switch, `LeavePlayer`), where a hot-plug game reopens it. A pad that only drops for a moment does not cause that: the seat hold keeps the virtual pad through the disconnect and quiet after it for the game's life (RUY-627, RUY-681). Tests: `routing.rs` `prepared_pads_are_ready_before_the_game_and_its_first_route_keeps_them`, `preparing_pads_is_refused_outside_the_shell_and_answers_at_once_with_no_pad`, `a_preparation_ends_with_a_lock_another_game_or_its_time`, `dbus.rs` `prepare_tests` (the call waits for the ACL), `tst_input_route.qml` (`test_play_starts_the_game_once_its_pads_are_ready`, `..._after_1_s_when_input_does_not_answer`, `test_a_late_answer_starts_nothing_twice`), and in the VM `scripts/vm-input-check.sh startpad` (a test app that looks at `/dev/input` once at its start sees exactly its pad).

**The shell's side, as built (RUY-409, `shell/qml/InputRoute.qml`, `shell/src/input/Input.*`).** `InputRoute` works the route out from what `Shell.qml` already knows and sends it on every change, coalesced to one call per event-loop turn: **`locked`** (profile `""`) while nobody is signed in (the picker, its PIN pad, after Lock and between the two halves of a switch, before the first sign-in); **`shell`** with the profile at Home, on a page, with the Hub over Home, with the apps sent behind Home (unless one is held: below), and for a window whose Session1 instance the shell does not know (Input1 needs the instance and the app id for `app`); **`overlay`** while the Hub, the "Keep this resolution?" dialog or the screen saver covers the app in front, and while that app is frozen, always with the app's instance and app id *(RUY-541; before, a frozen app's overlay carried `""` and its pads went)*, so its pads are held, the same devices, frozen or not; **`app`** when the focused window's app (`instanceOfWindow`, the same record the Hub shows) is in front and not frozen. Closing the Hub over a frozen game keeps `overlay` with the instance until Session1 reports the Thaw, then sends `app`, and the game reads its same pads again. With no app in front the route is also `overlay` with the instance of a game frozen behind Home or the Hub, and of a game being closed until it has exited (§5.2, RUY-611). The facade (`Input`) does not send the route it last asked for again unless that call failed or was refused, logs a failed or refused call (`ruya-shell: Input1 SetRoute <route> answered <status>`), never waits on it, and sends the newest route with the next change; a `QDBusServiceWatcher` on `org.ruyaos.Input1` sends the current route again whenever the name gets a new owner (a restarted service is back in `shell`). **The navigation keys (RUY-583, `NavKey::evdev_code`)** are chosen by the Qt key they reach the shell as through the compositor's xkb keymap: Start is `KEY_COMPOSE` (127, keysym `Menu`, `Qt::Key_Menu`), not `KEY_MENU` (139, `XF86MenuKB`, `Qt::Key_MenuKB`); a unit test pins it and `scripts/vm-input-check.sh start` proves the path (pad Start gives one `ruya-shell: options menu open (...)` journal line). Guide needs nothing from the shell's route: the service always sends it as `KEY_HOMEPAGE` and `KeyRouter` takes it from the app. **Guide on every pad (built, RUY-11; since RUY-38 only before a sign-in):** the service masks Guide out of every virtual pad, in every route; while nobody is signed in it sends Guide to the shell from any pad, and afterwards only from the pad that navigates now (player 1's, or the navigator: §11.3), the others' Guide being a `ForeignInput`; the long press is timed by the shell (`Theme.guideHoldMs`, `Shell.qml` `guideHoldTimer`), not by the service, so there is no per-model button id in the shell. Tests: `routing.rs` `guide_reaches_the_shell_from_any_pad_before_a_sign_in_and_from_player_1_after_it` (three pads with the gate off, so each has a virtual pad: before the sign-in every Guide is KEY_HOMEPAGE; after it player 1's is, player 2's is `player-guide` and the unseated pad's `guide`, and no virtual pad sees BTN_MODE against a BTN_SOUTH control), `tst_hub_controllers.qml` (two mock pads through `Input.mockPadButton`: either one's Guide before the sign-in, then only player 1's opens the Hub, short and short, the keyboard's long press, with a game that counts every key), and in the VM `scripts/vm-input-check.sh guide` (two uinput pads: before the sign-in either Guide gives KEY_HOMEPAGE; in `app` with pad 0 as player 1 and pad 1 as player 2 only pad 0's does, pad 1's is a `ForeignInput player-guide`, and no BTN_MODE reaches either virtual pad, with a BTN_SOUTH control), `tst_input_route.qml` on the mock (which checks the arguments by the service's rules and models the pads), and in the VM `scripts/vm-input-check.sh shell`.

**`UserActive` (RUY-588, built, `activity.rs`).** In `app` the shell sees none of the pad's input, so its idle clock (01 §2.2) would run on during play. `Input1.UserActive()` is a signal with no arguments, no device and no button (it is not a key logger). `Router::input_at` asks the `ActivityGate`, which says yes for a button press or an axis past its threshold (a stick at a quarter of its range, a trigger at a tenth; a release, a return to rest and drift do not count) and at most once per 30 s (`Clock` passed in; `RUYA_IDLE_DIVISOR` shortens the gap for the VM checks, as for the shell). Only the route `app` emits it: in the others the input arrives as navigation keys, which the shell counts itself. The payload is empty, so a bus client that matches the broadcast learns only that someone plays. The shell ignores it while its saver or dark screen is up (01 §2.2). Apps cannot observe it: no developer page.

**Finding pads (RUY-624, built, `nodes.rs`, `linux/mod.rs`).** The service lists `/dev/input/event*` every 2 s and at once after a udev `add` of an event node. A node it looked at and found not to be a physical pad (its own virtual pads, keyboards, sensors) is remembered by **path and inode** and not opened again while both stay the same. The kernel gives a freed `eventN` to the next device and devtmpfs makes a new inode for it, so a controller plugged in (or reconnecting over Bluetooth) within 2 s of a virtual pad on that number being destroyed is a different node and is opened at the next scan; keyed by path alone it was ignored until it was replugged.

### 5.2 Sign-in, switch, lock, run end, Quick Resume
- **Who tells whom.** The shell, through `SetRoute`: it already learns sign-in, switch and lock from `Profiles1` (`SwitchTo`, `Lock`, `ActiveProfile`) and freezing from `Session1`. No new call from `ruya-profiles` or `ruya-session` to the input service and no new bus-policy line on their interfaces; the one new policy is `org.ruyaos.Input1`'s own (owner `ruya-input`; `ruya-shell` and root may call; `ruya-link` nothing until ADR-029's allow-list names a method).
- **An already open descriptor is not closed by removing an ACL** (Linux checks access at `open`). So at **lock**, **profile switch** and **run end** the service **destroys** the profile's virtual devices (`UI_DEV_DESTROY`: the app reads `ENODEV`, SDL reports "unplugged", seen on the Dell) and creates new ones for the next owner: a pad never outlives its profile. **An app switch** (another instance in `app`), and Home over a game that is **not** frozen (route `shell`), also destroy them; the game gets fresh pads when it is in front again, which SDL's hot-plug picks up; nothing depends on node or instance ids staying the same (requirements §14).
- **A Freeze by the Hub, in the same profile, keeps the frozen app's pads** *(RUY-541, lead decision inside ADR-017 / ADR-033)*. The shell's `overlay` names the frozen app, so the service sees the same owner; the pads stay, the same devices, and Quick Resume through the Hub (the Thaw, then `app`) hands the game back the pads it had open. Destroying them at the Freeze made a hot-plug game reopen whichever new pad it could open first, and on the Dell a one-pad game (LibreQuake) lost the player's pad to the idle one. Why this is safe: the descriptors stay with the app that already held them, the profile has not changed (a lock or a switch still destroys), and the service writes nothing to them while the route is not `app` (one neutral frame when the overlay starts, then nothing; no rumble), so a frozen app reads nothing new and finds no backlog after the Thaw; a button still held at the Thaw (the B that closed the Hub) is masked until it is let go (`mask_held`), as for an overlay over a running game.
- **Overlay over a frozen game**: its pads exist but carry nothing (held in neutral); nothing the player does in the Hub reaches them.
- **Each seat uses its own player's controller profiles** *(RUY-643)*. The virtual pad of seat 2-4 is compiled from the seated player's profiles (§7), not the route owner's; a bind after a hold or a move keeps the seat's player; a seat whose player has no profile files (a guest) gets the defaults. A change to a seated player's profiles rebuilds the engines of that player's pads only. The Controllers pane still edits player 1's.
- **A controller that drops does not unplug the game's pad** *(RUY-627, ADR-017 point 9)*. A game that sees its pad vanish may give up on it for good (RUY-541, RUY-611: LibreQuake saved `joy_device -1`), and a Bluetooth pad that runs flat or sleeps must not cost a player that. So a seated pad that disconnects leaves its virtual pad in place for its seat's 60 s hold, idle in neutral (rumble dropped), and the pad that comes back is bound to the same device. When the hold runs out the seat ends but the virtual pad stays quiet until the run ends *(RUY-681, §5.1)*: only `LeavePlayer`, a profile change or the end of the owner destroys it.
- **Pads outlive a close until the game has exited** *(RUY-611, lead decision inside ADR-017; owner report 2026-11-14)*. A game saves its controller state on quit, and a pad removed under it is part of that state: LibreQuake (ironwail) quit from the Hub saw "Gamepad removed" after the Hub's Home destroyed pad1/pad2 and the Stop thawed it, wrote `joy_device "-1"` into its `ironwail.cfg`, and then opened no pad on any later launch. So a game's pads live as long as the game can still observe them. The shell side alone carries this (no watch of Session1 by inputd; `Shell.qml` `heldGame`, `InputRoute.qml` `heldInstance`): with no app in front, the route is **`overlay` with the game's instance** (1) while the game that was in front last is **frozen** behind Home or the Hub (this extends RUY-541's Hub Freeze to Home), and (2) while an instance **Close** asked to stop, whose pads the route held when Close began, has not exited: Close thaws it (T-457), Home is already in front, and the route stays `overlay` until `AppExited`, a refused Stop, or the kill check giving up, then `shell`. Close from the Hub and from a card's Options menu take the same path. Lock, a profile switch, an app switch and a game that was **not** frozen behind Home (pause off) keep the destroy rule above; so does the exit itself. `StartTest` (the Controllers pages' button test) therefore also runs under `overlay`, and a test ends only on `app` or `locked`.
- **Two windows of one app keep its pads** *(RUY-814, shell only; seen on the Dell with Steam: its installer, then the game, then Big Picture)*. xwayland-satellite gives every X window its own surface, so focus moves between windows of one client, and the service rightly destroys the pads on `shell` (above). The shell therefore never sends `shell` between two windows of a running instance. (1) A window whose client pid already belongs to a window record with a known instance takes that instance at once (`Shell.qml` `addApp`), with no `InstanceOfPid`. (2) While the front window's lookup is pending, `InputRoute` holds its last sent `app`/`overlay` of the profile (the Hub over it still makes `overlay`) as long as that instance runs, and sends nothing new until the reply comes (no timer): the same instance changes nothing, another instance or none sends where things end up. (3) When the last window of a running instance closes (not frozen, not being closed) and no other window is in front, the route is `overlay` with that instance (the held-game path above, `Shell.qml` `gapInstance`) for `windowGapMs` (3000 ms; a hold bound, not a UI duration) at most. It ends when a window is in front again, the instance is gone, the Hub opens, Home is chosen, the profile signs out, or the time is up; then the route is `shell`.

### 5.3 Ownership modes *(planned, T-371)*
`managed` (default; the routing above), `passthrough` (the running app's user gets an ACL on the physical event nodes for that run; the service applies no mapping and creates no virtual pad, keeps reading the pad for Guide and the shortcuts, and grabs it outside the route `app`, below), `steam` (as passthrough, plus the pad's hidraw nodes; Steam Input does the rest; we never edit Steam's files), `semantic` (native Ruya apps receive actions through `Platform1`, T-374). The mode is a per-app setting stored by the service; switching mode takes effect at the next launch.

**Leaks in `passthrough` and `steam` (RUY-2 review).** The app then holds descriptors on physical nodes that can be neither destroyed nor revoked (§5.2). Rules, built and tested by T-371:
- **evdev:** in every route but `app` (overlay, Hub, PIN pad, picker, a frozen app), the service holds `EVIOCGRAB` on those pads' event nodes, so the app's descriptors receive nothing, also not as a backlog after a Thaw; it releases the grab when the route returns to `app` for that app. The service reads the grabbed node itself, so navigation keeps working.
- **hidraw** cannot be grabbed: a reader keeps receiving reports (and a frozen reader finds them buffered after Thaw). So hidraw is granted in `steam` mode only, never in `passthrough`, and while an app holds a pad's hidraw that pad **enters no PIN**: the PIN pad takes digits from the keyboard and from other pads, and shows "Close <app> to use this controller here" for that pad. Acceptance test (T-371): no report from a grabbed node reaches the app's descriptor during an overlay or after a Thaw, and the PIN pad refuses a hidraw-held pad.
- Steam Input creates its own uinput pads: `steam` mode needs `/dev/uinput` for the profile user for that run, which breaks §3.1's "only root and `ruya-input` create input devices". T-371 decides how (check the creating process of a `ruya-input/` node, not only its phys prefix, or keep Steam's pads outside the prefix); the same question applies to T-412 (phone) and T-418 (development pad).

### 5.4 Grabs
In `managed` the service never grabs a pad: apps cannot open physical nodes (no ACL), so there is nothing to hide. It grabs (`EVIOCGRAB`, proven non-root) only in the cases of §5.3.

## 6. Bluetooth pairing as an attack surface *(built, RUY-411; T-397 open)*
- Only bonded devices connect: BlueZ `ClassicBondedOnly=true` (the BlueZ default; the image must not change it), and HID goes through the kernel (`UserspaceHID=false`, T-375). `scripts/vm-devices-check.sh bluetooth` asserts both from the image's config files: no `ClassicBondedOnly=false` in `/etc/bluetooth/*.conf`, `UserspaceHID=false` in `input.conf` (RUY-411).
- Pairing is possible only while the shell's pairing screen is open (the pairable timeout, T-299), and the screen shows the new device's name and **class**; a device that announces itself as a keyboard needs a second confirmation ("This is a keyboard. Pair it?", with its name; Cancel has focus, Back cancels), because a keyboard can type anywhere the shell can. The service tells it in `Devices1.Bluetooth.ListDevices` as `keyboard` (Class of Device major Peripheral with the keyboard bit, which a keyboard/pointer combo has too; a LE device without a class by its HID keyboard appearance; BlueZ's `Icon` `input-keyboard`). **The service is the gate (RUY-422):** `Pair(id, keyboard_confirmed)` pairs, trusts and connects a device with the `keyboard` flag only when the shell passes `true` (its Accept on that question); otherwise it answers `not-confirmed`, touches nothing and logs the refusal (`refused to pair <address>: it announces a keyboard and the shell did not confirm it`), also for a keyboard that is paired already. **Connect is gated too (RUY-444):** `Connect` of a bonded `keyboard` device that is not `trusted` (trusted = confirmed through Pair) answers `not-confirmed` and logs `refused to connect <address>`; the shell then asks the same question and, on Accept, sends Pair with the confirmation (which trusts and connects). A manual Pair holds the adapter Pairable for up to 20 s; any other device that bonds in that time is removed again (`sweep`) like an unsolicited bond in the controller window. The flag is ignored for every other device. Pads, headsets and mice pair as before. **The controller pairing window never pairs a keyboard** (RUY-411: the agent and the sweep treat a keyboard-class device as a stranger, refuse it and remove it if it bonded); a keyboard pairs only from Settings > Bluetooth, also when it is paired again after Forget. If the device leaves the list while the confirmation is open, the confirmation closes. The class is told by the remote device, so this is a speed bump for the user, not a defence against a spoofing device. The guided controller screen lists controllers only and is unchanged; the confirmation is on Settings > Bluetooth's device rows.
- **What a new pad may do before a profile owns it** (ADR-017, ADR-027): navigate the profile picker and the "Who's playing?" dialog; inside a session it drives nothing unless it is player 1's or the navigator (§11.3, built RUY-38). It never reaches a game as anything but a seat's virtual pad; **until RUY-122 turns the seat gate on** an unseated pad still gets one, numbered after the seats (§5.1).

## 7. Profiles *(built: the global profile, RUY-42 / T-369, one per slot, RUY-545, and its pages, RUY-465; game and platform T-370)*
> **Owner decisions, 2026-11-13 (lead-16; RUY-43's comments):** (1) no online sharing or community catalogue before the first release, profiles move by USB only; (2) no shipped per-game defaults for now; (3) macros and turbo deferred, off for imported files by default; (4) a guest gets its own global profile plus player 1's profile for the game in front; (5) a player may hold several device profiles, chosen by `match` (device over family over all); (6) the platform level stays in the service, nearly hidden in the shell. Known gaps against the levels below (scope fall-through vs `inherits`, a `match` miss, whose book, `game_id` on the route, portable export) are listed on RUY-43 and are settled in this section by RUY-490 before T-370 is built.
- **Format**: JSON, `schema_version: 1`, described by [`schemas/input-profile-v1.json`](schemas/input-profile-v1.json); the service validates every profile on load, save and import, refuses unknown fields and reports errors as `path: message` lines. The requirements' example (§9.3) is valid. No scripts: macros are data.
- **Reserved ids** *(RUY-596)*: the `controls-` id prefix belongs to global profiles (the shell names its slots `controls-all`, `controls-family-<f>`, `controls-device-<id>`). A profile with that prefix and a platform or game scope is `invalid` (`/id: the "controls-" prefix is reserved for global profiles`), in `ValidateProfile` and `SaveProfile` alike, so an imported game file cannot replace another pad's stored profile. Other imported ids are kept (re-importing the same game profile replaces it).
- **Precedence**: game → platform → global → the built-in default; a profile names its parent in `inherits` and lists only what differs. Resolution walks at most 8 levels and refuses cycles. Per controller: a profile may be limited to a family (`match.family`) or one stable id (`match.device`).
- **Global slots** *(Accepted (lead, 2026-11-13), inside owner decision 5; built RUY-545)*: (1) a console profile has up to one global assignment **per slot**: all controllers, `family:<f>` per family, `device:<id>` per device; a pad takes its device's slot, then its family's, then all controllers', then `default`. (2) `AssignProfile(profile, "global", scope_id, profile_id)` with `scope_id` `""` (all), `"family:<f>"` or `"device:<id>"`; the profile's `match` must name that slot (its device, else its family, else all; `invalid` otherwise); `profile_id ""` empties that slot only; assigning one slot never touches another; a save that changes an assigned profile's `match` takes it out of its old slot. `ListProfiles` reads the slots: `assigned` (its slot names it) and `global_slot` (the slot its `match` names). A stored `{"global": "<id>"}` (before RUY-545) loads into the slot its profile's `match` names. (3) The shell's Controls in games works on its page's pad: an edit changes the pad's own profile (its device's slot, its family's, or the one Applies to = All controllers put there); when nothing else applies (no profile, a built-in, or an all-controllers profile the page did not put there) the first edit makes a copy for **This <pad>**, so it reaches no other pad. Applies to moves the pad's settings to the chosen slot (replacing what it held) and never rewrites another pad's own profile. A wider slot also empties the pad's narrower ones, so the pad takes it: choosing All controllers on a Nintendo pad that had the Nintendo family's profile empties the family's slot, and the family's other pads then take All controllers too (a family profile another pad chose is displaced; it stays stored, unassigned). (4) "Changed" on the controller page and Settings > Controllers is per pad, from what applies to that pad. (5) Platform and game scopes (RUY-490 / RUY-43), whose book per pad (RUY-38) are separate.
- **Limits**: 256 mappings per list (the top level and each layer), 8 layers, 32 macro steps, a macro step never targets a macro (no recursion; a service rule), `press`/`release`/`tap` steps need a `target` and `wait` a `ms` (service rules), 10 s total macro duration, delays ≥ 10 ms, turbo ≤ 30 Hz, a chord of at most 4 inputs, names ≤ 64 characters, 64 KiB per file. Imported profiles are untrusted data (requirements §15): validated, never executed.
- **What a profile changes**: only what the **virtual devices** emit in the route `app` (the game's view). The shell's navigation is never remapped by a profile: it follows the family and the Confirm row (§11.2). A "Nintendo layout" is a built-in preset profile (south ↔ east, west ↔ north) for games, not a navigation setting.
- **Stick maths** (per stick, on the vector, so the dead zone is round, not square): magnitude `r` in 0..1. Then `r' = clamp((r − inner) / (1 − inner − outer), 0, 1)`. Then the curve `c`: Linear `r'`, Precise `r'²`, Aggressive `√r'`. Then `out = 0` if `r' = 0`, else `anti + (1 − anti) · c`, times `sensitivity`, clamped to 1. The direction is kept, and inversion applies per axis afterwards. Triggers use `trigger_threshold` as their inner dead zone. Smoothing is off unless set (an exponential moving average with the factor `smoothing`). The defaults are inner 0.08, outer 0.02, anti 0, sensitivity 1, Linear.
- **Deleting a parent**: its children are re-parented to its own parent and keep their overrides. A built-in profile cannot be deleted (`not-allowed`).
- **Game and platform keys**: `game_id` is the Library's stable game id (ADR-028; for a Flatpak game today its app id); `platform_id` is the launcher's app id (Heroic, RPCS3, Steam). The service learns the app in front from `SetRoute`'s `app_id`.
- **Where an edit goes** *(RUY-506 decision, pinned by a test in RUY-500)*: a layout, remap or stick change made on a controller's page, in Controls in games or (RUY-503) in pairing goes to **the pad's own profile**: its device slot, or the slot it already uses when that is its own family's or device's; when nothing else applies (no profile, a built-in, or an all-controllers profile the page did not put there) a copy for that pad is made (`controls-device-<id>`). It goes to All controllers only when the player chose All in Applies to (`GameControls.editable()`; the pairing step's `setOwnLayout` is stricter: always the device slot). There is no family-level layout.
- **Storage**: per console profile, by the service, under `/var/lib/ruya-input/profiles/<profile id>/` (the unit's `StateDirectory`, owned by `ruya-input`, 0700; profile users cannot read it). **The directory goes with its console profile** (RUY-468, lead decision lead-22): the shell calls `Input1.ForgetConsoleProfile(profile)` (1) after `Profiles1.DeleteProfile` answers `ok`, (2) for every guest id that leaves `Profiles1.ListGuests` (RemoveGuest, and the wipe at Lock, at a switch and at the service's start: `Profiles.cpp` compares the old list with the new), and (3) once at its own start, for every id that `Input1.StoredConsoleProfiles()` lists and that is neither a profile nor a live guest, only after both `ListProfiles` and `ListGuests` have answered `ok` (never on a partial view; an id listed by either while the sweep waits for its answer is kept). The service checks only the id rule of `ruya-profiles` (`accounts.rs` `valid_profile_id`: 1 to 32 of `[A-Za-z0-9_-]`, so never `..`, `/` or `.`; `invalid` otherwise, nothing touched), not that the account exists (it is gone by then); it removes the directory and the files in it without following a link (a link in the directory's place is unlinked after an `lstat`; a real directory goes with `std::fs::remove_dir_all`, which works from open directory handles and unlinks a link inside, its target kept), drops what it had read of it, and a pad still seated with that profile takes `default` at once; `ok` (also when nothing was there) and `failed` (part of it may be left) send one `ProfilesChanged`. A failed Forget is logged by the shell and not retried; the next start's sweep finds what is left. So no seat ever reads the controls of a deleted profile or of a guest that went (RUY-643 seats read their player's own). Tests: `book.rs` (removal, hostile ids, links; the link tests run on Linux only), `routing.rs` (a seated pad back on `default`, one signal), `tst_input_forget.qml` and `tst_input_forget_start.qml` (the three triggers, no sweep after a failed `ListGuests`, an id listed while the sweep waits is kept), and in the VM `scripts/vm-input-check.sh profiles`.
- **Export and import** are JSON text over `Input1` (`GetProfile`; `ValidateProfile` then `SaveProfile`). The shell writes the file to, and reads it from, a removable drive through the existing removable-volume path of `Devices1.Storage` (as `SaveReport` does: no symlinks followed, never as root into a user-controlled directory, a size cap of 64 KiB before parsing). The input service never touches removable media.

**As built (RUY-42).** *Model and validation* (`services/ruya-inputd/src/profile.rs`): a typed model of the whole schema (layers, chords and macros included), checked keyword for keyword with the schema and, on top, the rules above plus: a `button` target names a §4.2 button and an `axis` target an axis; a stick's `inner_deadzone + outer_deadzone` is below 1; a profile does not inherit from itself; names and descriptions have no control character and no bidirectional override or isolate (U+202A..U+202E, U+2066..U+2069). The 64 KiB cap is checked before the text is parsed; serde_json's nesting limit refuses deep nesting. `tests/profile_schema.rs` runs every fixture (the §9.3 example, a full profile, the broken and hostile files) through the schema and the typed model: they agree, and the service's extra rules are fixtures the schema passes and the service refuses. *Built-ins* (`book.rs`): `default` (every input to itself, the stick defaults) and `nintendo` (south ↔ east, west ↔ north, inherits `default`); a profile without `inherits` inherits `default`. A chain walks at most 8 `inherits` links (the one to `default` counts); a save that would loop or go deeper for the profile or for one that inherits from it is `not-allowed`, a missing parent `invalid`; at most 64 stored profiles per console profile. *Inheritance* merges parent first: a child's mapping replaces the parent's for the same `from`, a child's stick setting the parent's field by field. *Storage*: `<id>.json` (the service's own writing: keys sorted, whole numbers without a fraction) and `_assignments.json` (`{"global": {"all": "<id>", "family:<f>": "<id>", "device:<id>": "<id>"}}` since RUY-545; the older `{"global": "<id>"}` is read into its profile's slot, an entry whose profile is missing or whose `match` names another slot is journalled and not used; `_` cannot start an id) in `/var/lib/ruya-input/profiles/<profile>/`, 0700 / 0600, written under a temporary name and renamed; every file is validated on load, and one that fails, whose name is not its id or that claims a built-in is left on disk, journalled (`profile file <profile>/<name> refused: ...`) and not used; a link is never followed. *What applies* (`book.rs` `applying`, `engine.rs`, `routing.rs`): each virtual pad shows the global profile of its pad's device slot, else its family's, else all controllers' (a slot's profile counts while its `match` names that slot and fits the pad), else `default` (RUY-545); the engine runs on every input batch in `app` after the held-at-entry mask (a batch is one evdev `SYN_REPORT` frame: `Normalizer::frames` splits what one read of the node returns, so a release and a press of one button in two frames both reach the virtual pad; RUY-493), and a save, delete or assignment for the owner reaches its pads at once, each pad recomputed for itself (a held button is released and its new target pressed). Applied in v1: a button or axis of the 360 pad to a button, an axis or `none`, with `invert`, `scale` (axis) and `threshold` (axis to button, default 0.5, above 0), mode absent or `press`; several sources on one output: a button is held while any is, an axis takes the largest magnitude. Stored, validated, not applied yet (the input keeps its default): keys, mouse, layers, chords, macros, other modes, raw, motion and paddle inputs, `output`, `gyro_enabled`, `rumble_*` (T-372, T-373), and `smoothing` (it needs a tick while the stick rests; inbox). ## 8. When the service fails *(restart built, RUY-3; emergency reader built, RUY-410)*
Chosen path: **both**, because each covers what the other cannot.
1. **Fast restart**: `RestartSec=100ms`, `StartLimitIntervalSec=0` (never give up), `WatchdogSec=5s` with `sd_notify` from the event loop (as built: `Type=notify`, `READY=1` once the navigation keyboard exists, `WATCHDOG=1` every 2.5 s from the loop that also takes the router lock). Target: navigation back within 0.5 s of a crash (today 2.2-2.4 s, §1). The VM check judges it by the median of three kills (at most 500 ms, worst at most 1000 ms), because the first run after heavy checks is slow.
2. **The compositor's emergency reader** *(built, RUY-410)*: when `org.ruyaos.Input1` has had no owner for 3 s (a crash loop, a failed start, a broken image, a masked unit), the compositor opens the physical pads itself (it keeps logind's ACL on them, §3) and maps D-pad, left stick, south, east, start and guide to the same keys as `ruya-inputd`'s Phase 0 table, until the name has an owner again. It never feeds a game. A journal line names both transitions.
   As built (`shell/src/input/`): `Input.serviceOwned` (the existing `QDBusServiceWatcher` of the Input1 client, plus one `NameHasOwner` at start) feeds `EmergencyReader`, which waits `graceMs` (3000) before it turns on and turns off the moment the name has an owner. `PadDevices` (Linux) finds the `/dev/input/event*` nodes that udev's database (`/run/udev/data/c<major>:<minor>`) tags `ID_INPUT_JOYSTICK=1`, opens those the shell may read (`O_RDONLY`, no grab, so a node it cannot open, such as a virtual pad, is skipped silently), rescans once a second for pads that appear during the outage and drops a pad whose read fails (a vanished pad). It never reads a node whose `EVIOCGPHYS` starts with `ruya-input/` (the service's own virtual devices), and after a `SYN_DROPPED` it discards events up to the next `SYN_REPORT`, reads the buttons and sticks again (`EVIOCGKEY`, `EVIOCGABS`) and feeds them as events, so what is no longer down is released. Closing the reader (`~PadDevices`) closes the nodes and tells no one. `PadMapper` is the pad's evdev table: the hat axes and `BTN_DPAD_*` and the left stick (`ABS_X/Y`, pressed at 60 % of the half range, released below 35 %, the pad's own range from `EVIOCGABS`) give Up/Down/Left/Right, `BTN_SOUTH` Return, `BTN_EAST` Escape, `BTN_START` Menu, `BTN_MODE` HomePage; a key two sources or two pads hold goes down once and up with the last, and a pad that vanishes (or the reader turning off) releases what it held. The shoulder buttons, the right stick and the triggers are not read, and a held direction does not repeat. The keys go to `KeyRouter.injectKey`, which sends them to the shell window like a keyboard's (so the idle clock, the screen saver's swallow and the focus rules apply) and, with an app focused, takes only the Guide key and drops the rest, so the reader never feeds an app. Journal: `ruya-shell: input fallback on` / `off`, and `ruya-shell: input fallback reads /dev/input/eventN` per pad.
The spike proved the restart path (§1). Tests: `tst_input_emergency.qml` (mapper incl. a state re-read, the 3 s rule with a faked watcher, two pads, the shell); `scripts/vm-input-check.sh fallback` (mask the unit, a uinput pad signs in at the picker; the Dell drill is the same on real pads).

## 9. Performance and instrumentation
The input path stays event-driven (one thread per source node, no polling). The service counts, per device, events in and out and the time from the kernel timestamp of the source event to the write of the output event (`CLOCK_MONOTONIC` on both sides), and logs `ruya-inputd: latency <device> n=<n> p50=<us> p99=<us> max=<us>` every 60 s while `RUYA_INPUT_TRACE=1`. Budget: added latency p99 ≤ 1 ms (measured today: p90 126 µs).

## 11. UI ownership, the family's buttons and glyphs (ADR-027; T-396 / RUY-5) *(planned: RUY-124; built: the seats, RUY-121, the seat hold, RUY-627, who drives the UI, RUY-38, the family's confirm button, RUY-40, and the glyphs, RUY-41)*

### 11.1 Actions (one vocabulary)
The shell, the hint bar, `Platform1` (T-374) and the development tools (T-418) name buttons by **action**, never by letter: `up down left right` (the D-pad or the left stick), `accept`, `back`, `options` (context menu), `view`, `guide`, `tabPrev` / `tabNext` (shoulders), `pagePrev` / `pageNext` (triggers: fast scroll), `done` (finish a text entry), `dpad` (any direction, for hints). The service turns pad events into these actions; today they reach the shell as the Phase 0 keys (`accept` = Enter, `back` = Esc, `options` = Menu, `guide` = HomePage, `tabPrev/Next` = PgUp/PgDn), which stay the keyboard's keys too.

### 11.2 The family's own confirm button
**Decided per event in the input service** (`ruya-inputd`, T-398), from the device's family (§4.1: the service's device table, T-261, then the driver, then `generic`); never in QML. Per family, by position:

A pad with no choice is "As on the controller". It swaps `accept` and `back` of that pad only; a game never sees it (games get positional buttons on the virtual pad).

**As built (RUY-40).** `mapping.rs`: `Confirm` (`family` | `south` | `east`) and the pure `nav_key(family, mode, button)`: the button that confirms is south for every family under `south`, east under `east`, and under `family` east for `nintendo` and south for every other family, an unknown one included (the table above, with Phase 0's keys as the actions); the other of south and east goes back, and no other button depends on the setting. The family is the pad's `PadInfo::family` from `identity.rs::family` (§4.1: vendor, then driver, else `generic`); `Router::input` hands it to `mapper_events` on every event with the mode the signed-in profile chose for the pad the event came from (its stable id, RUY-603), else `family` (that function is the one seam of the family; `ActiveInputChanged` reports the same value). Keyboard keys do not depend on it. A `Mapper` remembers, per button, the key its press emitted and releases that one, so a change of the setting or of the profile while a button is held leaves no key down; a pad that vanishes mid-press releases it as before. The modes are stored per console profile in `<StateDirectory>/profiles/<profile>/_settings.json` as one entry per pad with a choice (`{"confirm_buttons": {"<device id>": "east"}}`, next to the profiles, written whole; "family" removes the pad's entry; an unreadable file, a bad device id or an unknown mode is journaled and means `family`). The profile-wide `{"confirm_button": ...}` of RUY-40 is dropped on load with a journal line (a pre-release draft; every pad is `family` until set again) and is not written again. The virtual pads and RUY-42's engine never see it. `Input1.SetConfirmButton(profile, device, mode)` answers `ok`, `invalid` (a mode or a device id it does not take), `unknown-profile` or `failed`; the pad need not be connected. `Input1.GetConfirmButtons(profile)` answers the status and the choices (device id -> `south` | `east`; a pad that is absent is `family`) for the controller pages. The `ConfirmButton` property is the mode of the active controller (the pad of the last press) for the signed-in (route's) profile, `family` with no profile or no active pad; `PropertiesChanged` is sent on a profile switch, on a set for the active pad that changes it, and when another pad with another mode becomes the active one (or the active pad goes), so the shell's accept and back glyphs (RUY-41) follow the pad in hand. `ActiveInputChanged(device_id, family)` is sent when a button press comes from another pad than the last announced one, among the pads that navigate now (since RUY-38, §11.3), and at `SetNavigator`. The shell's row and its note are in `02-shell.md` §1.2.

**As built (controller menus UX, RUY-500; design 2026-11-13).** On each controller's page, directly under **Confirm in menus** and its note, **Button layout in games** edits that pad's layout (the §7 Nintendo layout; the same stored value as Controls in games' Button layout, through `GameControls.setLayout`), with a one-sentence note on the pad: which of its buttons games see as A and as B, in its printed glyphs ("Games see [B] as A and [A] as B, unlike menus." when the button that confirms in menus on this pad is not the one games see as A, else "Games see [A] as A and [B] as B."; hidden when south or east is remapped away). `GameControls.gamesButtons()` works it out from the shown pad's profile: the layout's south/east swap, then a remap of south or east follows its target. The design's pane group label "Buttons" and the pane rows are dropped (the Confirm row lives on the pad's page since RUY-603). ### 11.3 Who drives the UI *(ADR-017 with its amendments, owner 2026-11-12/13/14; built: the seats, RUY-121, the hold, RUY-627, who navigates, `ForeignInput`, `SetNavigator` and the lost-pad pause, RUY-38; the pad's owner, RUY-124; the prompt is 02 §1.9, RUY-122)*

**Seats.** While a profile is signed in, the session has up to **4 seats**. A seat is one profile on one pad.
- Seat 1 is **player 1**: the signed-in profile and its **active controller**, the pad that signed it in (RUY-540/551). A keyboard sign-in gives seat 1 no pad.
- A profile has at most one pad, and a pad holds at most one profile.
- Seats last for the session; any profile change (Lock, Switch, sign-out) clears them.
- `ruya-inputd` keeps the seats (`Input1.JoinPlayer`, `LeavePlayer`, `ListPlayers`, `PlayersChanged`; the device record's `slot` and `profile`). The shell asks for the PIN (`Profiles1.VerifyPin`) before it calls `JoinPlayer`. The service never sees a PIN.
- Only seated pads get a virtual pad, and pad *n* is seat *n* (§5.1).
- **As built (RUY-121, `seats.rs`, `routing.rs`; the shell's client `Input.players`, `joinPlayer`, `leavePlayer`).** Any change of the route's profile (a sign-in, a Hub switch, Lock, the route's caller leaving the bus) empties every seat and seats the new profile, if any, in seat 1 on the pad that pressed since the change before, or on no pad. `JoinPlayer(d, p)`: (a) `p` is player 1: `d` becomes seat 1's pad (the active controller) and the old one is unseated; (b) `p` sits in seat *n* ≥ 2 on another pad: it moves to `d` and keeps *n*, the old pad is unseated; (c) `d` sits as another profile: that one leaves its seat first (from seat 1, player 1 stays without a pad); (d) else the lowest free seat of 2–4, or `full` with nothing changed; (e) the same `d` and `p` again: `ok`, no change and no signal. The statuses, checked in this order: `invalid` (not a device id), `not-allowed` (nobody signed in), `unknown-profile` (not a profile account), `unknown-device` (no connected pad with that id), `full`. `LeavePlayer(n)`: `invalid` for 0 or more than 4, `not-allowed` for seat 1 or with nobody signed in, else `ok` (also for an empty seat). A seat taken by another profile keeps the virtual pad of its number, bound to the new pad with that player's engine *(RUY-681, §5.1; before, it was a new virtual pad)*.
- **The hold, as built (RUY-627, `seats.rs` `hold`/`resume`/`take_over`/`expire`, `routing.rs` `remove_pad_at`, `take_held_seat`, `bind`, `expire_holds`).** A seated pad that disconnects (removed, battery dead), seat 1 included, holds its seat for `SEAT_HOLD` = 60 s: the player record keeps its `device_id` with `held` true and `held_secs` the whole seconds left (rounded up, worked out when the record is sent); `PlayersChanged` is sent when the hold starts and when it ends, never per second (the shell counts down itself). Its virtual pad, if the route has one, stays: one neutral frame, then nothing whatever the route; the rumble effects of the lost node are dropped (nothing is sent to it), and the app's effect uploads are kept (one uploaded during the hold too), its plays ignored. The same stable id reconnecting within the hold, or the one like pad (§4.1), is the seat's pad again (`held` false; seat 1 is the active controller again): its virtual pad is **bound** to the new physical pad (no device made or destroyed), what that pad holds at the bind is masked until let go (`mask_held`: for a move, the press that answered the prompt; a reconnecting pad holds nothing the service has seen, since a button pressed before its node was opened sends only its release, which changes nothing on the virtual pad), the profile is compiled for it, and every effect the app uploaded is uploaded to it again at the rebind, so the next play reaches it; a ready virtual pad's one-entry ACL is asserted again at the rebind (a udev event on its node while it was parked is not answered). A held seat without a virtual pad (the pad went outside `app`) gets one with its number when the pad is back in `app`. When the hold runs out (checked on the half-second tick): seat *n* ≥ 2 is freed (the player leaves); seat 1 keeps its profile with `device_id` ""; their virtual pads stay quiet for the owner's life and are bound again by the next pad seated in their number *(RUY-681, §5.1; before, they were destroyed)*. A pad reconnecting later is unseated and only `JoinPlayer` with the signed-in profile seats a pad as player 1 again (the prompt's Move, RUY-628; amendment 6e). A move of a held seat (`JoinPlayer` cases a, b) ends the hold and binds the virtual pad to the new pad; `LeavePlayer` of a held seat (or of a quiet pad's number) destroys it; a profile change (Lock, Switch) clears every hold with the seats and destroys the held virtual pads. A held seat keeps its number: with the gate off unseated pads are numbered from 5 up, so they never take it. `RUYA_SEAT_HOLD_SECS` (whole seconds, the VM checks only) shortens the hold; it is read once at start and journaled (`RUYA_SEAT_HOLD_SECS: a seat is held <n> s, not 60 (a test setting)`). Journal: `player <n> (ruya-<profile>) held for <s> s: <id> is gone`, `player <n> (ruya-<profile>) is back on <id>` (`, a like pad of <old id>`), `<id> is like the pads of <k> held seats: it takes none`, `player <n>'s hold ran out: <id> did not come back`, `virtual pad ruya-input/pad<n> bound to <id>`. **A restart during a hold:** a hold is service state only; the new process knows no seats, and the shell's replay (below) joins a held player again only once its pad is listed, i.e. when the pad comes back; a pad that never comes back is dropped from the replay queue after the hold length (60 s; the shell's `Input` timer, RUY-644; players whose pads are listed then join). The replay joins in slot order and never past a pad that is still away: seat 3 waits for seat 2's pad, so each player keeps their own number (RUY-644; the shell holds the later joins back, JoinPlayer is unchanged: a slot request would add contract for a case the 60 s deadline already bounds). Only when the deadline drops seat 2's player does seat 3 join as the lowest free seat, 2, as it would have after the held seat expired. VM check pending: `vm-input-check.sh seathold`. `PlayersChanged` carries the whole list once per change, and every pad whose `slot` or `profile` changed gets one `DeviceChanged`. The journal names ids only: `player <n> is ruya-<profile> on <device id>` (`on no pad`), `player <n> left`. Navigation, Guide and the active input follow the seats since RUY-38 (below the table). **The seat gate (lead decision, RUY-121 round 2).** `Router::new` takes `seat_gate`; the image passes `SEAT_GATE` = **false until RUY-122** (the prompt that calls `JoinPlayer`), so local co-op does not shrink to player 1's pad meanwhile: with the gate off an unseated connected pad still gets a virtual pad in `app` (and what `overlay` keeps), numbered after the seats with the lowest free number from 5 up, in connect order; `pad1`..`pad4` stay the seats', so a join replaces only the joining pad's own virtual pad and renumbers no other live one, and a pad that leaves its seat is remade after the seats. Seats, `ListPlayers` and every `Input1` member work the same either way; the tests run with the gate on, and two with it off. **Another profile's player is only an input source to the route owner's game**: every virtual pad is ACL'd to the owner's uid, and the game cannot tell which profile a pad belongs to (attribution is not built: below). **A restart of the service** (06 §8): the new process knows no seats and the shell's re-sent route reads as a keyboard sign-in, so the shell (`Input`, on every new owner of the name) joins the players it last knew again: seat 1's pad as the route's profile (none for a seat 1 without a pad), then the others by slot, each once the service lists its pad; these answers are not `joinFinished`. VM check pending: `vm-input-check.sh players`, and the `shell` step (after the `kill -9`, `pad1` and seat 1 come back without the script joining).

| State | Navigates the shell | An unseated pad's button | An unseated pad's Guide | A seated pad, seat 2–4 |
|---|---|---|---|---|
| Nobody signed in (picker, its PIN pad, first boot, Setup) | every pad, the keyboard | navigates | Guide as today (`KEY_HOMEPAGE`) | — (no seats) |
| Signed in: Home, pages, the Hub | seat 1's pad, the keyboard | `ForeignInput press` (at most 1/s): "Who's playing?" opens, unless the pad chose Not now (quiet) | `ForeignInput guide`: the prompt opens, also when quiet | nothing; its Guide is `ForeignInput player-guide` (only journaled until a players' Hub is designed) |

**Who navigates, as built (RUY-38, `routing.rs` `navigates`, `sync_navigation`, `set_navigator`, `input_at`; the shell's `Input.setNavigator`, `Input.foreignInput`; tests `routing.rs` "who drives the UI", `tst_input_navigator.qml`, `tst_hub_controllers.qml`; VM check pending: `vm-input-check.sh owner`, `guide`).** A pad navigates the shell (its keys on "RuyaOS Navigation", Guide as `KEY_HOMEPAGE` included) when nobody is signed in (no seats: `locked`, or `shell` with ""), else when it is the navigator, else, with no navigator, when it is seat 1's pad and the seat is not held; so with seat 1 held or without a pad only the keyboard navigates. Under `app` a pad that navigates gives the shell its Guide only, as before. **No padless console (RUY-122):** a press takes no seat (RUY-38's interim fallback for the gate-off image, `claim_padless_seat1`, is gone with the gate); while seat 1 has no pad and is not held (a keyboard sign-in, or its pad's 60 s hold ran out) another pad's press is a `ForeignInput` "press", the shell's prompt opens and offers player 1's own profile, and its `JoinPlayer` makes that pad seat 1's (and `pad1`, by §5.1). A pad that does not navigate gives the shell nothing, and its virtual pad, if it has one, still gets its input (seats 2-4; an unseated pad has none). While a profile is signed in, a pad that does not navigate sends `ForeignInput(device_id, kind)` for one batch (one evdev report) at most: `"guide"` for an unseated pad's Guide press, `"press"` for an unseated pad's press of any other button (never an axis, a hat moving back or a release), at most once per pad connection per `FOREIGN_PRESS_GAP` = 1 s, counted from the last one sent; `"player-guide"` for the Guide of a seat 2-4 pad; seat 1's pad (only silent while a navigator is set) sends none. `SetNavigator(device_id)` answers `ok`, `not-allowed` (nobody signed in) or `unknown-device` (no connected pad with that id), "" is always `ok` and clears it; it is also cleared when its pad's last connection goes, at any change of the route's profile and when the bus name that set it leaves the bus (`caller_left`); the journal says `navigator <id>` and `navigator cleared (<why>)`. At an `ok` call the service sends `ActiveInputChanged` for the navigator (always, also when it was the last announced pad) and `ConfirmButton` changes with it when the navigator's Confirm choice differs; when it is cleared the active input stays the navigator until a pad that navigates presses. Whenever who navigates changes (a navigator set or cleared, a move of player 1, a sign-in, a pad that comes back to its held seat), a pad that stops navigating releases through the `KeyBoard` the keys it held, and one that starts forgets what its mapper saw meanwhile (none of it was counted), so no key sticks and none is released twice. Only a pad that navigates becomes the active input or the next profile's seat 1 (`pad_since_change`): a press of a pad that does not navigate is no sign-in. `UserActive` is unchanged. **The shell's side:** `Input.setNavigator(id)` and `Input.navigator` (what the shell asked; dropped at a refusal, when the pad leaves the device list, not while a restart's replay still waits for it, and at a change of the route's profile), `Input.navigatorFinished`, `Input.foreignInput(id, kind)`; after a new owner of the name the shell sets the navigator again once its pad is listed, after the players' joins (`continueReplay`; that answer is not `navigatorFinished`). `"player-guide"` is only journaled, `ruya-shell: player <n>'s Guide (no players' Hub yet)`; `"press"` and `"guide"` open "Who's playing?" (02 §1.9, RUY-122; a quiet pad's `"press"` does not). **Seat 1's pad lost over a game** (`Shell.qml`, `player1Held`): when `PlayersChanged` shows seat 1 `held` (the start of RUY-627's hold) while an app is in front and the Hub is closed, the Hub opens (`ruya-shell: player 1's controller is gone: the Hub opens over the game`), with its usual focus on the game card, and `HubPause` freezes the game; the keyboard drives it, the pad that comes back within the hold drives it again (no prompt), and Accept on the game card or Back resumes as always. Over Home or a page nothing opens and no toast shows. The mock (`MockInputBackend::padButton`, `Input.mockPadButton(id, button)`) plays the same rule for the shell's tests.

**A pad connects.** When it reconnects within 60 s to a held seat, that seat is its own again, with the same virtual pad, so the game sees nothing (RUY-627). Otherwise, while a profile is signed in, "Who's playing?" opens at once (`DeviceAdded` with `slot` 0) and pauses the app in front as the Hub does. It never opens on the picker. *(Built, RUY-122: the shell sees a new id with `slot` 0 in a successful `ListDevices` after the first one, 02 §1.9.)*

**Preselect (RUY-124).** "Who's playing?" starts its focus on the asking pad's `owner` card (after player 1's padless card, before the first profile without a pad; 02 §1.9). It only focuses: no auto-join, the PIN is asked as always. Nothing else in the routing uses the owner.

**The prompt** (02 §1.9; *part 1 built, RUY-122: the opening, the pause, Pick, Join or Switch without a PIN, Not now, the errors; Move and the PIN RUY-628, Add profile RUY-630, Guest RUY-631*) pauses the game while it is open, and the game continues by itself when it closes. It offers the profiles, Guest and Add profile:
- **A profile that does not play:** **Join** (focused) or **Switch**, with its PIN if it has one. Join seats it in the lowest free seat. Switch makes it the session (Lock, then `SwitchTo`, then `JoinPlayer` for the asking pad), and the old player 1's apps freeze and are kept (RUY-87, ADR-019).
- **A profile that plays now, Player One included:** **Move** (Cancel focused first; its PIN). It keeps its seat number on the new pad, and the old pad becomes unseated.
- **Guest:** it joins at once as Guest, Guest 2, ... (no PIN, no Switch).
- **Add profile:** behind an admin's PIN.
- **Not now** (= Back) keeps that pad quiet until the game in front exits (over Home: until it disconnects or the session ends). Its Guide still opens the prompt.
- No idle timer ever seats or moves a pad (RUY-384).

**Losing a pad.** A seated pad that disconnects or runs flat keeps its seat for **60 s**. Its virtual pad stays, idle (neutral), and is rebound to the pad when it returns, also to a like serial-less USB pad (§4.1); after the 60 s the seat ends and the virtual pad stays quiet until the game ends, so the player who joins again gets it back *(RUY-681, §5.1)*. *(The hold and the rebind are built, RUY-627, as above; the Hub opening for seat 1 is built, RUY-38, above; the quiet pad, RUY-681.)*
- **Seat 1:** with an app in front the Hub opens, which pauses the game. After 60 s seat 1 has no pad, and only the prompt's Move (or Switch) puts player 1 on another pad.
- **Seats 2–4:** they leave after 60 s. A temporary guest is then wiped (03 §1).
- There is no pause for seats 2–4.

**Active input** (§11.4) is the pad of the last press among the pads that navigate now, or the keyboard. While the prompt is open it is the asking pad, so the hint bar shows that pad's glyphs and its own Confirm choice (§11.2, RUY-603).

**Admin** features (Settings that need an admin, Power) are reached only through seat 1's pad or the keyboard, and still ask the admin PIN.

**What a player's profile means** (ADR-017):
- Apps run as player 1's user, so **saves are player 1's**.
- The other profiles get their achievements and play time **attributed**; guests get none.
- The **strictest age limit** of everyone seated applies at launch.
- No ticket builds attribution or the age rule yet (inbox).

**Each pad's owner** (RUY-124): the last non-guest profile seated on a pad is kept per stable id (`owner` in the device record). The prompt starts on that profile. It never signs in or joins by itself.

### 11.4 Glyphs follow the active input
- **Active input** = the device that sent the last **press** among the pads that navigate now (§11.3) and the keyboard; it changes on the first press of another device, never on connect, a battery report, stick or trigger noise below the navigation threshold, or mouse motion (no flicker). The service sends `ActiveInputChanged(device_id, family)`; the shell tells the keyboard apart by the event's source device (not "RuyaOS Navigation").
- **Glyph of an action** = the label of the button that performs it **after** the Confirm setting (with "Right" on a PlayStation pad, `accept` shows Circle). One set per family, all our own drawings (no vendor artwork; the T-199 question stays open): Xbox letters, PlayStation shapes, Nintendo letters, keyboard key caps, and a **generic** set of position diamonds (four dots, the pressed one filled) for unknown pads. Guide is one home glyph for every pad. Drawing and sizes: `04` §3.7.
- **As built (RUY-41).** `Input.activeDevice` / `Input.activeFamily` (shell) take each `ActiveInputChanged`; the keyboard is told apart in the shell: an application event filter on `Input` sees every key press (not repeats) and `Input::keyboardSourceOf(deviceName, key)` calls it `keyboard` when `QKeyEvent::device()` has a name that is neither "RuyaOS Navigation" nor Qt's own "core keyboard" (a platform that names no device, a key the shell made), and only for the keys the shell navigates or types with (letters, digits, Esc to PgDn, Menu, HomePage, Super), so a remote's volume key or the power button never switches. Then `activeFamily` is `keyboard` and `activeDevice` "". The service announces a pad only when it differs from the last one, so a key from "RuyaOS Navigation" while the keyboard is active brings the last announced pad back. A key whose source cannot be told apart changes nothing. The journal says once per source device `ruya-shell: key events come from "<name>"`, and `ruya-shell: active input is the keyboard ("<name>")` on each switch to it. **Unverified:** what Qt's eglfs/libinput reports as a key's device on the image (if it names no device, the keyboard is never told apart and the glyphs stay the pad's). The glyph table is `shell/qml/Glyphs.qml` (04 §3.7).
