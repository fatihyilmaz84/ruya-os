# 06 — Ruya Input (design)

**Status.** Design, from the spike T-366 / RUY-2 (lead, 2026-11-12). Built: `ruya-inputd`'s Phase 0 bridge (pads to navigation keys, ADR-003) and, since RUY-3 (T-367), the service half of §3, §4.1, §5.1-5.2 and §8.1, marked *(built, RUY-3)*: the service, its user and udev rules, the virtual pads, the routing core and `Input1`'s Devices and Routing members. Since RUY-409 the shell calls `SetRoute` on every change (§5.1, "The shell's side"), so a game in front gets its profile's virtual pads (verified on the host with the mock; the VM run of `vm-input-check.sh shell` and the Dell race are pending). Everything else here is the **target** that the tasks T-367..T-374 build, each marked *(planned, T-nnn)*. The owner's requirements are the appendix [`06-input-requirements.md`](06-input-requirements.md); where this file and an *Accepted* ADR differ, the ADR wins. Contract draft: [`api/dbus/org.ruyaos.Input1.xml`](../../api/dbus/org.ruyaos.Input1.xml); profile format: [`schemas/input-profile-v1.json`](schemas/input-profile-v1.json).

**InputPlumber, not measured here.** Building it from source on the host was refused by the session's permission check (third-party code); the facts below are from its repository (v0.84.0, 2026-11-05): GPL-3.0-or-later; Rust; the unit has no `User=` (root) and only `ProtectSystem=full`; the bus name may be owned by root only; virtual targets `xb360`, `xbox-elite`, `dualsense`, Steam Deck, keyboard, mouse, touchpad and more; an `InterceptMode` property for overlays; YAML device configs (about 100) with a generic-gamepad fallback; source nodes hidden by moving them to `/dev/inputplumber/sources`; **no per-user or per-session concept for its virtual devices** (they are daemon-global); packaged for Fedora only in a COPR.

## 2. Engine decision (ADR-003, ADR-024)

**`ruya-inputd` grows into the Ruya Input service; InputPlumber is not used** (ADR-003's named fallback). Reasons, in order:
1. **Least privilege.** The requirement is "not the whole engine as root" (§2.3 of the requirements; the hardening invariant in `CLAUDE.md`). The spike shows the whole service can run as an unprivileged system user with udev ACLs; InputPlumber runs as root with almost no hardening, and its design (moving device nodes) needs it.
2. **The profile boundary is ours anyway.** ADR-024's core rule, "a virtual node has one ACL entry, for the signed-in profile, re-made at every lock and switch", has no place in InputPlumber; we would write that layer next to it and keep a root daemon we do not control between the pads and the games.
3. **Packaging.** A COPR in a signed image is a third-party repository in the supply chain (01 §4); a source build is a new Rust stack in our image build, for one daemon.
4. **Cost of ours.** It already reads every pad, survives pads vanishing (T-337) and adds 88 µs median. What it lacks (virtual pads, routing, profiles) is the work T-367..T-374 plan either way.

What we take from InputPlumber: an intercept mode for overlays (our route `overlay`), a device database separate from user profiles, the generic-gamepad fallback, and its list of virtual targets as the long-term goal for §7 of the requirements. Revisit only if handheld-specific hardware (built-in pads exposed as keyboards, vendor HID buttons) becomes a target: InputPlumber's device configs are its real value there.

## 3. Process, privilege and device access *(built, RUY-3)*

- **User.** `ruya-inputd` runs as the system user `ruya-input` (sysusers, no home, no login shell), not root. Unit hardening stays as today plus `User=ruya-input`, `DeviceAllow=char-input rw`, `DeviceAllow=/dev/uinput rw`, `DeviceAllow=char-hidraw rw` (T-373 only), `RestrictAddressFamilies=AF_UNIX AF_NETLINK` (the udev monitor). **As built:** `PrivateNetwork=` is off, because udevd broadcasts its monitor messages in the host's network namespace only; `IPAddressDeny=any` and the address families leave the service no IP at all. Its state (the id salt, §4.1) is the unit's `StateDirectory` `/var/lib/ruya-input` (0700).
- **udev rules** (`70-ruya-input.rules`, replacing the old single line, and, as built, `74-ruya-input-acl.rules` for the `RUN` entries of rule 2: after `73-seat-late.rules`, whose uaccess builtin flushes named ACL entries, so `ruya-input`'s entry must be added after it on every event):
  1. `/dev/uinput`: `GROUP="ruya-input", MODE="0660"`. Only root and `ruya-input` can create input devices, so only they can claim the `ruya-input/` phys prefix below.
  2. **Physical pads** (`ENV{ID_INPUT_JOYSTICK}=="1"` and not ours): `RUN+="/usr/bin/setfacl -m u:ruya-input:rw $devnode"` (after logind's builtin, so both entries stay). The pad's **motion and touchpad nodes** (same HID parent, `ID_INPUT_ACCELEROMETER` / `ID_INPUT_TOUCHPAD` on a joystick's parent) get the same entry and **lose `uaccess`** (no ACL for the shell): the service reads them (T-373), libinput in the shell no longer does.
  3. **Virtual pads** (`ATTRS{phys}=="ruya-input/pad*"`; a pad's phys is `ruya-input/pad<n>`): `OWNER="ruya-input", MODE="0600"`, and the uaccess tag is not set for them. Other `ruya-input/` devices (the keyboard and mouse of T-372 / RUY-45, which the compositor reads, not a profile user) keep uaccess; the service never reads any `ruya-input/` device back as a physical pad. systemd's own `70-uaccess.rules` still tags joysticks, so the service **re-asserts its ACL after every udev event on its own node** (it watches the udev monitor for its phys prefix) and only then announces the device as ready. The spike showed both halves: an ACL set after the `add` event holds, a `change` event wipes it. This rule is for **virtual pads** (`ruya-input/pad*`). **Virtual keyboards and mice** (`ruya-input/kbm*`, T-372) are different: a Wayland game (and Xwayland or Wine through it) never reads keyboard or pointer nodes; it gets keys and motion from the compositor's seat. So those nodes keep `uaccess` (the shell's libinput reads them) and never get a profile ACL. The service emits on them only while the route is `app`, and the compositor delivers them to the focused app through `KeyRouter` like a real keyboard, Guide keys included.
  4. **hidraw** of a known pad family (T-373: adaptive triggers, lightbar, gyro calibration): `ruya-input` only. Never a profile user, except in `steam` mode (§5.3) for the running app's user, and only for that run.
  5. **No legacy joystick API** *(built, RUY-3 round 2)*: `joydev` is blacklisted (`/usr/lib/modprobe.d/ruya-no-joydev.conf`: `blacklist joydev`, `install joydev /bin/false`), so no `/dev/input/js*` node exists. Fedora's stock rule makes every `js` node `0664` (world-readable, seen on the Dell): with joydev loaded, any user could read any pad, a physical one or another profile's virtual pad, past every ACL above. SDL, Wine and Proton read evdev, so nothing supported needs `js`. `vm-input-check.sh` asserts that joydev is not loaded, that no `js` node exists with a virtual pad up, and that a profile user opens none.
- **The shell keeps its own path**: the physical pad nodes keep logind's `ruya-shell` entry (uaccess), so the emergency reader (§8) can open them without the service.

## 4. Device model

### 4.1 Identity *(stable and instance ids built, RUY-3; matching like pads is T-264)*
- **Stable id**, `<bus>-<vid>-<pid>-<key>`, where `<key>` is a 12-hex-digit hash (SHA-256 of a machine salt kept in `/var/lib/ruya-input/salt` plus the identifying string): Bluetooth → the device address (`uniq`, measured on the Dell: the DualSense's MAC); USB with a serial (`ID_SERIAL_SHORT`) → the serial; USB without one → the USB port path (`ID_PATH`), so two identical serial-less pads are told apart by socket. Never `eventN`. The hash keeps MAC addresses and serials off the bus.
- **Instance id**: a counter per connection (`<stable id>#<n>`). Signals carry both; the shell keys rows by the stable id.
- **Like pads (ADR-017).** A serial-less USB pad plugged into another socket is a new stable id. The registry (T-264) matches it to a known one only when exactly one known pad of the same `vid:pid` is absent; otherwise the "Who's playing?" dialog asks. A pad that reconnects within 60 s gets its slot back (ADR-017).
- **As built** (`identity.rs`): the salt is 32 random bytes, made once (a salt of the wrong size is reported and never overwritten: ids are then unstable until it is fixed); `<bus>` is `usb`, `bluetooth` or `virtual`; the identifying string is the address for Bluetooth, else the serial, else `ID_PATH`, else `uniq` or `phys`; the family goes by vendor (Microsoft, Sony, Nintendo), then by driver (`xpad`, `playstation`/`sony`, `nintendo`).
- **Family** (`xbox`, `playstation`, `nintendo`, `generic`, ...): from the service's own device table by `vid:pid` (first entries: T-261's audit and RUY-154's 360 receiver), then the kernel driver, then `generic`. SDL's mapping database is a separate data file the service reads for unknown pads (requirements §4.2); it never decides capabilities.

### 4.2 Normalised input
Buttons: `south east west north l1 r1 l3 r3 start select guide dpad_up dpad_down dpad_left dpad_right` plus `paddle1..4`, `misc1` (share/capture) and `touchpad_click`. Axes: `left_x left_y right_x right_y` as i16 (-32768..32767, up negative) and `left_trigger right_trigger` as 0..32767. Motion: `gyro_{x,y,z}` in deg/s ×16, `accel_{x,y,z}` in mg; touchpad contacts as (id, x, y) in 0..65535 of the pad's surface; `touchpad` names the surface as a whole (for touchpad-as-mouse). Every event keeps its **raw source** (`<node kind>:<evtype>:<code>`) so a profile can map an input that has no normal name. Buttons are named by **position**, not label: Nintendo's A is `east` (the family's confirm button, ADR-027, is a mapping on top: T-398).

### 4.3 Capability descriptor *(built, RUY-39)*
Per device, per capability (`buttons`, `sticks`, `analog_triggers`, `dpad`, `gyro`, `accelerometer`, `touchpad`, `rumble`, `trigger_rumble`, `adaptive_triggers`, `lightbar`, `player_leds`, `speaker`, `microphone`, `battery`), four booleans:
- `hardware` — the model has it (device table);
- `driver` — the kernel exposes it here (a motion node exists, `EV_FF` with `FF_RUMBLE` on the node, a power-supply entry);
- `available` — usable now (the node opened, the battery reports, Bluetooth rumble acknowledged);
- `output` — the virtual device the pad is routed to can carry it (an Xbox 360 virtual pad: rumble yes, gyro no).
Only what is detected is reported (`rumble` never implies `adaptive_triggers`). `GetCapabilities` returns them as `a(sbbbb)`.

**As built** (`caps.rs`, filled when the pad connects): every name is listed, in the order above, and `hardware` false means the model has no such part. `hardware` is the device table's entry (by `vid:pid`: DualSense and Edge, DualShock 4, Xbox 360 wired and receivers, Xbox One and Series, Switch Pro) or, for a model it does not know, only what the kernel shows; a part the kernel exposes counts even when the table lacks it. `driver` comes from the pad's own node (`BTN_SOUTH`; `ABS_X`/`ABS_Y`; `ABS_Z` or `ABS_RZ`; a hat or `BTN_DPAD_*`; `FF_RUMBLE`), its sibling nodes under the same HID parent (`ID_INPUT_ACCELEROMETER` for gyro and accelerometer, `ID_INPUT_TOUCHPAD`) and the parent's `power_supply/` entry. `available` needs that node to open (the ACL of §3 rule 2) or the battery to report a capacity: a node that is missing is neither `driver` nor `available`, one that does not open is `driver` only. The service has no kernel path yet for `trigger_rumble`, `adaptive_triggers`, `lightbar`, `player_leds`, `speaker` and `microphone` (hidraw, T-373): never `driver`. `output` is the Xbox 360-style virtual pad's set: buttons, sticks, analog triggers, D-pad and rumble. The descriptor is not refreshed while the pad stays connected (a battery that starts reporting later shows at the next connection).

### 4.4 Button test *(built, RUY-39)*
`StartTest(device_id)` streams one pad's input to the shell as `TestInput(device_id, input, value, source)`: `input` is the normalised name of §4.2, or the raw source for an input without one; `value` is 1/0 for a button, the normalised value for an axis, the kernel's value for a raw input; `source` is the raw source (`raw:pad:<type>:<code>`, `pad` being the pad's main node). Buttons go out at once; each axis at most 30 times a second, its newest value never lost (held back at most 1/30 s; the service then ticks every 16 ms instead of 500). A digital trigger next to its analog axis, a hat that did not move and key autorepeat send nothing. Only in the route `shell` (`not-allowed` otherwise), one test per device (`busy`). A test ends by `StopTest`, a route other than `shell`, the pad disconnecting, its caller leaving the bus, or 120 s after the pad's last input; every end is one `TestEnded(device_id, reason)` with `stopped`, `route`, `gone`, `caller` or `idle`. The navigation keys and the virtual pads are not touched by a test. Settings > Controllers > a controller > Button test is the client (02 §1.2).

## 5. Routing *(built: the service RUY-3, the shell's calls RUY-409; ownership modes T-371)*

### 5.1 States
| Route | Set when | Pads produce |
|---|---|---|
| `shell` | the shell (or the Hub, a page, the picker's pre-session state) is in front | navigation keys on "RuyaOS Navigation" (today's behaviour); no virtual pad exists |
| `app` | an app has the focus | the app's profile's virtual pads only; navigation keys stop, except **Guide**, which always goes to the shell as `KEY_HOMEPAGE` and is never forwarded to the virtual pad |
| `overlay` | an overlay over a running app (Hub, Guide menu, a system dialog: ADR-033) | navigation keys; the virtual pads are held in neutral (sticks centred, nothing pressed) |
| `locked` | the picker or the PIN pad after Lock, or no profile signed in | navigation keys; **no virtual pad exists** |

Every transition releases on the side being left whatever is held (the `KeyBoard` count of T-337, extended to pad buttons and axes), then switches: no stuck button and no double input. The shell is the only source of the route: the compositor knows the focus first (`KeyRouter`), and the shell calls `Input1.SetRoute(route, instance, app_id, profile)` on every change (`app_id`: the Flatpak id of the app in front, which lets the service pick a game or platform profile, RUY-43; `instance` stays opaque), exactly as it reports presence to `Session1` today. The service trusts the shell's argument (the bus policy lets only `ruya-shell` and root call it, like `Session1.Launch`), refuses profiles that are not profile accounts, and **falls back to `locked` when the caller that set the route leaves the bus** (`NameOwnerChanged`), so a dead shell never leaves a game owning the pads.

**As built (RUY-3, `routing.rs`).** The service starts in `shell` with no profile. Virtual pads (`Ruya Xbox 360 Pad`, `045e:028e` version `0x0114`, the 11 xpad keys with `BTN_MODE` declared so that SDL's "Xbox 360 Controller" mapping applies, sticks, 0..255 triggers, the hat, `FF_RUMBLE` when the physical pad has it) exist only while the route is `app`, and stay, held in neutral once, for `overlay` with the same instance and profile; `shell`, `locked`, an `overlay` with another or no instance (a frozen app) and an `app` with another instance or profile destroy them. Entering `app`, every navigation key but Guide is released, and a button or axis already held (a quarter of its range or more) is not forwarded until it is let go, so the press that closed an overlay never reaches the game. Pads are numbered `pad1`, `pad2`, ... in connection order (the lowest free number); a pad connected while an app is in front gets its virtual pad at once. Rumble: the app's `FF_RUMBLE` uploads, plays and erases go to the physical pad while the route is `app`; the overlay stops what plays, and a destroyed pad's effects are erased. `SetRoute` answers `invalid` for an unknown route, an `app` without instance or app id, an `overlay` whose instance and app id are not both set or both empty, a `shell` or `locked` with an instance and a `locked` with a profile, and `unknown-profile` for a profile that is not an account `ruya-profiles` made (`ruya-<id>`, a regular uid, home `/var/home/ruya-<id>`, comment "RuyaOS profile").

**The shell's side, as built (RUY-409, `shell/qml/InputRoute.qml`, `shell/src/input/Input.*`).** `InputRoute` works the route out from what `Shell.qml` already knows and sends it on every change, coalesced to one call per event-loop turn: **`locked`** (profile `""`) while nobody is signed in (the picker, its PIN pad, after Lock and between the two halves of a switch, before the first sign-in); **`shell`** with the profile at Home, on a page, with the Hub over Home, with the apps sent behind Home, and for a window whose Session1 instance the shell does not know (Input1 needs the instance and the app id for `app`); **`overlay`** while the Hub, the "Keep this resolution?" dialog or the screen saver covers the app in front, with the app's instance and app id while it runs (its pads held) and with `""` once it is frozen (the Hub's pause: its pads go); **`app`** when the focused window's app (`instanceOfWindow`, the same record the Hub shows) is in front and not frozen. Closing the Hub over a frozen game keeps `overlay` with `""` until Session1 reports the Thaw, then sends `app`, so the service makes the fresh pads after the Thaw. The facade (`Input`) does not send the route it last asked for again unless that call failed or was refused, logs a failed or refused call (`ruya-shell: Input1 SetRoute <route> answered <status>`), never waits on it, and sends the newest route with the next change; a `QDBusServiceWatcher` on `org.ruyaos.Input1` sends the current route again whenever the name gets a new owner (a restarted service is back in `shell`). Guide needs nothing from the shell's route: the service always sends it as `KEY_HOMEPAGE` and `KeyRouter` takes it from the app. Tests: `tst_input_route.qml` on the mock (which checks the arguments by the service's rules and models the pads); in the VM `scripts/vm-input-check.sh shell`.

### 5.2 Sign-in, switch, lock, run end, Quick Resume
- **Who tells whom.** The shell, through `SetRoute`: it already learns sign-in, switch and lock from `Profiles1` (`SwitchTo`, `Lock`, `ActiveProfile`) and freezing from `Session1`. No new call from `ruya-profiles` or `ruya-session` to the input service and no new bus-policy line on their interfaces; the one new policy is `org.ruyaos.Input1`'s own (owner `ruya-input`; `ruya-shell` and root may call; `ruya-link` nothing until ADR-029's allow-list names a method).
- **An already open descriptor is not closed by removing an ACL** (Linux checks access at `open`). So at **lock**, **profile switch**, **run end** and **Freeze** the service **destroys** the profile's virtual devices (`UI_DEV_DESTROY`: the app reads `ENODEV`, SDL reports "unplugged", seen on the Dell) and creates new ones for the next owner. Quick Resume: on `Thaw` the service creates fresh pads for the app's profile; SDL's hot-plug picks them up; nothing depends on node or instance ids staying the same (requirements §14).
- **Overlay over a frozen game**: no pad exists for the frozen app, so nothing can leak into it.

### 5.3 Ownership modes *(planned, T-371)*
`managed` (default; the routing above), `passthrough` (the running app's user gets an ACL on the physical event nodes for that run; the service applies no mapping and creates no virtual pad, keeps reading the pad for Guide and the shortcuts, and grabs it outside the route `app`, below), `steam` (as passthrough, plus the pad's hidraw nodes; Steam Input does the rest; we never edit Steam's files), `semantic` (native Ruya apps receive actions through `Platform1`, T-374). The mode is a per-app setting stored by the service; switching mode takes effect at the next launch.

**Leaks in `passthrough` and `steam` (RUY-2 review).** The app then holds descriptors on physical nodes that can be neither destroyed nor revoked (§5.2). Rules, built and tested by T-371:
- **evdev:** in every route but `app` (overlay, Hub, PIN pad, picker, a frozen app), the service holds `EVIOCGRAB` on those pads' event nodes, so the app's descriptors receive nothing, also not as a backlog after a Thaw; it releases the grab when the route returns to `app` for that app. The service reads the grabbed node itself, so navigation keeps working.
- **hidraw** cannot be grabbed: a reader keeps receiving reports (and a frozen reader finds them buffered after Thaw). So hidraw is granted in `steam` mode only, never in `passthrough`, and while an app holds a pad's hidraw that pad **enters no PIN**: the PIN pad takes digits from the keyboard and from other pads, and shows "Close <app> to use this controller here" for that pad. Acceptance test (T-371): no report from a grabbed node reaches the app's descriptor during an overlay or after a Thaw, and the PIN pad refuses a hidraw-held pad.
- Steam Input creates its own uinput pads: `steam` mode needs `/dev/uinput` for the profile user for that run, which breaks §3.1's "only root and `ruya-input` create input devices". T-371 decides how (check the creating process of a `ruya-input/` node, not only its phys prefix, or keep Steam's pads outside the prefix); the same question applies to T-412 (phone) and T-418 (development pad).

### 5.4 Grabs
In `managed` the service never grabs a pad: apps cannot open physical nodes (no ACL), so there is nothing to hide. It grabs (`EVIOCGRAB`, proven non-root) only in the cases of §5.3.

## 6. Bluetooth pairing as an attack surface *(built, RUY-411; T-397 open)*
- Only bonded devices connect: BlueZ `ClassicBondedOnly=true` (the BlueZ default; the image must not change it), and HID goes through the kernel (`UserspaceHID=false`, T-375). `scripts/vm-devices-check.sh bluetooth` asserts both from the image's config files: no `ClassicBondedOnly=false` in `/etc/bluetooth/*.conf`, `UserspaceHID=false` in `input.conf` (RUY-411).
- Pairing is possible only while the shell's pairing screen is open (the pairable timeout, T-299), and the screen shows the new device's name and **class**; a device that announces itself as a keyboard needs a second confirmation ("This is a keyboard. Pair it?", with its name; Cancel has focus, Back cancels), because a keyboard can type anywhere the shell can. The service tells it in `Devices1.Bluetooth.ListDevices` as `keyboard` (Class of Device major Peripheral with the keyboard bit, which a keyboard/pointer combo has too; a LE device without a class by its HID keyboard appearance; BlueZ's `Icon` `input-keyboard`). **The service is the gate (RUY-422):** `Pair(id, keyboard_confirmed)` pairs, trusts and connects a device with the `keyboard` flag only when the shell passes `true` (its Accept on that question); otherwise it answers `not-confirmed`, touches nothing and logs the refusal (`refused to pair <address>: it announces a keyboard and the shell did not confirm it`), also for a keyboard that is paired already. **Connect is gated too (RUY-444):** `Connect` of a bonded `keyboard` device that is not `trusted` (trusted = confirmed through Pair) answers `not-confirmed` and logs `refused to connect <address>`; the shell then asks the same question and, on Accept, sends Pair with the confirmation (which trusts and connects). A manual Pair holds the adapter Pairable for up to 20 s; any other device that bonds in that time is removed again (`sweep`) like an unsolicited bond in the controller window. The flag is ignored for every other device. Pads, headsets and mice pair as before. **The controller pairing window never pairs a keyboard** (RUY-411: the agent and the sweep treat a keyboard-class device as a stranger, refuse it and remove it if it bonded); a keyboard pairs only from Settings > Bluetooth, also when it is paired again after Forget. If the device leaves the list while the confirmation is open, the confirmation closes. The class is told by the remote device, so this is a speed bump for the user, not a defence against a spoofing device. The guided controller screen lists controllers only and is unchanged; the confirmation is on Settings > Bluetooth's device rows.
- **What a new pad may do before a profile owns it** (ADR-017, ADR-027): navigate the profile picker and the "Who's playing?" dialog; inside a session it drives nothing until it is assigned (T-397 decides takeover rules). It never reaches a game as anything but a player slot of the signed-in profile. **Until T-264 and T-397** every connected pad counts as the signed-in profile's (today's behaviour), and RUY-3 gives each one a virtual pad for that profile; the ownership rules of §11.3 narrow that.

## 7. Profiles *(built: the global profile, RUY-42 / T-369, and its pages, RUY-465; game and platform T-370)*
> **Owner decisions, 2026-11-13 (lead-16; RUY-43's comments):** (1) no online sharing or community catalogue before the first release, profiles move by USB only; (2) no shipped per-game defaults for now; (3) macros and turbo deferred, off for imported files by default; (4) a guest gets its own global profile plus player 1's profile for the game in front; (5) a player may hold several device profiles, chosen by `match` (device over family over all); (6) the platform level stays in the service, nearly hidden in the shell. Known gaps against the levels below (scope fall-through vs `inherits`, a `match` miss, whose book, `game_id` on the route, portable export) are listed on RUY-43 and are settled in this section by RUY-490 before T-370 is built.
- **Format**: JSON, `schema_version: 1`, described by [`schemas/input-profile-v1.json`](schemas/input-profile-v1.json); the service validates every profile on load, save and import, refuses unknown fields and reports errors as `path: message` lines. The requirements' example (§9.3) is valid. No scripts: macros are data.
- **Precedence**: game → platform → global → the built-in default; a profile names its parent in `inherits` and lists only what differs. Resolution walks at most 8 levels and refuses cycles. Per controller: a profile may be limited to a family (`match.family`) or one stable id (`match.device`).
- **Limits**: 256 mappings per list (the top level and each layer), 8 layers, 32 macro steps, a macro step never targets a macro (no recursion; a service rule), `press`/`release`/`tap` steps need a `target` and `wait` a `ms` (service rules), 10 s total macro duration, delays ≥ 10 ms, turbo ≤ 30 Hz, a chord of at most 4 inputs, names ≤ 64 characters, 64 KiB per file. Imported profiles are untrusted data (requirements §15): validated, never executed.
- **What a profile changes**: only what the **virtual devices** emit in the route `app` (the game's view). The shell's navigation is never remapped by a profile: it follows the family and the Confirm row (§11.2). A "Nintendo layout" is a built-in preset profile (south ↔ east, west ↔ north) for games, not a navigation setting.
- **Stick maths** (per stick, on the vector, so the dead zone is round, not square): magnitude `r` in 0..1. Then `r' = clamp((r − inner) / (1 − inner − outer), 0, 1)`. Then the curve `c`: Linear `r'`, Precise `r'²`, Aggressive `√r'`. Then `out = 0` if `r' = 0`, else `anti + (1 − anti) · c`, times `sensitivity`, clamped to 1. The direction is kept, and inversion applies per axis afterwards. Triggers use `trigger_threshold` as their inner dead zone. Smoothing is off unless set (an exponential moving average with the factor `smoothing`). The defaults are inner 0.08, outer 0.02, anti 0, sensitivity 1, Linear.
- **Deleting a parent**: its children are re-parented to its own parent and keep their overrides. A built-in profile cannot be deleted (`not-allowed`).
- **Game and platform keys**: `game_id` is the Library's stable game id (ADR-028; for a Flatpak game today its app id); `platform_id` is the launcher's app id (Heroic, RPCS3, Steam). The service learns the app in front from `SetRoute`'s `app_id`.
- **Storage**: per console profile, by the service, under `/var/lib/ruya-input/profiles/<profile id>/` (the unit's `StateDirectory`, owned by `ruya-input`, 0700; profile users cannot read it).
- **Export and import** are JSON text over `Input1` (`GetProfile`; `ValidateProfile` then `SaveProfile`). The shell writes the file to, and reads it from, a removable drive through the existing removable-volume path of `Devices1.Storage` (as `SaveReport` does: no symlinks followed, never as root into a user-controlled directory, a size cap of 64 KiB before parsing). The input service never touches removable media.

**As built (RUY-42).** *Model and validation* (`services/ruya-inputd/src/profile.rs`): a typed model of the whole schema (layers, chords and macros included), checked keyword for keyword with the schema and, on top, the rules above plus: a `button` target names a §4.2 button and an `axis` target an axis; a stick's `inner_deadzone + outer_deadzone` is below 1; a profile does not inherit from itself; names and descriptions have no control character and no bidirectional override or isolate (U+202A..U+202E, U+2066..U+2069). The 64 KiB cap is checked before the text is parsed; serde_json's nesting limit refuses deep nesting. `tests/profile_schema.rs` runs every fixture (the §9.3 example, a full profile, the broken and hostile files) through the schema and the typed model: they agree, and the service's extra rules are fixtures the schema passes and the service refuses. *Built-ins* (`book.rs`): `default` (every input to itself, the stick defaults) and `nintendo` (south ↔ east, west ↔ north, inherits `default`); a profile without `inherits` inherits `default`. A chain walks at most 8 `inherits` links (the one to `default` counts); a save that would loop or go deeper for the profile or for one that inherits from it is `not-allowed`, a missing parent `invalid`; at most 64 stored profiles per console profile. *Inheritance* merges parent first: a child's mapping replaces the parent's for the same `from`, a child's stick setting the parent's field by field. *Storage*: `<id>.json` (the service's own writing: keys sorted, whole numbers without a fraction) and `_assignments.json` (`{"global": "<id>"}`; `_` cannot start an id) in `/var/lib/ruya-input/profiles/<profile>/`, 0700 / 0600, written under a temporary name and renamed; every file is validated on load, and one that fails, whose name is not its id or that claims a built-in is left on disk, journalled (`profile file <profile>/<name> refused: ...`) and not used; a link is never followed. *What applies* (`engine.rs`, `routing.rs`): a virtual pad shows the console profile's global profile when its own `match` fits the pad (family, stable id), else `default`; the engine runs on every input batch in `app` after the held-at-entry mask (a batch is one evdev `SYN_REPORT` frame: `Normalizer::frames` splits what one read of the node returns, so a release and a press of one button in two frames both reach the virtual pad; RUY-493), and a save, delete or assignment for the owner reaches its pads at once (a held button is released and its new target pressed). Applied in v1: a button or axis of the 360 pad to a button, an axis or `none`, with `invert`, `scale` (axis) and `threshold` (axis to button, default 0.5, above 0), mode absent or `press`; several sources on one output: a button is held while any is, an axis takes the largest magnitude. Stored, validated, not applied yet (the input keeps its default): keys, mouse, layers, chords, macros, other modes, raw, motion and paddle inputs, `output`, `gyro_enabled`, `rumble_*` (T-372, T-373), and `smoothing` (it needs a tick while the stick rests; inbox). Guide never reaches a virtual pad. *Contract*: the profile members of `Input1` and `ProfilesChanged`, with the summary keys the pages need (`assigned`, `layout`, `remapped`, `left_stick_changed`, `right_stick_changed`, `changed`, `match_*`); `AssignProfile` takes the global scope only (platform and game answer `invalid` until T-370). *Removable media* (`ruya-devices`, `volume_files.rs`): `Devices1.Storage.ListFiles(id, suffix)` (regular files at the top of a mounted removable volume, readdir and lstat only, newest first) and `ReadFile(id, name, max_bytes)` (a plain name, `O_NOFOLLOW | O_NONBLOCK`, a regular file, its size compared with `max_bytes` before reading). The shell's `Input.exportProfile` writes `RuyaOS-controls-<profile>-<yyyy-mm-dd>.json` with `SaveReport` (its name rule; the design's `ruya-controls-...` name would have needed a new one), and `Input.importProfile` reads with a 64 KiB cap, validates, saves and, for a global profile, assigns it. Tests: the Rust tests of `profile.rs`, `engine.rs` (the formula as a table), `book.rs`, `routing.rs` and `volume_files.rs`; `tst_input_profiles.qml` (the client's table against the XML, the mock's calls and statuses, export and import); in the VM `scripts/vm-input-check.sh check` and `profiles`, `vm-devices-check.sh system` with a stick (lead run).

## 8. When the service fails *(restart built, RUY-3; emergency reader built, RUY-410)*
Chosen path: **both**, because each covers what the other cannot.
1. **Fast restart**: `RestartSec=100ms`, `StartLimitIntervalSec=0` (never give up), `WatchdogSec=5s` with `sd_notify` from the event loop (as built: `Type=notify`, `READY=1` once the navigation keyboard exists, `WATCHDOG=1` every 2.5 s from the loop that also takes the router lock). Target: navigation back within 0.5 s of a crash (today 2.2-2.4 s, §1).
2. **The compositor's emergency reader** *(built, RUY-410)*: when `org.ruyaos.Input1` has had no owner for 3 s (a crash loop, a failed start, a broken image, a masked unit), the compositor opens the physical pads itself (it keeps logind's ACL on them, §3) and maps D-pad, left stick, south, east, start and guide to the same keys as `ruya-inputd`'s Phase 0 table, until the name has an owner again. It never feeds a game. A journal line names both transitions.
   As built (`shell/src/input/`): `Input.serviceOwned` (the existing `QDBusServiceWatcher` of the Input1 client, plus one `NameHasOwner` at start) feeds `EmergencyReader`, which waits `graceMs` (3000) before it turns on and turns off the moment the name has an owner. `PadDevices` (Linux) finds the `/dev/input/event*` nodes that udev's database (`/run/udev/data/c<major>:<minor>`) tags `ID_INPUT_JOYSTICK=1`, opens those the shell may read (`O_RDONLY`, no grab, so a node it cannot open, such as a virtual pad, is skipped silently), rescans once a second for pads that appear during the outage and drops a pad whose read fails (a vanished pad). It never reads a node whose `EVIOCGPHYS` starts with `ruya-input/` (the service's own virtual devices), and after a `SYN_DROPPED` it discards events up to the next `SYN_REPORT`, reads the buttons and sticks again (`EVIOCGKEY`, `EVIOCGABS`) and feeds them as events, so what is no longer down is released. Closing the reader (`~PadDevices`) closes the nodes and tells no one. `PadMapper` is the pad's evdev table: the hat axes and `BTN_DPAD_*` and the left stick (`ABS_X/Y`, pressed at 60 % of the half range, released below 35 %, the pad's own range from `EVIOCGABS`) give Up/Down/Left/Right, `BTN_SOUTH` Return, `BTN_EAST` Escape, `BTN_START` Menu, `BTN_MODE` HomePage; a key two sources or two pads hold goes down once and up with the last, and a pad that vanishes (or the reader turning off) releases what it held. The shoulder buttons, the right stick and the triggers are not read, and a held direction does not repeat. The keys go to `KeyRouter.injectKey`, which sends them to the shell window like a keyboard's (so the idle clock, the screen saver's swallow and the focus rules apply) and, with an app focused, takes only the Guide key and drops the rest, so the reader never feeds an app. Journal: `ruya-shell: input fallback on` / `off`, and `ruya-shell: input fallback reads /dev/input/eventN` per pad.
The spike proved the restart path (§1). Tests: `tst_input_emergency.qml` (mapper incl. a state re-read, the 3 s rule with a faked watcher, two pads, the shell); `scripts/vm-input-check.sh fallback` (mask the unit, a uinput pad signs in at the picker; the Dell drill is the same on real pads).

## 9. Performance and instrumentation
The input path stays event-driven (one thread per source node, no polling). The service counts, per device, events in and out and the time from the kernel timestamp of the source event to the write of the output event (`CLOCK_MONOTONIC` on both sides), and logs `ruya-inputd: latency <device> n=<n> p50=<us> p99=<us> max=<us>` every 60 s while `RUYA_INPUT_TRACE=1`. Budget: added latency p99 ≤ 1 ms (measured today: p90 126 µs).

## 11. UI ownership, the family's buttons and glyphs (ADR-027; T-396 / RUY-5) *(planned, T-397..T-399)*

### 11.1 Actions (one vocabulary)
The shell, the hint bar, `Platform1` (T-374) and the development tools (T-418) name buttons by **action**, never by letter: `up down left right` (the D-pad or the left stick), `accept`, `back`, `options` (context menu), `view`, `guide`, `tabPrev` / `tabNext` (shoulders), `pagePrev` / `pageNext` (triggers: fast scroll), `done` (finish a text entry), `dpad` (any direction, for hints). The service turns pad events into these actions; today they reach the shell as the Phase 0 keys (`accept` = Enter, `back` = Esc, `options` = Menu, `guide` = HomePage, `tabPrev/Next` = PgUp/PgDn), which stay the keyboard's keys too.

### 11.2 The family's own confirm button
**Decided per event in the input service** (`ruya-inputd`, T-398), from the device's family (§4.1: the service's device table, T-261, then the driver, then `generic`); never in QML. Per family, by position:

| Action | Xbox / generic | PlayStation | Nintendo | Keyboard |
|---|---|---|---|---|
| `accept` | A (south) | Cross (south); Circle (east) with "Confirm button: right" | A (east) | Enter |
| `back` | B (east) | Circle (east); Cross with "right" | B (south) | Esc / Backspace |
| `options` | Menu | Options | + | M / context key |
| `view` | View | Create | − | Tab |
| `guide` | Guide | PS | Home | Super |
| `tabPrev` / `tabNext` | LB / RB | L1 / R1 | L / R | Q / E, PgUp / PgDn |
| `pagePrev` / `pageNext` | LT / RT | L2 / R2 | ZL / ZR | Home / End |

The **Confirm button** row lives in **Settings > Controllers** (the one Settings home for controllers, with T-368's list): "As on the controller" (default) / "Bottom" / "Right", per console profile, stored by the service (`Input1.SetConfirmButton`). It swaps `accept` and `back` only; a game never sees it (games get positional buttons on the virtual pad).

**As built (RUY-40).** `mapping.rs`: `Confirm` (`family` | `south` | `east`) and the pure `nav_key(family, mode, button)`: the button that confirms is south for every family under `south`, east under `east`, and under `family` east for `nintendo` and south for every other family, an unknown one included (the table above, with Phase 0's keys as the actions); the other of south and east goes back, and no other button depends on the setting. The family is the pad's `PadInfo::family` from `identity.rs::family` (§4.1: vendor, then driver, else `generic`); `Router::input` hands it to `mapper_events` with the signed-in profile's mode on every event (that function is the one seam of the family; `ActiveInputChanged` reports the same value). A `Mapper` remembers, per button, the key its press emitted and releases that one, so a change of the setting or of the profile while a button is held leaves no key down; a pad that vanishes mid-press releases it as before. The mode is stored per console profile in `<StateDirectory>/profiles/<profile>/_settings.json` (`{"confirm_button": "east"}`, next to the profiles; an unreadable file or an unknown mode is journaled and means `family`). The virtual pads and RUY-42's engine never see it. `Input1.SetConfirmButton(profile, mode)` answers `ok`, `invalid`, `unknown-profile` or `failed`; the `ConfirmButton` property is the signed-in (route's) profile's mode and changes with `PropertiesChanged` on a set for that profile and on a profile switch. `ActiveInputChanged(device_id, family)` is sent when a button press comes from another pad than the last announced one (today every pad counts; owner pads come with T-264/T-397). The shell's row and its note are in `02-shell.md` §1.2.

**Planned (controller menus UX, design 2026-11-13, RUY-500; not built).** The row is renamed **Confirm in menus** and sits under a "Buttons" label next to a new **Button layout in games** row (the §7 Nintendo layout, the same stored value as Controls in games), each with a one-sentence note on the active pad: what confirms and goes back in menus, and which of its buttons games see as A and B ("..., unlike menus." when the two differ). Nothing changes here in the service: the Confirm setting still swaps `accept` and `back` only, and games still get positional buttons by default. **Open for the owner:** whether a Nintendo-family pad should get the Nintendo layout in games by default (a built-in family default in the platform level) rather than positions; the design keeps positions and asks once after pairing (RUY-503). Emulators of Nintendo consoles expect positions, so a family default may later want a per-platform exception (T-370).

### 11.3 Who drives the UI

> **Owner amendment, 2026-11-12 (ADR-017 amendment in 00):** a controller that connects without a player asks "Who's playing?" **when it connects**, and the app in front is paused while the prompt is open. A profile has **one** controller; picking a profile that has one moves it to the new pad. Every player is **signed in** (PIN if set). Guests can be picked several times and are wiped when they leave. The table below still describes the older rule (a toast on press, the prompt on Guide). It is rewritten when RUY-121, RUY-122 and RUY-38 are replanned.
| State | Pads that navigate the shell | Another pad's press | Guide on another pad |
|---|---|---|---|
| Picker, PIN pad, "Who's playing?" dialog, first boot | any pad, the keyboard | (it navigates) | opens the Guide menu as usual |
| Signed in | the **owner pads** of the active profile and the keyboard | nothing in the UI; the first press of each foreign pad per session shows one toast: "This controller isn't <profile>'s. Press Guide to switch or join." | a pad with a default owner (T-267): "Switch to <its profile>?"; an unknown pad: "Who's playing?" (ADR-017) |
| Every owner pad gone (disconnected or battery dead) | the keyboard | "Use this controller for <profile>?": Accept makes it an owner pad; **a PIN-protected profile asks its PIN first**; no idle timeout ever starts a takeover | as the row above |
| App in front | owner pads drive the app (slot 1, ADR-017); other pads reach the app only as assigned player slots; unassigned pads nothing | — | an owner pad opens the Hub; an assigned non-owner player's Guide opens the Hub without Settings and Power (ADR-017 point 3); an unassigned pad: "Who's playing?" |

**Owner pads** are the active profile's pads: with ADR-017's registry (T-264) its assigned slots; before it, the pad that sent the input that signed the profile in, plus any pad that took over or was assigned. The service keeps the set (it sees which pad sent an event; the keys the shell receives carry no source), publishes it in the device record (`profile`), turns only owner-pad events into navigation keys while the route is `shell` or `overlay`, and reports a foreign pad's press as `ForeignInput` for the toast and the prompts; the shell answers with `AssignPad`. Lock clears the set.

### 11.4 Glyphs follow the active input
- **Active input** = the device that sent the last **press** among the owner pads and the keyboard; it changes on the first press of another device, never on connect, a battery report, stick or trigger noise below the navigation threshold, or mouse motion (no flicker). The service sends `ActiveInputChanged(device_id, family)`; the shell tells the keyboard apart by the event's source device (not "RuyaOS Navigation").
- **Glyph of an action** = the label of the button that performs it **after** the Confirm setting (with "Right" on a PlayStation pad, `accept` shows Circle). One set per family, all our own drawings (no vendor artwork; the T-199 question stays open): Xbox letters, PlayStation shapes, Nintendo letters, keyboard key caps, and a **generic** set of position diamonds (four dots, the pressed one filled) for unknown pads. Guide is one home glyph for every pad. Drawing and sizes: `04` §3.7.
