# RuyaOS — `.play` Packages (self-contained games and apps)

Status: **Draft v1, design only, nothing is built; reviewed 2026-11-10: read §18 first, it corrects §6, §7, §9 and §11** · Parent: [00-overview](00-overview.md) · Decision: ADR-014 (*Accepted 2026-11-06, conditional on the T-229 spike*; work parked by the owner) · Epic: [T-228](../tasks/T-228-epic-play-packages.md)

A `.play` package is one folder or one `.play.zip` file that holds a game or app **and everything it needs to run on RuyaOS**: the program, a Wine or Proton build or an emulator (or a pointer to the one the OS provides), artwork and video for the shell, metadata, a permission request and a signature. A developer builds it once; a player copies it to a USB stick or downloads it, and it appears in the library with its art. Think of a macOS `.app` in a `.dmg`, with a signature and a sandbox.

This document is the format, the install and run model, the security model and the update model. The build order is in the epic. Where a statement depends on something that has to be proven on Linux first, it says so and names the spike (**T-229**); the format itself does not depend on the answer.

## 0. Principles

1. **A package is data, never code that runs at install.** Installing a package runs nothing from it. No scripts, no hooks, no "installer". The only code that ever runs from a package runs at launch, inside the sandbox, as the player's profile user.
2. **Everything runs in a Flatpak sandbox** (ADR-005, security invariant "third-party apps run only in Flatpak sandboxes"). A `.play` is a *container for a Flatpak app plus art and policy*, not a new runtime and not a new sandbox. The sandbox, not Wine, not the emulator, not the package, is the security boundary.
3. **Nothing is trusted until verified, and nothing is verified twice by different rules.** One verifier (`ruya-play`), one set of parsing rules, used by the shell's "install from USB" screen, the update path, the Store and the developer tool.
4. **Permissions are a closed vocabulary**, requested statically, shown in plain words before install, and capped by how far the package is trusted. A package cannot ask for something the vocabulary does not name.
5. **The player decides, the developer proposes.** Which runner to use, whether to check for updates, which permissions to grant (down, never up): the package's manifest is a request and a default, never a command.
6. **Small packages are the developer's choice, not a rule.** A package can ship its own Wine (works anywhere, big) or point at the OS's (small, gets OS fixes), or accept either.
7. **Honest wording.** A signature proves *the same key signed this*, not that the developer is who they say. The UI says "Signed by key 3f9a… (first time seen)", never "verified publisher", unless the Official store signed it.

### Non-goals (v1)
- A new runtime, a new sandbox, a package manager, or a replacement for Flatpak. Flatpak and the Flathub route stay the main way to get apps (ADR-005).
- Running a package without installing it (a "play from USB" mode). Installs are fast enough, and verified content must be immutable.
- DRM, licence keys, online activation, anti-cheat. A package can include a game that needs them; we do not provide them.
- Shipping firmware, BIOS files, game discs or ROMs ourselves (03 §5). See §12 for what a *developer* may put in a package.
- Delta updates and a dedicated package store protocol (designed for in §11, built later).

## 1. Terms

| Term | Meaning |
|---|---|
| **Package** | The `.play` folder or `.play.zip` file. |
| **Payload** | The game or app files (`payload/`). |
| **Component** | Something the payload runs on: a Wine build, a Proton build, an emulator, a game engine, a library set (`components[]`). |
| **Runner** | A component that executes the payload (`wine`, `proton`, `emulator`, `engine`) or the payload itself (`native`). |
| **System runner** | A runner the OS provides and updates (a Flatpak extension of the Play platform, §6.4). |
| **Bundled** | Shipped inside the package. |
| **Trust tier** | `official` (countersigned by the RuyaOS store key), `developer` (signed by the developer's key), `unverified` (unsigned, admin's developer mode only). §9.2. |
| **Installed id** | `play.<id>`: the Flatpak id the package is installed under (§7.1). |
| **Importer** | The `ruya-play` service plus its unprivileged unpack helper (§7.3). |

## 2. Package forms

| Form | Name | Notes |
|---|---|---|
| Folder | `Star Hopper.play/` | Easiest for developers and for USB. The folder's own name is display-only; identity is `id` in `play.json`. |
| Archive | `Star-Hopper.play.zip` | One file. ZIP (with ZIP64), entries stored or deflated. For games, "stored" is recommended: payloads are already compressed and the importer reads faster. |
| Later | `.play.tar.zst`, delta feeds | Not v1. The manifest and file table are the same, only the reader changes. |

- The MIME type is `application/x-ruya-play` (folder: `inode/directory` with a `play.json`); the shell recognises a package by `play.json` at its root (after unwrapping a single top-level folder in a zip), not by the extension alone.
- **Removable media:** a package on a USB drive is listed by an explicit "Install from USB" action; nothing is opened, previewed from raw files, or run just because a drive appeared (security invariant).
- **Symlinks, modes and special files are data, not filesystem objects.** exFAT and FAT USB sticks have no symlinks or Unix modes, and symlinks are the classic escape in archives. So a package contains **only regular files and directories**; links and the executable bit are recorded in `play.files` (§4.2) and recreated by the importer. A real symlink, hard link, device node, FIFO or socket in a folder or a zip makes the package invalid.

## 3. Layout

```
Star Hopper.play/
  play.json            manifest: metadata, run, components, permissions, data, update (required, <= 1 MiB)
  play.files           file table, JSON Lines (required)
  play.sig             developer signature, §9.2 (required for official and developer tiers)
  store.sig            countersignature by the RuyaOS store (only on store builds)
  art/                 icon, logo, hero, cover, screenshots, trailer (§5)
  payload/             the game or app, any layout
  components/          bundled runners: components/wine/, components/rpcs3/ ... (optional)
  licences/            licence texts and written source offers for bundled third-party code
  README.txt           optional, for people opening the folder on a PC
```

Everything under the root except `play.json`, `play.files`, `play.sig`, `store.sig` must be listed in `play.files`. A file that exists but is not listed, or listed but missing or different, makes the package invalid.

## 4. Manifest and file table

### 4.1 `play.json`

UTF-8 JSON, at most 1 MiB, nesting depth at most 12. Unknown keys are ignored (so a newer developer tool does not break an older console) **except** keys under `permissions`, `run` and `components`, where an unknown key is an error (a permission the console does not understand must not be silently dropped). A key named twice in one object (keys compared after `\uXXXX` escapes are decoded), at any depth, is refused with `json.duplicate_key`: a second reader of the same file, such as the launcher, could otherwise see another value than the one that was checked. `format` is the major version; a console that does not know it refuses the package with "needs a newer RuyaOS" and reports nothing else (§15).

**Field rules** (limits are initial values, tuned in T-230 and kept in one schema file, `api/play/play.schema.json`):

| Field | Rule |
|---|---|
| `id` | Reverse-DNS, the Flatpak id grammar (letters, digits, `_`, `-`, at least three elements, none empty, none starting with a digit, at most 120 bytes), lower-case recommended. The app is installed as `play.<id>`, which must itself be a valid Flatpak id: `-` only in the **last** element and at most 255 bytes (`id.flatpak_invalid`). Must not start with `org.ruyaos.` or `play.` unless it is ours; reserved names refused. Identity of the app for ever: a changed id is a different app. |
| `name`, `summary`, `description` | Localized maps (`"en"` required, other BCP-47 tags optional, at most 30 languages). `name` <= 60 chars, `summary` <= 140, `description` <= 4000, **plain text** with `\n\n` paragraph breaks (no markup, no HTML, no links inline). Control characters (a line break only in `description`), bidi overrides and zero-width characters are **refused** (`text.control`, `text.bidi`, `text.zero_width`), not silently stripped: a signed manifest is shown exactly as written. Text that looks like markup (`<b>`, `</`, `<!`) or contains `://` is refused (`text.markup`, `text.link`). A name that looks like a system name (Settings, RuyaOS, Store, Home, Guide, "Update") is refused unless the Official tier. |
| `version`, `build` | `version` is display text (<= 32 chars); `build` is a positive integer that **only increases** and is what update ordering uses. |
| `developer`, `publisher` | `name` <= 80 chars, optional `url` (https). Self-asserted; shown with the signature state, never as proof. |
| `genres` | From a closed vocabulary (action, adventure, arcade, platformer, puzzle, racing, role-playing, shooter, simulation, sports, strategy, fighting, music, party, family, sandbox, horror, visual-novel, retro, utility, other; list kept in the schema) at most 4; the first maps to the shell's category tint (04). `tags` are free text, <= 12, <= 24 chars. |
| `controller` | `full` \| `partial` \| `none`, same meaning as `x-ruya-controller` (03 §4.1); the Store's gamepad filter reads it. |
| `age_rating` | OARS 1.1 content attributes (as in AppStream); the shell derives the label, parental controls (T-211) read it. Missing = "Not rated" (never "All ages"). |
| `licence` | SPDX id or `LicenseRef-proprietary` for the package contents; `terms_url` https. Bundled third-party code declares its own (see components). |
| `links` | At most 12; `kind` from `homepage`, `support`, `manual`, `source`, `community`, `store`, `privacy`, `changelog`, `donate`, `other`; `https` URLs only (no `javascript:`, `file:`, `data:`, `http:`). The shell shows them as text and a QR code; **it never opens them automatically** (there is no browser in the base image). |
| `requirements` | Facts for the "can this run here" check and the install-space check: `arch` (`x86_64` only in v1), `min_ram_mb`, `gpu_api` (`vulkan`, `opengl`). The installed size is **computed** from the file table (the sum of the file sizes, `Package::installed_bytes`), never declared; a manifest that still has `installed_mb` is accepted and the key ignored (`requirements` is not a strict object). |
| `run`, `components`, `permissions`, `data`, `update` | §6 to §11. |

### 4.2 `play.files` (the file table)

JSON Lines, UTF-8, one object per line, sorted by `p` (bytewise), no blank lines, at most 64 MiB. It is the single list of everything in the package and the thing the signature protects.

```
{"p":"payload/StarHopper.exe","t":"f","s":18350080,"h":"<sha256 hex>","x":1}
{"p":"payload/data/level1.pak","t":"f","s":512000000,"h":"<sha256 hex>"}
{"p":"components/wine/lib/libwine.so","t":"l","to":"libwine.so.1"}
{"p":"payload/saves","t":"d"}
```

- `t`: `f` file (size `s`, SHA-256 `h` as 64 lower-case hex digits, optional `x:1` = executable), `l` symlink, `d` empty directory. Everything else is invalid, and so is a key not listed here.
  - **Links** (`to` relative to the link's folder, resolved lexically): the link is inside a top-level folder (not at the root); the target stays inside the **same top-level folder** and exists in the table; nothing is stored *below* a link or a file. A link may point at another link: a chain may pass through **at most 8 links** (a bundled Wine's `libx.so -> libx.so.1 -> libx.so.1.2` is legal; `ruya-pack build` flattens what it can). A loop is invalid.
  - **A Wine prefix template** (`run.prefix.template`) never contains a folder named `dosdevices` (it has a colon and absolute links); the launcher creates it.
- **Reserved top-level names:** `.ref`, `launcher`, `runners` and `share` (the folder itself or anything below it) may not be listed (`table.reserved_top_level`; `ruya_play_format::table::RESERVED_TOP_LEVEL`): the console writes them into the installed app or mounts there (`launcher`, `runners`: ADR-038, RUY-900). A package of the `wine` or `proton` runner may also list nothing at or below `lib/i386-linux-gnu` (`run.lib_i386_reserved`; `limits::I386_LIB_DIR`), where the runtime's 32-bit libraries are mounted; a native package may. A nested `a/share` is legal.
- Paths: relative, `/` separators, NFC-normalised UTF-8, no empty, `.` or `..` components, no leading `/`, no `\`, no `:` in a component, no control characters, each component <= 255 bytes, the whole path <= 1024, **unique even when case is ignored** (exFAT and Wine games), no Windows reserved names (`CON`, `NUL`, ...) and no trailing dot or space. At most 200,000 entries.
- The importer sets file modes itself: 0644, or 0755 with `x:1`. No setuid/setgid/sticky, no file capabilities, no xattrs, ownership root (after commit), timestamps from the manifest's build time.

### 4.3 Folder versus zip, one rule set

The folder and the zip are read through the same verifier (the crate `services/ruya-play-format`, the only parser: the importer, `ruya-pack`, the service and the Store all use it). It lists entries (for a zip, the container rules below run here), then reads **one** file early: `play.json`, only when the listing shows it as a regular file of at most 1 MiB, through a bounded read (in a zip with its declared size and CRC enforced), and only for its `format` (§15: a newer major returns `format.too_new` alone). Then it applies §4.2's rules to the *names and kinds*, and opens nothing else before they pass; then it reads `play.files` and `play.json`, checks the table against the listing, and only then streams content while hashing. A package that fails an earlier step is not read further. A zip adds, as built (`zip.rs`, written for this format rather than taken from a general zip crate):

- no encrypted entries (flags, strong encryption, AES), only the methods stored and deflate, no split archives;
- no entry that is a symlink, a device or a FIFO (the Unix mode in the external attributes), a hard link (two directory entries for the same local header) or an NTFS reparse point;
- no duplicate names (also not `x` and `x/`);
- central directory only: the end record is the last 22 bytes (no archive comment), the directory ends where the end record (or the ZIP64 record) begins, every entry's local header agrees with the directory (name, flags, method, CRC and sizes), and the entries tile the file exactly from offset 0 up to the directory (no data in front, between or behind; an entry with a data descriptor may have one of the four legal descriptor lengths after it);
- declared sizes enforced while reading (the content has exactly the declared size and CRC);
- **expansion limit**: any entry over 1 MiB that expands more than 200:1 is refused. A single top-level folder around `play.json` is unwrapped (§2).

The total unpacked size is the sum of the table's file sizes (`Package::installed_bytes`); fitting it into free space (with 10 % to spare) is the importer's check (T-237, built in RUY-99, §7.3), made before the first byte is written.

### 4.5 Error codes

A check returns a list of problems `{ code, path, message }`. `code` is a stable dotted string (a code never changes meaning); `path` is a JSON pointer for `play.json` and the package path for files; `message` is English for developers (and for `ruya-pack` output); the shell shows its own translation chosen by `code`, never `message`. Text from the package that a problem repeats (a key, a value, an env name, a path) goes through one helper: control, bidi and zero-width characters become `\u{XXXX}` escapes and the text is cut to 80 characters (a whole `path` to 160, a `message` to 600), so a hostile name cannot reorder or flood what a developer reads (T-236). `tests/codes.rs` fails when a code is missing from this list or is asserted by no test.

## 5. Artwork and video

The art slots are the contract between a developer and the shell; the shell never shows a raw file from a package. The importer decodes every image in a sandboxed helper, checks dimensions and size, **strips metadata, converts to sRGB and re-encodes** to canonical WebP at the sizes the shell uses (§12), then the shell loads only those vetted files. A package whose art fails validation installs without it and says so (the generated tile of 03 §4.1 is used), unless `hero` or `icon` is *malformed* (a broken image is a refusal; a missing one is not).

| Slot | File | Spec | Used for |
|---|---|---|---|
| `icon` | PNG or WebP | **Square 1024x1024** (512 minimum), RGBA, full bleed. The shell applies the rounded-square mask itself, so do not pre-round; keep the subject in the centre 80 %. <= 2 MB. | Library list rows, Store, toasts, the system's "Running" list. **Required.** |
| `logo` | PNG or WebP | Transparent, at least 256 px high, at most 4:1 wide, <= 2 MB, light colours (it sits on the dark scrim). Per-language map allowed. | Home hero title (replaces the text title), detail page. Optional (the localized `name` is used as text). |
| `hero` | WebP, JPEG or PNG | **16:9** (+-1 %), recommended 3840x2160, at least 1920x1080, <= 8 MB. Keep the important content in the **right two thirds and the upper three quarters**: the shell puts its title block and a left scrim over the left third and its row of cards over the bottom (04 §5.1). | Home hero, the 16:9 art card, the launch splash, the blurred page backdrop. **Required for Home placement**; without it the tinted tile is used. |
| `cover` | WebP, JPEG or PNG | **2:3**, recommended 1200x1800, at least 600x900, <= 4 MB. | Library grid (Cover card, 04 §5 proposed). Falls back to a centre crop of the hero. |
| `screenshots[]` | WebP, JPEG or PNG | 1 to 20, **16:9**, at least 1280x720, <= 4 MB each, localized optional caption (<= 100 chars). | Detail page gallery. |
| `trailer` | WebM (VP9 or AV1 video, Opus audio) or MP4 (H.264, AAC); `poster` image | One, <= 120 s, <= 1080p60, <= 80 MB; poster 16:9. | Detail page. See the risk below. |
| `preview` | WebM or MP4, **no audio track** | One, <= 15 s, <= 720p30, <= 8 MB, loops. | Muted loop on the Home hero a second after focus (the console-style "live" hero). Optional. |

- No animated images (GIF, APNG, animated WebP), no SVG (a parser with a long CVE history, and it can embed scripts and external references), no EXIF (stripped), and colour profiles are not kept: a profile on the source is converted to sRGB and then dropped (a profile that cannot be read or is not an RGB profile is a refusal, `art.colour_profile`).
- **Video is the largest parsing surface in the package.** v1 rule: the importer validates the container and codecs with an allow-list in a sandboxed helper (no network, no files outside its input) and refuses anything else; the shell plays the vetted file with its normal media stack. Out-of-process playback is the later hardening step (open question Q5).
- **As built (`services/ruya-play-art`, RUY-94).** A library with no dependency on the format crate: `vet(&[(Slot, path)], out_dir)` returns one `Outcome` per slot (`Ok { files }`, `Missing`, `Invalid { code, message }`), the importer (`ruya-play`) maps it into its own problem list. It opens only the given input files and writes only into `out_dir` (files are written after every output of the slot was encoded; nothing for an invalid slot).
  - **Images.** Order of checks: regular file (no symlink) and size, magic bytes (a wrong extension is `art.magic_mismatch`; SVG `art.svg`; GIF or unknown `art.format_unsupported`; JPEG is refused for `icon` and `logo`), end marker of the container (a cut-off file is `art.corrupt`: the decoders are lenient with truncated JPEGs), header only (`art.animated` for APNG and animated WebP; `art.dimensions_too_large` over **8192 x 8192 or 64 Mi pixels**, so no decoder runs on a bomb; `art.too_small`; `art.aspect_ratio` at +-1 %, the logo at most 4:1), and only then the pixel decode. EXIF orientation is applied before the checks. Pixels are then converted to sRGB (profile read by the `image` decoder, applied with `moxcms`), resized with Lanczos3 (never upscaled: a smaller source keeps its width) and written as **lossless WebP** (VP8L, no metadata chunks). `icon` and `logo` keep alpha; the other slots are flattened onto black and written without alpha.
  - **Canonical files** (05 section 12 gives the sizes): `icon-512|256|128.webp`, `logo.webp` (height at most 512), `hero-2160.webp` (3840x2160 or the source size), `hero-1080.webp`, `card-540.webp`, `cover-900.webp`, `screenshot-N-1080.webp`, `screenshot-N-thumb.webp`, `trailer-poster-1080.webp`. Output is deterministic (same bytes on every run).
  - **Size ceilings** per file: icon and logo 2 MB, hero 8 MB, cover, screenshot and poster 4 MB (`art.file_too_large`); at most 20 screenshots (`art.too_many_screenshots`).
  - **Metadata chunks are bounded before the decoder sees them.** The PNG decoder inflates iCCP and compressed text chunks (and silently drops an iCCP over its own budget), the WebP decoder allocates a chunk's declared size before reading it. So a PNG is rebuilt from IHDR, PLTE, tRNS, eXIf (the orientation), IDAT and IEND only (every other chunk is dropped unread), its iCCP is inflated by us with a 2 MiB output ceiling (`art.icc_too_large`), and every WebP chunk must lie inside the file with an ICCP of at most 2 MiB. JPEG segments are at most 64 KiB each and bounded by the file.
  - **Aspect.** A source inside the +-1 % tolerance is centre-cropped to the exact ratio (the largest whole multiple of 16:9, 2:3 or 1:1 that fits, in place), then resized; it is never stretched.
  - **Files are opened once** (`O_NOFOLLOW` on Unix, `FILE_FLAG_OPEN_REPARSE_POINT` plus an attribute check on Windows), type and size are checked on the handle, and the read is capped at the limit plus one byte. A vetted video is copied from the same handle.
  - **Memory.** Worst case for the largest allowed image (64 Mi pixels): 16-bit RGBA decode 512 MiB + RGBA8 copy 256 MiB + resampler rows 270 MiB + outputs 190 MiB, under 1.25 GiB (`peak_decode_bytes`, asserted in a unit test; the pixel decode also runs with a 1 GiB allocation budget set at construction; it does not cover metadata chunks, which are bounded separately, see the previous point). An ordinary 8-bit image of that size peaks near 0.7 GiB. Computed, not measured. The helper process that calls the library (RUY-99) should run with a memory limit above this.
  - **Video** (`trailer`, `preview`): headers only, by two small hand-written readers (EBML for WebM, ISO-BMFF boxes for MP4; WebM reads the first MiB, MP4 reads `ftyp` and `moov` by seeking, `moov` at most 8 MiB). Allow-list: WebM with VP9 or AV1 and Opus, MP4 with H.264 (`avc1`, `avc3`) and AAC (`mp4a`); exactly one video track and at most one audio track, any other track refused; each MP4 track must have exactly one sample entry in its `stsd` (`video.sample_entries`); a WebM track with `ContentEncodings` (compressed or encrypted) is refused (`video.content_encoding`); a preview must have no audio. Limits: trailer <= 120 s, <= 1920x1080, <= 60 fps, <= 80 MB, <= 20 Mbit/s; preview <= 15 s, <= 1280x720, <= 30 fps, <= 8 MB, <= 6 Mbit/s. Frame rate is checked when the header declares it (WebM `DefaultDuration`, MP4 `stts`). A vetted file is copied unchanged as `<slot>.webm` or `<slot>.mp4` (the name comes from the container, never from the package). Residual risk (Q5): the headers are not the streams. A hostile bitstream still reaches the shell's media decoder; the audio object type inside `mp4a` is not checked; sizes and durations are the file's claims.
  - **Codes** (stable): `art.not_a_file`, `art.file_too_large`, `art.io`, `art.svg`, `art.magic_mismatch`, `art.format_unsupported`, `art.animated`, `art.corrupt`, `art.dimensions_too_large`, `art.too_small`, `art.aspect_ratio`, `art.colour_profile`, `art.too_many_screenshots`, `art.icc_too_large`; `video.not_a_file`, `video.io`, `video.file_too_large`, `video.container_not_allowed`, `video.header_invalid`, `video.no_video_track`, `video.codec_not_allowed`, `video.track_not_allowed`, `video.sample_entries`, `video.content_encoding`, `video.audio_not_allowed`, `video.no_duration`, `video.too_long`, `video.resolution_too_large`, `video.frame_rate_too_high`, `video.bitrate_too_high`.
  - **Libraries** (all pure Rust, `cargo deny` clean): `image` 0.25 with only `png`, `jpeg` and `webp` (MIT OR Apache-2.0; pulls `png`, `zune-jpeg`, `image-webp` for decode and the lossless encode), `moxcms` 0.8 for ICC to sRGB (BSD-3-Clause OR Apache-2.0). `miniz_oxide` 0.8 for the bounded iCCP inflate (MIT OR Zlib OR Apache-2.0), `libc` for `O_NOFOLLOW` and `O_NONBLOCK` (MIT OR Apache-2.0, Unix only). Lossless WebP is larger than lossy: measured from generated fixtures, a 3840x2160 hero (JPEG source with noise) gives 5.9 MB for `hero-2160`, 1.6 MB for `hero-1080` and 0.4 MB for `card-540`; smooth art is far smaller.
- The shell does not need to show every slot; slots a screen does not use are still validated at import so a package that works today does not break later.
- A `.play` made for a store carries **no ads, no price, no rating, no "buy now"** in its art or text: the store adds those from its own data.

## 6. Running things: components and runners

### 6.1 Runner kinds

| `run.runner` | Meaning | Payload is | Component |
|---|---|---|---|
| `native` | Linux x86-64 program | an ELF (or script) inside the package | none required; uses the Play platform's runtime libraries |
| `wine` | Windows program | `.exe` and data | `type: wine` |
| `proton` | Windows program through Proton, run directly (no umu, no Steam Linux Runtime, §6.4) | `.exe` and data | `type: proton` |
| `emulator` | A disc/ROM image run by an emulator | image(s), saves skeleton | `type: emulator` (an emulator build, e.g. PS3, PSP, GameCube) |
| `engine` | A game engine or interpreter that runs content (ScummVM, DOSBox, ...) | the game's content files | `type: engine` |

A package has **exactly one** `run`. (Several launch entries, "Game" and "Launcher", are v2.)

Wine is not the only system runner (ADR-025, spike RUY-91): **GE-Proton is the OS's preinstalled system runner** and the default for Windows games, and other Wine and Proton builds are Store runners chosen per game. For `source: system`, a `type: proton` component means the OS's `proton-ge` (§6.2); a bundled Proton is a separate family and is never replaced by it. Both run directly, without umu and the Steam Linux Runtime (§6.4).

### 6.2 Components and where they come from (`source`)

`components[].source` says where the runner comes from; this is how a developer picks "small and OS-provided", "self-contained" or "either":

| `source` | Behaviour | Needs |
|---|---|---|
| `bundled` | Only the shipped copy, always. Reproducible, size cost. | `bundled` block |
| `system` | Only the OS's runner of that `type` and at least `min`. If the OS has none, the installer offers to fetch it from the official store (§18 item 7) and refuses the install without network. | `min` |
| `prefer-system` | The OS's runner if it is present and at least `min`; otherwise the bundled copy. Smallest while safe. | `min` and `bundled` |
| `prefer-bundled` | The shipped copy, unless the player chooses the system one in the game's Compatibility setting. | `bundled` |
| `newest` | Whichever of bundled and system has the higher version; a tie goes to bundled. "Bundle my tested Wine, but use the OS's if it is newer and fixes more." | `min` and `bundled` |

- `tested` is the version the developer verified. It is shown on the Compatibility screen ("Tested with Wine 9.20; running with 10.2") and is not enforced. `max_major` (optional) is enforced: a system runner with a higher major version is skipped (a developer can fence off a known break), falling back to the bundled copy or failing with a clear message.
- Versions compare only within a runner **family** (`wine`, `proton`, `proton-ge`, one per emulator id). Each runner carries a `runner.json` (family, version, architecture, entry commands, capabilities), read as untrusted data like everything else. Different families never replace each other.
- **One function decides, in one place.** `ruya_play_format::resolve::resolve(components, system_runners, bundled_families, override) -> Resolution` is pure (no disk, no clock); `bundled_families` maps a component id to the family its bundled copy declares in its `runner.json` (missing: the type's own family, `wine`, `proton`, or the component id). The launcher (RUY-101) and `ruya-pack validate` call the same code, so the dry run shows what the console will do. **Which system runners count:** for `source: system` the OS's runner of the type: `wine` for `type: wine`, `proton-ge` and then `proton` for `type: proton` (the OS ships GE-Proton, ADR-025), the component's own `id` for an emulator or engine. For `prefer-system`, `newest` and `prefer-bundled` (and the player's System override) a system runner counts **only when its family equals the bundled copy's family**: a bundled Valve `proton` is never replaced by, or compared with, the system `proton-ge`, and the result is the bundled copy. A too-old (or too-new) runner of the family never falls back to another family. Versions compare as the numbers in the version text (`10.2` is above `9.20`; `GE-Proton10-9` is 10, 9); `max_major` compares the first number. Of one family the newest system runner counts; it is unusable below `min` or above `max_major`, and then `newest` and `prefer-system` fall back to the bundled copy (a note says it was the fence) while `system` fails with `resolve.system_too_old` or `resolve.system_too_new`. With no system runner of the family, `system` fails with `resolve.no_system_runner` (the installer offers to fetch one, §18 item 7).
- **The player's override** (`Override::Bundled` or `Override::System`) wins only if it can: a bundled choice needs a bundled copy, a system choice needs a usable system runner of the bundled copy's family; otherwise the package default runs and the result carries a note. **The System override never applies to `source: bundled`**, which is "only the shipped copy, always".
- **Per-game override (the player's choice).** Settings for a game (Options menu, "Compatibility") offer "Package default", "Bundled" (if it has one) and "System" (if it satisfies `min`), plus a "Try the bundled runner" safety net after a crash. The choice is stored per profile by `ruya-library` (T-385, §18 item 3), not in the app's own `config/` where the game could change it, and cannot widen permissions, since every runner runs in the same sandbox.
- **Why not always "system"?** Wine regressions are real: a game tested on 9.20 may break on 10.x. The developer decides how much to trust the OS's runner; the player can still choose.
- **Licensing duty of bundled third-party code.** A bundled component declares its SPDX `licence`; for copyleft code (Wine is LGPL-2.1, many emulators are GPL) it must include the licence text under `licences/` and a `source_url` (or the source itself). `ruya-pack validate` checks this and the Official review enforces it. RuyaOS only provides the tool; the developer is the distributor of what they bundle.

#### 6.2.1 `runner.json` (ADR-037, as built)

Every runner carries `runner.json` at the root of its folder: a bundled copy under `components/`, and (RUY-901) each runner the OS provides. `ruya_play_format::runner::parse_runner` is the one parser; `ruya-pack`, the importer and the launcher call it, and `api/play/runner.schema.json` states the shapes (`tests/runner_schema.rs` keeps it equal to the constants in `limits.rs`).

```json
{
  "format": 1,
  "family": "wine",
  "kind": "wine",
  "version": "9.20",
  "arch": "x86_64",
  "entry": { "wine": "bin/wine", "wineserver": "bin/wineserver" },
  "capabilities": ["multiarch", "dxvk"],
  "licence": "LGPL-2.1-or-later",
  "source_url": "https://dl.winehq.org/wine/source/"
}
```

- **The file.** One UTF-8 JSON object of at most 64 KiB (`runner.too_big`, `runner.not_utf8`, `runner.invalid_json`), no key named twice (`json.duplicate_key`), and inside a package a regular file (`runner.not_a_file`). Every key is one of the nine above (`runner.unknown_key`); a value of the wrong JSON type is `runner.type`, a missing required key `runner.missing_field`.
- **`format`** is checked first: the integer `1` (`1.0` is `runner.format_invalid`); `2` or more is `runner.format_too_new` and nothing else is checked; anything else is `runner.format_invalid`.
- **Required:** `family` `[a-z0-9][a-z0-9.-]{0,63}` (`runner.family_invalid`); `kind` `wine`, `proton`, `emulator` or `engine` (`runner.kind_invalid`), equal to the component's `type` (`runner.kind_mismatch`); `version` at most 32 letters, digits and `. _ + -` holding a number, so versions compare as in §6.2 (`runner.version_invalid`); `arch` `"x86_64"` (`runner.arch_invalid`).
- **`entry`**: wine `{"wine", "wineserver"}`, proton `{"proton"}`, exactly those keys; an emulator or engine has none (`run.command` names `${component:<id>}` itself). Each is a plain relative path under the path rules of §4.2 (`runner.entry_invalid`) and, in a package, a regular file of the copy's folder in `play.files`, not a link or a folder (`runner.entry_missing`, located in the file: `<path>/runner.json#/entry/<key>`).
- **Optional:** `capabilities` from the closed list `multiarch`, `dxvk`, `vkd3d`, `ntsync`, no repeats (`runner.capability_invalid`; informational in format 1), `licence` SPDX (`runner.licence_invalid`), `source_url` https (`runner.url_invalid`).
- **In a package.** `validate` reads the `runner.json` of each bundled copy after the table matched the package (through the same bounded reader as the metadata files, also with `verify_content` off). A copy **without** the file gets lead-29's defaults: the type's own family (`wine`, `proton`, the component id) and the entries above (`bin/wine` and `bin/wineserver`, `proton`). The default entries must be regular files of the copy just the same, since the launcher starts them (`runner.entry_missing`, located at the missing path, e.g. `components/wine/bin/wineserver`). A **present but invalid** file refuses the package (`invalid-package` at the importer), never the defaults. `Package::runners` holds the result per component id and `Package::bundled_families()` is what `resolve` takes, so `ruya-pack validate` and the console read the family the same way.
- **The prefix.** `runner::prefix_dir(kind, data)` is the one answer to where `${prefix}` is: wine `<data>/prefix`, proton `<data>/proton/pfx`, none for other kinds.
- **The runner hash** formula of §7.3 lives here as well (`runner::RunnerHasher`, fed one entry at a time in path order).

### 6.3 Launching

- `run.command` is an **argv array**, never a shell string. Placeholders (the only substitutions): `${payload}`, `${component:<id>}` (that component's root), `${data}` (`$XDG_DATA_HOME`), `${config}`, `${prefix}` (the Wine prefix), `${disc}` (the first disc image). Anything else is literal. An argument (or setup command) that starts with a placeholder has no `..` part (`run.argument_path`).
- `run.env` is a **deny list**, not an allow-list (native games need variables of their own, and a package can do nothing in its own sandbox that it could not do anyway): names match `[A-Z][A-Z0-9_]*` (at most 64 bytes, so `__GLX_*` and `__EGL_*` fail the grammar) and are none of the names the platform sets. The table (`limits.rs`, `ENV_DENY_EXACT` and `ENV_DENY_PREFIX`; refused with `env.reserved`):
  - exactly: `PATH`, `HOME`, `DISPLAY`, `XAUTHORITY`, `WINEPREFIX`, `WINESERVER`, `WINELOADER`, `WINEDLLPATH`, `WINEARCH` (it conflicts with `run.prefix.arch`), `TMPDIR`, `GCONV_PATH`, `LOCPATH`, `NLSPATH`;
  - prefixes: `LD_`, `XDG_`, `FLATPAK_`, `DBUS_`, `WAYLAND_`, `PULSE_`, `PIPEWIRE_`, `SDL_`, `STEAM_COMPAT_` (the launcher sets them for GE-Proton), `PRESSURE_VESSEL_`, `VK_`, `MESA_`, `LIBGL_`, `GST_`, `QT_`, `GTK_`, `GDK_`, `GIO_`, `RUYA_` (the launcher's own variables, ADR-037).

  `WINEDLLOVERRIDES`, `WINEDEBUG`, `DXVK_*`, `VKD3D_*`, `PROTON_*` and `MANGOHUD*` pass. At most 64 variables; values are plain strings of at most 1024 bytes without control characters.
- **`run.discs[]`** (optional, at most 16, ordered): payload files for emulated games and multi-disc sets, each a file listed in the table under `payload/`. `${disc}` is `discs[0]`; a `${disc}` in `run.command`, `run.cwd` or a setup command with no `discs` is an error (`run.disc_placeholder_without_discs`).
- `launch_mode`: `fullscreen` (default) \| `gamescope` \| `default`, the same values as `x-ruya-launch-mode` (03 §4.1).
- **Wine prefix.** `prefix` lives in the player's data directory (one per profile, one per game): `~/.var/app/play.<id>/data/prefix` for wine, `.../data/proton/pfx` for proton (`runner::prefix_dir`, §6.2.1), created on first run from `prefix.template` if the package has one (copied, not linked), else by the runner. `epoch` is an integer: when an update raises it, the importer's first launch backs up the paths in `data.saves`, recreates the prefix, and restores them (so a runner change that needs a fresh prefix keeps saves).
- **First-run setup** (`setup[]`): commands such as a Visual C++ redistributable, run **once per prefix, at first launch, inside the sandbox with the game's own permissions**, never at install time and never as root. They are shown on the launch splash ("Preparing the game for the first time") and have a timeout (10 minutes). A failed setup step is reported, not ignored. There is no network fetch at setup (no `winetricks` downloads): redistributables are shipped in the package.
- **The launcher as built (`services/ruya-play-launch`, RUY-901; ADR-037).** `ruya-play-launch [--runner=package|bundled|system]` (no other argument; the choice comes from ruya-session, RUY-904) runs inside the sandbox as the profile user and `exec`s the game, never through a shell. Every failure is one English sentence on stderr with its code (`launch.*`, `resolve.*`, or the format's problem code), exit status 1.
  1. **Re-read, not re-validated.** It reads `/app/play.files` and `/app/play.json` with `table::parse_table` and `manifest::parse_manifest` (untrusted even after install; the reserved-id rule is lifted, since the tier was decided at install) and each bundled copy's `runner.json` with `runner::bundled_runners`. No full `validate`: `/app` also holds the OS's folders, and a content pass would hash the game at every launch. A damaged file is "This game's files are damaged (...); reinstall it."
  2. **System runners** (ADR-038): the folders of `/app/runners/` in name order, at most 32, links not followed, each read through `runner::parse_runner`; family and version come from the file, never the folder name. A runner whose file is missing or invalid, or whose entry is not a regular file, is skipped with a log line; two folders with one family and version keep the first. A valid `.ruya-runner-hash` at a runner's root is reported in the status file; nothing is hashed at launch.
  3. **Runner choice** through `resolve::resolve` for every component; one that has none fails with the resolver's code and sentence. A chosen system runner whose `kind` is not the component's `type` is `launch.runner_kind`. `${component:<id>}` is that runner's root (`/app/<bundled.path>` or `/app/runners/<Name>`).
  4. **Command** as ADR-037 says (wine `[root/entry.wine] + S(run.command)`, proton `[root/entry.proton, "waitforexitandrun"] + S(...)`, the others `S(run.command)`); the working folder is `run.cwd`, else `${payload}` (`/app/payload`). `${data}` and `${config}` are `$XDG_DATA_HOME` and `$XDG_CONFIG_HOME`, which must be absolute (`launch.environment`). A named placeholder without a value for the runner (`${prefix}` for a native game) is `launch.placeholder`; any other `${...}` stays as written. The environment is the one the launcher was started with, then `run.env`, then the launcher's own: wine `WINEPREFIX`, `WINESERVER`, `WINELOADER` (and `WINEARCH` from `run.prefix.arch` only on the launch that creates the prefix; an inherited one is removed) or proton `STEAM_COMPAT_DATA_PATH` and `STEAM_COMPAT_CLIENT_INSTALL_PATH`, whose folders it creates (an inherited `WINEPREFIX` is removed: Proton derives its own). The proton layout (`<data>/proton`, `.../client`, `.../pfx`) is one function, `runner::proton_dirs`, which `prefix_dir` derives from.
  5. **Prefix.** A missing prefix is the template copied (links as links) plus `dosdevices/c:` (`../drive_c`) and `dosdevices/z:` (`/`); without a template the runner creates it. A prefix whose recorded epoch is below `run.prefix.epoch` (no status file counts as 0) is rebuilt: the `prefix:` saves are copied to `${data}/.ruya-play/epoch-<old>-backup/`, the prefix is removed and created again, the saves are copied back, and the backup stays until a later rebuild from the same epoch replaces it (only a rebuild whose status file has no `backup_of` marker for that epoch clears and rewrites it). Every read, copy and write keeps links as links and refuses a link among the folders of its path below the data folder or `/app`, so a planted link is never followed; a save behind a linked folder is skipped with a log line. A copy deeper than 64 folders is refused (`launch.prefix` for a template), and a read-only folder is copied with its mode; removing a prefix or a backup walks the tree itself, making each folder writable before emptying it, so a read-only folder never blocks a rebuild. A rebuild cut short resumes from its complete backup.
  6. **Setup.** A step with `once: true` runs when this prefix has not done it (for a runner without a prefix: once per profile); a step without it runs at every launch. Each step runs through the runner's wrapper (wine `[wine] + S(step)` then `wineserver -w`, proton `[proton, "run"] + S(step)`) in the game's environment and working folder, in its own process group, and gets 10 minutes (the wrapper's wait included, itself in its own group); a step that ends non-zero, by a signal or by the timeout (every group started for the step is killed, so a timed-out `wineserver -w` also ends what the step left running) is `launch.setup_failed`: "The game's first-time setup step <id> ended with code 3." The game does not start, and the next launch runs the step again.
  7. **Status file** `${data}/.ruya-play/state.json`, written atomically (temporary file, flushed, renamed) after every step that changes it, for the next launch and the launch splash: `format` (1), `epoch` (the epoch the prefix was made for), `backup_of` (the old epoch while a rebuild is under way, else `null`), `setup_done` (the `once` step ids done for this prefix), `setup_failed` (`{"step", "message"}` of the last failed step, `null` once a launch passes every step), `runner` (`{"component", "family", "version", "source": "bundled"|"system", "hash"}` of `run.component`, `hash` `null` when unknown; `null` for a native game). The game can write that folder, so the launcher reads the file as untrusted (at most 64 KiB, every field type-checked); one it cannot read counts as absent, the safe direction (a rebuild with saves kept, setup again); so does a file of another `format`, which makes a format change a rebuild for every game, the price of never misreading an old file. `${data}/.ruya-play/` belongs to the launcher, but the game can write it: **the shell must treat every text in it (`setup_failed.message`, `runner.*`) as untrusted, game-written data** (plain text, bounded, never markup or a path it acts on). Writes are atomic: a temporary file, flushed, renamed, then the folder flushed.
- Under Wine the Windows `Z:` drive is the *sandbox's* root, not the host's: the Flatpak sandbox is what limits files, not Wine's drive mapping.
- **Display:** apps reach the compositor through the per-profile Wayland socket (T-164).
  - **Windows packages (`wine`, `proton`) get `sockets=x11`, not `wayland`.** They run on X11 through `ruya-session x11-run` (xwayland-satellite, ADR-034). Spike Q2 measured full screen, 60 FPS and 17 ms frames at 1080p on the Dell.
  - Wine's own Wayland driver (`winewayland`) does not start on the compositor today. It needs `wl_data_device_manager` >= 2, `wl_output` >= 3 and `xdg_wm_base` >= 2, plus pointer constraints and relative pointer for mouse-look. It becomes an option after a compositor task.
- **The launcher owns `WINEPREFIX`.** A package-set `WINEPREFIX=/tmp/...` would silently put the prefix in the sandbox's tmpfs, so saves would be lost at exit (spike Q4). `run.env` refuses it (§18 item 21).
- **32-bit Windows code** needs `--allow=multiarch` and the `Compat.i386` (and `GL32`) extensions: without them Flatpak's seccomp kills it with SIGSYS (spike Q4). Flathub's Wine 11 and GE-Proton 11 both use the old WoW64 layout (`i386-unix`).

### 6.4 The Play platform (what the sandbox contains)

Proven by the T-229 spike (RUY-91, 2026-11-16, Q1): the package is installed as a Flatpak **app** whose runtime is the freedesktop platform plus **extensions we publish on the `ruyaos` remote**. Installing the app pulled the declared launcher extension on its own (a related ref), and `command=` may be an absolute path into that extension (`/app/launcher/bin/ruya-play-launch`).

- `org.ruyaos.Play.Launcher`: the small launcher (`ruya-play-launch`) that reads `/app/play.json`, resolves components (§6.2), prepares the prefix, applies the env deny table (§6.3) and `exec`s the runner. One launcher for every package, a file in the OS image that updates with the OS (ADR-038), so a launcher fix reaches every game.
- `org.ruyaos.Play.Runner.<Name>//1` (e.g. `org.ruyaos.Play.Runner.ProtonGE10//1`; ADR-038): **system runners**, one id per family and major (the branch is the ABI), mounted by every app under `/app/runners/<Name>` through the `org.ruyaos.Play.Runner` point (`subdirectories=true`), shared by all packages (this is what makes `source: system` cheap). Each carries a `runner.json` (ADR-037). The preinstalled ones are files in the OS image on `/usr/lib/ruyaos/play/runners/`, shown to Flatpak as unmaintained extensions through `tmpfiles.d` links (proven in the VM, RUY-899); every runner RuyaOS offers ships this way (RUY-37). They bundle DXVK and VKD3D-Proton as part of the runner.
- Support libraries a game commonly wants (32-bit compat, gamescope, MangoHud, GameMode) as extensions the app may mount.

**The image preinstalls GE-Proton** (ADR-025, owner 2026-11-09; the default Windows runner), and it is **always in the OS image and updates with it** (owner, 2026-11-19, RUY-897), so a Windows package with `source: system` works offline from the first boot. A packager who needs another version bundles it (§6.2). The image also keeps the previous GE-Proton major and ships plain Wine stable (owner, 2026-11-20, RUY-915, narrowing 2026-11-19's "ship them all"; RUY-37); Wine staging, Wine-GE and UMU-Proton are not shipped and a package that needs one bundles it. A package names the one it wants, and the player can override it per game. Valve's Proton with its Steam Linux Runtime, emulators, console firmware and BIOS files are never shipped or hosted by RuyaOS: a packager who needs them bundles them (as `components[]` with `source: bundled`) and carries the licence and distribution duty. **Proton without its container (spike Q3).**
- Proton through umu and the Steam Linux Runtime (pressure-vessel) does **not** run inside the sandbox on Flatpak 1.18.4. The sub-sandbox portal is reachable, but its `--usr-path` / `--app-path` fails ("Can't find source path /proc/self/fd/N"); without the portal, pressure-vessel exits 125.
- So in v1 a Proton runner (the preinstalled GE-Proton, or a bundled one) runs **directly**, without umu and the runtime, like a Wine runner. It needs `STEAM_COMPAT_DATA_PATH` under `${data}` and `multiarch`, and it runs on the X11 path. Measured: 60 FPS; 2.2 s to the game's GL load with a fresh 280 MB prefix, 1.6 s warm.
- A package that bundles the Steam Linux Runtime is unsupported until a Flatpak with a working portal passes the re-test in `scripts/spikes/play/q3-proton.sh`. If that ever becomes supported, the runtime is one shared extension, never 696 MB per profile and app (umu's default).

**On the image, as built (RUY-34; image and VM checks pending the lead's build, `scripts/vm-runner-check.sh`).**
- **The launcher** is built in the `services-build` stage of `image/Containerfile` as a static binary (`x86_64-unknown-linux-gnu` with `-C target-feature=+crt-static`, a static-pie on Fedora's `glibc-static`; Fedora ships no musl Rust std. The launcher must not use NSS, iconv or dlopen; the build fails when `readelf` shows a program interpreter or a needed library) into `/usr/lib/ruyaos/play/launcher/bin/ruya-play-launch`.
- **The runners are data.** Each is a folder `image/play/runners/<Name>/` with a `pin` (the upstream release: `url=`, `sha256=`, `root=` the archive's folder) and the `runner.json` it ships. `image/play/install-runners.sh` loops over the folders in two stages: `fetch` (stage `play-runners`) downloads each release, refuses any other SHA-256, unpacks its root folder to `/usr/lib/ruyaos/play/runners/<Name>/` without group or world write bits and puts `runner.json` at its root; `check` (stage `play-runners-check`) runs `ruya-pack runner-check <tree> --write-hash --record` (§13), the format's parser and runner hash, never `jq` or a shell hash, which writes `<Name>/.ruya-runner-hash` and adds the runner's line to `/usr/lib/ruyaos/play/runners.list`. The trees are a layer of their own that changes only with the pins; the hashes and the list are a small one. Another runner or another major is another folder, its `L+` line and a row in `docs/image-packages.md` (RUY-37), no new build code. Today: `ProtonGE11`, GE-Proton11-12 (family `proton-ge`, kind `proton`, 1528 MiB unpacked), the release the spike ran (RUY-91).
- **`runners.list`**: one line per runner, `<Name> TAB <family> TAB <kind> TAB <version> TAB <licence> TAB <source_url>` (an absent optional value empty), in folder name order. Settings → About reads its `wine` and `proton` lines (02 §1.2, `SystemInfo.windowsRunners`). It is image data for the shell, not part of the sandbox (no app sees it).
- **The links**: `image/rootfs/usr/lib/tmpfiles.d/ruya-play-platform.conf` has the launcher's line and one `L+ /var/lib/flatpak/extension/org.ruyaos.Play.Runner.<Name>/x86_64/1 ... /usr/lib/ruyaos/play/runners/<Name>` per runner folder; `services/ruya-play/tests/platform.rs` checks it against what the generated metadata declares and against the runner folders, both ways.
- **Steam**: one more line per Proton runner links the same tree into the Steam Flatpak's `com.valvesoftware.Steam.CompatibilityTool.<Name>/x86_64/stable` (RUY-35; the Flathub manifest's point is `subdirectories: true`, `directory: share/steam/compatibilitytools.d`, `version: stable`). `ruya-session` sets the default tool once per profile (`03` Steam row).
- **Not built:** the offline freedesktop runtime set (Platform 26.08 with Compat.i386, GL32 and GL.default): installing it into `/var/lib/flatpak` at build time breaks the image's rule that `/var` is created by `tmpfiles.d` only (bootc copies `/var` at the first install and never updates it), so it waits for a decision on how the image carries it. Until then an install pulls the runtime from Flathub (network).

## 7. Installing

### 7.1 Where things live

Design confirmed by the T-229 spike (RUY-91, Q1; it keeps every existing service working):

- **Install = import as a system Flatpak app** named `play.<id>`, built by the importer from the package and committed to the system Flatpak installation (`/var/lib/flatpak`, the same place and the same machinery as every other app). Consequences, all by reuse: the app is shared by profiles; per-profile data is `~/.var/app/play.<id>/{data,config,cache}` (03 §4.5a, so backups, "Keep saves?" and storage sizes already apply); `ruya-store` lists, updates, rolls back (`Rollback`) and uninstalls it; `ruya-library` finds it (exported desktop entry, `Game` category); `ruya-session` launches it (`flatpak run play.<id>`); permissions are Flatpak's. OSTree stores files by content hash, so **two packages that bundle the same Wine build share one copy on disk**.
- The importer adds to the app's `/app`: `play.json`, `play.files`, `play.sig`, the vetted art (`/app/share/ruyaos/play/art/`), the **trust record** `/app/share/ruyaos/play/trust.json` (RUY-851), the payload and bundled components. Its Flatpak metadata (`command=ruya-play-launch`, permissions) is **generated from the manifest** by the importer; the package never supplies Flatpak metadata, so it cannot request what §8's vocabulary does not allow.
- **The trust record** (`ruya_play_trust::TrustRecord`, RUY-851): one line of JSON the commit writes from what the console verified, never from the package (a package with a top-level `share/` is refused, `commit.failed`, because the console writes that folder): `{"format":1,"tier":"developer","signer_id":"<32 hex>","signer_name":"Example Games","store_signed":false}`. `format` is 1 (a reader refuses another); `tier` is `official`, `developer` or `unverified`; `signer_id` is the developer key's id and `signer_name` the manifest's `developer.name`, which that signature covers (self-asserted: the key, not the name, was verified), both `null` for an unsigned package (`signer_name` also without a `developer`); `store_signed` says a store countersignature by a pinned key was verified. In the deployment it is `files/share/ruyaos/play/trust.json`; `ruya-library` reads it for the item's tier and signer (RUY-104) and never verifies a signature itself.
- Trust of the generated commit: after the importer verified the package's signature (§9), it signs the OSTree commit with a **device-local key** generated on first use (root, 0600, under `/var/lib/ruya-play/`, never in the image, never in the repo). Flatpak verifies that signature as with any remote, so `ruya-store`'s rule "never `--no-gpg-verify`" is unchanged. The local key only says "this device's importer accepted this package", which is what we want.
- The package file itself is not needed after install (a USB stick can be removed). Keeping or deleting the downloaded copy is the player's choice.

**What the commit step must do (spike Q1, Flatpak 1.18.4):**
- Create every extension point's mount directory in `/app`. Otherwise bwrap fails at run time ("Can't mkdir parents ... Read-only file system").
- Write the app's own `share/applications/play.<id>.desktop` (category `Game`). Without it nothing is exported, and exports not named after the app id are refused.
- Use `install --or-update`: a plain `install` of an installed ref does nothing.
- Use a **`bare-user-only` staging repo on the same reflink-capable filesystem as `/var/lib/flatpak`** (XFS on the image). The Dell measured these numbers:

| Payload | Repo mode | Commit | Install | Disk peak | A second app with the same files |
|---|---|---|---|---|---|
| 20 GiB | `bare-user-only` | 52 s | 0.4 s | 1.03x the payload | +0 bytes |
| 20 GiB | `archive-z2` | 472 s | 117 s | 3.1x | +0 bytes |
| 2 GiB | `bare-user-only` | 5.3 s | 0.6 s | 1x | +0 bytes |

Two apps that bundle Flathub's 430 MB Wine tree added 23 MiB in total, because they share objects with the installed `org.winehq.Wine`.

The bubblewrap fallback is not needed: the spike confirmed the Flatpak route (ADR-014, "Spike result").

### 7.2 Who may install

Follows 03 §4.4. Admins install directly. A Standard profile needs an admin's PIN for every package it installs from USB (§18 item 4: sideloading needs an admin or an admin's PIN; the Store's dialog; as built by RUY-98, `admin_approved`); the confirm sheet's PIN line follows Inspect's `gate` (04 §5.4); the gate changes the wording and the warning, never who is asked, and a Guest is asked like a Standard profile. `unverified` packages need **developer mode** (an admin setting, default off, red "Unverified" badge on every screen that shows the app) and are limited to low and medium permissions. A restricted profile (parental controls, T-211) cannot install.

### 7.3 The import pipeline (what `ruya-play` does)

1. **Open** the source read-only (a USB path or a downloaded file in `/var/lib/ruya-play/incoming/`). Removable media is mounted `nosuid,nodev,noexec`.
2. **Inspect** (unprivileged helper, no network, no access outside its input and a staging directory; started by the service as a transient systemd unit with `DynamicUser=yes`, `PrivateNetwork=yes`, `ProtectSystem=strict`, `NoNewPrivileges`, a system-call filter, memory and CPU limits and a time limit): parse `play.json`, `play.files`, signatures, apply every rule of §4. The order is fixed (`ruya_play_trust::inspect`, RUY-93): read `play.json`, `play.files`, `play.sig` and `store.sig` as bounded bytes; verify the signatures; decide the tier; run the full `ruya_play_format::validate` with `ValidateOptions.official` set only when the tier is `official`; then check the signed id and build against the manifest, key continuity, the tier's permission ceiling and the blocklist (§9.2). This is the cheap step; the shell's package page (name, art, permissions, size, trust badge, signer) is built from its result, so a player sees the app *before* a single payload byte is copied.
3. **Confirm** (shell): permissions in plain words, size, trust tier, update behaviour, "Install". Nothing was written beyond a small staging manifest.
4. **Unpack** (same helper, same limits): stream entries into staging on the target filesystem (free space was checked up front), hashing as it goes; every hash must match `play.files`; art and video are decoded and re-encoded here, never in the shell or in the root service. Progress goes to the shell (`JobProgress`-style).
5. **Commit** (the root part of the service, small): re-walk the staged tree without following links (names, kinds, modes; the helper's uid is gone, nothing else can write), recreate links and modes from `play.files`, generate the Flatpak metadata, build and sign the OSTree commit, install it. Any failure removes the staging directory; there is no half-installed package.
6. **Announce** `InstalledChanged` so the library updates (the Store/Library services already react).

**The contract (RUY-96, `api/dbus/org.ruyaos.Play1.xml`, a draft and internal, no `Stability` annotation; served by `ruya-play` since RUY-829; the header states the trust boundary of `admin_approved` that the service enforces).** Methods: `ListSources()` (candidate folders and `.play.zip` files on mounted drives, data only, nothing opened), `Inspect(path) -> (status, info)` (step 2; the record carries the identity, the `permissions` as `(key, words, risk)`, the `tier`, `signer_key_id`, `signer_name`, `key_state` `new | same | different`, the vetted `art`, a `verdict` that predicts how Install would end, and the `problems` as `(code, path, message)` with the codes of §4.5 and `ruya-play-art`), `Install(path, options) -> (status, job)` (option `admin_approved`, §18 item 4), `Verify(app_id) -> (status, job)`, `Cancel(job) -> status`, `GetDeveloperMode() -> on` and `SetDeveloperMode(on, options) -> status` (option `admin_approved`, RUY-98) and `ListJobs()`; signals `JobProgress`, `JobFinished`, `SourcesChanged` and `DeveloperModeChanged`. Method statuses reuse the Store's names (`ok`, `unknown-app`, `busy`, `forbidden`, `invalid`, `failed`) and add `unknown-source`, `unknown-job` and `too-late`; job statuses are `ok`, `invalid-package`, `bad-signature`, `different-developer`, `needs-developer-mode`, `revoked`, `unsupported`, `disk-full`, `cancelled` and `failed`. The shell sees **one job** from step 4 to the installed app; its phases are `staging`, `verifying`, `vetting-art`, `committing` and `installing` (the Store's Flatpak transaction, step 5, runs inside the last), and its percent never decreases. The shell side is `shell/src/play` (the `Play` singleton, `PlayBackend`, a mock with eleven fixture packages and the D-Bus client; the job bookkeeping is the Store's `JobBook`); the mock and the XML header's status lists are held together by `tests/tst_play.qml::test_contract_statuses`.

**The importer core as built (RUY-99, split by RUY-828; `services/ruya-play`; the binary, D-Bus and the Flatpak commit are RUY-829's, below).** Pure logic behind traits (`core::deps`: `Helper`, `FreeSpace`, `Commit`, `Clock`, `Blocklists`, `InstalledBuilds`, `Hooks` for the service; `Opener` and `ArtVetter` for the helper, `core::helper::HelperDeps`; fakes in `core::fakes`), configured by four folders (`incoming/`, `staging/`, `state/`, `inspect/`), so every rule runs on Windows with temporary folders. It uses the three merged crates and re-implements none of their rules.

- **Jobs** (ADR-026: each service owns its jobs; `Play1.ListJobs` is this table). `state/jobs` is JSON Lines: a header `{"format":1,"counter":N}`, then one record per job with ADR-026's v2 names where they apply, `job`, `source` (`"play"`), `kind` (`install` \| `verify`), `state` (`queued` \| `running` \| `finished`), `phase`, `bytes_done`, `bytes_total`, `started`, `finished`, `error` (the first problem's code of a job that did not end `ok`), plus the contract's `path`, `app`, `status`, `reason` and `percent`. It is written atomically (temporary file, flushed, renamed, folder flushed, mode 0600) and read as untrusted input like `ruya-store`'s (a line that breaks a rule is dropped; at most 1 MiB is read); the 20 newest finished jobs are kept. **One install at a time**: `run_next` runs the oldest queued job to its end and a second caller waits. The counter comes from the file. If it is already at its largest value, `Install` answers `failed` and hands out no name, rather than wrapping around or panicking. A job left queued or running when the service stopped becomes `failed` with the reason `interrupted` and the error `job.interrupted`, once, at the next start; nothing is ever resumed and job names are never reused.
- **Method statuses:** `Install` is `forbidden` without `admin_approved`, `invalid` for a path that is not absolute plain text, `busy` while a job for the same path is queued or running; `Inspect` is `unknown-source` when nothing is at the path (a path the service saw before and after the helper run, which still got no descriptor, is a refusal `source.unreadable`, status `failed`: PID 1 was denied the open, which `OpenFile=...:graceful` makes look like a missing file; the same rule applies to the install's unpack run, where a path that was there before and after and ends `missing` fails the job with `source.unreadable`, not `source.missing`); `Cancel` is `unknown-job`, or `too-late` once the job is finished or in its commit step. Checking the caller's uid and the `ListSources` candidates is the D-Bus side's (RUY-829, below).
- **`Inspect`** runs steps 1 to 3 below and writes nothing but its helper folder `inspect/inspect-<n>/` (no staging folder, no job, no free-space query). The helper also copies the art files out of the package (each hashed against `play.files`) and vets them as step 7 does. Once the service's checks pass, only `art/` stays in that folder, and the record's `art` points at its files (`InspectReport.art`, Play1's `art`; the D-Bus mapping is RUY-829's). The newest four `Inspect` folders are kept, and all of `inspect/` is removed at start. Art problems join the record's problems, and a broken `icon` or `hero` makes the verdict `invalid-package`, as the install would end. A helper that breaks its contract makes `Inspect` answer `failed`.
- **The install pipeline**, in this order (lead-29; the records moved before the commit in round 2; steps 1, 2, 5, 6 and 7 split between the helper and the service by RUY-828, below):
  1. Open the path (a folder, or a `.play.zip`; a link is not a package) and wrap it so the listing and the four root files are **read once**: `ruya_play_trust::inspect` reads `play.json` and `play.files` to verify the signatures and `validate` reads them again to parse them, and a drive that answered the second read differently could have one manifest verified and another installed. Every later read gets the first bytes, and those bytes are what lands in `meta/`.
  2. `ruya_play_trust::inspect` with `ListCheck::of(select_blocklist(image, download))`, never `ListCheck::NotChecked` (a missing or broken image list refuses every install with `blocklist.unavailable`, status `failed`), the runner hashes empty (unknown before the unpack) and `verify_content` off: the unpacker hashes every file as it copies it, so the source is read once.
  3. A `build` not above the build installed for the id (ids compared in lower case) is `build.not_newer` (05 §11). The builds live in `state/installed.json` (atomic, 0600; a file that cannot be read as written is `installed.corrupt`, never reset; a key the reader does not know, at the top or on an entry, is ignored, so a file from a newer image reads after a rollback: a field may only be added with a safe default, and a breaking change raises `format`; RUY-900, the same for `state/jobs`).
  4. Free space in `staging/`: the installed size plus 10 % (`size + ceil(size / 10)`; the spike measured a 1.03x peak), asked before anything is written; less is `space.not_enough`, status `disk-full`.
  5. Unpack into `staging/<job>/tree`, the job folder created exclusively (mode 0700; a name someone else put there is `staging.changed` and is removed, not followed). Every name goes through a directory handle (`core::staging::Dir`): on Linux `openat(O_DIRECTORY | O_NOFOLLOW)` from the parent's descriptor, `mkdirat`, files with `openat(O_CREAT | O_EXCL | O_NOFOLLOW)`, links with `symlinkat`, modes with `fchmod` (files 0644, or 0755 with `x:1`; folders 0755; whatever the umask and the source's attributes, so no setuid, setgid or sticky bit), and each name is checked again to be one plain component. On Windows (development only) a rooted path that refuses reparse points at every step, which is not race-free. Files are streamed in 256 KiB chunks, must have exactly their listed size and SHA-256 (`package.size_mismatch`, `package.hash_mismatch`, or the zip's own read fault), and links are created from the table only. A planted link on the way is an error, never a way out: an open folder handle keeps pointing at the folder the importer made. Out of space while writing is `space.not_enough`; any other write fault `staging.io`.
  6. **Verify** (phase `verifying`): the helper, then the service again (below), re-walk the staged tree without following links and hold it against the table (kinds, sizes, modes on Unix, link targets, and nothing else; `staging.changed` otherwise), then check revocation again with the **runner hash** of every bundled component, computed from the staged copy: the SHA-256 of one line per entry below the component's `bundled.path`, in table order, path relative to that folder, `f NUL path NUL sha256 NUL x-or-dash LF` for a file (its hash as written into staging), `l NUL path NUL target LF` for a link, `d NUL path LF` for an empty folder (the formula is `ruya_play_format::runner::RunnerHasher`, the one copy the importer, `ruya-pack` and the image build use). A `runner <sha256>` blocklist line with that value is `revoked.runner`; runner resolution (T-239) must report the same value for a bundled runner.
  7. **Art** (phase `vetting-art`): `ruya_play_art::vet` slot by slot on the staged paths (after the re-walk proved no link is on the way) into `staging/<job>/art/` (a logo per language into `art/logo-<n>/`, numbered in the manifest's order, so no package text names a file). The slot results join the problem list with the slot's package path. A broken `icon` or `hero` is `invalid-package`; another broken slot only loses its art and the job can still end `ok` with that problem. **Memory for RUY-100's helper limit:** the art decode peaks near 1.25 GiB for the largest allowed 16-bit image (0.7 GiB for 8-bit, §5); the limit must be above that.
  8. **Records first, fail closed** (RUY-99 round 2). From here `Cancel` answers `too-late` and the job runs to its end. `record_install` writes the trust record, then the installed build is written, **before** the commit. A committed app without a key record would make the next package for its id a first sight, so any key could replace it and take its saves, and a lost build record would drop the downgrade guard. If the build record cannot be written, the trust record is rolled back and nothing is committed (the store's code, `state.io` or `installed.io`, status `failed`). `record_uninstall(id, data_kept)` belongs to RUY-100's uninstall.
  9. **Commit** (phase `committing`, then `installing`): the `Commit` trait gets the tree, `art/`, `meta/` (the verified root files), the manifest, the tier, the assessment and the signatures. `NoSpace` is `space.not_enough`; any other failure is `commit.failed`. A failed commit rolls both records back. A trust record this install created is dropped, and one that existed before (a rotation) is put back as it was. The installed build is forgotten, or set back to the build that was there. If the rollback fails, the job keeps the commit's status and adds `rollback.failed`, and a line goes to `state/journal` (JSON: `time`, `job`, `id`, `event` = `rollback_failed`, `detail`). The stale record names this package's key, so it can only refuse a different key later: that is the safe direction.

  Any failure or cancel removes `staging/<job>` (without following links); an `ok` job removes it too. A crash or a power cut leaves only staging folders, and the importer removes everything in `staging/` when it starts. Progress: `staging` covers 0 to 70 % by bytes written, `verifying` 70 to 75, `vetting-art` 75 to 85, `committing` 85 to 95, `installing` 95 to 100; the percent never decreases and a phase never comes back.
- **The helper split (RUY-828, lead-33, inside ADR-014).** Everything that reads package bytes runs in the unprivileged helper; the root service never opens a package (a test opener panics when it is called outside the helper). One binary, two modes: the service, and the helper the service starts per run (`helper::run(request, deps, out, cancel)`, a library function, so tests and Windows run it in-process through `InProcessHelper`; on the console `SystemdRunHelper`). An install is **two helper runs**, so that the service decides between them with state the helper never sees:
  - **Run 1, `inspect`**, into `inspect/<job>/`: open the path, read the listing and the four root files once, run `ruya_play_trust::inspect` with the request's developer mode and image blocklist and **no key records** (continuity is the service's), then write the root files as they were read into `meta/`. A helper refusal is the job's refusal, with the format's full problem list. The service then reads `meta/` back once through a folder handle, bounded by the format's limits (`core::meta::MetaSource`: the root files, with the listing that `play.files` implies). It runs `ruya_play_trust::inspect` itself over those bytes, with its own key records, `select_blocklist` and developer mode, then the build check (step 3) and the free-space check (step 4). `inspect/<job>/` is removed before step 4. One consequence: a package that is both signed by a different developer and over its ceiling or blocked reports the ceiling or the block, because the helper refuses first.
  - **Run 2, `install`**, into `staging/<job>/` (created by the service, exclusively, after step 4): open the path again. Each root file must have the SHA-256 the service verified; one that changed, appeared or vanished is `source.changed` (status `failed`). Then `validate`, unpack into `tree/` (step 5), re-walk it (step 6) and vet the art from the staged copy into `art/` (step 7). The cancel checks inside the unpack and the art step run in the helper.
  - **The service's own pass** after run 2 trusts nothing the helper wrote. `staging/<job>/` must hold the folders `tree/` and `art/` and nothing else. The tree is re-walked against the `play.files` the service verified (kinds, sizes, modes, link targets), and every file is **re-hashed** through folder handles (`unpack::rehash`; a file whose size or SHA-256 changed is `staging.changed`). Revocation is checked with the runner hashes of that re-hash. `art/` must hold exactly the files the helper named (regular files without a setuid, setgid or sticky bit, folders one level down). Then the service writes its own verified root bytes into `meta/`. Only then come the last cancel check, the records and the commit.
  - **The wire.** The request is JSON: `mode` (`inspect` \| `install`), `job`, `source`, `staging`, `now`, `developer_mode`, `blocklist` (the image's list, hex), `art`, `official` and `expect` (root file to SHA-256). Unknown fields are refused, and at most `2 * 4 MiB + 64 KiB` is read. The answer is JSON Lines on the helper's output: `{"type":"progress","phase":..,"done":..,"total":..}` (`staging` counts bytes, `verifying` and `vetting-art` count steps), `{"type":"problem","code":..,"path":..,"message":..}` (path and message cut to 4 KiB), and one last `{"type":"result","outcome":"ok"|"refused"|"cancelled"|"missing","art":[{"slot","lang","files"}],"art_refuses":..}`, with art paths relative to `art/`. The service reads it as untrusted input (`core::helper::Session`). These all end the job `failed` with `helper.failed`: a line over 64 KiB, more than 200 problems, a line that is not one of the three shapes, an unknown phase, art that is not a plain relative path, a line after the result, output that ends inside a line, no result, a non-zero exit, a run that could not be started, a stop without a cancel (a memory or time limit), and `cancelled` when no cancel was asked. A stop after a cancel is `cancelled`. Progress lines only move the job along its own ranges (the byte total is the service's, and the percent never goes back). The service's own pass runs at the end of `vetting-art`.
  - **The unit** (`core::systemd_run`, Linux). Its command line is unit-tested on every host; the unit runs for the first time in RUY-100's VM check. It is `systemd-run --wait --collect --quiet --service-type=exec --unit=ruya-play-helper-<job>` of the service's binary with `--helper`, with `DynamicUser=yes`, `NoNewPrivileges=yes`, an empty `CapabilityBoundingSet`, `RestrictSUIDSGID=yes`, `PrivateNetwork=yes`, `IPAddressDeny=any`, `RestrictAddressFamilies=AF_UNIX`, `ProtectSystem=strict`, `ProtectHome=yes`, `PrivateTmp=yes`, `PrivateDevices=yes`, the kernel, clock, hostname and cgroup protections, `RestrictNamespaces=yes`, `LockPersonality=yes`, `SystemCallArchitectures=native`, `SystemCallFilter=@system-service`, `/var/lib/ruya-play` inaccessible, `MemoryMax=2G` (above the art step's 1.25 GiB peak, with room for the unpacker), `MemorySwapMax=0`, `CPUQuota=200%`, `RuntimeMaxSec` 600 for `inspect` and 21600 for `install`, and `UMask=0077`. **The wire is two files, never `--pipe` (RUY-839):** `systemd-run --pipe` passes the caller's descriptors to PID 1 over D-Bus, and under SELinux PID 1 (`init_t`) may not use those of a service (`unconfined_service_t`; the denial is `dontaudit`, so no AVC shows): the start fails with `Connection reset by peer` and PID 1's bus connection stays wedged until `daemon-reexec` (measured in the VM, systemd 259). So the service writes the request to `in.json` in the run's folder `/var/lib/private/ruya-play-helper-<job>.io` (root, 0700, next to the state folder, removed with it and at start) and the manager opens both files itself: `StandardInput=file:<io>/in.json`, `StandardOutput=file:<io>/out.jsonl`, `StandardError=journal`. The helper's own state folder is not used for them because systemd sets it up after it opens the standard streams. The service follows `out.jsonl` while the unit runs (`Follower`: each poll hands the new bytes to the same bounded line parser, so a partial line waits for its newline; an over-long line, garbage or more than 16 MiB is `helper.failed` and stops the unit), reads the rest once `systemd-run --wait` has returned, and takes the exit status from that return. **The source is one read-only file descriptor (RUY-829):** the service manager opens it as root and passes it in (`OpenFile=<path>:source-<dev>-<ino>:read-only,graceful`), because a bind keeps the file's own mode and `incoming/` is root 0600, so the dynamic uid could not read a download. Before the run the service `lstat`s the path (a link refuses the run) and puts the device and inode it saw in the descriptor's name; the helper (`service::fd_source::PassedFdOpener`, `LISTEN_PID`/`LISTEN_FDS`/`LISTEN_FDNAMES`) checks them on the descriptor, so a file swapped in between is refused (`package.read_failed`). A zip is read through the descriptor itself (a copy per open: no permission check of the dynamic uid applies); a folder through `/proc/self/fd/3`, so its entries must be readable by others (a FAT or exFAT drive mounted by udisks is, VM-pending). Nothing at the path (`graceful`) is `missing`, and so is a file PID 1 may not read. Under SELinux, PID 1 (`init_t`) reads FAT/exFAT/NTFS (`dosfs_t`) and FUSE (`fusefs_t`) files only through the image's module `ruya_play_openfile` (ADR-036; without it every USB install failed in the VM on 0.0.92). A path with a control character, `:` or `\`, or a job name that is not plain, refuses the run; the request names `/run/ruya-play-helper/source`, where nothing is mounted. **The one writable folder is `StateDirectory=ruya-play-helper-<job>`:** systemd creates it as `/var/lib/private/ruya-play-helper-<job>`, owned by the dynamic uid, mode 0700, on `/var` like `/var/lib/flatpak` (the reflink rule of §7.1). The helper's request names that real folder, never the `/var/lib/ruya-play-helper-<job>` link systemd also makes: the helper opens folders without following links, so the link is `staging.io` "Not a directory" (every install that passed inspection failed that way in the VM on 0.0.93; RUY-866). After the unit is gone, the service renames its top-level entries into its own `inspect/<job>/` or `staging/<job>/` (a link is moved as a link, never followed), removes the state folder, and runs its own pass. For that rename, the service's `staging/` and `inspect/` are in `/var/lib/private/ruya-play-work/` (root, 0700), not in `/var/lib/ruya-play/` (the empty `staging/` and `inspect/` an older install keeps there are removed at every boot by `R` lines in `tmpfiles.d/ruya-play.conf`, RUY-867): in the service's namespace every `ReadWritePaths=` entry and its `StateDirectory=` is a mount of its own, and a rename between two mounts is EXDEV even on one filesystem. A job that does not end `ok` or `cancelled` logs each of its problems (code, path, message; at most 8, cleaned of control characters, each field cut to 256 characters) to the journal, because its record keeps only the first code. At start it removes every `ruya-play-helper-*` state folder a crash left. Cancel stops the unit (`Helper::stop`, `systemctl stop`). Two questions are RUY-100's in the VM (`vm-play-check.sh helper`): reading a USB source and an `incoming/` file through the descriptor, and the unit's `systemd-analyze security` score.
- **Cancel** is checked before the unpack, after every chunk and every file, after the unpack, before every art slot and once more, under the job table's lock, right before the records and the commit; a queued job that is cancelled finishes `cancelled` without its package being opened.

- **The importer's own codes:** `build.not_newer`, `space.not_enough`, `staging.changed`, `staging.io`, `source.missing`, `source.unreadable`, `installed.corrupt`, `installed.io`, `commit.failed`, `uninstall.failed`, `rollback.failed`, `job.interrupted`, `helper.failed`, `source.changed`, `source.unsafe_mount`, `installed.unreconciled` (`ruya_play::codes`; `tests/codes.rs` keeps them unique, asserted by a test and listed here).
- **Tests:** `tests/hostile_install.rs` runs **every** hostile fixture of RUY-92 through the full install (the format crate's `tests/hostile.rs` itself, included by `build.rs`, with `check` and `validate` replaced by an install) and holds each refusal to a directory snapshot: nothing in staging, nothing committed. `install.rs` (pipeline, space with zero writes, build, blocklist, runner revocation, read once, trust, art), `cancel.rs` (the five points), `jobs.rs` (restart), `helper.rs` (RUY-828: the service never opens the package; a forged tree, forged root files and forged lines; `source.changed`; `Inspect`'s art for the `hello-play-native` sample). All of them run through `InProcessHelper`. The Unix-only tests (`toctou.rs`: planted links; `modes.rs`; the leftover-link cleanup in `jobs.rs`) carry a named `ignore` on Windows and run in CI on Linux and in the VM queue (`vm-play-check.sh`, RUY-100).

**The service as built (RUY-829; the `ruya-play` binary, `src/main.rs`, `src/dbus.rs`, `src/service/`).** `ruya-play` serves `org.ruyaos.Play1` on the system bus as root (`ruya-play.service`, `Type=dbus`); `--session` serves the session bus with an in-process helper, a commit that only logs and state under `RUYA_PLAY_ROOT`; `--helper` is the helper inside its unit. `tests/contract.rs` holds the served interface to the XML.
- **The D-Bus side's checks** (`service::gates`, host-tested). `admin_approved` (Install, SetDeveloperMode) counts only when the caller's uid (`GetConnectionUnixUser`) is 0 or `ruya-shell`'s (from `/etc/passwd`); an unknown caller fails closed; an option that is not a bool is `invalid`. A path for `Inspect` or `Install` must be plain (rooted, no `..`) and either one of the candidates `ListSources` lists at that moment or a file directly in `incoming/`; otherwise `unknown-source`. A path under `/run/media` on a mount that is not `nosuid,nodev,noexec` (read from `/proc/self/mountinfo`; the last mount on a point counts) is `unknown-source` too, with a log line. Right before every helper run the service looks again (`service::GatedHelper`): a drive mounted again without the flags ends the job `failed` with `source.unsafe_mount` before the helper starts. Nothing is opened before a call.
- **`ListSources`** (`service::sources`): the drives under `/run/media` mounted `nosuid,nodev,noexec`, each read at its top and one folder down (at most 1024 entries a folder and 256 candidates a drive, hidden names skipped, no link followed): `*.play.zip` files (any case) and folders that hold a regular `play.json`. `drive` is the udisks object path of the mount's block device (Devices1's volume id), `drive_label` the mount folder's name, `size` a zip's size and 0 for a folder. `SourcesChanged` is sent when the set of those mounts changes (polled every 2 s); a package copied onto a drive that is already mounted is seen at the next `ListSources`.
- **The `Inspect` record**: the XML's keys from the importer's report; `permissions` with the words of §8's table (`ruya_play_trust::permissions`, the same as `ruya-pack inspect`'s); `gate` is the assessment's (`allowed`, `admin-pin`, `admin-pin-warning`; RUY-851); for a package whose id is installed, `permissions_added`, `permissions_removed` and `adds_high_risk` compare its requests with those of the installed app's own `play.json` (read from the deployment with the reconcile's size limit; absent when it cannot be read or names a value outside the vocabulary; `ruya_play_trust::diff`); `art` maps `icon` (512 px), `hero`, `card`, `cover`, `logo` (English, else the first), `poster`, `trailer` and `preview`, and `screenshots` lists the 1080 p files in order. `key_state` is `new` for a first sight, `same` for the same key or a rotation, `different` when the verdict is `different-developer`. `age_label` (the manifest has an OARS map, not a label) and `signer_name` (a signature carries a key, not a name) are absent.
- **Developer mode** is the trust store's flag; `SetDeveloperMode` sends `DeveloperModeChanged` when the value changes. **`Verify(app_id)`** (RUY-834) is a job of kind `verify` (`Importer::queue_verify`, `core/verify.rs`): `invalid` for an empty id or one with a separator or control character, `unknown-app` for an app without a recorded build or whose deployment (`<flatpak>/app/play.<id>/current/active/files`) is gone, `busy` while a verify of it is queued or running or its install runs, else `ok` and a job id. The job runs on the job worker (one job at a time, behind installs), reads the `play.files` stored in the deployment (never the staged package), walks the deployed `files/` without following links, leaves out what the console wrote itself (the root files, `launcher/`, `share/`, and the other extension points' mount folders with their parents when the table neither lists nor implies them, ADR-038: `runners/`, `lib/i386-linux-gnu/`; anything put inside one is compared) and Flatpak's empty top-level `.ref`, holds the rest against the table with `check_tree` in its structure-only mode (a missing, extra, changed-kind, changed-mode or relinked entry: `staging.changed`; sizes are left to the re-read, so a longer or shorter file is `package.hash_mismatch`, not `staging.changed`) and re-reads every file with `rehash_with` (size or SHA-256 differs: `package.hash_mismatch`, naming the file). It ends `ok`, `invalid-package` (the first problem; a read fault is `failed` with `staging.io`) or `cancelled`; progress is phase `verifying`, files hashed of all as percent (the bytes in `bytes_done`/`bytes_total`). A deployment that turned foreign between the queue and the run (its `deploy` names another remote) is refused when the job opens it: `failed` with `staging.io`, nothing read. It never writes to the deployment.
- **The helper's output, checked by the service.** On an `ok` result the helper may report only the art step's problems (`art.*`, `video.*`); any other code is `helper.failed`. Every vetted art file must have a name `ruya-play-art` writes (`icon-512.webp`, `screenshot-3-thumb.webp`, `trailer.webm`, ...), at most the bytes such a file can have (an image 4 bytes a pixel of its output size plus 64 KiB; the trailer 80 MiB, the preview 8 MiB, §5) and the first bytes of its container (WebP with its `RIFF` size equal to the file's, EBML, `ftyp`); otherwise `staging.changed`. This runs before the shell can see a file, for `Inspect` and for an install.
- **The commit** (`service::commit::FlatpakCommit`; its command lines are host-tested through a recording runner over a real staged install). In `staging/<job>/` it lays out a Flatpak build folder `app/`: the tree becomes `app/files`, the verified root files are copied next to it, the vetted art goes to `files/share/ruyaos/play/art/`, the mount folder of each extension point (below) and `files/share/applications/play.<id>.desktop` (`Categories=Game;`, `X-Ruya-Launch-Mode`, name and summary in English without control characters) are written, and `app/metadata` is generated: `runtime=org.freedesktop.Platform/x86_64/26.08` (the runtime of the developer guide's sample), `command=/app/launcher/bin/ruya-play-launch` (an absolute path into the extension, as the spike proved), the permissions of §8's table for the requests of the assessment (`commit::metadata(manifest, assessment)`, RUY-851: the lines every app gets with the runner's display socket, then each request's lines; a request without a row grants nothing, and an assessment whose gate is `refused` is never laid out), then the extension points (`commit::extension_points(runner)`, RUY-900, ADR-038): for every app `org.ruyaos.Play.Launcher` (`directory=launcher`, `version=1`, `no-autodownload=true`) and `org.ruyaos.Play.Runner` (`directory=runners`, `subdirectories=true`, `version=1`, `no-autodownload=true`, `autodelete=false`), and for the `wine` and `proton` runners also `org.freedesktop.Platform.Compat.i386` (`directory=lib/i386-linux-gnu`, `version=26.08`, the runtime's branch, `no-autodownload=true`) and `org.freedesktop.Platform.GL32` (`directory=lib/i386-linux-gnu/GL`, `version=1.4`, `versions=26.08;1.4`, `subdirectories=true`, `add-ld-path=lib`, the runtime's `merge-dirs`, `no-autodownload=true`: offline first: the image is to preinstall both, not built yet, 6.4), exactly as the spike declared them (`scripts/spikes/play/q3-proton.sh`). The 32-bit points are inert without the `multiarch` permission, which stays a request with its row in §8's table (`features=multiarch`), never something the runner grants. Each id and mount folder is one constant in `service::commit` (`EXTENSION_DIRS` lists every mount folder). A mount folder is made folder by folder, never through a link; one that is already there may hold nothing but other mount folders (a mount never hides a file of the package), otherwise `commit.failed`; the format refuses such a package before it gets here (`table.reserved_top_level` for `runners`, `run.lib_i386_reserved`), so this stays a backstop. The launcher point had `no-autodownload=false` before RUY-900: `METADATA_GENERATION` 1 carries the change (and the new points) to apps installed before, through the start-up re-commit below. The trust record is written next to the art. A package whose `play.files` lists a top-level `.ref`, `launcher`, `runners` or `share` (or anything below one) never gets here: the format refuses it before the payload is unpacked, as `table.reserved_top_level` (`invalid-package`, RUY-870; `ruya-pack validate` says the same), because Flatpak's deploy writes its own empty `files/.ref` and `flatpak run` locks it (RUY-848) and the other three names are the importer's; a nested `a/.ref` or `a/share` is an ordinary name. The lay-out keeps its own check of `launcher`, `runners` and `share` in the tree as an internal invariant (`commit.failed`). Everything below `app/` then belongs to root, folders 0755 and files 0755 or 0644 (the tree's modes were checked against `play.files`; the helper's art comes out 0600 and is made readable). Then `flatpak build-finish` (exports the desktop entry), `flatpak build-export --gpg-sign=<device key>` into `/var/lib/ruya-play/repo` (`ostree init --mode=bare-user-only` on first use, on `/var` like `/var/lib/flatpak`), and `flatpak install --system --or-update` of `app/play.<id>/x86_64/stable` from the system remote `ruyaos-play-local` (`file:///var/lib/ruya-play/repo`, added with `--no-enumerate --no-use-for-deps` and the device key imported; never `--no-gpg-verify`). The **device key** is a GPG ed25519 signing key made on first use in `/var/lib/ruya-play/gnupg` (0700, root, no passphrase: it only says "this console's importer accepted it"); its fingerprint is kept in `device-key.id` and its public part in `device-key.gpg`, never in the image. A command whose error says the disk is full is `space.not_enough`, any other failure `commit.failed`. **Announce:** the Store's `InstalledChanged` is not sent (it is another service's signal); `ruya-library`'s watcher of the installation sees the new app, and the shell's Store list shows it at its next read (a follow-up).
- **Start-up** (`core::reconcile`): `state/journal`'s `rollback_failed` lines go to the log (cleaned and cut). Before the bus name is taken, the `play.*` apps in `/var/lib/flatpak/app/` that are **ours** are reconciled with `installed.json` and the trust store: a recorded build with no app is forgotten (its key record stays, so the id comes back only under its key); an app whose own `/app/play.json` names another build, or that has no record, gets that build recorded; an app whose build cannot be read, or that is signed (`/app/play.sig`) but has no key record, is **held**: installs of its id are refused with `installed.unreconciled` until it is uninstalled. When the installed apps cannot be listed or the records cannot be read, **every** id is held (`Importer::reconcile_listed`, fail closed) until a reconcile succeeds; the service reconciles once at start, so that takes a restart. **Metadata generation** (RUY-900, ADR-038): `commit::METADATA_GENERATION` (1: the runner and 32-bit points; raised with every change of the generated metadata or desktop entry that installed apps need) is stamped into the app's `installed.json` entry (`generation`; an entry without it, from before generations, reads 0) after each successful commit; a lost stamp only costs one re-commit. The reconcile plans a **re-commit** for every app of ours that is not held and whose record is older (no record is 0; a newer one, after an OS rollback, is left alone). The service runs them after it took its bus name, on a thread of their own, one job at a time with the installs (`Importer::recommit`): under the job lock the generation is checked again (an install may have committed the app meanwhile), the same free-space question as an install is asked for the size of the deployed `/app` (`space.not_enough`), the deployed `/app` is copied through the folder `open_ours` opened into `staging/recommit-<id>/files` (without Flatpak's `.ref`; the bytes go through `copy_file_range`, a reflink on XFS), the manifest is read back from it (`reconcile::installed_app`: the format's parser over the stored `play.json` and `play.files`, the tier of the trust record the commit wrote, the install's ceiling; anything that does not read back so is `installed.unreconciled` and the app stays as it is), and the copy goes through `Commit::recommit`, the same commit as an install (`FlatpakCommit`: the generated parts are written again over the copy, which keeps the root files, art and trust record, then finish, signed export and install). The staging folder is removed and the generation stamped; a failure is logged, leaves the installed app as it was and is tried again at the next start. **Ours** (RUY-863) means the deployment's `deploy` file (its GVariant's first string, read bounded) names the remote `ruyaos-play-local`: `.play` is a real top-level domain, so a Flathub app can be named `play.<x>`, and one check (`reconcile::open_ours`) gates every reader of `app/play.*` (the reconcile, `Verify`, the installed permissions of the diff): it opens the deployment folder once (`current` and `active` are Flatpak's links, resolved there), reads `deploy` through that opened folder, and hands the folder back only for our remote, so a reader reads only what was checked. A missing `deploy` file, another remote or a prefix of ours is foreign: not adopted, not held, `Verify` says `unknown-app`, no permissions are read; a build recorded for an id whose deployment is now foreign is forgotten (a `ForgetBuild` like any other missing app) and the foreign app is never uninstalled or touched. `staging/` and `inspect/` are cleared as before.
- **Uninstall** (RUY-816): `Play1.Remove(app_id, options)` is the one owner of removing a `.play` app; the shell never sends a `play.*` app to `Store1.Uninstall`. `admin_approved` is required as for `Install` (`forbidden`); `unknown-app` is an id that is not `play.<id>` of an app that is ours (`reconcile::open_ours`, above: a Flathub app named `play.<x>` is never touched), `busy` any queued or running job of the same app. It is a job (kind `remove`, phase `removing`, in the same queue as the installs): the root part runs `flatpak uninstall --system --noninteractive -y play.<id>` through the commit's runner (`Commit::uninstall`, `commit::uninstall`; no `--delete-data`: the player's data in `~/.var/app/play.<id>` is kept, as `Store1.Uninstall` with `delete_data = false` keeps it) and, when Flatpak succeeded, `record_uninstall(id, data_kept = true)` (the key record stays, so a package for the same id under another key is still refused after a removal, §9.2; the admin's "forget this game's data and key", item 17, is not built) and forgets the installed build and the id's hold. Once Flatpak starts the job passes the point of no return (`Cancel` answers `too-late`). A failed uninstall is `failed` with `uninstall.failed` and changes no record; a record that cannot be written after a successful uninstall is `failed` with that record's code and is corrected by the next start's reconcile, which stays the safety net for a removal done outside Play1 (`flatpak uninstall` by hand).
- **Image:** `ruya-play.service` (root; `StateDirectory=ruya-play` 0700; writes `/var/lib/flatpak`, `/var/lib/private` (the helpers' state folders and the service's own `ruya-play-work/{staging,inspect}`, RUY-866) and `/var/tmp`; `ProtectSystem=strict`, so removable media is read-only; `CapabilityBoundingSet=CAP_CHOWN CAP_DAC_OVERRIDE CAP_DAC_READ_SEARCH CAP_FOWNER CAP_FSETID` for the commit; `AF_INET` and `AF_INET6` for a missing runtime, as `ruya-store`; no `RestrictNamespaces` and the plain `@system-service` filter, so `systemd-run` and flatpak's triggers work), `org.ruyaos.Play1.conf` (root owns; root and `ruya-shell` call and receive the signals), `tmpfiles.d/ruya-play.conf` (`/var/lib/ruya-play/{incoming,state}` 0700 root) and `/usr/share/ruyaos/store-blocklist` (serial 1, no entries; a host test parses it). `scripts/vm-play-check.sh` (modes `check` and `helper`) is RUY-100's VM check; its `verify` mode is RUY-834's and its `perms` mode RUY-851's (the installed app's `flatpak info --show-permissions` against §8's mapping, and its `trust.json`).

Re-verification: "Verify files" in the app's options re-hashes the installed payload against `play.files` (cheap defence against disk corruption; OSTree also checks its own objects).

## 8. Permissions

A closed vocabulary. The manifest requests; the importer maps each entry to the Flatpak permission set of the generated app; the shell shows each in plain words before install; the effective set is the request **capped by the trust tier** (and can be reduced by an admin, 03 §4.4).

One row per value that asks for something; `network: false` (the default), `removable_media: none` (the default) and a `false` bool ask for nothing and grant nothing. "Flatpak metadata" is every line the value adds to the generated app's metadata, exactly (`ruya_play_trust::permissions::PERMISSIONS`, RUY-851; `tests/permissions_spec_sync.rs` parses this table and fails when the code says otherwise).

| Key | Value | Flatpak metadata | Risk | Plain words |
|---|---|---|---|---|
| (always) | | `[Context] shared=ipc`, `[Context] sockets=wayland` (`sockets=x11` instead for the `wine` and `proton` runners, §6.3), `[Context] sockets=pulseaudio`, `[Context] devices=dri`; the app's own data directory is Flatpak's | low | "Plays sound, uses graphics" |
| `input` | `controllers` | none: every app gets `/dev/input` from `ruya-session` (`--device=input`, 06 §1), keyboards come through the compositor | low | "Uses controllers" |
| `input` | `controllers+keyboard-mouse` (default) | none, as above | low | "Uses controllers, keyboard and mouse" |
| `input` | `all-devices` | `[Context] devices=all` | **high** | "Accesses all devices" |
| `network` | `true` | `[Context] shared=network` | medium | "Uses the network" |
| `removable_media` | `read` | `[Context] filesystems=/run/media:ro` (the mounted drives, read-only) | medium | "Reads files on USB drives" |
| `removable_media` | `write` | `[Context] filesystems=/run/media` | medium | "Changes files on USB drives" |
| `multiarch` | `true` | `[Context] features=multiarch` (32-bit Wine) | medium | "Runs 32-bit programs" |
| `gamemode` | `true` | `[Session Bus Policy] com.feralinteractive.GameMode=talk`, no other bus name | low | "Asks the system to prioritise it" |
| `realtime` | `true` | none: the Realtime portal is open to every app | low | "Asks the system to prioritise it" |
| `devel` | `true` | `[Context] features=devel` (ptrace, perf), needed by rare anti-tamper | **high** | "Can inspect other programs" |
| `network` + `removable_media` | both asked | nothing beyond each one's lines | **high** | "Uses the network and reaches USB drives" |
| `microphone`, `camera`, `bluetooth` | not in the vocabulary yet | no portal backend exists (§18 item 12): a package that asks is refused with `permissions.unknown_key`, not silently reduced | | |
| `reasons` | map key -> localized text (<= 120 chars) | shown next to the permission | | the developer's own words |

- **No host filesystem access, no session or system bus names, no `--talk-name`, no `--filesystem` of any other path, no access to other apps' data, no portal override**, because those keys do not exist in the vocabulary. A package that needs them is not a `.play` (it is a Flatpak and goes to Flathub or the developer remote).
- **Ceilings by trust tier:** `official`: low, medium, high (high needs the Official review and the admin gate); `developer`: low and medium freely, high with the admin's PIN and a warning; `unverified`: low and medium only (a high request makes the package uninstallable, not silently reduced). `network` together with `removable_media` counts as high risk (§18 item 13). The table and these ceilings are data in `ruya-play-trust` (`PERMISSIONS` and `HIGH_RISK_PAIRS` in `permissions.rs`, RUY-851; `CEILINGS` in `tier.rs`, RUY-93; `tests/ceilings.rs` checks every tier against every row). The gate of an assessment is what Play1's Inspect reports as `gate`; `Install` needs `admin_approved` for every package (§7.2), so a gated one (`admin-pin`, `admin-pin-warning`) needs it too, and the shell asks a profile that is not an admin for an admin's PIN whatever the gate; the gate only sets the sheet's PIN line and, for `admin-pin-warning`, its warning (§7.2, RUY-853). A refusal stays `check_ceiling`'s `ceiling.refused`.
- **As built (RUY-851):** the generated app gets exactly the lines of the table for its requests under the ceiling, and nothing else (`commit::metadata`, exact strings in `ruya-play`'s `tests/metadata.rs`: a value smuggled through `run.env`, `reasons` or a field name of the package's own reaches no line). The Wine sample (`controllers+keyboard-mouse`, `multiarch`) gets `shared=ipc;`, `sockets=x11;pulseaudio;`, `devices=dri;`, `features=multiarch;`.
- Permissions are **static** (03 §4.4). An update that adds one is shown as "The update adds: ..." and, when it adds a high-risk one, needs the admin's PIN, exactly as T-156 does for Flatpak updates. The comparison is `ruya_play_trust::diff` (added, removed, high-risk added, by key and value; a pair that becomes complete is a high-risk addition); Play1's Inspect returns it for a package whose id is installed (RUY-851); the shell shows it as built (RUY-853): "The update adds: ..." on the package page and on the confirm sheet when `updateKnown` (in `warningText` when it adds a high-risk request), and the sheet lists high-risk rows first.
- The platform, not the package, sets resource limits on the running unit: the same for every app (Flatpak, `.play`, Steam), `MemoryMax=90%` (systemd's share of physical RAM; a leaking game is killed before the shell) and `TasksMax=8192`, set by `ruya-session` in `launch_command_in` (RUY-855; `requirements.min_ram_mb` is a minimum, not a cap). CPU weight lower than the shell's is not built yet.

## 9. Security model

### 9.1 What an attacker controls, and what stops them

| Threat (a hostile or compromised package, USB stick or update server) | Defence |
|---|---|
| Path traversal, absolute paths, odd Unicode, case-collision tricks, device files | §4.2 rules checked on names before content; extraction by an unprivileged helper into staging; commit walks without following links. |
| Symlink / hard-link escape from an archive | Links exist only as data in `play.files` (relative, in-tree, one hop); real links in the package are invalid; the importer creates them. |
| Zip bomb, huge file counts, endless nesting, slow parsers | Size, count, ratio, depth and time limits; free-space check first; helper under memory/time limits. |
| Malformed JSON / schema abuse | Size and depth caps, strict schema for the security-relevant sections, no dynamic evaluation of anything. |
| Image/video decoder exploits | Decoding only in the sandboxed helper; allow-listed formats; re-encode so the shell and the library load only vetted, canonical files; no SVG, no animated images. Video playback hardening is Q5. |
| Install-time code execution | None exists: no hooks or scripts. Setup steps run at first launch inside the sandbox. |
| Privilege through file attributes | setuid/setgid/caps/xattrs dropped; modes normalised; files owned by root and read-only in the Flatpak deployment. |
| Asking the sandbox for too much | Closed permission vocabulary; ceilings per tier; admin PIN for high risk; the manifest never supplies Flatpak metadata. |
| Impersonation (a game that is called "Settings" or copies another game's icon and name) | Reserved names, `id` uniqueness (installing over an existing id needs the same signing key, §11), signer shown on the detail page, the Official tier is the only "verified" label. |
| Lookalike names (a Cyrillic `Ѕettings`, `Settings` with a zero-width letter, `Settiոgs`) | The format refuses invisible characters and exact system names only; it does not catch lookalikes. The shell always shows the tier badge and signer next to a name, and the Official tier is the only "verified" label. |
| Reading other profiles' or other apps' data | Unix profile homes (0700) and per-app Flatpak data dirs; the Wine prefix is per profile and per game; the sandbox has no path to anything else. |
| Network exfiltration | `network: false` by default, shown on the page; a game without it cannot phone home. |
| Tampering after install | Read-only deployment; OSTree object checks; "Verify files". |
| TOCTOU between verify and use | The helper's identity is exclusive and gone before commit; commit re-walks without following links; files are copied into OSTree, not used in place from the stick. |
| A bundled runner with a known vulnerability | `source: newest/prefer-system` lets the OS's fixed runner win; the revocation list (below) can disable a runner by hash; the Store shows "uses an old Wine". |
| Malicious update (key takeover, downgrade, redirect, replayed old feed) | §11: same-key rule, `build` only increases, signed feed with `expires`, https with a pinned host, the service (not the game) downloads. |
| USB autorun | Never: nothing is opened until the player chooses "Install from USB"; step 2 reads data only. |
| Compromise of the Official store | The `official` badge needs two things (developer key *and* store key); revocation can be pushed by the OS image's pinned root key; the OS signing key is separate from the store key. |

### 9.2 Signatures and trust tiers

*As built in RUY-93 (crate `services/ruya-play-trust`, on top of `ruya-play-format`; pure rules, no D-Bus, no network, the caller passes the time).*

- **Signing is Ed25519 in a small format of our own** (lead decision, RUY-93): library `ed25519-dalek` 2.2 (BSD-3-Clause, pure Rust, `cargo deny` clean), verified with `verify_strict` (no malleable signatures, no small-order keys). Not minisign or `ssh-keygen -Y sign`: each brings a second text format and prehash variants the console does not need, and `ruya-pack` (T-233) signs anyway, so developers need no other tool.
- **The envelope.** `play.sig`, `store.sig`, a rotation statement and the signature of a downloaded blocklist all have one shape: `{ "format": 1, "key": "<base64>", "statement": "<base64>", "sig": "<base64>" }`. The encoding, exactly:
  - `key` is the raw 32-byte Ed25519 public key, `sig` the raw 64-byte signature, `statement` the statement's bytes; all three in base64 with the standard RFC 4648 alphabet (`A-Z a-z 0-9 + /`) and `=` padding, read strictly (no line breaks, no other alphabet, no missing padding).
  - The signature covers `prefix || statement`, the statement bytes exactly as given in the envelope (no canonical JSON: the verifier never re-serialises). The prefix is ASCII text followed by one real NUL byte (0x00), written `\0` here: `ruyaos-play-sig-v1\0` (`play.sig`), `ruyaos-store-sig-v1\0` (`store.sig`), `ruyaos-play-rotate-v1\0` (rotation), `ruyaos-blocklist-v1\0` (downloaded blocklist). Each use has its own prefix, so a signature made for one never verifies as another.
  - A statement is a UTF-8 JSON object with exactly its keys: an unknown or a missing key is `sig.malformed`, a key named twice `sig.duplicate_key`. `format`, `build` and `seq` are JSON integers (`7`, not `7.0` or `"7"`); `id` is ASCII; hashes are 64 lower-case hex characters of a SHA-256; times are UTC `YYYY-MM-DDTHH:MM:SSZ`.
  - A **key id** is the first 32 lower-case hex characters (128 bits) of the SHA-256 of the 32 key bytes; it is what the shell shows and what the blocklist names.
- **Every signed file is untrusted input:** at most 64 KiB, a statement at most 4 KiB, nesting at most 4, UTF-8; an envelope `format` of 2 or more is `sig.format_too_new`.
- **`play.sig`** statement: `{ "id", "build", "play_json_sha256", "play_files_sha256", "signed_at" }`, plus `"rotations_sha256"` when it carries rotations (below). `signed_at` is the developer's claim, recorded and never used to decide trust. The hashes are over the exact bytes of `play.json` and `play.files`; because `play.files` lists every other file's SHA-256, **one signature covers the whole package** (a changed file is the format's `package.hash_mismatch`). The signed `id` and `build` must equal the manifest's exactly (`sig.wrong_id`, `sig.wrong_build`). The signer's display name is the manifest's `developer`; the key id is always shown next to it.
- **Rotations travel in `play.sig`** (lead, RUY-93): `"rotations": [ <envelope>, ... ]`, 1 to 8 rotation envelopes, after the four envelope keys; no other envelope may carry them. They are bound to the package key's own signature: `rotations_sha256` is the SHA-256 of the ASCII text made of each carried envelope's `statement` and `sig` base64 strings in carried order, joined by one `\n` (0x0A) and with no trailing one (`statement1\nsig1\nstatement2\nsig2`). Rotations without a matching `rotations_sha256`, or a `rotations_sha256` without them, is `sig.rotations_changed`, so nobody who passes a package along can add, drop or swap one.
- **`store.sig`** statement: `{ "id", "build", "play_sig_sha256", "signed_at" }`: the store countersigns exactly these `play.sig` bytes for this id and build (`store_sig.play_sig_changed`, `sig.wrong_id`, `sig.wrong_build`). It counts only when its key is one of the store keys the image pins (more than one while the store key is rotated by an OS update; the real key arrives with the image work). A valid `store.sig` by any other key is **ignored**: the package keeps its `developer` tier (a third-party store's own key is RUY-106's), and its key id is kept for display. A broken `store.sig` is an error like any other signature, and a `store.sig` without `play.sig` is `store_sig.without_play_sig`.
- **Tiers:** `official` (a valid `play.sig` *and* a valid `store.sig` by a pinned key), `developer` (a valid `play.sig`), `unverified` (no `play.sig`; developer mode only, otherwise `trust.needs_developer_mode`). A *bad* or mismatching signature is never downgraded to `unverified`, in developer mode either: it is an error ("This package was changed after it was signed"). `ValidateOptions.official` (reserved ids and system-like names, §4.1) is set **only** from a verified `store.sig` by a pinned key, never from the manifest. The place a `developer` package comes from is a "third-party store" (§18 item 6).
- **Permission ceilings** are data in the crate (`CEILINGS`, and `PERMISSIONS` and `HIGH_RISK_PAIRS`, §8's one table, RUY-851): §8's table, plus `network` together with `removable_media` counting as high risk; a value the table does not class counts as high. `unverified` with a high-risk request is `ceiling.refused` (uninstallable, not reduced).
- **Id ownership is the signature tier's job, not the format's.** Ids that differ only in letter case are the same id (records are looked up by the ASCII lower-case id; the format only compares the reserved prefixes `org.ruyaos.` and `play.` that way).
- **Key continuity (trust on first use).** The console keeps per id: the key that owns it, when it was first seen, the `seq` of the last rotation applied and the key ids it retired for the id, plus the admin's developer-mode flag. The file is `/var/lib/ruya-play/trust.json` (created with mode 0600, flushed, renamed over the old one, then the folder flushed; a temporary file left by a crash is replaced, never read); a file that cannot be read as written is `state.corrupt` and is never reset silently. Rules:
  - The first signed install of an id records its key, and the newest `seq` of the bound rotations it carries that end at its key (an unsigned install records nothing). Later installs and updates must be signed by the same key; an unsigned package for an id with a record is refused too.
  - Another key is accepted only through **rotation statements** `{ "id", "old_key", "new_key", "seq", "signed_at" }` (keys in base64, `seq` at least 1), each signed by its `old_key` (`rotation.not_by_old_key` otherwise; another id is `rotation.wrong_id`). From the recorded key the chain is followed in `seq` order, each `seq` strictly above the last one applied, until the package's key; then the id moves to the new key and the old one is retired. A statement from the recorded key whose `seq` is equal or lower is `rotation.replayed`; no chain is `trust.different_developer` ("This isn't the same developer").
  - **A retired key stays retired:** a rotation that hands the id to a key retired for it is `rotation.to_retired_key`, and a package signed by a retired key is `trust.different_developer`. Retired key ids are shown to an admin. The record keeps the last 64 retired key ids of an id (`MAX_RETIRED`); a key retired 64 rotations ago is forgotten, which needs 64 rotations by the holder of the current key and gains an attacker nothing.
  - The record **survives an uninstall while any profile keeps data for the id**, so a package signed by another key cannot inherit the saves. An uninstall without kept data frees the id.
  - The admin action **"Forget this game's data and key"** (`forget(id)`) drops the record; the next install starts trust on first use again. It is the way out for a squatted id (§18 item 17), and the `trust.different_developer` message says so.
  - **A key that was stolen or leaked** (not only lost): rotate at once while the old key is still held (`ruya-pack sign --rotate-from <old key file>` with the new key) so installed copies follow the chain, and report the old key id for the `[packages]` blocklist (`key <key id> <reason>`). Until then the holder of the key can sign packages the console accepts as the developer's.
  - **A developer who lost the key** (§18 item 18) cannot rotate: rotation needs the old key. There are two ways out, and a `store.sig` never overrides the key record (lead, RUY-93): the player or an admin uses "Forget this game's data and key" and installs the package signed with the new key; or a store reissues the game under the new key, and players do the same.
  - The detail page shows "Signed by Example Games (key 3f9a...c01), first installed on ..." with the key id always visible to an admin.
- **Revocation** (§18 item 7, `10-stores.md` §6) is the `[packages]` section of the store blocklist, one file shipped in the image at `/usr/share/ruyaos/store-blocklist`. The image's copy is authenticated by the OS update itself: no signature, no `expires`. The text: `#` comments and empty lines are ignored; a header line `serial <n>` before the first section; `[stores]` belongs to the store service (T-441) and is not read here; `[packages]` has one entry per line with a reason an admin can read (at most 200 characters):
  - `key <key id> <reason>`: the developer key, or the store key of an `official` package;
  - `id <id> <builds> <reason>`: builds are `*`, `N`, `N-M` or `N-`; the id compares case-insensitively;
  - `content <sha256> <reason>`: the SHA-256 of the package's `play.files` (it covers every file);
  - `runner <sha256> <reason>`: the hash of a runner, as runner resolution (T-239) reports it for the runner a package uses.

  A line with an unknown first word is skipped (a newer list may add kinds); a known kind with bad fields, a control character or text that is not UTF-8 is `blocklist.malformed`. A matching entry refuses the install with `revoked.key`, `revoked.id`, `revoked.content` or `revoked.runner`. What an installed, revoked package does (it stops launching; "Removed for safety: ..." with the reason; uninstall still works) is T-241's.
- **The image's list fails closed:** when the image's file is missing or does not parse, nothing can be checked, so every install is refused with `blocklist.unavailable` (no download makes up for it). A check in the image build that the shipped file parses is planned.
- **A fresher downloaded copy** (fetching it is later work) is the same text plus `store-blocklist.sig`, an envelope with the prefix `ruyaos-blocklist-v1\0` and the statement `{ "blocklist_sha256", "signed_at", "expires" }`. It is added only when its key is a pinned store key (`blocklist.not_store_key`), the text is the signed one (`blocklist.changed`), the console's clock is before `expires` (`blocklist.expired`) and its `serial` is above the image's (`blocklist.not_newer`). **A download never removes an entry:** the checks use the union of the image's entries and the download's; the serial only decides which download is kept. **Q6 policy (decided):** otherwise the image's copy is used alone, and the reason is kept so the shell can say the safety list is out of date; a stale or bad download never blocks an install or a launch on its own.
- **The clock.** `expires` is compared with the console's own clock. That is safe even when the clock is wrong: a wrong clock can only make the console set aside a download it could have used (the image's copy is still checked), and because the checks use the union, no clock can un-revoke an entry. No other rule here reads a time to decide trust.
- **Where private keys live:** only on developers' machines (`ruya-pack sign` reads a key file or an agent; the library has `generate_key()` and `sign_package()`) and with the store. Never in this repo, the image, or CI logs. The tests generate their keys, except the published test seeds of the vectors below, which are worth nothing.

### 9.3 Rules for the code that handles packages

1. Everything inside a package is **untrusted data**: names, text, JSON, images, video, hashes, even sizes.
2. Parsing and unpacking never run as root and never in the shell process or in `ruya-library`.
3. Only the small commit step runs privileged, and it re-validates paths and kinds itself.
4. A package never reaches a `Command` string: argv arrays only; no shell, no `sh -c`.
5. Display strings are escaped for the target (QML text with `Text.PlainText`; never rich text from a package).
6. Every limit is a named constant tested at, below and above the boundary, with a fixture package for each hostile case (T-230, T-237).

## 10. Data, saves and uninstall

Follows 03 §4.5a without change: per-profile `~/.var/app/play.<id>/{data,config,cache}`; recommended layout `data/saves`, `data/states`; `data.saves` / `data.cache` in the manifest declare paths for backup (T-215), written with a root name: `data:` (XDG data), `config:`, `prefix:` (inside the Wine prefix, where Windows games keep `Documents/My Games/...`). Uninstall keeps data by default ("Keep saves?"); an OS update never touches `/var`. Emulator saves and states belong in `data:` so they survive an update of the game or the emulator.

## 11. Updates

Principle: **updates are signed, ordered by `build`, run by the OS and never by the game.** There are three ways, in priority order.

1. **From a store (replaced by §18 item 1 and `10-stores.md` §11: the store's signed index, the same importer; the text of this item is the old design).** If the package was installed from the `ruyaos` or a developer remote, `ruya-store` updates it like any other app (OSTree deltas, `Rollback(id, commit)`, the permission-diff flow). The manifest's `update` block is ignored. This is the recommended path for anything distributed publicly: one trusted place, one update mechanism, no per-game servers contacted. *Yes: the Store should be the update channel for Store packages.*
2. **Self-hosted feed (sideloaded packages).** `update.feed` is an https URL of a signed JSON feed:
   ```json
   { "format": 1, "id": "com.example.starhopper", "channel": "stable", "expires": "2026-12-31T00:00:00Z",
     "releases": [ { "version": "1.4.3", "build": 143, "released": "2026-11-01",
                     "notes": { "en": "Fixes the second boss." }, "min_os": "0.1",
                     "url": "https://example.com/files/starhopper-1.4.3.play.zip",
                     "size": 4900000000, "sha256": "..." } ] }
   ```
   plus `feed.json.sig` by the **same key** that signed the installed package (or a rotation); it is an envelope of §9.2 with its own domain prefix, fixed by T-241. Rules: the feed host is the one in the installed manifest (redirects must stay on its registrable domain); `expires` must be in the future (stale feeds are ignored, which defeats replaying an old feed that hides a fix); only `build` greater than the installed one is offered (a downgrade is never an update); the download is performed by `ruya-play`, written to `incoming/`, **verified and imported exactly like an install** (§7.3), including the permission diff and the same-key rule. The shell shows "Update available: 1.4.3 (4.9 GB) from example.com".
   - **Privacy:** checking a developer's server tells that server this console's IP and the game. So sideloaded packages ask once at install ("This game can check example.com for updates. Allow?", default **No**), the choice is a per-app toggle in its options, and checks happen only when the console is idle and online (and the game's page was opened or weekly). Store-installed packages never contact the developer.
   - Never while the game runs; never silently when the update adds a permission; `Update automatically` is available for the `official` tier only, off by default elsewhere.
3. **By hand:** the player installs a newer `.play` over the old one (from USB or a download). Same verification; same-key rule; keeps the data. A package with a different key for the same id is refused with "This isn't the same developer".

Details:
- **Rollback:** the previous deployment stays until the next successful launch of the new one; "Roll back to 1.4.2" uses `Store1.Rollback`. A downgrade that is not a rollback of an installed deployment is refused.
- **Prefix / runner changes** are handled by `epoch` (§6.3). A runner update (system Wine) is an update of the extension, not of the game; the Compatibility screen shows the runner in use, and "Try the bundled runner" is the escape.
- **Delta updates (not v1):** `play.files` already hashes every file, so a future feed can list changed files only and the service can fetch just those objects (HTTP range / object URLs); Store builds already get OSTree deltas.
- **Size accounting:** an update downloads the whole new package in v1. The feed's `size` is shown before the download; the free-space check covers old + new.

## 12. Shell integration

- **Library and Home.** A `.play` is an installed Flatpak; `Library1` lists it with the vetted art and facts (built, RUY-852: the item keeps its `a{sv}` and gains `play` true, `genres`, `players (uu)`, `controller`, `age_rating a{ss}`, `play_tier`, `play_signer`, `play_signer_key_id` (`trust.json`'s `signer_id`, passed through), `play_screenshots` (`as`: the 1080p screenshots in order, at most 20; RUY-872) and the art roles `logo`, `card`, `cover`, `preview`, `trailer` next to `icon` and `hero`; nothing is added to a non-`.play` item). A native game has none of the four; a package that fails the strict re-parse gets `play_resolve_error` ("This game's files are damaged ...") and keeps its title and art. They say nothing of a per-game choice or the "Try the bundled runner" net, and they are not recomputed when a runner is installed later, only at the next scan. Off Linux (the Windows test host) the real file system is not there and the four keys are absent. The unit needs no change: `ProtectSystem=strict` leaves `/var/lib/flatpak` readable, and `ruya-shell` reads the art by path. ## 13. Developer tooling (`ruya-pack`)

A command-line tool for developers (Windows, Linux, macOS; Rust, MIT OR Apache-2.0; crate `services/ruya-pack`, library plus binary). It links the same crates the console verifies with (`ruya-play-format`, `ruya-play-art`, `ruya-play-trust`) and re-implements none of their rules, so a package the tool accepts is a package the console accepts. All commands live in the library (`ruya_pack::run(args, ctx) -> Outcome`), so the one `ruya` CLI (T-416, ADR-031) can mount them as `ruya pack` with the same JSON, exit codes and error catalogue.

| Command | Does |
|---|---|
| `ruya-pack init <dir> [--id ID] [--name NAME] [--force]` | Writes a skeleton `play.json`, a `README.txt` that explains it (JSON has no comments), `art/`, `payload/` (with a placeholder `run.sh`) and `licences/`, and a **64x64 placeholder icon** that fails `validate` with `art.too_small` until it is replaced by a 512x512 image. |
| `ruya-pack validate <pkg>` | `<pkg>` is a folder or a `.play.zip`. Runs `ruya_play_format::validate` (schema, paths, file table, hashes), vets every art and video file with `ruya_play_art::vet` into a scratch folder, checks the **licence duty** of bundled components, warns about FAT32, and dry-runs the runner resolution of §6.2 against the system runners named on the command line: `--system-wine 10.2`, `--system-proton-ge 10.9`, `--system-runner family=version` (all repeatable). The family of a bundled copy is the one its `runner.json` declares, checked by `ruya_play_format::validate` (§6.2.1; none: the type's own family). A component whose family has no runner named is skipped and a `resolve.not_checked` warning says so. The result also carries the installed size and the memory the manifest asks for. |
| `ruya-pack build <dir> [-o out.play.zip] [--deflate] [--links-as-data] [--exec PATH]` | Writes `play.files` into the folder (sorted bytewise, SHA-256, sizes, `x:1` from the executable bit; on Windows a file that starts with `#!` or an ELF header, or is named by `--exec`, gets it; empty folders as `d`), builds the **deterministic zip**, and runs `validate` on the result; no zip is left behind if it fails. `installed_mb` is not written (it is computed). A real symlink in the folder is refused (`build.symlink`); `--links-as-data` turns a relative link that stays inside the package into an `l` line (`build.symlink_unsupported` otherwise). A `play.sig` or `store.sig` in the folder is not built in (`build.signature_dropped` warning): `play.files` is rewritten, so the old signature would not match. The default output is `<folder name>.play.zip` next to the folder. |
| `ruya-pack keygen <name> [--force]` | Writes `<name>.key` and `<name>.pub` and prints only the key id (32 hex) and the public key. It never replaces a key unless `--force`. |
| `ruya-pack sign <pkg> [--key FILE] [--rotate-from OLDKEYFILE] [--signed-at TIME] [--deflate]` | Writes `play.sig` with `ruya_play_trust::sign_package` and verifies it with the console's `verify_signatures` and `bind_to_manifest` before saving. A folder gets the file; a zip is written again with the entry added (stored; `--deflate` to compress; a `store.sig` is dropped). `--rotate-from` adds a rotation envelope from the old key to the signing key and sets `rotations_sha256` (RUY-93); rotations already in the package's `play.sig` are carried and the new one is numbered after them. `--signed-at` fixes the time (`YYYY-MM-DDTHH:MM:SSZ`) for reproducible signatures. |
| `ruya-pack inspect <pkg>` | Prints what the console will show, using the console's own `inspect` step with developer mode on and no store key pinned: name, signer and tier, the permissions in the plain words of §8 with their risk, the admin gate, size, the runner and how it resolves (with `--system-*` flags), and the state of each art file. A trust refusal (`sig.*`, `ceiling.refused`) is a problem. |
| `ruya-pack runner-check <dir> [--write-hash] [--record FILE]` | (RUY-34) Checks a runner folder on disk as the console reads it: `runner.json` a regular file that `runner::parse_runner` accepts (`runner.not_a_file` when missing), every entry it names a regular file (`runner.entry_missing`), and every entry something a file table can hold (a link relative and inside the folder, no hard link or special file: `build.symlink_unsupported`, `entry.*`). Prints the runner and its **runner hash** (§7.3: `RunnerHasher` over the table `build` would write for the tree, files with their SHA-256 and executable bit, links as written, empty folders; a root `.ruya-runner-hash` left out), so it equals what the importer computes for the same tree in a package. `--write-hash` writes `.ruya-runner-hash` (the hash and a line feed; `runner::HASH_FILE`); `--record` appends the runner's `runners.list` line (§6.4) to FILE and needs a folder name that can be `org.ruyaos.Play.Runner.<Name>` (`runner::is_system_runner_name`; a usage error otherwise). The image build runs it on every system runner; a packager may run it on a bundled copy. JSON fields `runner` (`name`, `family`, `kind`, `version`, `licence`, `source_url`), `hash`, `entries`. |
| `ruya-pack run <pkg>` | A later task (install and launch on a console in developer mode). |

**Key file.** `keygen` writes two lines: `ruyaos-play-key-v1` and the base64 (RFC 4648, with padding) of the 32-byte Ed25519 seed; mode 0600 on Unix. `<name>.pub` holds `ruyaos-play-pub-v1` and the base64 of the public key. `sign` reads the key from `--key <file>` or from the environment variable `RUYA_PACK_KEY` (the base64 line alone). **No option takes key text**: it would stay in the shell history. The key appears in no output or error, text or JSON; a key typed where a file name belongs is refused without being echoed.

**Result and exit codes.** Every command takes `--json` and prints one object: `{ "schema": 1, "ok": bool, "command": "...", "problems": [ {"code", "path", "message", "fix"} ], "warnings": [ ... ], ...the command's own fields }`. `schema` is the version of this object; `command` is the subcommand name (`validate`), and under the one `ruya` CLI it reads `pack validate`. `code` is the crates' own (§4.5, `art.*`, `video.*`, `sig.*`, `trust.*`, `ceiling.*`) or one `ruya-pack` adds (`licence.text_missing`, `licence.source_missing`, `build.*`, `size.fat32`, `key.missing`, `key.invalid`, `key.same`, `key.exists`, `resolve.*`, `init.not_empty`, `usage.error`, `io.error`); usage and I/O failures are in `problems` too (an I/O failure fills `path`). `fix` is one line the tool adds per code, kept in one table (`services/ruya-pack/src/fixes.rs`) from which the error catalogue of the developer guide is generated (`fixes::catalogue()`). Exit codes: **0** ok, **1** problems found, **2** usage, **3** I/O. For scripts: warnings never change the exit code; in text mode exits 0 and 1 print to stdout and exits 2 and 3 to stderr; `--json` always prints to stdout. Anything a message echoes from the command line passes one redaction helper (`ruya_pack::redact`: it masks the key file header and any base64 run of 40 or more characters), and the values of `--key` and `--rotate-from` are never echoed.

**Deterministic zip.** Entries are sorted bytewise, every timestamp is 1980-01-01 00:00:00, the Unix mode is the only attribute (0644, 0755 with the executable bit), and there are no comments or extra fields except ZIP64 where a size or offset needs it. Entries are stored by default (payloads are compressed already and the console reads stored zips faster); `--deflate` compresses with miniz_oxide through flate2 at its default level, so the bytes are reproducible for one tool version. The result is then read back by the format crate's own zip reader.

**Licence duty of bundled code** (checked by `validate`): every bundled component names an SPDX licence (shape checked by the format crate), has a licence text under `licences/` (a path segment or file name there that names the component, the licence id or the bundled folder as whole words: `licences/wine-LGPL-2.1.txt`, `licences/Wine/COPYING`; not a substring), and, for copyleft licences (GPL, LGPL, AGPL, MPL, EPL, CDDL, EUPL, OSL, CC-BY-SA, SSPL, CECILL, MS-RL), a `source_url` or the source itself as a file under `sources/` (or `licences/sources/`). RuyaOS only provides the tool; the developer is the distributor of what they bundle.

**FAT32.** A zip, or a file in the folder form, of 4 GiB or more cannot be copied to a FAT32 drive: `validate` and `build` warn (`size.fat32`) and recommend exFAT (§18 item 23).

**The developer guide and the samples (RUY-105, built).** [`docs/developers/play-packages.md`](../developers/play-packages.md) is the guide: the walk from `init` to a signed zip, the layout, a field reference, the art and hero composition guide, runner sources, the Wine prefix, permissions, keys, updates, legal duties, and the error catalogue. Two tests keep it true: `services/ruya-pack/tests/guide.rs` compares the catalogue with `fixes::catalogue()` (regenerate with `RUYA_WRITE_CATALOGUE=1 cargo test -p ruya-pack --test guide`) and the field reference with the properties of `api/play/play.schema.json`; `scripts/lint-dev-docs.ps1` validates every JSON block of the guide that is a whole `play.json` against that schema (a small validator for the keywords the schema uses, with fixtures in `dev.ps1 docs`). The samples are `samples/hello-play-native/` (the Hello Game sources, runner `native`) and `samples/hello-play-wine/` (a Win32 program cross-compiled with `x86_64-w64-mingw32-gcc`, `source: system`, a saves path in the prefix, a no-op setup step). `newest` and `prefer-system` need a bundled Wine, which would put it in git, so that manifest is a JSON block in the guide (validated against the schema by the lint), not a sample. No binary is committed: each sample has a `package/` folder plus `build.sh`, and `services/ruya-pack/tests/samples.rs` copies the folder, writes stub payload files and runs `build`, `validate` and `inspect`. The console parts the guide marks planned are RUY-100 (the install service, and the VM check that installs the native sample) and RUY-101 (the launcher, `ruya-pack run`).

## 15. Compatibility and versioning of the format

- `format` is a major number. **Every new key in a strict object (`permissions`, `run`, `run.prefix`, `run.setup[]`, `components[]`, `components[].bundled`) and every new value in a closed vocabulary (genres, link kinds, runners, component types and sources, launch modes, input modes, ...) bumps the major**, and a package that uses one must declare that major. There is no `min_format` field: a console that knows the major knows every key and value of it. Keys outside the strict objects are ignored by an older console and may be added without a bump.
- A console supports every major it knows. For a package whose `format` is a JSON number of 2 or more (including `2.0` or a number beyond 64 bits that still fits a double; `1e400` is `manifest.invalid_json`), it reads nothing else of the package and returns only `format.too_new` ("needs a newer RuyaOS"), because the table and manifest rules of a newer major are not ours to apply. A `format` that is not a number, or below 1, or not a whole number, is `format.invalid`.
- The schema file `api/play/play.schema.json` is the machine-readable contract (like `api/dbus/*.xml`: a draft until the first release, extend it in the same commit as the code that uses it). It states the shapes, vocabularies and numbers; the crate `services/ruya-play-format` is the only parser and applies the rules a schema cannot (the file table, paths, cross-references, reserved ids and names). `tests/schema.rs` keeps the schema's numbers and vocabularies equal to the crate's constants. Strict objects (`permissions`, `run`, `components`, and the objects inside them) refuse unknown keys with `permissions.unknown_key`, `run.unknown_key` or `component.unknown_key`; a `format` above the one the crate knows gives `format.too_new` and nothing else is checked.
- The `play.` Flatpak id prefix and the `${...}` placeholders are part of the format; changing them is a major bump.
- **Signatures (§9.2, RUY-93).** The envelopes and their statements change only through the envelope `format`: a new statement key, a changed meaning, a new domain prefix or another hash or key encoding is envelope `format` 2, which an older console refuses with `sig.format_too_new`. A version 1 envelope and its statements never change.
- **Blocklist kinds (§9.2).** The fields of an existing `[packages]` kind (`key`, `id`, `content`, `runner`) never change; a changed form gets a new keyword, which older consoles skip.

## 18. Review of this draft (lead, 2026-11-10): what to fix before T-230 starts

*Built in RUY-92 (T-230): items 8, 9, 10, 12, 15, 21 and 24 are in the format crate and `api/play/play.schema.json`; items 11, 13, 14, 16 to 20, 22 and 23 belong to later tickets (T-231, T-237, T-239 and the importer).* Found while planning stores (ADR-032, `10-stores.md`). Nothing here is built, so nothing is broken yet; each item names where it gets fixed. **A to D change the design and win over the sections above; the rest are corrections for the first task that touches the section.**

**A. Decided here (the text above is stale where it differs)**
1. **Stores carry `.play` files, never ready-made `play.<id>` Flatpaks** (`10-stores.md` §11). §11 way 1 ("OSTree deltas, like any other app") is replaced: every install and update, from any store, a feed or a USB drive, goes through the one importer. Reason: a store-built Flatpak would bring its own Flatpak metadata and art, the two things §7.1 and §5 say a package never supplies.
2. **One Flatpak transaction queue.** `ruya-play` builds and signs the commit; installing it into `/var/lib/flatpak` is a job of `ruya-store`'s queue (ADR-011, ADR-026). §7.3 step 5 read as if two root services ran Flatpak transactions side by side. The device-local origin is a built-in, hidden store that nothing can remove or shadow (`10-stores.md` §3.1).
3. **The per-game runner choice is not stored in the app's own `config/`** (§6.2): the game can write there, so "the player decides" would not hold. It is kept by `ruya-library` (T-385, one mechanism for every Windows game, ADR-025).
4. **Sideloading needs an admin (owner, confirmed 2026-11-10).** §7.2 let a Standard profile install any signed low or medium package from a USB stick, system-wide, for every profile; a signature proves nothing about a stranger's key (§0.7). Store and USB installs follow `10-stores.md` §4: an admin, or an admin's PIN.

**B. Contradictions with later decisions**
5. **Runners (ADR-025, 2026-11-09).** §6.4, §14, Q3 and D3 still say Wine is the only system runner and Proton is never shipped; GE-Proton is now preinstalled and the default. So Q3 (does Proton's container nest inside the sandbox) is no longer optional: it decides whether the default runner works for `.play` at all, and is the first question of T-229. *Answered (RUY-91):* the default runner works for `.play`, but only without its container (§6.4).
6. **Words.** The tier `developer` and "developer remote" collide with the store trust `third-party` and with "developer mode". Keep the tier names, write "third-party store" for the place.
7. **Revocation (§9.2, Q6)** assumed the `ruyaos` remote; with D2 there is none in v1. It is one file with the store blocklist, shipped in the image and changed by OS updates (`10-stores.md` §6); a fresher copy from the official store is later. T-241 owns what an installed, revoked package does. (*Built in RUY-93:* the `[packages]` section and the check of a downloaded copy, §9.2.)

**C. Things the format cannot express today (T-230 must settle them in the schema)**
8. **Wine prefix templates do not fit the path rules.** A prefix has `dosdevices/c:` and `z:` (a colon in a name, forbidden by §4.2) and `z:` points at `/` (an absolute link, forbidden). Rule: a template never contains `dosdevices`; the launcher creates it.
9. **Real runner trees do not fit the link rule.** "A link must not point at another link" refuses the usual `libx.so -> libx.so.1 -> libx.so.1.2` chains of a bundled Wine or emulator. Allow chains up to 8 hops that stay inside the same top-level directory; `ruya-pack build` flattens what it can.
10. **Emulated games have no manifest fields.** `${disc}` exists (§6.3) but nothing declares discs, their order, or a multi-disc set. Add `run.discs[]`.
11. **"Timestamps from the manifest's build time"** (§4.2): the manifest has no such field. Use `play.sig`'s `signed_at`, or a fixed epoch for unsigned packages.
12. **`permissions` that have no mapping yet:** `microphone`, `camera`, `bluetooth` are "as the platform provides", and there is no portal backend (03 §4.4). Until one exists they are not in the vocabulary (an unknown key is an error, §4.1), and raw `bluetooth` is high risk, not medium.
13. **Combinations.** `network` with `removable_media`, `microphone` or `camera` is a way out for the player's files or voice: the pair counts as high risk even though each alone is medium. (*Built in RUY-93* for `network` + `removable_media`; the other two are not in the vocabulary.)
14. **`multiarch`** needs 32-bit runtime extensions that the console may not have offline; say where they come from (the official store) and that the install fetches them or refuses, like `source: system`.
15. **Flatpak id grammar.** `play.<id>` must be a valid Flatpak id: check the `-` rule and the length for the prefixed form, not only for `id`.

**D. Security and data gaps**
16. **Kept saves and a different key.** After an uninstall with "Keep saves", a package with the same `id` signed by another key may be installed (the `id -> key` record: is it kept after uninstall? unspecified) and would inherit `~/.var/app/play.<id>`. Rule: the record survives uninstall while any profile keeps data for the id; a different key is then refused, and an admin can "Forget this game's data and key" to free the id. (*Built in RUY-93* as rules: `record_uninstall`, `forget`.)
17. **Squatting an id.** The first package to claim an id on a console owns it (trust on first use); the genuine game is then refused as "not the same developer". The same admin action as item 16 is the way out; the message must say so. (*Built in RUY-93:* the `trust.different_developer` message names the action.)
18. **A developer who loses the key** has no rotation path (rotation needs the old key). Say it plainly in the guide: players must remove and reinstall (item 16), or the official store's countersignature decides. (*Decided in RUY-93 (lead):* a `store.sig` overriding the key record is **not in v1**. The two ways out are in §9.2: "Forget this game's data and key" and install again, or a store reissues the game under the new key and players do the same.)
19. **Feeds (§11 way 2).** "Redirects must stay on the registrable domain" needs a public-suffix list on the console: use the exact host. `expires` needs a correct clock, and a console can boot offline with a wrong one: a feed is also refused when its newest release is older than the installed build's `signed_at`. A feed signed with the package key keeps that key on a web server: allow a feed key delegated by the package key (one statement, like rotation).
20. **Disk space.** A downloaded 30 GB package needs the archive, the staging copy and the OSTree objects unless staging and repository share extents; §11 only says "old + new". T-229 measures the peak and the importer checks that number before the download. *Measured (RUY-91):* the staging copy is the whole peak, about 1.03x the payload, while staging, the local repo and `/var/lib/flatpak` share one reflink-capable filesystem. The check asks for archive + payload + 5 % there, and for archive + 2x payload anywhere else. A filesystem without reflinks was not measured.
21. **`run.env` is a deny-list, called an allow-list** (§6.3): `WINEPREFIX`, `WINESERVER`, `VK_ICD_FILENAMES`, `VK_LAYER_PATH`, `GST_PLUGIN_PATH`, `QT_PLUGIN_PATH` pass it and break what the platform sets. Not an escape (the package runs its own code in its own sandbox either way), but make it a real allow-list of prefixes. *Seen in RUY-91 (Q4):* `LD_PRELOAD` reaches the process, `VK_ICD_FILENAMES` can leave the game with no GPU, and `WINEPREFIX=/tmp/...` loses saves. So the list also leaves out `WINEPREFIX`, `VK_*`, `__GLX_*`, `__EGL_*`, `MESA_*` and `LIBGL_*`.
22. **Threats missing from §9.1:** a hostile store index (answered in `10-stores.md` §11.1), a hostile `runner.json` in a bundled component (it is parsed by the launcher inside the sandbox: fine, but say so), and a child profile seeing a system-wide package whose rating is the developer's own claim (T-211: treated as not rated).
23. **USB limits.** A `.play.zip` over 4 GiB does not fit on FAT32, the commonest stick format; the folder form does unless one file is over 4 GiB. `ruya-pack build` warns; the guide recommends exFAT. A stick pulled during import is a clean failure (staging removed): add it to the hostile-case fixtures.
