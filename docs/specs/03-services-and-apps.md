# RuyaOS — System Services, Apps, Media & Gaming

Status: **Draft v1** · Parent: [00-overview](00-overview.md)

## 1. Profiles & security (ADR-004)

### 1.1 Model
- A profile is a Unix user `ruya-p<N>` with home `/var/home/ruya-p<N>` (0700). Display name, avatar, role and PIN hash live in one root-only file, `/var/lib/ruyaos/profiles.toml` (0600, written atomically). Ids are never reused. Implemented in `services/ruya-profiles`; the contract is `api/dbus/org.ruyaos.Profiles1.xml`.
- Roles: **Admin** (one or more; the first profile created in OOBE) and **Standard**. There's also **Guest**, whose user is created on demand and whose home is wiped at logout.
- PIN: optional for Standard, mandatory for Admin, never for Guest. 4–6 ASCII digits, stored as an argon2id hash and verified only by `ruya-profiles`. After 5 failures, exponential back-off from 30 s up to 1 h. The counter is shared by every PIN check (sign-in, admin authorisation, PIN change) and lives in memory, so a service restart resets it. The first profile (OOBE) must be an admin. Later profiles need admin credentials, passed explicitly in v1 and via polkit from Phase 2.
- Admin-only actions (polkit `org.ruyaos.admin`): OS update/rollback/channel, add/remove remotes, install system-wide apps, create/delete profiles, factory reset. The shell asks for the admin PIN, which `ruya-profiles` turns into a short-lived polkit authorization.
- **Rename and delete (T-118 service, T-131 UI).** `RenameProfile(actor_id, actor_pin, id, name)`: the actor is an admin or the profile itself and is checked with its own PIN; the name follows the create rules (trimmed, 1-32 characters, no control characters). `DeleteProfile(admin_id, admin_pin, id)`: admin only; refused with `not-allowed` for the last admin and for the active profile; it runs `userdel --remove` (the Unix user and its home are gone, there is no "keep data" option) and, if that fails, answers `failed` and leaves the store unchanged. The store is written first and `userdel` runs after it; a failed `userdel` puts the profile back (a store-write failure therefore never leaves a listed profile without its Unix user; a leftover user after a double failure is harmless, since ids are never reused). Both count their PIN checks towards the shared lockout, and a deleted profile loses its lockout state. Ids stay unique forever.
- **VerifyAdmin (T-135).** `VerifyAdmin(admin_id, admin_pin)` answers `ok` when the id is an admin and the PIN matches, `not-allowed` otherwise (unknown id or not an admin), and changes nothing; it counts towards the shared lockout. The shell uses it to gate actions of other services behind an admin PIN (the system rollback).
- Locking: on profile switch, on idle timeout (configurable), and on resume from suspend if the profile has a PIN.

#### UI flows (as built, T-105, T-131)
Two Settings categories (T-315). **Manage profiles** (admins only) lists the profiles (colour, name, role, PIN yes/no, "You" for the active one) and offers Add profile, Rename and Delete. **My profile** (every signed-in profile) shows who you are (name, role, PIN yes/no) and offers Rename (yourself), Set / Change / Remove my PIN and Activity. Each item below says where it lives.
- **Add profile** (Manage profiles, admins only): an inline form with Name (the on-screen keyboard), Role (Standard or Guest) and, for Standard, "Protect with a PIN". "Create profile" then collects the new PIN twice (only for a Standard profile with a PIN) and the admin's own PIN, and calls `CreateProfile` with the active admin's id and that PIN.
- **Change my PIN / Set a PIN** (My profile; Admin and Standard): the current PIN (only if there is one), then the new PIN twice, then `SetPin`.
- **Remove my PIN** (My profile; Standard with a PIN only; an Admin cannot remove theirs, so the row is hidden): the current PIN, then `SetPin` with an empty new PIN.
- **Rename and Delete** (T-131, split in T-315): in Manage profiles, Accept on another profile's row shows two rows under the list, "Rename <name>" and "Delete <name>" (hidden when the rule forbids them; the Guest entry shows neither; your own row shows neither and a line pointing to My profile). Renaming yourself (admin or standard) is the "Rename <name>" row of My profile. Rename: the on-screen keyboard, pre-filled with the current name, then the actor's PIN (skipped when the actor has none), then `RenameProfile`. Delete is offered to an admin for any profile except the active one and the last admin: a confirmation ("Delete <name>? Their saved data and settings are removed. This can't be undone.", focus on Cancel; the same dialog as the power actions), then the admin's PIN, then `DeleteProfile`. After a rename, focus stays on that profile's row; after a delete it moves to the row that took its place (the previous row at the end of the list). Replies go through the same status messages as below.

PINs are collected by the PIN pad in `collect` / `collect-confirm` mode (it calls no service); a mismatched confirmation shows "PINs don't match" and starts over. Every contract status maps to a message in the pane: `wrong-pin` ("%n attempt(s) left"), `locked-out` ("Try again in N s"), `invalid`, `not-allowed`, `failed`, plus `pin-required` and `unknown-profile`. `SwitchTo`, `CreateProfile` and `SetPin` all return `attempts_left` and `retry_after_secs` (meaningful for `wrong-pin` and `locked-out`, 0 otherwise), so the pane shows the counts straight from the reply. The mock enforces the same rules as `service.rs` (name 1-32 characters after trimming and no control characters, role, PIN format, admin check, the shared lockout counter with doubling back-off).

### 1.2 Isolation guarantees (acceptance)
- A profile can't read another profile's home (0700 homes, verified by test).
- Apps run as the profile's user inside Flatpak. Nothing third-party runs as root or as `ruya-shell`.
- Without FDE (01 §3.4), the documentation must say plainly that physical access bypasses PINs.

### 1.3 Parental controls (later)
Use `malcontent` with AppStream OARS ratings: per-profile age limit for store and launch, plus a "requires admin to install" toggle.

## 2. Devices (`ruya-devices`)

### 2.1 Controllers
- Handled by the input daemon (ADR-003). In-kernel drivers: `xpad` (Xbox wired), `hid-playstation` (DualSense), `hid-sony` (DS4), `hid-nintendo`. Optional, not in the image (T-354 researches them): `xone` (Xbox wireless dongle), `xpadneo` (Xbox BT extras).
- Pairing over BlueZ D-Bus: Settings → Controllers → "Pair new" shows how to put each controller into pairing mode, then scans and auto-trusts.
  - **As built, shell side only (T-136):** `org.ruyaos.Devices1.Bluetooth` (`api/dbus/org.ruyaos.Devices1.xml`: `Powered`, `Discovering`, `ListDevices`, `StartScan`/`StopScan`, `Pair` = pair + trust + connect, `Forget`, `Connect`, `Disconnect`, `DevicesChanged`; battery -1 = unknown) is used by the `Bluetooth` singleton (`shell/src/bluetooth/`, mock off Linux; the D-Bus client is compiled; the service is below). Settings → "Bluetooth & controllers" has the power switch, "Add a device" (scan) with a pairing-mode hint, the devices with state and battery, and "Forget" rows. "Just works" pairing only; no PIN/passkey dialogs. A connected device whose battery falls to 15 % or less raises a warning toast once per crossing (T-223: the same limit, `Batteries::LowBatteryPercent`, as the status cluster's alert) (`Bluetooth.batteryLow`, shown by `ToastLayer`). Player assignment, button test and remapping are not built.
  - **As built, service side (T-173, `services/ruya-devices`: `bluetooth.rs` pure core, `bluez.rs` the `org.bluez` client on the system bus).** The list is paired devices first, then by name; an unpaired device that never told its name (alias = its address) is left out; `kind` comes from BlueZ's `Icon` (`input-gaming` controller, `audio-headset`/`audio-headphones` headset, `audio-card`/`audio-speakers` speaker, `input-keyboard` keyboard, `input-mouse` mouse, `phone` phone, else other; T-199: the same words as `Batteries`, so `audio` became `speaker`) and `family` (T-199) is `playstation`, `xbox`, `nintendo` or `""`, set for a `controller` only, from the vendor id of BlueZ's `Modalias` (`usb:v054C...` Sony, `usb:v045E...` Microsoft, `usb:v057E...` Nintendo, and the Bluetooth SIG company ids `0x012D`, `0x0006`, `0x0553`); a vendor that is not in the table (8BitDo, a generic pad) is `""` whatever the pad is called, and only a pad with no usable `Modalias` is guessed from its name (`dualsense`, `dualshock`, `xbox`, `pro controller`, `joy-con`, ... and Sony's plain "Wireless Controller", tried last because "Xbox Wireless Controller" ends the same way). The table is one small file, `services/ruya-devices/src/families.rs` (`VENDORS`, `NAMES`), which the controller audit (T-261) extends; nothing else decides a family; `battery` is `org.bluez.Battery1.Percentage` or -1. `StartScan` starts discovery and the service ends it after 30 s (the watcher loop waits on BlueZ's signals and on that deadline, so nothing polls; a burst of signals is read after 300 ms of quiet or 1 s at most and never past the deadline; the same rule, `debounce.rs`, applies to the NetworkManager, UPower and BlueZ watchers, T-177). Changes found by any read are announced by the next refresh (`Discovering`, `Powered`, `DevicesChanged`); `Powered` off empties the list and ends the scan, `Powered` on brings the list back; with no adapter (or no BlueZ) `Powered` is false, `ListDevices` is empty, `StartScan`/`Pair`/`Connect` answer `unavailable`, and a `Powered` write is a D-Bus error (as it is when rfkill blocks). `Pair` = `Device1.Pair` (skipped for an already paired device), `Trusted = true`, `Device1.Connect`. **Timeout rule:** `Pair` gives up after 20 s in all (connecting gets what pairing left) and `Connect` after 20 s; the cancelling call has 2 s more, cancel what BlueZ was doing and answer `timeout` themselves, before the 25 s D-Bus default, so the shell's client keeps the default timeout. BlueZ errors map to the contract's statuses (`AuthenticationFailed/Canceled/Rejected`, `ConnectionAttemptFailed` and `Rejected` while pairing -> `pairing-failed`; `NotReady/NotAvailable/Blocked` and a missing BlueZ -> `unavailable`; `DoesNotExist` -> `unknown-device`; `AuthenticationTimeout` and bus timeouts -> `timeout`; `AlreadyExists/AlreadyConnected/NotConnected` -> `ok`; the rest `failed`). `DevicesChanged`, `Powered` and `Discovering` follow BlueZ's `PropertiesChanged`/`InterfacesAdded/Removed` (300 ms of quiet, 1 s at most, T-177). The service reports each device's `battery` as the pane needs it but raises no low-battery event of its own (UPower is the source for controllers, below). Bus policy: nothing of ours is needed: Fedora 44's `bluetooth.conf` (bluez 5.87) lets every user send to `org.bluez` in its default context, so the user unit reaches BlueZ as `ruya-shell` (the unit file and its hardening are unchanged; **vm-pending** for this release of the text: `vm-devices-check.sh bluetooth` on an image without the earlier extra rule). `bluetooth.service` is enabled, with a drop-in that drops the stock `ConditionPathIsDirectory=/sys/class/bluetooth` so `bluetoothd` runs before an adapter exists. **Unverified:** a real adapter and controller (the VM has none): scanning, pairing, battery and rfkill are tested against a fake BlueZ only.
- Player assignment: the first controller to press Accept on the profile picker becomes that profile's player 1. Battery level comes from `upower` and is shown in the overlay. Low battery shows a toast.
  - **Battery, as built (T-161, widened in T-223).** Since T-223 the list holds every wireless device UPower reports with a reading, not only gamepads, and each record has a `kind` (`controller` | `headset` | `speaker` | `mouse` | `keyboard` | `other`, from UPower's `UpDeviceKind`: 12 gaming input; 17 headset, 19 headphones and 21 other audio (BlueZ's audio classes) are `headset`; 18 speakers; 5 mouse and 14 touchpad are `mouse`; 6 keyboard; 22 remote control and 28 Bluetooth generic are `other`; every other kind, a pen (13) included, is dropped by design; the PC's own battery, power supplies, UPSs, monitors, phones and tablets stay out; a device without a name is called after its kind). The shell shows one status-cluster chip per device (`Batteries.devices`, `chips`, `more`; `02-shell.md` System UI) and `Batteries.batteryLow` (and its toast) stays controller-only, because the other kinds toast through `Bluetooth.batteryLow`; `lowest`, `lowestState` and `low` are gone. Contract `org.ruyaos.Devices1.Batteries` (`ListBatteries` -> `id`, `name`, `kind`, `percent` 0-100, `state` `charging` | `discharging` | `full` | `unknown`; signal `BatteriesChanged`; no status strings). `ruya-devices` (`battery.rs` pure core, `upower.rs` client) reads UPower on the system bus: `EnumerateDevices` plus each device's `GetAll`; only the UPower kinds named above are listed, sorted by id; a device with state unknown and 0 % has no reading and is not listed. UPower's signals (device added/removed, any `PropertiesChanged`) and UPower appearing or leaving the bus are followed, debounced (300 ms of quiet, 1 s at most), no polling. UPower missing or not startable is an empty list, never an error. The image installs `upower` (D-Bus activated; no unit hardening of `ruya-devices` changed, `AF_UNIX` is enough for the system bus). The shell's `Batteries` singleton (`shell/src/battery/`, mock off Linux) exposes `devices` (every listed device, lowest level first, ties discharging first: `id`, `name`, `kind`, `percent`, `state`, `low`), `chips` (the devices that earn a chip: all but one at 100 % on the charger or full, at most three) and `more` (the rest), and `batteryLow(id, name, percent)`; a record without a `percent` is dropped (no chip). The status cluster on Home and the section pages draws `chips` and "+N" for `more` (`02-shell.md`, `04` §3.7); `ToastLayer` raises "Controller battery low (15%)" (warning) once when a controller (kind `controller` only) is discharging at 15 % or less, again only after it recovered or was charging. The D-Bus client numbers its `ListBatteries` calls and drops a reply older than one already shown. A real controller's battery is unverified (no controller in the VM).
  - **Pairing must bond, and the firmware must be there (first Bluetooth run on the Dell, 2026-11-06).** BlueZ 5.87 keeps the adapter's `Pairable` off, and an adapter that is not pairable answers a pairing with "No Bonding": `Paired: yes`, `Bonded: no`, no link key, and BlueZ's input plugin logs `Rejected connection from !bonded device` and never creates the pad's input device. `Pair` therefore sets `Adapter1.Pairable` for the length of the pairing and clears it again whatever happens (`Bluez::set_pairable`; a refusal means no pairing attempt, status `failed`); a device that is already paired is not touched. Checked on the Dell with a DualSense: Bonded yes, the pad's input devices appear and `ruya-inputd` takes the pad. The image also installs the radio firmware that `linux-firmware` only recommends (`image/build/20-base.sh`: Intel Wi-Fi and Bluetooth, MediaTek, Marvell, SOF audio); before that an Intel Bluetooth dongle never initialised (`Failed to load Intel firmware file intel/ibt-19-0-4.sfi`) and Intel Wi-Fi would have failed the same way.
  - **Pairing a controller with no keyboard (T-203, `bluetooth.rs`/`pairing.rs`/`bluez.rs`/`input.rs`).** `Devices1.Bluetooth.StartControllerPairing(seconds)` (0 = 120, at most 300), `StopControllerPairing`, the property `ControllerPairingState` (`idle`, `open`, `paired`, `timeout`; the outcome stays until the next start or stop), the property `InputPresent` and the signal `ControllerPairingRejected`. **Who:** only root and the user the service runs as (`ruya-shell`): the bus policy already allows no one else, and the service checks the caller's uid itself (`GetConnectionUnixUser`, fails closed) and answers `refused`; it is never opened by default. **While the window is open** (one at a time, a second start answers `busy` and changes nothing) the service registers a BlueZ agent (`AgentManager1.RegisterAgent` with capability `NoInputNoOutput`, `RequestDefaultAgent`; the agent object lives on the `BluezClient` connection, the one that registers it), makes the adapter pairable (not discoverable: a pad in pairing mode advertises and is found by the scan, and a bonded pad pages the console, so nobody else needs to see it), and starts a scan unless one runs. **What the agent accepts:** `RequestAuthorization`/`RequestConfirmation` (incoming just-works pairing) only inside the window and only for an input device, that is a device whose Class of Device has the major class Peripheral (`0x05`: gamepad, keyboard, mouse), or, for a device without a class (Bluetooth LE only), an appearance in the HID category; `AuthorizeService` only for the HID service UUIDs (`0x1124`, `0x1812`) of such a device. A phone, an audio device, a computer or a device that tells nothing is refused (`org.bluez.Error.Rejected`) and announced with `ControllerPairingRejected`; every PIN or passkey request is refused (B-006). **The agent is not enough:** with capability `NoInputNoOutput` the kernel accepts an incoming just-works pairing by itself and BlueZ never calls `RequestAuthorization`, so a phone could bond during the window. The window therefore remembers which devices were paired when it opened; after every read (`pump`) a device that is paired now and was not is, if it is an input device, the controller that ends the window, and otherwise a stranger that is removed again (`Adapter1.RemoveDevice`, on every read that shows it paired, so a phone that taps pair twice is removed twice; the call is idempotent) and announced with `ControllerPairingRejected`; the agent's refusal path removes a device that bonded too. A device the user pairs by hand in Settings during the window is not a stranger. **Residual risk:** the Class of Device and the LE Appearance are told by the remote device and are trivially spoofed, so a device in range that claims class `0x05xx` inside a window can bond, be trusted and act as a keyboard or pad. Mitigations: the window is short (120 s) and never open by default, the adapter is not discoverable, the shell's automatic reopening is capped (3 windows), and strangers are swept; PIN-protected devices are refused. **Also from our side:** a pad in pairing mode (PS + Create) does not call the console, so the window pairs, trusts and connects by itself a gamepad that its scan finds (`Icon` = `input-gaming` and an input class; at most 3 attempts per address). **How it ends:** an input device that has paired (with or without the agent being asked) is trusted (BlueZ then lets its HID connection through) and the window closes with `paired`; or the time is up (`tick`, the watcher also waits on the window's deadline) and it closes with `timeout`; or `StopControllerPairing` (`idle`). Closing restores what the window changed: the scan it started is stopped (a scan of the user's own is left running, and `StopScan` does not end the window's), `Pairable` returns to what it was (a value that was already on is left on), the agent is unregistered. `window_pair` acts only for the pairing the window handed out and only while that window is open (after a stop or a timeout it calls nothing; a pairing that completes afterwards is left untrusted); a second `Start` while the first is still talking to BlueZ is `busy`. When `ruya-devices` first sees an adapter (and no window is open) it switches `Pairable` and `Discoverable` off, so a crash inside a window cannot leave the console pairable (`PairableTimeout` in BlueZ's `main.conf` is an inbox item). A manual `Pair` during the window does not turn `Pairable` off under it. **`InputPresent`** is true when the kernel shows a keyboard (keys 1-31 all present, like udev) or a gamepad (a button in `0x120`-`0x13e`) in `/sys/class/input/input*/capabilities/key`, over USB or Bluetooth; the console's own `RuyaOS Navigation` keyboard (`ruya-inputd`) does not count. It is read every two seconds (the same pace as `ruya-inputd`'s rescan; sysfs offers no change notification without udev) and announced when it changes. It sits on the Bluetooth interface because the shell asks it for the sake of the window. The shell side: `Bluetooth.controllerPairing`, `inputPresent`, `inputKnown` (false until the service answered, so nothing flashes at start-up), `startControllerPairing()`, `stopControllerPairing()`, `controllerRejected`; the mock scripts the outcome (`mockPairingScript`: `wait`, `success`, `timeout`, `rejected`) and has an input device unless `mockSetInputPresent(false)`. In `ruya-devices --session`, `RUYA_DEVICES_NO_INPUT=1` makes the fake report no input device. **`ruya-inputd` needs no ordering against `bluetooth.service`:** it rescans `/dev/input` every two seconds and takes any pad that appears, so a pad that connects after the shell started is picked up within two seconds (no image change). **Unverified (hardware, T-203 Outcome):** cold-boot reconnect of a bonded pad at the picker, a pad pairing itself from the first screen with no bond, and a phone being refused, on the Dell.
  - **Idle controllers (T-202, `idle_pads.rs`, `bluetooth.rs`).** `Devices1.Bluetooth.ReportIdle(idle_seconds, timeout_seconds, hold)`: the shell reports how long the console has had no input (every minute while idle, and at once when input ends an idle period); the service disconnects each connected, paired `controller` once per idle period when the idle time (never longer than the time since it was seen connected, nor since the last `hold`) reaches the timeout; 0 = never; `hold` (an app in front, a job running) starts the count over.   - **Controller onboarding (T-260, `input.rs`, `bluetooth.rs`, `families.rs`).** `Devices1.Bluetooth` gained `Rename(id, name)` (BlueZ `Alias`; the name is trimmed, at most 48 characters, no control characters, else `invalid`; `unknown-device`, `unavailable`, `failed`) and the signals `GamepadConnected` / `GamepadDisconnected(id, name, family, transport)`. The shell debounces and decides what to say (`02` System UI). **Xbox 360 wireless receiver (RUY-154, `input.rs`, `battery.rs`).** The in-kernel `xpad` driver creates one input device per pad that is switched on behind the receiver (`045e:0719` or `045e:0291`, also clones) and names it after the receiver; `gamepad_of` renames such a pad "Xbox 360 Controller" (family `xbox`, transport `usb`, id the port with its interface, `.../input0`, `input2`, ...), so each pad is told and announced on its own. The match is on the two id pairs, never on the name: another vendor's "Xbox 360 Wireless Receiver" keeps its own name and has no family. The pad's battery is xpad's power supply (`xpad_battery-...`, no model): `Batteries` lists it as a controller named "Xbox 360 Controller", family `xbox`, whichever kind UPower files it under (battery or gaming input). Pairing is by the sync buttons on the receiver and the pad, not by the OS; the shell only explains it (`02`). Rust tests in `input.rs` and `battery.rs`; **hw pending**: a real receiver with a real pad, and the kind UPower gives the xpad battery.

  - **System information, as built (T-226).** Contract `org.ruyaos.Devices1.System`: `GetInfo` -> one `a{sv}` of grouped keys (`console.*`, `cpu.*`, `memory.*`, `graphics.*`, `storage.drives` (`aa{sv}`), `network.*`, `bluetooth.*`; the list is in the XML) and the signal `SystemInfoChanged`. **A value that cannot be read is absent, never 0.** The collector is its own crate, `services/ruya-sysinfo` (pure core, no D-Bus, no notion of who the data is for; the telemetry hardware report, T-224, reuses it): a `Source` trait (`read`, `list`, `resolve` symlinks, `run` a command with a 3 s limit), `RootSource` for the running system, and `FakeSource` built from a text dump of a machine, which is also how the tests and `ruya-devices --session` (the sample Dell) get their data. Parsers: `/proc/cpuinfo` (model, physical cores from the `physical id`/`core id` pairs, threads, mean clock), cpufreq (busiest core now, highest allowed), `/proc/meminfo` (total, available, swap; no swap -> no keys), zram, `/sys/class/dmi/id` (maker and model, BIOS placeholders such as "To Be Filled By O.E.M." dropped, Lenovo's `product_version`), os-release and `/usr/lib/ruyaos/version`, `/proc/cmdline` (ostree deployment), `bootc status --json` (needs root, so on a real image it is usually absent for the shell's user; the service tries and says nothing when it fails), EFI SecureBoot variable, `/sys/class/drm` (primary GPU: PCI ids, the udev database file `/run/udev/data/+pci:<slot>` for the maker and the model name, the driver link, `/sys/module/<driver>/version` else the kernel release for in-tree drivers, Mesa from the package database (`rpm -q`), `/proc/driver/nvidia/version`, the first connected connector and its first listed mode), `/sys/block` (internal drives only: not removable, not behind USB, not loop/zram; model, type by name and rotation, size; health for NVMe from the controller `state`, no SMART), `/proc/net/route` (default route's interface, its MAC and wired link speed) and the USB adapter behind `/sys/class/bluetooth/hci0` (udev names) with `bluetoothctl show` for the address. ### 2.2 Storage
- `ruya-devices` auto-mounts removable media through udisks2 (T-174: `nosuid,nodev,noexec`, read-write; as built below). Supported filesystems: ext4, exFAT, FAT32, NTFS (read-write), Btrfs.
  - **What RuyaOS finds on a removable drive (T-331).** `Devices1.Storage.ScanVolume(id) -> status`, `GetVolumeScan(id) -> a{sv}`, `CancelScan(id)` and the signal `VolumeScanChanged(id)` (`services/ruya-devices/src/drive_scan.rs`, wired in `dbus.rs`; statuses `ok`, `unknown-volume`, `unsupported` (not removable or not mounted), `busy` (another volume is being scanned), `invalid`, `failed`). `ScanVolume` answers at once and the walk runs on the blocking pool, one at a time; `VolumeScanChanged` says it ended (done, cancelled or failed) and the client reads `GetVolumeScan`: `state` (`idle`, `running`, `done`, `cancelled`, `failed`), `partial`, `used_bytes`, `categories` (`key`, `bytes`, `files`; only categories that have an entry, largest first) and `other_bytes` (`used_bytes` is the categories plus `other_bytes`). **Read-only: names and sizes.** The walk reads through a `ScanSource` trait that offers `list(dir)` and `stat(path)` and nothing else (no `open`, `read` or `exec` exists in it, so content cannot be read by construction; a test pins that the production code has no call that could), and the unit runs it as `ruya-shell` on a volume mounted `nosuid,nodev,noexec`. It counts allocated blocks like `sysusage.rs`, never follows a symlink, never enters another device, counts a hard-linked file once, and stops at **depth 6, 200 000 entries or 10 s of wall clock** (a fake clock in the tests). A directory is never read whole: `list(dir, max, stop)` returns at most the entries the bound still allows (`truncated` otherwise) and looks at the cancel flag and the clock every 64 entries, so a hostile directory with millions of entries costs a bounded read. A bound that was hit, a directory it could not read, a name that is not UTF-8 and a cancel make the result `partial` (clients write "at least"); an unreadable mount point is `failed`. A name from the drive is never echoed (the log prints a cleaned, shortened leaf name for the first unreadable directory only). `CancelScan` stops the walk at the next directory (or after 64 entries inside a big one); `Eject` cancels the volume's scan first and waits (at most 2 s, a `Condvar` notified when the walk ends, on the blocking pool) until the walk has let go of the directory it reads, because an open directory makes the unmount answer `busy`. A finished result is kept per volume until the volume's mount point, size, free space or read-only flag changes (a `VolumesChanged` that alters it) or it is unplugged; a second `ScanVolume` for a volume with a fresh result, or one being scanned, answers `ok` without a new walk; a cancelled or failed result is walked again.

Rules (unit-tested): a block device with a filesystem is a volume; *removable* means the drive is removable or on a USB/SDIO bus and udisks does not mark it `HintSystem`; ignored devices (`HintIgnore`) and devices without a drive are never listed; internal volumes are listed only when mounted outside the system paths (`/`, `/boot`, `/boot/efi`, `/efi`, `/sysroot`, `/var`, `/home`, `/etc`, `/usr`), so the OS itself never shows up; internal disks are never mounted, ejected (`failed`) or formatted. Filesystems `ext4`, `btrfs`, `exfat`, `vfat`, `ntfs` are supported, anything else is `unknown`: listed, never mounted, `Eject` answers `unsupported`. A removable supported volume is mounted **once, when first seen** (also at service start), before the list is published, so `VolumeAdded(id)` (hot-plug only, not for volumes present at the first read; then `VolumesChanged`) already finds it mounted; after an eject or a failed mount it is not mounted again until it was unplugged. Mounted for `ruya-shell` (the user the service runs as), not for the active profile, at udisks2's `/run/media/ruya-shell/<label>`; profile users and apps get media access with the Media task. `free_bytes` is `statvfs` of the mount point. `Eject` unmounts the volume and every other mounted partition of its drive (`busy` when a file is open: what was unmounted is mounted again), then `PowerOff` (or `Eject` for media drives; a drive that can do neither counts as safe to remove), and refreshes at once so the volume leaves the list before the call returns. The dictionary keys are written in alphabetical order (so `drive` comes first). Polkit (`50-ruyaos-storage.rules`) lets only `ruya-shell` do `filesystem-mount`, `eject-media` and `power-off-drive` (and their `-other-seat` variants) and answers NO to every other `org.freedesktop.udisks2.*` action for `ruya-shell`, which also overrides udisks2's own default that an active session may format, unlock or set up loop devices without a password (VM-checked with `pkcheck`); other users keep the default policy.
  - **One toast per drive (T-184).** Each volume has a `drive` (the udisks drive object, opaque; partitions of one stick share it). The service still sends `VolumeAdded` once per volume, also for a partition with a filesystem it does not mount. The shell's `Storage` waits until an announced volume is in the list, then holds the announcements for 400 ms (`Storage::groupWindowMs`, from the first one, so partitions that appear in separate lists still join) and emits `driveAdded(drive, label, volumeCount)` once per drive: `label` is the first volume with a supported filesystem, `volumeCount` counts those. The toast reads "Drive inserted: <label>" or, for a stick with more, "Drive inserted: <label> (and 1 more)". A partition with an unsupported filesystem stays in the list (Settings -> Storage) but is not counted; a drive that has nothing else gives no toast (the Storage pane still lists it with its reason). A partition that shows up more than 400 ms after the first is its own toast.
  - **The console's own storage (T-196).** `Devices1.Storage.GetSystemUsage() -> a{sv}` and the signal `SystemUsageChanged` (`services/ruya-devices/src/sysusage.rs`, wired in `dbus.rs`). The OS image is still not a volume (`ListVolumes` is unchanged); this answers "how full is the console": `total_bytes` and `free_bytes` of the filesystem that holds `/var` (where apps, games and profile homes live), `apps_bytes` (the system Flatpak installation, `/var/lib/flatpak`), `data_bytes` (`/var/home`, **unknown today**, see below) and `system_bytes` (the rest of what is used, `total - free - apps - data`, never negative; while `data_bytes` is `-1` it is `total - free - apps`, everything used that is not apps; `-1` while total, free or apps is unknown). Unknown parts are `-1`. Total and free are one `statvfs` per call (on the blocking pool). The two directory sizes are the expensive part: they are measured on the blocking pool (`blocking::unblock`, never on the D-Bus executor), cached for 60 s and measured once at service start; a call that finds the cache older than that answers with the cached numbers at once (`-1` before the first measurement finished) and starts a new measurement, which ends in `SystemUsageChanged` when `apps_bytes` or `data_bytes` differ (not for free space alone, which moves all the time: clients read it when they show it). The Store's `InstalledChanged` (a match rule on `org.ruyaos.Store1`, through the shared 300 ms / 1 s debounce) marks the cache stale and triggers a measurement; a change that arrives while a walk runs makes that walk's result stale again, so it is measured once more. The walk counts allocated blocks (`st_blocks * 512`), counts a hard-linked file once (a Flatpak deployment is hard links into the OSTree repository), never follows a symlink and never enters another mount. A directory that cannot be measured at all is `-1`; it never fails the call. **Profile data is unknown today (`data_bytes` is `-1`).** Every profile is a Unix user (`ruya-p<N>`) with a 0700 home in `/var/home` and the service runs as `ruya-shell`, so the walk sees the home directories and none of their files; a number from it would be a few kB and would show every save and `~/.var/app` as "system". A walk that could not read everything it walked is therefore reported as unknown (`TreeSize.partial` makes the part `-1`, also for `apps_bytes`), never as a partial number. Exact per-profile sizes need a root source (`ruya-profiles` reporting them); not done, no new privilege. "Apps and games" counts only `/var/lib/flatpak`: game libraries and app data under a profile's home (`~/.var/app`, `~/.local/share/Steam`) are not in it until per-profile sizes exist. Read-only: the unit's hardening is unchanged. The core is a pure struct over two traits (`SystemSource`: statvfs and tree size; `Clock`), tested with a fake source and a fake clock (cache reuse, expiry, a change signal during a walk, failing walks, the remainder); the real walk is tested on a scratch tree (symlinks, hard links and unreadable directories on Linux only). In the shell, `Storage.internal` is a map `{ valid, totalBytes, freeBytes, appsBytes, dataBytes, systemBytes }` (`valid` false until the first reply) and `Storage.refreshInternal()` reads it again (the Storage pane calls it when it opens); late replies are dropped (`RequestSequence`, T-191). Settings -> Storage shows it first, as "This console" (see `02-shell.md`): free space with the bar, "Apps and games", and, while `data_bytes` is `-1`, one row "Other" with `system_bytes` (with the data known: "Profile data" and "System"). The mock disk is 464 GB with 450 GB free (`Storage.mockLowSpace(true)`: 28 GB free).
- Per-app usage (Flatpak installed size plus `~/.var/app/<id>`) with uninstall and clear data from Settings → Storage comes later; today the pane shows the totals above.
- Optical (stretch): audio CD and data-disc detection only. Video DVD/Blu-ray playback is delegated to an app (e.g. VLC/Kodi Flatpak). We don't ship libdvdcss or AACS keys.

### 2.3 Audio
- PipeWire + WirePlumber. `ruya-devices` exposes sinks (HDMI/DP per port, analog, USB, Bluetooth), the default sink, and per-role volumes. Contract: `api/dbus/org.ruyaos.Devices1.xml`, interface `org.ruyaos.Devices1.Audio` (`ListSinks`, `SetDefaultSink`, `SetChannelVolume`, properties `MasterVolume`, `Muted`, `ChannelVolumes`; network and Bluetooth become sibling interfaces on the same object). The shell side (mock and D-Bus client, Settings -> Audio) is built (T-114). The service is built (T-128, `services/ruya-devices`): a pure core with the policy below, PipeWire read through `pw-dump` and driven through `wpctl`. **Followed by events, not polled (T-133, `events.rs`):** one long-running `pw-dump --monitor --no-colors` child prints a JSON array per change batch; batches that only update PipeWire clients are skipped (the monitor is a client itself and re-reports clients hundreds of times a minute), and a quiet burst of the rest (100 ms of quiet, and at most 1 s from the first event, `debounce::MAX_WAIT`, T-184) triggers one refresh, so a graph that never goes quiet is still read about once a second, so changes made from outside (`wpctl`, hot-plug) reach the shell within a second and an idle system spends nothing. If the monitor dies (PipeWire restarted) it is started again after 1 s, doubling to 30 s, with one refresh on every reconnect, channel levels persisted in `$STATE_DIRECTORY/audio.toml`. The kind of an output comes from `device.api`/`device.bus`/the node name and is `analog` when unsure; applying `ambient` and `media` to app streams is not done yet (only `ui`, in the shell). The Linux shell uses it over D-Bus by default (`RUYA_SERVICES=mock` for the mock).
- **Default policy (T-322, `output_policy.rs` pure ranking, `audio.rs` applies it).** The default is the first of: (1) the output the player chose (`SetOutput`), (2) a plugged headset or headphones (usb, bluetooth, a jack whose route is `available = yes`), (3) an HDMI/DP output whose ELD is valid (route `available = yes`) that the player has not rejected, (4) the internal speaker, (5) whatever exists (unplugged outputs last). "HDMI first" and "analog first" are both wrong somewhere: an ELD proves a monitor, not speakers (the Dell's monitor has none), so the player can reject it: choosing another output while the policy would have picked a valid-ELD HDMI output records that HDMI output as *rejected*, and it drops below the speaker (choosing it again lifts that). The choice is one output id (`<card name>:<port name>`, a sink without ports: its node name) plus the rejected ids, in `outputs.toml` next to `audio.toml` (`/var/lib/ruya-shell/.local/state/ruya-devices`, the state directory of the `ruya-shell` user unit; atomic writes, a corrupt file stops the service rather than being overwritten); `ResetOutputChoice` (Settings' reset) empties it and applies the table at once. **The service sets the default itself** at its first read after start and whenever the saved output becomes usable (comes back, or its port turns `available`): it sets PipeWire's default sink, so what WirePlumber remembered (`default.configured.audio.sink` naming a node that is not there this boot) never decides. A saved output that is absent at start only makes the table pick a fallback; the saved id stays in the file and the output becomes the default again the moment it returns (a TV switched on late). Between those events only three things move the default: a headset plugged in (it takes over for as long as it is plugged; the saved choice is not overwritten; when it goes, the previous default comes back), the default disappearing (the previous default, else the table), and the player. A new HDMI output never steals the default. Never interrupt playback; streams move. The shell's toast for any default change is "Sound moved to <name>" (02, T-348).
- **Outputs (T-322, contract `ListOutputs`, `SetOutput`, `TestOutput`, `ResetOutputChoice`, signal `OutputsChanged`).** PipeWire shows only the sinks of a card's active profile; `ruya-devices` lists every output of a card from its Device object's `EnumRoute` (analog speaker, headphones, HDMI 0..n) beside the sink-less ones, and ties an output to its sink (`node`, shown as `active`) through the Device's current `Route`, `device.id` and `card.profile.device`. A sink that no listed route explains (a USB or Bluetooth device without routes) is an output of its own. Fields: `id`, `name`, `kind` (`speaker` | `headphones` | `hdmi` | `usb` | `bluetooth`), `card`, `port`, `available` (`yes`/`no`/`unknown`), `active`, `is_default`, `is_saved`. `TestOutput` plays a 0.4 s tone (`pw-play --target=<sink>`, a WAV written to the unit's private `/tmp`), leaving the default and the choice alone. **Profiles and routes (T-347).** An output without a sink is reached by switching its card: `PipeWire::switch_to` (`WpCtl`: `wpctl set-profile <device> <profile>` when the port belongs to another profile, then `pw-cli set-param <device> Route { index, device, save: true }` when it is not the route in use, then waits up to 4 s for the sink; `pipewire::plan_switch` reads the `EnumRoute` `profiles`/`devices` and the current `Profile`/`Route` from `pw-dump`). The same path serves `SetOutput`, the output policy (it may now pick an HDMI port with a valid ELD on an inactive profile, and a headset plugged into a jack route) and the hot-plug rule. WirePlumber stays the one that owns profiles and volumes: the service only asks for the switch, and WirePlumber keeps each route's volume and restores it when the route comes back ("remembered per output"). **A card is never left on a profile without a sink:** when the switch or `set_default` fails, `Audio::activate_output` puts the card back as `card_profile` described it (`restore_profile`). `TestOutput` on an output of another profile borrows the profile for the tone and gives it back (the restore waits for the tone, under half a second, and for the old sink to return, so the call takes that long), then sets the default again. **Every switch runs off the D-Bus executor** (`blocking::unblock`, like Network): `SetOutput`, `TestOutput`, `ResetOutputChoice` and the watcher's refresh take the audio lock on the blocking pool, so a slow card switch delays only other `Audio` calls that need the same state, never another interface; `inactive` is now only for an output that no profile can reach. The first read that shows any output applies the policy; an empty output list (WirePlumber is still starting, also with a sink already there) and a failed read wait, and the policy runs when the first non-empty list arrives (T-360). A failed boot read does not make the watcher's first good read silent: that read emits the signals for what it finds. The bus getters (`ListSinks`, `ListOutputs`, `MasterVolume`, `Muted`, `Playing`, `ChannelVolumes`) answer from a copy of the state refreshed after every change, so a 4-8 s card-profile switch, which holds the audio state, never delays them; the setters and `SetOutput` run on the blocking pool (T-347, T-360). **Volumes.** The first output starts **high** (owner, 2026-11-08: the TV or monitor controls the loudness): the first time a default sink exists the service sets it to 100 % **once** and then writes the marker `first-volume-done` beside `audio.toml`; on an existing install (when the service starts `audio.toml` is there, or `outputs.toml`, or WirePlumber's `default-routes` / `stream-properties` in `wireplumber/`, a sibling of our state directory; T-360) the marker is written at once and the volume is left alone; with the marker present nothing is ever applied again (reboot, service restart, profile or output change, update), so a volume the player set, or one WirePlumber saved, is never touched. Done by the service, not a WirePlumber drop-in (a drop-in applies to every route and every boot and cannot know "once"). **Which rule holds for a later output (T-360):** an output the console uses for the first time (a profile switch to an output not in the `seen` list of `outputs.toml`) starts at the first volume, 100 %, **only if it is line level** (HDMI/DisplayPort, built-in or external speakers); headphones, Bluetooth and USB audio devices (they may be headsets) and any output of unknown kind start at the safe 40 % (`SAFE_NEW_VOLUME`, WirePlumber's own default), because 100 % on someone's ears can hurt (lead, 2026-11-09). The same kind rule applies to the very first start: if the default output then is headphones, the one-time volume is 40 %, not 100 %. The output is then in `seen` and keeps what the player sets per route. `seen` is filled for the output in use at every read, so an existing install treats only outputs it never used as new. The test tone's peak is 0.4 of full scale and can never exceed `TONE_CAP` (80 %). The older `ListSinks`/`SetDefaultSink` stay for the current pane (T-348 moves it to outputs); `SetDefaultSink` does not save a choice.
- **Microphones (T-449, contract `ListInputs`, `SetInput`, property `InputMuted`, signal `InputsChanged`; first piece of Ruya Hub, ADR-033).** `pipewire::parse_sources` lists the PipeWire nodes whose `media.class` is exactly `Audio/Source` (a sink's monitor, `Audio/Source/Virtual` and streams are not microphones), sorted by `node.name`: `id` (the node name), `name`, `kind` (`analog` | `usb` | `bluetooth`, from `device.api`/`device.bus`/the node name, `analog` when unsure), `available` (`yes`/`no`/`unknown`, the `available` of the card's input `Route` in use for that node; `unknown` when the node has no card route, as for USB and Bluetooth), `is_default` (PipeWire's `default.audio.source`, else the configured one, and only when it names a listed microphone). A console without a microphone returns an empty list, never an error. `SetInput(id)` first checks the id against the list (`unknown-input` otherwise, nothing reaches PipeWire; this is the trust boundary, so `@DEFAULT_AUDIO_SOURCE@` or a sink name cannot get through) and then runs `wpctl set-default <object id>` (the object id is looked up among `Audio/Source` nodes only); choosing the current default is `ok` and writes nothing. The choice is not saved by the service: WirePlumber keeps the default source itself. `InputMuted` reads `wpctl get-volume @DEFAULT_AUDIO_SOURCE@` and writes `wpctl set-mute @DEFAULT_AUDIO_SOURCE@`; it is `false` while there is no default microphone and a write then fails (nothing is written). The mute belongs to the microphone, so it changes with `SetInput`. A change from outside (a headset's own button, a plug) arrives by the same `pw-dump --monitor` events as the outputs and is announced by `InputsChanged` (list or default) and `PropertiesChanged` of `InputMuted`. The getters answer from the same copy as the others. Shell: `Audio.inputs`, `Audio.defaultInput`, `Audio.inputMuted`, `Audio.setInput`, `Audio.setInputMuted`, `Audio.toggleInputMute`; the mock starts with one built-in microphone (`mockPlugInput` / `mockUnplugInput` in tests). No UI yet (T-450). Out of scope: levels, noise suppression, a per-app permission (T-220).
- HDMI passthrough (AC3/DTS/TrueHD) is enabled per sink in Settings → Audio (Phase 4).

### 2.4 Display
- Mode list and switching via the compositor (KMS). Default is the TV's preferred mode, capped at 4K60 for the shell.
- **As built (T-198, `ruya-devices` `display.rs` and `edid.rs`, contract `org.ruyaos.Devices1.Display`).** The service reads the kernel's `/sys/class/drm/card*-<connector>/{status,modes,edid}` at every call (no watcher: the pane reads it when it opens). **What the kernel gives:** `modes` has only `WxH` lines (preferred first, then larger and faster first; the same size repeats once per refresh rate; no rates), `status` says `connected`, `edid` is the 128-byte base block plus extensions. **What the EDID adds** (`edid.rs`, VESA E-EDID 1.4 and CTA-861): the monitor name descriptor, the picture size in millimetres (the first detailed timing's, else bytes 21/22 in centimetres; the projector placeholders 16x9 and 4x3 cm count as unknown), and the timings with their rates: detailed timings (rate = pixel clock / totals), standard timings, established timings and the CTA video data block's VIC codes (a table of the progressive ones up to 4K120). `modes_from` gives the k-th line of a size the k-th fastest rate the EDID announces for it (the display's own first detailed timing leads), drops lines beyond the announced rates and interlaced modes, merges rates that round to the same Hz (Qt's config cannot tell 59.94 from 60), and leaves a size the EDID knows nothing about once with rate 0 (the shell then offers the size without a rate). A mode in use is not readable from sysfs: **current** is the owner's stored choice if the output still offers it, else the **default**: the preferred mode, capped at 3840x2160 and 60 Hz (the first mode within the cap when the preferred is beyond it). **Applying:** the choice (`display.toml`: output, width, height, refresh in mHz, and the UI size percent) and the KMS config live in the service's state directory (`~/.local/state/ruya-devices`, i.e. `/var/lib/ruya-shell/.local/state/ruya-devices`: the compositor and the service are the same user). `kms_config` writes the JSON that `ruya-compositor@.service` hands to Qt eglfs (`QT_QPA_EGLFS_KMS_CONFIG`). **Qt names its screens differently from the kernel** (`nameForConnector` in qkmsdevice.cpp: a short type name and the connector's number, no dash): the kernel's `HDMI-A-1` or `HDMI-B-1` is `HDMI1`, `DP-1` is `DP1`, `eDP-1` is `eDP1`, `VGA-1` is `VGA1`, `DVI-I/-D/-A-n` is `DVIn`, `Virtual-1` is `Virtual1`, `SVIDEO` is `TV`, `Component` is `CTV`, `9PinDIN` is `DIN` (`qt_output_name`, tested). The entry carries the Qt name, and the kernel's own name as a second entry when it differs (harmless where Qt does not know it): `{"outputs": [{"name": "HDMI1", "mode": "1920x1080@60"}, {"name": "HDMI-A-1", "mode": "1920x1080@60"}]}` (golden file `services/ruya-devices/tests/fixtures/kms-hdmi-1080p60.json`); the `WxH@Hz` mode string is right; no file means Qt's preferred mode. `SetMode` writes `display-pending.toml` (`starts = 0`) and then the config; `Keep` stores the candidate and removes the marker; `Revert` removes it and rewrites the config for the stored choice. **The fall-back marker:** `ExecStartPre=-/usr/bin/ruya-devices --display-guard` runs before every compositor start as the shell user (`display::guard`): a marker with `starts = 0` becomes `starts = 1` (the first start on the candidate, the shell now asks the owner); a marker that is still there at the next start was never confirmed, so the choice is dropped (the TV's preferred mode comes back), the marker and config are removed and a `display-fallback` note is left, which `TakeFallbackNotice` returns once; an unreadable marker counts as unconfirmed; a stored mode the screen no longer offers is forgotten (the UI size stays); with no stored choice the guard writes the capped default when the preferred mode is beyond 4K60; with no output to look at it leaves everything as it is. `--display-list [dir]` prints the outputs and modes the service would offer, from `/sys/class/drm` or a capture of it (`scripts/display-capture.sh`); `RUYA_DRM_DIR` points the service at such a capture, and `--session` serves two fake outputs. **Shell side:** `Display` singleton (`shell/src/display`, mock and D-Bus client; the mock has three screens, a 55" 4K TV, a 40" 1080p TV and a 32" 4K monitor, plus "none"); on a successful `SetMode` or `Revert` it asks the backend to restart the shell (the D-Bus backend ends the process with exit code 0, the mock counts). **The compositor's start limit.** `ruya-compositor@.service` allows `StartLimitBurst=10` starts in `StartLimitIntervalSec=120` (it was 5): a mode change, a revert and a reset are each a start, and six within two minutes used to mean `start-limit-hit`, a black screen until power-cycle. Ten is enough for a change and its revert with room to spare, and a crash loop (`RestartSec=1`) still reaches it in about ten seconds, so the protection stays (the greenboot health check on a broken image just sees ten failed starts instead of five). The guard records every start (`display-starts`, pruned to the window) and **`SetMode` and `Reset` answer `busy` while eight or more are in the window** (`REFUSE_MARGIN`: the change, its revert and one to spare); `Keep` and `Revert` are never refused. **`Reset`** (`display::reset`) clears the stored mode and the UI size, rewrites the config for the default, answers `ok` when the mode in use changes (the shell restarts, no confirmation: the preferred mode is the safe one), `unchanged` when only stored values were reset, `busy` while a change waits or restarts are crowded; it works with no output and replaces a damaged state file. **Unverified:** that systemd counts the starts the way the guard does (every start of the unit; `vm-display-check.sh switch` checks the four restarts stay under it). Hardware: what the Dell reports (its modes, the chosen mode, the UI size) is recorded in the T-198 Outcome.
- **Brightness (T-454, `ruya-devices` `backlight.rs`, contract `Devices1.Display.GetBrightness` / `SetBrightness`).** `GetBrightness` answers `(su)`: `supported` with a percentage of 1..100, or `unsupported` and 0. The service reads the kernel's `/sys/class/backlight/*` at every call (`max_brightness`, the hardware's `actual_brightness` else `brightness`, `type`); of several devices it takes `firmware`, else `platform`, else `raw` (the order systemd-backlight uses; the name settles a tie), and ignores a device whose maximum is 0. **A TV or a monitor on HDMI or DisplayPort has no backlight device, so it is `unsupported` and the shell shows no control** (DDC/CI would need `i2c-dev` and a package: not built). The percentage is rounded and never 0 (a level of 0 reads as 1). `SetBrightness(percent)` takes 1..100 (`invalid` for 0 or above 100, checked first), scales it to the device (at least 1: **a panel is never set to 0**, which on many laptops is a black screen that a controller cannot undo) and answers `ok`, `unsupported` or `failed`. **The service is not root** (a user unit of `ruya-shell` with `ProtectKernelTunables`, so `/sys` is read-only to it): it writes through logind, `org.freedesktop.login1.Session.SetBrightness("backlight", name, level)` on `/org/freedesktop/login1/session/auto` (for a user unit, the user's display session), which logind allows for the session's owner. `RUYA_BACKLIGHT_DIR` points the service at a fixture directory and then writes the level to the device's file itself (tests, development). **Shell side:** `Display.brightnessSupported`, `Display.brightness`, `Display.setBrightness(percent)` (`setBrightnessFinished(status)`) and `Display.refreshBrightness()`; the level shown is always the service's answer. The mock has a fourth screen, "laptop" (`eDP-1`, a backlight at 60 %); the other three have none. **Unverified:** that logind accepts the call from the service's user unit on the Dell or a laptop (QEMU has no backlight device; `vm-devices-check.sh system` checks the `unsupported` answers).
- **Refresh-rate matching** for video apps (Phase 4): when a fullscreen surface requests a content rate (via `wp_content_type`/frame-rate hint, or an app-specific integration), switch to 23.976/24/25/50 Hz. Opt-in.
- HDR/VRR are stretch goals and depend on ADR-002 (gamescope supports both; QtWaylandCompositor support is unverified and needs a spike).

### 2.5 Network
NetworkManager over D-Bus: Ethernet status, Wi-Fi scan/connect (WPA2/3-Personal; Enterprise is out of MVP), captive-portal detection (NM connectivity check → open a portal page in a minimal web view, Phase 3+), proxy (later).

**As built (T-129, shell side only):** the contract is the `org.ruyaos.Devices1.Network` interface in `api/dbus/org.ruyaos.Devices1.xml` (`State`, `Primary`, `ListWifi`, `Scan`, `Connect`, `Forget`, `NetworksChanged`; statuses `ok`, `unknown-network`, `wrong-password`, `unsupported`, `invalid`, `failed`). The shell has the `Network` singleton (`shell/src/network`, mock by default on every OS, D-Bus client unverified) and Settings → Network (`NetworkPane.qml`): status row, Wi-Fi list, rescan, a Forget row per saved network, masked password entry. 

**As built (T-132, `ruya-devices`, `network.rs` + `networkmanager.rs`):** the service implements the interface on the same object as the audio part, over NetworkManager's own D-Bus API with zbus (no `nmcli`, no polling: NM's signals, debounced, drive `NetworksChanged` and the property changes). `State` comes from NM's `State` and `Connectivity` (`limited` for local-only, portal and failed checks); `Primary` is the active connection with its kind, name and IPv4 address; the Wi-Fi list has one entry per SSID (strongest signal wins) with `known`/`active` flags; `Connect` and `Forget` only ever touch Wi-Fi connections and map NM's failures to `wrong-password`, `unknown-network`, `unsupported` (enterprise) and `failed`. A password goes into one D-Bus call and into no log or error. NM authorizes through polkit: see `01-platform.md` for the rule. The Linux shell uses the service by default (`RUYA_SERVICES=mock` for the mock). Real Wi-Fi is not exercised in the VM (QEMU has none); the Wi-Fi rules are proven by unit tests and the fake.

## 4. Applications (ADR-005)

### 4.1 Format & runtime
- Only Flatpak. Installs are system-wide (`/var/lib/flatpak`) so they're shared by profiles. App data is per profile in `~/.var/app/<id>`.
- Metadata comes from AppStream (`metainfo.xml`). We read the standard fields (name, summary, description, screenshots, categories, `content_rating`, `<supports>`/`<recommends><control>`, releases) plus **RuyaOS custom keys**:
  ```xml
  <custom>
    <value key="x-ruya-hero">https://…/hero.webp</value>
    <value key="x-ruya-logo">https://…/logo.webp</value>
    <value key="x-ruya-launch-mode">fullscreen|gamescope|default</value>
    <value key="x-ruya-controller">full|partial|none</value>
  </custom>
  ```

- **The real spawner (T-162, `systemd.rs`, vm-verified):** runs as root on the system bus (`ruya-session.service`, empty capability set, exposure 1.1 OK; only root owns the name, only `ruya-shell` and root call it). An app is a transient service of the profile user's own systemd manager: `systemd-run --user --machine=ruya-<id>@.host --wait --collect --property=Type=exec --unit=ruya-app-ruya-<id>-<app>.service -- flatpak run <app>`, one such process per running app. Its stderr lines are the events: `Running as unit:` is `AppStarted`, `Main processes terminated with: code=exited|killed, status=N/...` is the exit code or signal (`RunFollower`, pure and tested). **Its stderr is a file in `/run/ruya-session` that the service tails, not a pipe:** `systemd-run --machine=` passes its stderr on to PID 1, and SELinux refuses PID 1 a pipe (or a file in a home directory) of ours, which ends the call with "Connection reset by peer". **The app lives in `app-flatpak-<id>-<n>.scope`,** not in our unit (`flatpak run` moves itself there), so `Stop` is `systemctl --user -M ... stop --no-block <unit> app-flatpak-<id>-*.scope` and the kill is `kill --signal=SIGKILL --kill-whom=all` on the same two (stopping the unit alone left the app running). **The run follows its scope (T-363; `scope.rs` pure and host-tested, wired in `systemd.rs` `Gate`):** a run is the unit (the `flatpak run` front end, 28 ms of CPU for a 45 minute game on the Dell) plus the scope where the game is. `RunScopes` finds the run's scope with one `systemctl --user -M <user>@.host show` per profile manager and round (the unit and the pattern `app-flatpak-<id>-*.scope`, once a second for the first 60 s, an adopted unit at once): the live scope of that app whose name is `<id>-<digits>` and that entered `active` no earlier than the unit (a second of slack), the earliest if several (ties in the same second go by name, so an Electron app's run may follow either of its two scopes, see below); then it looks at the exact scope every 5 s. **The run ends only when both are gone:** the unit's end (`Exited`/`ExecFailed`, with its own exit status) is held while the attached scope lives and handed on when the scope is gone (5 failed looks in a row count as gone: the manager is gone); until then the run stays in `ListRunning`, `Stop` and the kill still reach it and a relaunch answers `already-running`. A run whose scope never appears in the 60 s (not a sandbox launcher) is never held. A unit that ends within the first second, before its scope was seen, is not held (accepted race). **A run can have more than one scope (T-435):** an Electron app's sandboxed zygote is started through the Flatpak portal (zypak, `flatpak-spawn --sandbox`) in a second `app-flatpak-<id>-<n>.scope`, in the same second as the first (ACBR on the Dell). **Stop and the kill therefore name every scope of the app** (`stop --no-block <unit> <scope>...`, `kill --signal=SIGKILL --kill-whom=all <unit> <scope>...`, `spawner::control_command`): one app runs once per profile user, so the app's scopes in that user's manager are all this run's. **The scopes are listed first and named exactly, never by the glob:** `systemctl --user -M <user>@.host list-units --all --plain --no-legend app-flatpak-<id>-*.scope` (`list_scopes_command`), kept only when the part after `<id>-` is digits (`app_scopes`, `is_app_scope`), because the glob also matches a sibling app whose id starts with `<id>-` (`io.github.Foo-bar.App` for `io.github.Foo`); with none listed only the unit is named. Every such `systemctl` is bounded to 5 s (`run_bounded`), so a manager that does not answer holds up neither a Stop nor the scope watcher for long. Naming only the attached one let the other run on after Close. **When a run's end is handed on** (by either path above, or the 5 missed looks), the service first lists the app's scopes the same way and runs `systemctl --user -M <user>@.host stop --no-block <scope>...` and `reset-failed <scope>...` on them (`RunScopes::take_sweeps`, `spawner::sweep_commands`; nothing when none is listed): what is left of the app stops, and a scope systemd had to kill (result `timeout`, listed as `failed`) is not listed any more, so no `app-flatpak-*` unit outlives its run. The listing and the stop happen before the end reaches the core, so a relaunch is never caught by them. **Usage:** `RunScopes::cpu_nsec` is the unit's CPU plus the scope's (`CPUUsageNSec`, never lowered by a smaller reading); the service logs `attached <scope>` and `scope gone, cpu N ms` per run in the journal. The play ledger (T-247) counts presence seconds of the foreground app between its start and its end, so a run now ends with the scope and the ledger and the time limit (T-211, which stops the app) follow where the game is; CPU is not stored in the ledger. **For T-165 (freeze on profile switch): freeze the scopes, not the unit.** The game's processes are in the app's scopes (`app-flatpak-<id>-*.scope`, every one of them: `RunScopes::scope_of(unit)` is only the one the run follows; `systemctl --user -M <user>@.host freeze <scope>`, or `cgroup.freeze` of its cgroup); freezing `ruya-app-*.service` freezes only the `flatpak run` front end (and an adopted run must be attached first: its scope is known within about a second of the service start). **The profile's manager must outlive the login session the call opens** (logind stops an idle one after 10 s, killing the app): before a launch the service runs `loginctl enable-linger`, then `systemctl start user@<uid>.service` (waiting for the start that linger began; a `systemd-run --machine=` that arrives during that start hangs it for 45 s). `ruya-profiles` ends the manager and the linger when it deletes the profile (`loginctl terminate-user`, `disable-linger`; otherwise `userdel` refuses). Installed means `/var/lib/flatpak/app/<id>/current` exists. The user units of PipeWire and WirePlumber are restricted to `ruya-shell` by drop-ins (`ConditionUser=ruya-shell`, ADR-010): before T-162 a profile's manager started its own against the hardware. **Environment (`spawner::console_env`):** every app gets `SDL_VIDEODRIVER=wayland` and `XDG_SESSION_TYPE=wayland` (T-435), then its profile's `WAYLAND_DISPLAY` (T-164) and `PULSE_SERVER` (T-365). The console has no X server: Chromium and Electron choose their Ozone platform by `XDG_SESSION_TYPE` and without it took X11 and exited (`Missing X server or $DISPLAY`; ACBR, Electron 42, on the Dell showed no window). **Restart (T-290, `Session::adopt`, `SystemdSpawner::adopt_running`):** the apps keep running when `ruya-session` restarts (they belong to the users' managers), but the `systemd-run --wait` processes that reported their end die with the service. At start, before the bus name is taken, the service lists the profile users (`loginctl list-users`), asks each manager for its `ruya-app-*.service` units (`systemctl --user -M <user>@.host show`, times as unix seconds) and rebuilds the registry from them: the profile from the user, the app id from the unit name (the user decides the split, `unit_app_id`), the start time from `ActiveEnterTimestamp`. They are `running`, announce nothing (no `AppStarted`; the shell asks `ListRunning`), a relaunch answers `already-running`, and `Stop`/the kill work as before. A unit of a profile `Profiles1.ListProfiles` no longer knows is stopped (killed after the grace time) and never listed or reported; when `ListProfiles` cannot be read nothing is stopped. Each adopted unit is followed over **one long-lived bus connection per profile manager** (T-340; `follow.rs`, `systemd.rs` `UserLink`): the same route `systemctl --machine=<user>@.host --user` takes, so the unit's hardening stays as it is. zbus starts `systemd-run --machine=<user>@.host --user --pipe --quiet --collect systemd-stdio-bridge --user` (a `unixexec:` address, `follow::bridge_address`, built from a validated `ruya-<id>` user only) and talks over its pipes; `Subscribe`, then the `PropertiesChanged` (`ActiveState`, `ExecMainStatus`, `ExecMainCode`) and `UnitRemoved` signals, so no `systemctl` process runs while the apps are followed and a `--collect`ed unit still gives its real status. **The exit code of an adopted app is that real status: a non-zero exit reads `crashed`, 0 reads `quit`, a signal reads `killed`** (after a `Stop`: `quit`). When the bridge dies the units are looked at with `systemctl show` every 2 s while it is started again (pause 2 s doubling to 60 s); after 5 failed looks in a row the manager is asked whether the unit still exists and only a "no" (or no manager for that user) ends the watch. A `Launch` right after a `Stop` waits (at most 8 s: the 5 s grace, the kill, a moment) until the old instance has ended before it starts; if it has not ended by then the answer is `failed` (never `already-running` for an instance that was told to stop, and never a second unit on the taken name). **Exec failure:** `systemd-run` printing `status=203/EXEC` is the event `ExecFailed`, reason `launch-failed` and code -1 (a bare exit code 203 and every other non-zero status stay `crashed`). Run with `--session` over a fake spawner on a development host. Check: `scripts/vm-session-check.sh` (`docs/dev-setup.md`).
- **Freeze and Thaw (T-457; the Ruya Hub pauses the game, ADR-033 point 3; `session.rs` `freeze`/`thaw`, `systemd.rs` `freezer`, `spawner::active_app_scopes`, host-tested; VM check `vm-session-check.sh`, lead run):** `Freeze(instance)` freezes a running app of the signed-in profile with the cgroup freezer: `systemctl --user -M <user>@.host freeze <unit> <scope>...`, the scopes listed first like Stop's (T-435) and kept only when they are the app's own (`app_scopes`) **and active** (systemd refuses to freeze or thaw an inactive unit, such as a `failed` scope not swept yet), so both scopes of an Electron app are frozen and a sibling app never is. The call waits for the freeze (each `systemctl` bounded to 5 s, under the registry lock, so a quick Thaw after it is served after it). The signed-in profile is `Profiles1.ActiveProfile`, read per call (system mode; `--session` does not check): another profile's app, or any app with nobody signed in, is `not-allowed`; an unknown, starting or stopping instance is `not-running`; a frozen app is `ok` without a second call. A failed freeze (the listing or the freeze fails or times out) is undone by a thaw of the same units and answers `failed`: the app keeps running. `Thaw(instance)` runs `thaw` on the same units, also for an app the service does not know as frozen (a restart of the service forgets the state; thawing a running unit is a no-op for systemd); a failed thaw keeps `frozen`. **`Stop` thaws a frozen app first** (synchronously, before the stop): a frozen process cannot handle the SIGTERM, so the Stop would end in the kill. The 5 s grace counts from the SIGTERM, after that thaw (T-466: `stop` takes a `Clock` and reads it after the thaw; before, a slow thaw of up to two bounded `systemctl` calls ate into it). Each change of a record's `frozen` (in `ListRunning`) is announced with `FrozenChanged`. Freeze and Thaw take turns in the order they arrive (an async mutex taken before the `Profiles1` read, so a quick Thaw is never served before the Freeze ahead of it). An app taken over after a restart reads its unit's `FreezerState` (`frozen`/`freezing` is frozen, part of the adoption's `systemctl show`), so a Stop thaws it first. The game's sound: its PulseAudio client (the profile's own `ruya-pulse` server, T-365) stops feeding its stream; the server itself is not frozen. **The server pauses a stream after 5 s of underrun (RUY-425; `pulse.idle.timeout = 5` in `ruya-profile-pulse.conf`):** unpaused, a stream with `prebuf` 0 (OpenAL-soft's) is still read while its app is frozen, and every quantum the server asks the app for one more quantum (pipewire-pulse `stream_pop_missing`); at the thaw the app got the whole freeze's worth at once, and after 1 h 53 min SuperTuxKart aborted in libpulse (`memblock.c` `stat_remove`, Dell, 0.0.68). Paused, the stream is not read and the ask stops at about 5 s of sound, however long the freeze; the first write after the thaw resumes it. **A frozen app's sound is parked (T-466; `session.rs` `sync_audio`, `spawner::park_audio_command`, `ruya-devices` `park.rs`, host-tested; VM check `vm-session-check.sh`, lead run):** a frozen stream linked to the card kept PipeWire and the ALSA sink `running` on silence (Dell, 0.0.64: about 1.4 % of a core, +1000 context switches and +300 interrupts a second, +0.15 W at idle). After every change of a profile user's frozen or running apps while it has a frozen app (a Freeze, a Thaw, a Stop, a launch or an end; after a restart of the service once per profile user with apps), the core asks `Spawner::app_audio(user, frozen, running)` with the whole state of that user. The real spawner queues it to one worker thread (in order; a newer request of a user replaces its queued one, `spawner::AudioQueue`; a failed run is tried again 2 s later, `PARK_TRIES` 3 in all, unless a newer request of that user came in meanwhile) that runs `systemd-run --machine=ruya-shell@.host --user --wait --collect -p RuntimeMaxSec=15 -- /usr/bin/ruya-devices --park-audio <user> --frozen=<ids> --running=<ids>` (bounded to 20 s): only `ruya-shell`'s manager reaches the console's PipeWire (ADR-010), and this service runs as root with no capability. That manager lives only while the compositor's session holds it (`ruya-shell` does not linger, decided in T-472, see Launch above): logind stops it 10 s after `ruya-compositor@tty1` stops (`UserStopDelaySec`), and with it PipeWire and every profile's `ruya-pulse` server, so a park or restore then fails with "Transport endpoint is not connected" (T-470, seen on the Dell; `vm-session-check.sh` lingers `ruya-shell` while it keeps the shell stopped). The sound card is the seat session's alone (logind's `uaccess` ACL on `/dev/snd`): with the shell stopped, its PipeWire sees only `auto_null`. `ruya-devices --park-audio` reconciles from one `pw-dump` and exits 1 when any `pw-metadata`/`pw-cli` step failed (so the retry above happens; every `pw-metadata` call puts `--` before its positional arguments): the user's streams are the `Stream/Output/Audio` nodes whose client's `pipewire.sec.pid` is the main process of `ruya-pulse@<user>.service` (asked of its own manager); a stream whose client carries `pipewire.access.portal.app_id` of a running app is parked when that app is frozen, any other stream of the user (today every one: the server runs as `ruya-shell` and cannot read another user's `/proc/<pid>/root/.flatpak-info`) only while every running app of the user is frozen, so a game that plays is never silenced. Parking writes the stream's old `target.object` to the `default` metadata under `ruya.parked` (JSON, `{"target":null}` when it had none), then sets `target.object` to the null sink `ruya-parked` (created on the first park with `pw-cli create-node adapter` of `support.null-audio-sink`, `object.linger`, `priority.session 0`, destroyed with `pw-cli destroy` when no stream is parked any more); WirePlumber relinks the stream there and suspends the idle card. Putting back sets the saved target again (or deletes `target.object`, so the stream follows the default) and deletes `ruya.parked`. `ruya-parked` is never an output or the default in `Devices1.Audio` (`pipewire::parse_dump` skips it). The Thaw runs before the stream is put back, so the first moment of sound after a thaw goes to the null sink (no burst; the gap is not measured yet). **A frozen app's memory is reclaimed (T-466; `session.rs` `tick`, `RECLAIM_AFTER`, `spawner::reclaim_command`):** once an app has been frozen for 30 s (an adopted frozen app: 30 s after its adoption), never at the Freeze (when the Hub opens and must stay instant), and only when swap is active (`systemctl list-units --type=swap --state=active`: this unit's `ProcSubset=pid` hides `/proc/swaps`; without swap a reclaim only drops clean cache), the core asks `Spawner::reclaim(unit)` once per freeze. `swap_active` never blocks the tick (it runs under the session lock): the real spawner reads the swap state on its own thread every 60 s and answers from that reading. The real spawner, on its own thread, lists the app's active scopes, reads the `ControlGroup` of the unit and of each scope from the user's manager and their `memory.current`, and runs `systemd-run --machine=<user>@.host --user --wait --collect --unit=ruya-reclaim-<app>.service -p RuntimeMaxSec=30 -- /usr/bin/sh -c <loop> ...` that writes `RECLAIM_PERCENT` (50 %, a starting value for the Dell numbers) of each `memory.current` to its `memory.reclaim`: the profile user owns its own app cgroups (the manager's delegated subtree), while this service may not write the cgroup tree (`ProtectControlGroups`, no capability). It logs `<unit>: memory reclaim done in N ms: asked X MiB of K cgroups, memory.current A -> B MiB` (or `no swap is active, its memory stays`). A Thaw or Stop of an app whose reclaim was started first runs `systemctl --user -M <user>@.host stop --no-block ruya-reclaim-<app>.service` (non-blocking), so a reclaim still running does not page the game out while it plays. The service cannot see whether the Hub is still open over the frozen game, so 30 s under the Hub count too (no `Session1` change: the shell needs to know nothing; `frozen` and "Paused" mean the same as before). systemd-oomd stays inert (no `ManagedOOM*` policy, T-465).
- **InstanceOfPid (T-459; `session.rs` `instance_of_pid`, `spawner::parse_cgroup`, host-tested; VM check `vm-session-check.sh`, lead run):** the running instance a process belongs to, for the compositor, because the app id a window gives itself is not always its Flatpak id (Asteroid Shooter, a pygame game, calls itself `python3.12`; Superfluous Returnz `superfluous-returnz`). The service reads `/proc/<pid>/cgroup` (root reads every user's process under `ProtectProc=invisible`, checked on the Dell), takes the cgroup v2 path below `user@<uid>.service`, names the uid's user (`getpwuid_r`) and walks the units on the path from the deepest up: the first that is a non-hidden instance's own unit, or one of its app's Flatpak scopes (`is_app_scope`, so both scopes of an Electron app and never a sibling app whose id starts with this one's), **in that instance's own user's manager**, is the answer (starting and stopping instances count). Anything else (no such process, a system service, a process of the user's manager outside every app, an unknown uid) is `not-found`; pid 0 is `invalid`. The mock gives every launched instance a made-up pid (`Session.mockPidOf`, 4001 up).
- **The play ledger (T-247; `usage.rs`, `usage_tracker.rs`, `usage_store.rs`, host-tested, VM check `scripts/vm-usage-check.sh` pending):** per profile, one record per run of an app: `app_id`, `app_version` (from the app's AppStream file when the run began; an update while it runs does not split the run), `start`/`end` (UTC unix seconds), `foreground_seconds`, `exit_reason` (`quit`, `crashed`, `killed`, `time-limit`, `bedtime`; the last two are set by T-211 through `Tracker::set_end_reason` before it stops the app) and, inside the service, the seconds per local day. **Only times and the exit reason**: nothing about what happens inside the app (`docs/developers/play-time.md` says this to developers). **Accounting rules (the pure `Tracker`, tested with a fake clock):** the adapter tells the core when an app reached `running` and when it exited (`AppStarted`/`AppExited`, with the exit reason of the event); the shell tells it who is in front: `ReportPresence(profile, instance, attention)` on every change and every 20 s, `attention` = `active` | `idle` | `locked` | `suspended` (`instance` "" = the shell itself). A second counts for an app only when the report says the profile is active and not locked, idle or suspended, the app is the foreground app, and the report is fresh (at most 75 s old: a dead or stuck shell counts nothing); only the foreground app accrues when several run. Time is the monotonic clock (`Instant`), so a clock change moves no duration; one tick (about a second) counts at most 5 s, so a stalled process or a suspend cannot count what it missed. A **heartbeat** is written every 30 s while there is new time (`open/<key>.rec`, rewritten atomically); at start-up a leftover heartbeat file means the run never ended (crash, power cut, the service itself killed) and the run ends **at the last heartbeat** with reason `crashed`. Runs under 10 s are dropped. A **profile switch** (a report for another non-empty profile) ends the previous profile's runs with `quit` (T-165: a switch stops its apps). The shell's idle report is its own clock for now (no input for 10 min, `UsagePresence.qml`; the first 10 minutes of silence still count): T-202's single idle clock replaces it, and audio playing does not keep it awake yet. **Days** are the device time zone's (T-213): `SystemZone` asks libc `localtime_r` after `tzset` for every second counted, so a DST change or a zone change is honoured and history is never rewritten; the second that just ended is the one counted. **Retention:** raw runs 90 days, then rolled up into one row per app and day (seconds, runs, longest run, first start, last end) kept 24 months; at most 5 000 raw runs and 20 000 rows (the oldest roll up or drop first). Deleted with the profile (`purge_except`, once a minute against `Profiles1.ListProfiles`; profile ids are never reused); not in the save backup; never in telemetry (T-224). **Files:** `/var/lib/ruya-session/usage/<profile>/ledger.tsv` (a line per run `S` and per rolled-up day `R`; a run is appended with one write, a rewrite is tmp + `fsync` + rename; a torn last line is dropped on load; a damaged file is kept as `ledger.corrupt`, never overwritten) and `open/` (running runs); directories 0700, files 0600, root only (`StateDirectory=ruya-session`, `StateDirectoryMode=0700` in the unit, the only path the service writes). **Interface (`Session1.xml`):** `ReportPresence`, `ListSessions(profile, since, limit)` (newest first, running ones with `open`), `GetTotals(profile, from, to)` -> `(status, today, rows)` per app and local day (`""` = earliest / today), `ClearHistory(profile, admin_id, admin_pin)`, signal `UsageChanged(profile)`; T-211 builds its counter and the parent's report on `GetTotals`, not on a second ledger. **Authorisation:** `ListSessions` and `GetTotals` answer `not-allowed` for any profile but the one `Profiles1.ActiveProfile` names (an admin does not browse another profile's play); `ClearHistory` with an empty `admin_id` needs the profile to be the active one (its own PIN was checked when it signed in; `Profiles1` has no verify-PIN call for a standard profile), otherwise `Profiles1.VerifyAdmin` decides (`wrong-pin`, `locked-out`, `not-allowed`). The bus policy still lets only `ruya-shell` and root call. **Known limits:** with two apps running the shell assumes the newest one is in front (the compositor does not tell it which window is which instance, T-164); Steam and other launchers count as the launcher until a later task reads their own play time; a restart of `ruya-session` does not split a run (T-290): the open run of an app that is still running is taken over from its heartbeat (time so far, start, file; `Tracker::recover_with`), so it ends as one row; an adopted app with no heartbeat (under 10 s counted) starts a run dated from the app's start; heartbeats of apps that are not running end as `crashed` as before. The seconds between the last heartbeat and the restart are lost (at most 30 plus the restart).

### 4.3 Store service (`ruya-store`)
Wraps libflatpak and libappstream. D-Bus `org.ruyaos.Store1`: `Search`, `GetApp`, `Install`, `Update`, `Uninstall`, `Rollback(id, commit)`, `ListRemotes`, `AddRemote` (admin), `ListJobs` (T-188), plus progress and error signals. There's a single transaction queue, and updates run when idle. Errors (signature, missing runtime, disk full, network) map to user-facing messages.

The contract is `api/dbus/org.ruyaos.Store1.xml`. Differences from the list above: `Install`/`Uninstall`/`Update`/`Rollback` answer `(status, job)`; progress and errors are the `JobProgress` and `JobFinished` signals (error kinds are `JobFinished` statuses `network`, `signature`, `missing-runtime`, `disk-full`); `ListInstalled` and `InstalledChanged` were added; since T-148 `Search(query, options)` takes `controller` (`any` | `gamepad`: controller `full` or `partial` only) and `limit`, and `CatalogChanged` (not `InstalledChanged`) tells the clients to search again. The shell side is `shell/src/store` (on `InstalledChanged` the `Store` reads `ListInstalled` and patches the `installed`/`updateAvailable` flags of the apps it holds, with no new `Search`; on `CatalogChanged` it searches again; `Store.controllerFilter` (`any` default, `gamepad`) is passed to `Search` for `Store.search()`, the catalogue stays whole; `Store.app(id)` answers from an index of the catalogue and `Store.rowIds(gamepadOnly)` gives the Store page's row ids in one pass (T-377); the `Store` singleton, D-Bus by default on Linux since T-134, `RUYA_SERVICES=mock` for the mock, the mock elsewhere); when the service's bus name loses its owner (crash, restart; `StoreBackend::serviceLost`) the `Store` drops all jobs and emits `jobFinished(id, "failed")` for every job it ran or queued (`serviceLost(jobApps)`, the backend's job id -> app id; an owner handover counts as a loss too), so no page waits for a job that is gone (resuming is not attempted; tests use `Store.mockServiceLost()`), and when the name is taken again the backend calls `ListJobs` (also once at start) and the `Store` applies the service's job table (T-188): `jobs` becomes exactly the table's running jobs, and an app that was given up as `failed` whose lost job (found in the table by its job id, not as the last job of the app) ended otherwise (Flatpak completed it: `ok`) gets a second `jobFinished` with the real result, so the page goes from the error to Open; a job the table also calls failed/interrupted is not reported twice, and an app that has reported a later job since the loss is not corrected (T-191). `Store.jobsReconciled()` is emitted after each application. A reply older than one already applied is dropped (`RequestSequence` in `StoreBackend`, T-181), and so is one older than a newer request that failed. The bookkeeping of the service's jobs is `JobBook` (T-191, shared by the D-Bus client and the mock): a signal that overtakes the reply naming its job is kept and replayed; while a `ListJobs` is pending every signal is logged and the reply is brought up to date with the ones that arrived after the request (a job that finished meanwhile is not shown as running); a job the table lists as running is tracked, and a tracked job the table lists as finished, whose `JobFinished` never arrived, gets its `jobFinished` instead of being forgotten. `ListInstalled` and `Search` replies are guarded the same way (the service answers concurrently, T-192: `InstalledChanged` can precede the reply of the call that caused it, and two replies can arrive out of order; the refresh that `InstalledChanged` triggers finds nothing to correct and sends no signal, so there is no loop). The app page shows `working` while its own request is unanswered or `Store.jobs` has a job of the app, so a job adopted at start shows on the page that did not start it; tests: `mockServiceRegained(finishedApps)`, `mockForgetJobs()`, `mockEndJobsUnheard(status)`, `mockRecordFinishedJob(app, kind, status)`, `mockListJobsDelayed(ms)`, `mockListJobsFailing()`, `mockInstalledDelayed(ms)`, `mockCatalogueDelayed(ms)`, `mockPauseJobs(bool)`, `mockAddApps(n)` (a catalogue of a real remote's size), `mockSearchReplyDelay(ms)`, `mockCatalogueReads()` (T-377); its D-Bus client does not call `GetApp`, `Rollback`, `ListRemotes` or `AddRemote` yet.

**As built (T-134, `services/ruya-store`):** it drives the `flatpak` command line (`--system --noninteractive`, as root, English messages) instead of libflatpak; the AppStream data flatpak keeps per remote (`/var/lib/flatpak/appstream/<remote>/<arch>/active/appstream.xml.gz`) is read with a pure-Rust XML parser (name, summary, description, developer, `content_rating` to the OARS summary (the worst attribute decides: none `all`, mild `7+`, moderate `12+`, intense `16+`, and `18+` when the intense one is a `sex-*`, `violence-sexual`, `drugs-*` or `money-gambling` attribute; an app with no `content_rating` has an empty rating, which the contract leaves out and the shell shows as "Not rated", never "All ages"; T-211 treats it as 18+ for children), `<control>gamepad` and `x-ruya-controller`, icon, `x-ruya-hero`/`x-ruya-logo`). An app a remote lists without AppStream data is shown under the last part of its id. `source` comes from the remote (`ruyaos` official, `flathub` community, anything else developer). Permissions come from the app's `metadata` (`flatpak remote-info --show-metadata`) and are read by `GetApp` on first use, not for the whole catalogue (a remote can have hundreds of apps); the lists carry the ones already read. Core rules: one transaction queue, jobs run one at a time in order, `busy` for an app that already has a job queued or running, `JobProgress` never decreases (0 at the start, 100 at the end; since T-140 the percentages in between come from giving `flatpak` a pseudo-terminal, opened with `rustix`, 200 columns wide, because it draws its progress bar only on a terminal; the output is cut into lines at carriage returns and newlines, escape codes are stripped, and an "n/m" in the line makes the percentage the share of the whole transaction, so the runtime and the app do not each run 0-100), error text maps to `network`, `signature`, `missing-runtime`, `disk-full` or `failed`, `InstalledChanged` comes before `JobFinished`. Every id, remote name, URL and commit that reaches the command line is validated first. `Uninstall(delete_data=true)` removes `~/.var/app/<id>` of every profile home under `/var/home` as the home's owner (`rm -rf` after `setuid`), so a symlink a profile planted cannot make root delete anything else. `AddRemote` is for root, or for the shell while the active profile (per `Profiles1`) is an admin; it never passes `--no-gpg-verify` and removes a remote that ended up unsigned (`invalid`). The catalogue is read once after start (a background thread) and again after every successful job and `AddRemote`. **Job table (T-188):** `ListJobs() -> aa{sv}` returns the jobs queued or running and the 20 most recent finished ones, oldest first: `id`, `app`, `kind` (`install` | `remove` | `update` | `rollback`), `state` (`queued` | `running` | `finished`), `status` (the `JobFinished` status once finished), `reason` (`interrupted` or empty), `percent`, `phase`. The table is written to `jobs` in the unit's `StateDirectory` (`/var/lib/ruya-store`, `RUYA_STORE_JOBS_FILE` overrides; without either it is in memory only) whenever a job is queued, starts or ends (progress is not written), as a small tab-separated text file that is read as untrusted input (bad lines and bad app ids are dropped). After a restart a job the previous run left queued or running is settled once, before the first `ListJobs` answer and at the start of the first catalogue read: a running install whose app is installed now and a running remove whose app is gone are `finished`/`ok` (Flatpak completed them), every other one (queued, update, rollback, or Flatpak unreadable) is `finished`/`failed` with `reason` `interrupted`; the service never resumes a transaction. The result is written back, so a second restart agrees. Job names (`job-N`) continue after a restart, because the shell maps signals by name; no signal announces the correction, the new bus name owner is the announcement. Jobs queued by the new run before the first `ListJobs` are left alone. **Installed state (T-182):** Flatpak, not the cache, decides what is installed: `Install`, `Uninstall`, `Update`, `Rollback` and `ListInstalled` first run `flatpak list` and correct the catalogue's `installed` flags, so an app removed with `flatpak uninstall` can be installed again without restarting the service and a correction that changed the installed set or an update flag sends `InstalledChanged` itself (T-192), so a client does not keep showing the removed app as installed until its next read. The service keeps the set it last announced; a correction and a catalogue read both compare against it and set it, so a change is announced once, by whichever sees it first (a job's refresh after a query that already corrected and announced it sends nothing more); a `flatpak list` read that a catalogue read overtook is dropped, and reads that overlap (the calls run on separate threads) are ordered by ticket (T-291): each takes a counter value before it reads and applies only if no read that started later has already applied, so a slow older read cannot undo a newer correction. The correction only fixes the flags of apps the catalogue lists: an app installed by hand from a remote the Store did not add (and that no remote of the catalogue offers) is not added, because the Store lists its own catalogue; only an installed app that no remote offers any more is listed, when the catalogue is read. The calls that run `flatpak` (`Install`, `Uninstall`, `Update`, `Rollback`, `ListInstalled`, `ListRemotes`, `GetApp`, `ListJobs`, `AddRemote`) run on a thread of the `blocking` pool, not on the zbus executor, so one slow `flatpak` does not hold up other calls and signals (T-192). The developer name is `<developer><name>`, else `<developer_name>`, never both. `InstalledChanged` is sent when the installed set or an update flag changed (every job that changed one, and a call that finds a difference by reading Flatpak); `CatalogChanged` only after the first read, after the AppStream refresh and after `AddRemote`, never for a job. After the first read and after every `AddRemote` the service runs `flatpak update --appstream --system <remote>` for each enabled remote and reads the catalogue again (`CatalogChanged` after both reads); without a network it logs once and keeps the cached data. Updates are not checked on a schedule. The unit is `ruya-store.service` (system, root, exposure 3.3 OK; it needs a larger capability set and network than `ruya-profiles`), the policy lets only root own the name and only `ruya-shell` and root call it. Checked in the VM with `scripts/vm-store-check.sh` (`dev-setup.md`).

### 4.4 Permissions
- Flatpak permissions are **static**. The app page shows them in plain language before install ("Uses network", "Reads your Downloads folder", "Accesses all devices"). High-risk permissions (`--device=all`, `--filesystem=host`, `--talk-name=org.freedesktop.Flatpak`) get a warning and, for Standard profiles, need the admin PIN.
- Runtime prompts exist only for portal-mediated access (file chooser, camera, screenshot). We need a **portal backend** (`xdg-desktop-portal-ruya` or a QML-themed reuse of an existing backend) so portal dialogs render in the shell, controller-navigable. **Gap to spike in Phase 3.**
- Admins can review and override permissions per app (a Flatseal-like view).
- **As built (T-111, `AppDetailPage.qml`):** the app page lists the permissions in plain words (`Plays sound`, `Uses the network`, ...); `all-devices`, `host-files` and `session-bus` carry a warning `High risk` badge and warning-coloured text. For a Standard profile, Install on an app with a high-risk permission asks for an admin's PIN first (`PinPad` in collect mode, `Profiles.verifyAdmin` against the first admin; a wrong PIN or lockout shows as the inline error, Back cancels) and a line under the permissions says so; admins install directly (T-152). **Updates (T-156):** the page calls `Store.loadApp` (`GetApp`) when it opens, because the lists carry permissions only once read; Install and Update wait for the answer (a press before it is queued, a failed read retries on the next press), since the gate depends on it. For an installed app with an update, `GetApp` reads the installed version's metadata (`flatpak info --show-metadata`) and the remote's again (never the cache), and returns `new_permissions`: what the update adds (`appstream::added_permissions`; an unreadable installed version counts as having none). The page says "The update adds: ..." (warning colour if one is high risk), and a Standard profile needs an admin's PIN for Update when an added permission is high-risk (same PIN flow and wrong-PIN behaviour as Install); admins and updates that add only harmless permissions start at once. After an update the page reloads, so its permission list is the new version's. Install / Update / Open (disabled until the session service exists) and Uninstall with an "Also delete my data" toggle (Cancel is the default); progress shows a bar with the phase, and errors (`network`, `signature`, `missing-runtime`, `disk-full`, `busy`, else generic) are shown inline.

### 4.5a App data and save games (decided, lead, 2026-11-06; the defaults behind `docs/developers/saves-and-data.md`)
Not every game will follow this; the defaults make the ones that do work well and let us treat the rest safely.
1. **Where.** Apps are installed system-wide (`/var/lib/flatpak`, shared); **everything an app writes belongs to the profile that runs it**, in the Flatpak per-user data directory `~/.var/app/<app-id>/` = `/var/home/ruya-p<N>/.var/app/<app-id>/` with the standard XDG split: `data/` (`$XDG_DATA_HOME`: saves, save states, profiles, downloaded content that is not a cache), `config/` (`$XDG_CONFIG_HOME`: settings), `cache/` (`$XDG_CACHE_HOME`: anything that can be rebuilt; the console may clear it when space is short and never backs it up). Profile homes are `0700`: one profile never sees another's saves, an admin neither (only the services see them, to back up or delete).
2. **Recommended layout inside `$XDG_DATA_HOME`** (a convention, not enforced): `saves/` (in-game save slots, battery saves), `states/` (emulator or snapshot states), `screenshots/`, `profile/` (per-player settings/stats). Emulators map their "saves" and "states" folders there; a conventional layout is what lets a backup list "Saves" and "States" separately in the future.
3. **What the console treats as saves when an app does not follow the convention:** the whole of `data/` and `config/` of that app. An app can narrow it with AppStream custom keys (planned): `x-ruya-save-paths` (comma list of paths relative to `$XDG_DATA_HOME`, the only things the backup includes) and `x-ruya-cache-paths` (extra paths under `data/` to leave out of backups).
4. **Backup and restore (planned, T-215).** "Back up saves" copies, per app and profile, `data/` and `config/` (not `cache/`) into a `.tar.zst` with a `manifest.json` (app id, app version, profile name, created time, sizes, SHA-256) under `RuyaOS-Backups/<profile name>/<app-id>/` on a USB drive; "Restore" works for an installed app only, writes the current data aside first (`.before-restore`) so it can be undone, and a restore into another profile needs an admin PIN. Done by a root service (profile homes are `0700`); the backup runs while the app is not running. Cloud saves are out of the MVP (Steam and others sync their own).
5. **Lifecycle.** An OS update never touches `/var` (saves survive updates and rollbacks). **Uninstalling an app keeps its data by default** (the shell asks "Keep saves?", default Keep; reinstalling finds them again); deleting the data is an explicit choice, shown per profile for admins, and always removes only that app's directory. Deleting a profile removes its whole home. A factory reset removes everything (01 §3.5).
6. **Developer rules (documented in the developer guide):** write saves atomically (temporary file in the same directory, `fsync`, rename; keep the previous slot as `.bak`), because the console may lose power at any moment (the filesystem is journaled but the app's own consistency is the app's job); on `SIGTERM` finish the save within the **5 s grace** `Session1.Stop` gives before `SIGKILL`; never put saves in `cache/`; never ask for `--filesystem=home` or host paths to store saves; use portals for user-chosen files.
7. **Not in v1 (Inbox):** a shared per-device content store for large downloadable game content (per profile copies are accepted for now); per-app data size and "clear data" in Settings -> Storage (T-196 follow-up); cloud sync.

Polling instead of inotify or a `Rescan` call from `ruya-store`: no new dependency, no coupling between services, and it also sees installs that did not come from the Store. Heroic integration is a stretch goal. |
| Saves | Stay where each app puts them, per profile, by the defaults of §4.5a (`~/.var/app/<id>`; recommended `saves/` and `states/` under `data/`). Backup and restore to USB are planned (T-215, was Phase 6). Cloud saves are left to Steam etc. |
| Streaming | Moonlight (Flathub), Steam Link (Flathub), Xbox Cloud Gaming via a browser Flatpak in kiosk mode (stretch, controller passthrough to be tested) |
| Anti-cheat | Documented as unsupported where the game blocks Linux. |

**Acceptance (Phase 5):** a native Linux Steam game, a Proton game and a RetroArch game each launch from the RuyaOS library, play with a controller, open the Guide overlay and return, and keep their saves across an OS update and a rollback.

## 6. Media

| Need | Approach |
|---|---|
| Personal media servers | Jellyfin Media Player / Kodi Flatpaks (Kodi gives a 10-foot UI out of the box). Plex: use the Plex HTPC Flatpak if available, otherwise none. |
| IPTV | Kodi PVR IPTV Simple client (M3U/XMLTV) instead of building our own player |
| Commercial streaming | Browser Flatpak (Chromium-based, Widevine L3) in kiosk mode. Resolution is limited by the service, which we state in docs. |
| Local files | Kodi or VLC from USB or the network |
| HW decode | Host side is solved by ADR-009 (`mesa-va-drivers-freeworld`, `intel-media-driver`, `libva-nvidia-driver`). Flatpak apps need `org.freedesktop.Platform.ffmpeg-full`/`codecs-extra` and the GL/VA-API extensions, which `ruya-store` installs on first boot. Verify with `vainfo` inside the Flatpak sandbox. |

**Acceptance (Phase 4):** a 4K HEVC 10-bit file plays with HW decode on the mid tier (verified with `intel_gpu_top`/`radeontop`), audio switches to a BT headset mid-playback without stopping, and controller navigation works in Kodi and Jellyfin.
