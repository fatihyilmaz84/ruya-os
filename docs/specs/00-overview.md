# RuyaOS — Overview, Architecture & Decisions

Status: **Draft v1** (consolidated 2026-10-22 from the three research docs; see `docs/REVIEW.md`).
Companion specs: [01-platform](01-platform.md) · [02-shell](02-shell.md) · [03-services-and-apps](03-services-and-apps.md) · [04-design-system](04-design-system.md) · [05-play-packages](05-play-packages.md) (draft)

## 1. Vision

RuyaOS is an immutable, image-based Linux OS for living-room PCs. It boots straight into a full-screen, controller-first, "cinematic" console UI: fluid 60 FPS motion, frosted-glass layers, and UI sound. There's no desktop. From one place it runs apps, media clients, streaming clients and games, for several PIN-protected profiles.

### Principles
1. **Reuse before build.** Fedora bootc, Flatpak, PipeWire/WirePlumber, NetworkManager, BlueZ, udisks2, polkit, greenboot, InputPlumber/SDL. Custom code is limited to the console-specific layers: shell, session orchestration, and glue services.
2. **Image-based and recoverable.** The OS is one signed container image. Updates are atomic, and a failed boot rolls back automatically.
3. **Controller-first.** Every flow, including installation and first-boot setup, works with a gamepad alone.
4. **Measured polish.** "Cinematic" is defined by KPIs ([02-shell §8](02-shell.md)) that run on real hardware tiers.
5. **Gated phases.** No phase starts until the previous one meets its exit criteria. Dates are estimates, not commitments.

## 2. Scope

### MVP (end of Phase 5)
- Boot, update and rollback, installer, first-boot setup.
- Shell: home, library, settings, store, overlay (Guide button), notifications, volume OSD.
- Profiles with PIN, plus a guest profile. One admin.
- Controllers over USB and Bluetooth. Keyboard and mouse as a fallback.
- Network (Ethernet, Wi-Fi), audio output switching, USB storage.
- Apps from Flatpak remotes (official plus a filtered Flathub).
- Media and streaming clients (Jellyfin, Kodi, Plex, Moonlight, Steam Link and the like) are **separate apps**, installed from the Store, and are not part of the first MVP (owner, 2026-11-06). The MVP provides the building blocks they need: launching and the Guide overlay over a running app, controller input, audio routing, hardware decode (ADR-009) and output switching. The focus is the OS, the shell UI and those building blocks.
- Gaming: Steam (Proton) and RetroArch are **separate apps** too (owner, 2026-11-06), not part of the first MVP. The MVP proves the gaming building blocks with a sample Flatpak game: launch, controller input, the Guide overlay over the running game, audio routing, and save locations that survive an OS update.

### Later / stretch
SDK and public developer programme, optical media, HDMI-CEC, HDR/VRR, cloud saves, parental controls UI, web-app runtime, custom "console bundle" format (the `.play` package: ADR-014 *Accepted, spike first; parked*, [`05-play-packages.md`](05-play-packages.md), epic T-228).

### Explicit non-goals
- Our own sandbox, package manager or display protocol.
- Proprietary DVD/Blu-ray decryption in the base image.
- Premium-streaming DRM parity with commercial TV OSes. Widevine L1 isn't available on Linux. Netflix and similar services run only via browser L3, at capped resolution.
- Anti-cheat titles that block Linux.

## 3. Target hardware

| Tier | Example | Expectation |
|---|---|---|
| Low | Intel NUC 8th–11th gen iGPU | 1080p, reduced effects, ≥ 30 FPS floor in transitions |
| Mid | Recent Intel Xe / AMD RDNA2+ APU mini-PC | 1080p/4K UI at 60 FPS, full effects |
| High | Desktop with discrete AMD or NVIDIA GPU | 4K60 UI, demanding games, HDR (later) |

All tiers are UEFI x86_64. NVIDIA needs the proprietary driver, which affects image build and Secure Boot ([01-platform §2.3](01-platform.md)).

## 4. Architecture

```mermaid
graph TB
  subgraph Image["Immutable OS image (fedora-bootc, /usr read-only)"]
    K[Kernel · Mesa/NVIDIA · firmware]
    SD[systemd · logind · polkit · greenboot]
    PW[PipeWire + WirePlumber]
    NM[NetworkManager · BlueZ · udisks2]
    INP[Input daemon<br/>InputPlumber or ruya-inputd]
    RS[Ruya services (Rust, D-Bus)<br/>ruya-session · ruya-profiles · ruya-store · ruya-devices]
    COMP[Compositor + Shell<br/>Qt Quick / QtWaylandCompositor]
  end
  subgraph State["Mutable state (/etc merged, /var persistent)"]
    HOME[/var/home/&lt;profile&gt;/]
    FP[/var/lib/flatpak/]
  end
  Apps[Flatpak apps & games<br/>(optionally inside gamescope)]

  K --> INP --> COMP
  INP -- virtual gamepads --> Apps
  COMP -- Wayland --> Apps
  COMP <-- D-Bus --> RS
  RS --> SD & NM & PW & FP & HOME
  Apps --> PW
```

### Components

| Component | Language | Responsibility |
|---|---|---|
| **ruya-shell** | QML + C++ | UI, the Wayland compositor (per ADR-002), focus/overlay, app windows, OSD |
| **ruya-session** | Rust | Launch/stop apps as the active profile's user, track running apps, suspend/resume hooks |
| **ruya-profiles** | Rust | Profiles, PIN verification and rate limiting, avatars, per-profile settings |
| **ruya-store** | Rust | Wraps libflatpak and AppStream: remotes, install/update/rollback, progress |
| **ruya-devices** | Rust | Facade over udisks2, BlueZ, NetworkManager and PipeWire (wpctl/libpipewire) for the shell |
| **Input daemon** | (reuse) | Grabs physical controllers, maps them (SDL GameController DB), re-emits virtual devices, routes to shell or game (ADR-003) |
| **ruya-update** | Rust (thin) | Drives `bootc upgrade`/`switch`/`rollback`, reports status, schedules reboot |
| **ruya-notifications** | Rust | The notification centre's history and settings, per profile (`Notifications1`, `03` §1.4; RUY-730) |

**IPC.** All shell↔service traffic goes over **D-Bus** (system bus, `org.ruyaos.*`) with `zbus` on the service side and QtDBus or generated C++ proxies on the shell side. Privileged actions (install system app, OS update, add repo, create profile) go through **polkit**. The shell gets an admin authorization after the admin PIN is checked by `ruya-profiles`. Each interface is versioned (`org.ruyaos.Store1`). Interface XML lives in `/api/dbus/` and is the contract between the QML and Rust teams.

## 5. Decision log (ADRs)

Status: **Accepted** · **Proposed** (recommendation, needs owner sign-off) · **Open** (needs a spike)

### ADR-001 — Base: plain `fedora-bootc` vs Universal Blue / Bazzite components — *Accepted (2026-10-22)*
Bazzite already ships Fedora-bootc images with NVIDIA variants, a gamescope console session, Steam and controller tooling. **Recommendation:** start from `quay.io/fedora/fedora-bootc` so the image stays minimal and understandable. Borrow specific, proven pieces (NVIDIA akmods layer, udev rules, InputPlumber packaging) from Universal Blue rather than rebasing on Bazzite. Revisit if Phase 0–1 effort runs high.

### ADR-002 — Compositor ownership — *Accepted: option A (owner, 2026-10-23); performance to be confirmed on hardware, option B is the fallback*
The shell must draw over running apps (Guide overlay, OSD, toasts), switch between apps, and control focus. Options:

| Option | Overlay over games | App switching | Effort | Licence |
|---|---|---|---|---|
| A. Shell **is** the compositor (QtWaylandCompositor, QML) | Native | Native | High | GPLv3 (or commercial) |
| B. gamescope + shell as client (OpenGamepadUI model) | Via gamescope's overlay atoms (Xwayland-centric) | Limited | Medium | BSD |
| C. Kiosk (cage / Weston kiosk-shell) + shell as client | No | No | Low | MIT |
| D. KWin (Plasma Bigscreen model) + shell as layer-shell client | Yes (layer-shell) | Via KWin scripting | Medium, heavy dependencies | GPL |

**Phase 0 uses C (cage)** to de-risk boot and session. **Recommendation for the product: A.** It's also the strongest fit for the cinematic UI, because effects can be applied to app surfaces. Games can still run *nested* in gamescope (as a Wayland client of A) to get FSR and frame limiting. Exit criterion for the spike: a Flatpak game runs fullscreen, the Guide button opens a blurred overlay over it at ≥ 55 FPS on the mid tier, and closing the overlay returns input to the game.

**Functional spike result (T-123, lead, 2026-10-23, in the VM): A works.** With Fedora's Qt 6.11 (`qt6-qtwayland`, already in the image, ships `QtWayland.Compositor`), `ruya-shell` ran as the compositor directly on KMS (`eglfs_kms`, llvmpipe, 1280×800 on `virtio-vga`), with the unchanged `Shell` as its bottom layer, a Qt test client fullscreen above it (xdg-shell), and the Shell's own Guide overlay moved above the client. Keys reached the client; Guide (Super, and the controller's `KEY_HOMEPAGE`) opened the overlay over the running client and the client got nothing while it was open; closing it returned the keys; when the client exited the shell took the screen and focus back. About 100 lines of QML (`shell/spike/Compositor.qml`). Found on the way, for the product path:
- **Device access.** Qt's eglfs opens DRM and evdev itself, with no logind `TakeDevice` (cage uses libseat). The DRM card already gets an ACL for the active session; input devices needed a `uaccess` udev rule. The product needs either that rule (the shell user then reads every input device, which is acceptable only because it is the session's sole UI) or logind-based device opening in a small platform plugin; decide in the follow-up task. VT switching and suspend/resume with eglfs are unexplored.
- **Client buffers.** llvmpipe has no `EGL_WL_bind_wayland_display`, so clients in the VM must use shm (software rendering); real GPUs use dmabuf/`linux-dmabuf`, untested here.
- **Key routing** belongs in C++ (an event filter in front of the client item) rather than QML `Keys`, so modifier-only keys and future InputPlumber routing (ADR-003) have one place.
- Not tested: Flatpak apps, gamescope nesting, Xwayland, blur over a client surface, per-profile sockets (ADR-004), frame rates.
**Decision (owner, 2026-10-23): option A is the product direction**, on the strength of this functional result. The performance half (≥ 55 FPS with the blurred overlay over a game on the mid tier) is still to be measured on hardware (B-003); if A fails it there, fall back to **option B** (gamescope with the shell as a client). **Product path done (T-130, lead, 2026-11-02):** the image boots `ruya-shell` as the compositor on KMS, cage is gone; apps sit in the shell's app layer and the C++ `KeyRouter` keeps Guide for the shell; input devices reach the shell through a permanent `uaccess` rule (01 §2.1). Still open: the performance half (B-003), dmabuf clients, VT switching and suspend under eglfs. **Per-profile sockets (T-164):** profile apps connect to their own socket, and each client is mapped to a profile by its peer uid (ADR-023); GL clients still render in software (no `linux-dmabuf` integration in Fedora's Qt).

### ADR-003 — Controller input arbitration — *Accepted (2026-10-22); Phase 0 uses a non-grabbing stopgap*
Wayland has no gamepad protocol, so games read evdev/hidraw directly. **Recommendation:** use **InputPlumber**, already used by ChimeraOS and handheld distros. It grabs physical devices, exposes virtual controllers to games, and exposes a keyboard/D-Bus target to the shell. When the overlay opens, the shell tells it to route input to the shell. Fallback: our own `ruya-inputd` in Rust (evdev `EVIOCGRAB` + uinput + SDL mapping DB). Steam Input must be configured so it doesn't double-handle controllers (see 03 §5).

*Phase 0 stopgap:* `services/ruya-inputd` translates gamepad buttons, D-pad and left stick into navigation keys on a virtual uinput keyboard. It **doesn't grab** the devices, which is fine while nothing but the shell runs. Every pad shares that one keyboard: a key goes down when the first pad presses it and up when the last pad lets go (`KeyBoard`, a count per key), and when a pad vanishes (read error, node gone, thread unwinding) the keys it still held are released (a key another pad holds stays down) and logged (`ruya-inputd: <name> gone: <err>; released <keys the pad held>`), so a pad that dies with Down held cannot leave Down pressed (T-337). In Phase 1 it's replaced by InputPlumber, or extended with grab and re-emit if InputPlumber can't be packaged for Fedora.

*Engine decision (T-366 / RUY-2, lead, 2026-11-12, evidence from the Dell in [`06-input.md`](06-input.md) §1-2):* **the fallback is taken: `ruya-inputd` grows into the Ruya Input service; InputPlumber is not used.** InputPlumber runs its whole engine as root with almost no hardening, has no per-user concept for its virtual devices (ADR-024's core rule), and is packaged for Fedora only in a COPR; the spike showed our service can run as an unprivileged `ruya-input` user (uinput group, udev ACLs, node ownership by phys prefix) and adds 88 µs median latency. The overlay routing is our route `overlay` (06 §5).

### ADR-004 — Session and user model — *Accepted (2026-10-22)*
- The shell/compositor runs as a dedicated system user `ruya-shell` in a logind session on seat0, started by a systemd unit (no display manager, no greeter).
- **Each profile is a real Unix user** created by `ruya-profiles` (`useradd` into the persistent `/etc`). Data isolation comes from Unix permissions.
- Apps launch in the profile user's systemd user manager (`systemd-run --user --machine=<user>@`). They connect to a per-profile Wayland socket created by the compositor and ACL'd to that user (as built, T-164: `/run/ruya-wayland/ruya-<id>`, ADR-023).
- Switching profiles suspends (or, if configured, stops) the previous profile's apps.
- **Not systemd-homed** for MVP: homed locks the home of logged-out users and doesn't fit 4-digit PINs. Revisit if per-profile encryption is required.
- The PIN is a profile lock, checked by `ruya-profiles` (argon2id hash, 5 attempts then exponential back-off). It is a security boundary only together with full-disk encryption (01 §3.4).

### ADR-005 — Application format — *Accepted (2026-10-22)*
**Flatpak is the only third-party format.** Console-specific metadata uses **AppStream** (localized name/description, screenshots, categories, OARS content rating, `<supports><control>gamepad</control>`), plus a small set of `x-ruya-*` custom keys (hero art, logo, background art, launch hints). Sources are Flatpak remotes: Official (ours, signed), Community (Flathub, filtered to gamepad-capable apps by default), Developer. A custom `.cbundle` archive is deferred until a concrete need appears. If one does, it will be a Flatpak bundle plus artwork, not a new runtime. *See ADR-014 (Accepted, parked): the `.play` container.*

### ADR-006 — OS updates — *Accepted*
bootc images signed with cosign, served from an OCI registry, verified via `containers-policy.json`. greenboot health checks give automatic rollback. Channels are tags (`stable`, `beta`, `dev`). Details are in 01 §4.

### ADR-007 — UI toolkit — *Accepted*
Qt 6 (Fedora's version, currently ≥ 6.8) with Qt Quick and QML. Effects use `MultiEffect` and precompiled `.qsb` shaders. Not Qt 5 or `Qt5Compat`.

### ADR-008 — Project licence — *Accepted (2026-10-22, owner)*
Fully open source. Shell, image and scripts are **GPL-3.0-or-later**, which makes ADR-002 option A (QtWaylandCompositor, GPLv3) free of licensing friction. Rust services are **MIT OR Apache-2.0**, docs are CC-BY-4.0. See `LICENSE.md`.

### ADR-009 — Codecs & drivers — *Accepted (2026-10-22, owner)*
**Ship everything in one image**: RPM Fusion free + nonfree, full `ffmpeg`, `mesa-va-drivers-freeworld`, Intel `intel-media-driver`/`libva-intel-driver`, GStreamer freeworld/ugly/libav, and the **NVIDIA proprietary driver** with modules prebuilt for the image kernel (`image/build/30-codecs.sh`, `40-nvidia.sh`). A single image covers every hardware tier, so there are no `-full`/`-nvidia` variants.

Consequences:
- **Patent exposure** for H.264/HEVC/AAC etc. lands on whoever distributes the image in jurisdictions that enforce software patents. This is accepted by the owner. Mirrors and downstream redistributors should be told.
- **NVIDIA:** GPUs dropped by the current driver branch are unsupported (nouveau is blacklisted by the driver package). Secure Boot needs MOK enrollment of our module-signing cert (01 §2.3). A stable signing key from CI secrets is a Phase 6 task. Until then each build uses an ephemeral key, and its private half is deleted from the image.
- **Not included:** `libdvdcss` and AACS keys (rpmfusion-free-tainted). These are copy-protection circumvention, not codecs, and remain a separate owner decision.
- **Flatpak apps** don't see host codecs. First boot must install `org.freedesktop.Platform.ffmpeg-full`/`codecs-extra` and the matching `GL.nvidia` extension (Phase 3, `ruya-store`).

### ADR-010 — Audio ownership — *Accepted (lead, 2026-10-23)*
PipeWire runs per user, and profile apps run as other Unix users (ADR-004), so exactly one instance must own the outputs.
- **One PipeWire, in the shell's session.** PipeWire, WirePlumber and pipewire-pulse run in `ruya-shell`'s user manager, as they already do (T-121). That session is the active one on seat0, so logind gives it the sound devices. Profile users run no PipeWire of their own against hardware: drop-ins in `/usr/lib/systemd/user/` restrict `pipewire`, `pipewire-pulse` (service and socket) and `wireplumber` to `ConditionUser=ruya-shell` (T-162; before that a profile's manager started them).
- **Apps reach it through a per-profile pulse socket** (as built, T-365; the same shape as ADR-023's Wayland sockets): a second pulse server per profile, `ruya-pulse@ruya-<id>.service` in `ruya-shell`'s user manager (`pipewire -c ruya-profile-pulse.conf`, a client of the shell's PipeWire), listens on `/run/ruya-pulse/ruya-<id>/native`. The directory is 0700, owned by `ruya-shell`, with one ACL entry `user:ruya-<id>:--x`, made before the server starts, so only that profile's user can reach the socket; `/run/ruya-pulse` is 0711 (no listing). The config refuses module loading from clients (`pulse.allow-module-loading = false`: an app could otherwise load a TCP server or a pipe sink with the shell's rights) and loads no pulse.cmd helper modules; it pauses a stream after 5 s of underrun (`pulse.idle.timeout = 5`, RUY-425: a game frozen by the Hub is otherwise asked for the whole freeze's worth of sound at the thaw, `03` section 4.1, Freeze and Thaw). `ruya-session` starts the instance before each app of that profile (a failed start is logged; the app runs without sound) and sets `PULSE_SERVER=unix:/run/ruya-pulse/ruya-<id>/native`; `flatpak run --socket=pulseaudio` binds exactly that socket into the sandbox. Rejected: one shared pulse socket (any profile's app could connect while another plays); loading `module-native-protocol-unix` into the shell's pulse server per profile (needs pulse module loading enabled on the shell's server, and a socket made by the server cannot be given its ACL before it listens). Open: per-profile levels on app streams (B-007), stopping a deleted profile's server (unreachable once its user is gone; it ends with the shell's session).
- **`ruya-devices` runs as a systemd *user* service of `ruya-shell`** (`/usr/lib/systemd/user`, `ConditionUser=ruya-shell`, after `wireplumber.service`). It talks to that PipeWire directly and owns `org.ruyaos.Devices1` on the system bus; its D-Bus policy lets only `ruya-shell` own the name and only `ruya-shell` and root call it. Network and Bluetooth go through NetworkManager and BlueZ as the active session's user (polkit), so the service needs no root at all.
- Rejected: a system-wide PipeWire (unsupported upstream, and Flatpak and WirePlumber assume the per-user model); one PipeWire per profile (they would fight over the devices at every profile switch, and the shell's own sounds would need a second path).
- Cost: user units take less hardening than system units. Acceptable, because the service has exactly the shell's privileges and no more; it still gets every option a user manager supports (`NoNewPrivileges`, `RestrictAddressFamilies`, `SystemCallFilter`, ...).

## 7. Glossary
**bootc**: tool that boots and updates an OS from an OCI container image. **greenboot**: health checks that trigger rollback. **OOBE**: out-of-box (first-boot) experience. **OARS**: Open Age Ratings Service, the content-rating vocabulary used in AppStream. **Overlay**: the shell UI drawn over a running app (Guide menu).

### ADR-011 — `ruya-store` drives the `flatpak` CLI — *Accepted (lead, 2026-10-24)*
`ruya-store` is a pure-Rust service (like the other services, it builds on Windows for its core) that drives the `flatpak` command line (`install`, `uninstall`, `update`, `remote-ls`, `remote-add`, `info`, `list`), with machine-readable output where the CLI offers it, and reads catalogue metadata (AppStream XML/YAML from the remote's appstream directory) with a Rust XML parser. It does not link libflatpak or libappstream (GObject bindings are not pure Rust and would not build on the Windows host). Progress comes from the CLI's output, parsed in the pure core. The service runs as root with hardening (it installs system-wide on behalf of the shell), sits behind the same restrictive bus policy, and refuses unsigned remotes itself. Revisit if CLI parsing proves brittle (then libflatpak through a small helper).

### ADR-012 — Design language "Dreamglass" and its governance — *Accepted (owner, 2026-10-28)*
The shell's look is defined by one design system, [`04-design-system.md`](04-design-system.md): dark ground, frosted glass over a tinted, drifting backdrop, white chrome, a white focus ring with 1.08 scale, category tints as the only accent colours, a seven-step type scale and an 8 px spacing grid, all as `Theme` tokens. It formalises what Phases 1–2 built (T-102, T-117) rather than restyling it. Builders use existing tokens and components; the lead adds or changes them, updating the spec and `Theme.qml` together (§8). The typeface is Inter (OFL-1.1), bundled as a Qt resource (owner, 2026-10-28). **Amended (owner, 2026-10-28):** the main UI is gaming-first: an art-led Home with large key art and Gaussian-blurred glass chrome, and apps and games run full screen with the shell drawing nothing over them but the Guide quick menu, the volume OSD and critical toasts (02-shell §1.5, 04 §5.1); this relies on ADR-002 option A.

### ADR-013 — Icon set: Material Symbols Rounded — *Accepted (owner, 2026-11-01)*
Shell icons come from Google's **Material Symbols Rounded** (Apache-2.0), bundled as a Qt resource font holding only the glyphs the shell uses (a subset made from the upstream variable font, the source commit and checksum recorded), so Windows, the offscreen tests and the image draw the same thing. The rounded style matches the pill shapes of ADR-012. Icons are drawn by name through one component, colour from the text tokens, never an emoji or a font the host happens to have. Controller buttons (A, B, LB, …) are not icons: they are drawn as letters in circles until pad-type glyphs exist (B-006). The licence text ships in the repo and the image. Details: [`04-design-system.md`](04-design-system.md) §3.7.

### ADR-014 — `.play` packages: a self-contained container for games and apps — *Accepted (owner, 2026-11-06), conditional on the T-229 spike confirming the Flatpak route (confirmed by RUY-91 on the Dell, 2026-11-16, see "Spike result" below); implementation started by the owner on 2026-11-17 ("fully focus on play packages", foundations first; epic RUY-90, goal RUY-780)*
**Question.** ADR-005 makes Flatpak the only third-party format and defers a custom bundle "until a concrete need appears; if one does, a Flatpak bundle plus artwork, not a new runtime". The owner now asks for a developer-made, self-contained format (the macOS `.app`-in-a-`.dmg` idea) that can carry a game together with its Wine or Proton build or its emulator, plus artwork, video, metadata, links, a permission request and update information, and can be a folder or a `.play.zip`.

**Proposal.** Adopt `.play` as specified in [`05-play-packages.md`](05-play-packages.md), under these constraints, which keep ADR-005's spirit and the security invariants:
1. A `.play` is a **container, not a runtime**. Installing it imports it as a system Flatpak app (`play.<id>`) built by `ruya-play`; it runs only in the Flatpak sandbox, as the profile's user. The package never supplies Flatpak metadata; permissions are a closed vocabulary (05 §8). If the spike (T-229) shows this route cannot work, the fallback is the same sandbox driven by bubblewrap and this ADR is amended before anything is built.
2. **Nothing in a package runs at install time.** All parsing and unpacking happens in an unprivileged, network-less helper; a package is untrusted data.
3. **Signed.** Ed25519 signature over a file table of SHA-256 hashes; tiers `official` (our store countersigns), `developer` (key continuity, trust on first use) and `unverified` (admin's developer mode only, low and medium permissions). Revocation list. Updates must come from the same key; the Store is the update channel for Store packages, an opt-in signed feed for sideloaded ones.
4. **System runners** (Wine first) are Flatpak extensions published on the `ruyaos` remote and updated independently of the OS; a package may bundle its own runner, use the system one, or take the newer of the two. *(Amended by the owner, 2026-11-19, RUY-897, and ADR-038: the preinstalled runner, GE-Proton (ADR-025), is always in the OS image as files on /usr and updates with the OS; further runners may come from the Store under their own ids.)*
5. Flatpak and Flathub remain the normal way to distribute apps. `.play` is for self-contained games, Windows games under Wine/Proton, emulated titles and developer testing.

**Consequences.** New services and tools: `ruya-play` (import, verify, feeds), `ruya-pack` (developer CLI), a launcher and runner extensions; a shell "install from USB" flow and a package page; Xwayland or Wine's Wayland driver becomes a prerequisite for Windows games (Xwayland came with ADR-034; the spike chose it for v1). Maintenance cost: the Play platform extensions, the runner builds, the review process for the Official tier. RuyaOS ships only Wine as a system runner; emulators, Proton/Steam runtime, firmware and disc images are supplied by packagers and carry no distribution duty for RuyaOS (owner, 2026-11-06; 05 §14). If RuyaOS hosts packages itself, that remote's acceptance rules are a separate later decision.
**Spike result (T-229 / RUY-91, Dell, image 0.0.89, Flatpak 1.18.4; lead, 2026-11-16).** Commands and numbers: `scripts/spikes/play/RESULTS.md`; the answers are in 05 §16.
- **The Flatpak route works, so there is no bubblewrap fallback** (constraint 1 holds as written). The spike built a generated app with a launcher extension and signed it with a device-local key. It was installed from a local remote with GPG checks on (`--no-gpg-verify` was never needed) and launched through `Session1`.
- **Cost.** With a `bare-user-only` staging repo on the same XFS filesystem as `/var/lib/flatpak`, a 20 GiB payload commits in 52 s and installs in 0.4 s, and the disk peak is 1.03x the payload.
- **Windows display in v1 is X11 through xwayland-satellite** (ADR-034's compatibility layer), not Wine's Wayland driver. Wine 11's and GE-Proton 11's Wayland drivers refuse the compositor's protocol versions.
- **Runner in v1 (amends ADR-025's "through umu and the Steam Linux Runtime" for `.play`).** GE-Proton (or Wine) runs directly, without umu and the Steam Linux Runtime. In Flatpak 1.18.4 the sub-sandbox portal (`flatpak-spawn --sandbox --usr-path`) fails, and pressure-vessel needs it.
- **Owner-visible consequences.**
  - Windows `.play` games show through Xwayland, full screen at 60 FPS on the Dell.
  - A Windows package needs the 32-bit runtime extensions (`multiarch`).
  - A Proton package that bundles the Steam Linux Runtime is documented as unsupported until a fixed Flatpak passes the re-test (05 §16, Q3).

**Alternatives rejected.** (a) Flatpak only, with Heroic/Lutris for Windows games (no single-file distribution, no console art/permission model, per-launcher prefixes outside our control). (b) A new runtime and sandbox (an ADR-005 non-goal, security cost). (c) AppImage-style run-in-place (no sandbox, no verification before use, no deduplication).
**Status of the rest.** Owner, 2026-11-06: accepted; RuyaOS provides Wine as the only system runner and the image preinstalls it; the epic (T-228) is **parked** (stays `blocked`) behind the current visual-polish lanes and T-164, and no `.play` code is written yet. Spec 05 describes the design, not the code. *(Superseded: the owner started the implementation on 2026-11-17 (heading); GE-Proton, not Wine, is the preinstalled runner (ADR-025); spec 05 marks what is built.)*

### ADR-017 — Local players and the controller that drives the UI — *Accepted (owner, 2026-11-07; amended by the owner 2026-11-12, 2026-11-13, 2026-11-14 and 2026-11-15; this text folds the amendments in, RUY-448, RUY-707)*

**Question.** What happens when a second controller connects? Which pad drives the shell, how a pad belongs to a person, and how a second person (a profile or a guest) plays in the same session. The owner put it this way (2026-11-07): "when we add a second controller how do we use it; which controller is used by who; on PS it asks which user; what about guests". And on 2026-11-12: "we should ask for the user on connect. a profile should not have two controllers. for local coop, both users should be signed in". ADR-027's request (2026-11-09) also applies: "assign a controller to a user so the UI is not operated by two controllers at the same time, as on PlayStation 5".

**Architecture fact.** ADR-004: one profile session at a time, and apps run as that profile's Unix user. Other people are therefore **players inside that session**, never parallel sessions.

**Decision.**
1. **Seats and player 1** (owner 2026-11-07, 2026-11-13).
   - A signed-in session has up to four seats (the number is a lead decision, 2026-11-14), each one profile on one pad.
   - **Player 1** is the signed-in profile, and its **active controller** is the pad that signed it in (pressed Accept on the picker, or picked it in "Who's playing?"). A pad that pressed last does not take over.
   - Player 1's pad is the app's first virtual pad (`pad1`, SDL index 0), and pad *n* is seat *n*. Only seated pads reach an app.
2. **Who drives the UI** (owner 2026-11-13, 2026-11-14).
   - On the picker, any pad acts.
   - After sign-in, **only player 1's pad** (and the keyboard, always) navigates the shell. Other pads' buttons do nothing in the UI.
   - While "Who's playing?" is open, **only the asking pad** (and the keyboard) answers it; player 1's pad cannot answer for it.
   - Admin features come only through player 1's pad, behind the admin PIN.
3. **Ask on connect** (owner 2026-11-12, 2026-11-13).
   - A pad with no seat in this session asks "Who's playing?" at once: when it connects, when it presses a **button** (stick drift does not count), and when its Guide is pressed.
   - While the prompt is open, the app in front is **paused as the Hub pauses it** (frozen). After a pick, or "Not now", the game **continues by itself** (owner 2026-11-14).
   - "Not now" (Back) keeps that pad quiet until the game exits; its Guide still opens the prompt.
   - A pad with a remembered owner opens the prompt with that profile preselected.
4. **One controller per profile** (owner 2026-11-12). A profile holds at most one pad in a session. Picking a profile that already plays, player 1's own included, **moves** it to the new pad after a confirm (Cancel first). The old pad becomes unseated and asks again when next used.
5. **Every player is signed in** (owner 2026-11-12, replacing 2026-11-07's "no PIN"). A profile with a PIN asks for it **on the TV, typed with the new controller**, for Join, Switch and Move alike (owner 2026-11-14). Guests need none.
6. **Join or Switch** (owner 2026-11-13, RUY-384 closed). For a profile that does not play, the prompt offers **Join** (focused; it becomes the next player) and **Switch** (one step right; the console becomes that profile's session).
   - On Switch, the old player 1's apps are frozen and kept as far as memory allows (ADR-019), and they come back when that profile signs in again. Nothing is closed silently. The old player 1's pad is an unseated pad in the new session.
   - There is **no idle timer** of any kind: the pause makes the prompt visible to whoever is in the room.
7. **Guests** (owner 2026-11-12, 2026-11-14). "Guest" can be picked more than once: Guest, Guest 2, Guest 3, numbered automatically.
   - A guest **only joins**: no Switch, no PIN.
   - Each guest is a **temporary profile user**, wiped when that guest leaves (its seat ends) or the session ends.
   - Lead decision (2026-11-14): its uid comes from a range that is never handed out twice.
   - A guest can still sign in alone from the picker (unchanged).
   - No new kept guests (owner 2026-11-15, RUY-716): `CreateProfile` refuses role `guest`; guest-role profiles stored earlier keep working and can be renamed and deleted.
8. **Add profile** stays in the prompt, behind an admin's PIN (owner 2026-11-14).
9. **A seat outlives a lost pad for 60 s** (owner 2026-11-13 for player 1, 2026-11-14 for every player).
   - The same pad coming back within the minute is the same player, with the same pad number.
   - Player 1's loss pauses the app as if the Hub had opened. After the minute, player 1 is put on another pad through the prompt's Move.
   - The other players leave after the minute.
10. **Joins last the session.** A player leaves through sign-out, the end of their seat or (once designed) Leave in the Hub.
11. **What a player's profile means** (owner 2026-11-07, unchanged):
    - Saves stay player 1's, because apps run as player 1's user.
    - The other players get their achievements (T-246) and play time (T-247) **attributed**. Guests get no attribution.
    - The **strictest age limit** of everyone signed in applies at launch (T-211).
12. **Shown on screen** (owner 2026-11-14): players appear in the top bar (avatars next to the profile) and in the Ruya Hub (a row of players). There is no "joined" toast.
13. **Waking from sleep asks who plays** (owner 2026-11-15, amendment 7, RUY-707). After a wake from sleep (not the screen saver or the dark screen), when seat 1 has no connected pad, "Who's playing?" opens at once in a **wake mode**:
    - The signed-in profile comes first and has the focus ("Continue as <name>"); the other kept profiles stand beside it, and picking one is a **Switch** (its PIN when it has one).
    - Continuing needs **no PIN** (sleep does not lock the console; a lock on wake would be a separate privacy setting, an owner question). The pad that answers becomes player 1; with the keyboard alone the prompt just closes. *(Superseded by the owner, 2026-11-21, amendment 8, RUY-953: **a wake from sleep asks a PIN-protected signed-in profile for its PIN** before anything else is shown, with or without a pad on seat 1; a profile without a PIN continues as above. Not a setting.)*
    - Back and Guide continue as the signed-in profile, so one press always restores what was there before the sleep. There is no "Not now" and no Guest card (lead ruling: a temporary guest can never be the active profile, point 7; guests join afterwards as usual).
    - The keyboard drives it until a pad connects; that pad then drives the same step (no second prompt). With seat 1's pad still connected a wake changes nothing (a pad whose drop reaches the shell just after the wake, within 10 s, still opens it).

**Consequences.**
- `Input1` gains seats (`JoinPlayer`, `LeavePlayer`, `ListPlayers`, `PlayersChanged`, `SetNavigator`, `ForeignInput`) in `ruya-inputd`, the one owner of the pads (ADR-024), and loses the draft `AssignPad`.
- `Profiles1` gains `VerifyPin` and temporary guests.
- The shell gets the "Who's playing?" prompt (design: canvas "RuyaOS Who's Playing", 2026-11-14), player chips and the Hub players row.
- 06 §11.3 is the rule table.
- Tickets: RUY-121, RUY-627, RUY-38, RUY-122, RUY-628, RUY-629, RUY-630, RUY-124, RUY-125, RUY-631, RUY-707 (formation RUY-553). RUY-123 (virtual pads per seat) is re-scoped by the lead.

(3) Order: no change; phase 5 as planned. ### ADR-019 — Multitasking: one foreground app, frozen background apps, politely closed under pressure — *Accepted (owner, 2026-11-08)*
**Question.** The owner wants iOS/Xbox/PlayStation-style switching between open apps and games, a smooth shell, and background apps closed when a game needs the memory. Today one app can be in front and the others "keep running until closed (memory limits: later)" (02 §1.5); T-147 plans a plain "Switch to" list, T-165 freezes a whole profile's apps on a profile switch, T-201 protects the shell from OOM.

**Proposal.** (1) One **foreground** app; every other open app is **frozen** with the cgroup freezer after a short grace (no CPU, memory kept, resumes in a frame), unless it declares a background reason (`X-Ruya-Background=audio|download`) that currently holds. (2) The compositor keeps a small **snapshot** of each app's last frame for the switcher and tells apps when they are hidden or visible (`xdg_toplevel` suspended, 03 §4.6). (3) Under memory pressure the **least recently used background app is closed** (SIGTERM, 5 s to save, then kill) with a toast and a relaunch card; never the shell, never the foreground app; the foreground game gets the weights, the background `MemoryHigh`. (4) At most N open apps (default 4, by RAM). (5) **Switcher** = a row of cards in the Guide quick menu; **Guide double-press** jumps to the previous app; hold Guide stays the power menu. (6) The spike T-274 measures freezing on the Dell before anything depends on it; games that break under freeze fall back to cooperative pause or save-and-close.

**Decided (owner, 2026-11-08):** (1) the gesture: **Guide short press = the quick menu with the switcher row, Guide double press = the previous app, Guide hold = the power menu**; (2) **one foreground app, every other app frozen** (cgroup freezer), **least recently used closed under memory pressure with a toast**; (3) **background apps opt in** (`X-Ruya-Background`, audio or download, only while the reason holds); (4) **a frozen online game warns once in the switcher** (it may disconnect). The technical parts (grace times, N, the memory policy) stay the lead's after the spike T-274, which measures freezing before anything depends on it.

**Consequences.** New contract surface in Session1 (states, `Switch`, `SetBackgroundReason`), compositor snapshots, a policy in `ruya-session`, developer-guide rules. Epic T-273, tasks T-274..T-279; everything is gated by T-164.
**Later (2026-11-22):** ADR-042 narrows what is frozen (a Steam game, never the Steam client; the image app table's `freeze` key) and keeps `X-Ruya-Background` as the public door; the owner added a public "do not freeze me" declaration (RUY-1060): ADR-046 (reason `client`, the one reason with no hold condition; all reasons declared in Flatpak metadata).

**Shutdown (RUY-888, lead, 2026-11-19; an implementation rule of this ADR, no new decision):** a frozen app is never left to systemd's own stop. The one that froze it, `ruya-session`, thaws and stops every app (the path of `Stop`: thaw, SIGTERM, 30 s, SIGKILL) before power off or restart, holding logind's shutdown delay lock until they have ended, so it runs before anything stops, while the compositor and the profiles' user managers still run; otherwise the user manager cannot stop the frozen unit and kills it, and a game that saves at quit loses its settings (the Dell, 2026-11-18). Details: `03` §4.1, "Power off and restart".

### ADR-020 — The game data hub (service `ruya-gamedata`, `GameData1`; renamed by the owner 2026-11-10: "Ruya Hub" is the overlay over a running game): one OS API for ROM folders, save and capture paths, and now-playing metadata — *Accepted (owner, 2026-11-08); behind `Platform1` per ADR-022*
**Question.** The owner wants RuyaOS to be a hub between game apps: an emulator asks the OS where the SNES ROMs are and where saves, states, configs, screenshots and recordings go; the OS learns from the app what is played (game, emulator, settings, who) and exposes it to the shell and to permitted apps. Today each app invents its own folders (03 §4.5a only recommends a layout), the emulator frontend would scan on its own (T-259), and nothing knows what is running beyond the app id.

**Proposal.** (1) A system service `ruya-gamedata` (`org.ruyaos.GameData1`) answers per profile (the caller's identity decides, never an argument). **It is an internal service (tier A of ADR-022): no sandbox reaches it directly. Its app-facing calls are an interface of `Platform1` (T-352), which identifies the app and profile, checks the player's permission, rate-limits and forwards; the shell and root reach `GameData1` itself.** The calls: `RomRoots(system)`, `Paths(kind, game)` (kinds saves, states, config, screenshots, recordings, mods), `Identify(file)` (stable content-based game id), `Players()` (ADR-017). (2) System ids follow libretro/No-Intro naming and live in a data file. (3) Apps **push** now-playing (`Report`: game, system, emulator, core, settings summary, state) with size and rate caps; the OS keeps the latest per running instance and shows it in the Library and Activity pages; the play ledger (T-247) keys time to the game id. (4) **Captures belong to the compositor**: screenshots (and, if the Dell budget allows, recordings and a "clip the last 30 s" buffer) are taken by the shell for any app and stored with metadata in the profile's Captures library. (5) Other apps read now-playing and captures only with a per-app permission, off by default, asked on first use, revocable in Settings > Privacy (T-220). (6) RuyaOS ships no ROMs, BIOS or emulators and scans removable media only after an explicit player action.

**Decided (owner, 2026-11-08):** (1) other apps may read now-playing and captures, **off by default, asked per app on first use, revocable in Settings > Privacy** (the per-app permission table of `Platform1`, T-220); (2) a **shared read-only ROM folder** visible to all profiles, besides the per-profile folders; (3) **captures stay local in v1** (they never leave the console); (4) **saves and states stay on the console** (a pulled drive must never lose or corrupt a save); drives hold ROMs, captures and backups. The technical parts are the lead's after the spike T-303.

**Consequences.** A new internal service, hub policy and unit (shell and root only), the `Platform1` interface in front of it (T-352), a compositor capture path, Library changes, a developer-guide chapter and a sample. Epic T-302, tasks T-303..T-308.

### ADR-022 — The public developer surface: three tiers, one narrow door for apps, versioned and documented as part of every task — *Accepted (owner, 2026-11-08)*
**Question.** Which parts of RuyaOS may apps (third-party and our own) rely on, how do they reach them, and who makes sure each one is documented, tested and stable? Today every D-Bus service answers only the shell and root (a security invariant), so nothing is callable from a sandbox. But tasks now add app-facing APIs one by one, each with its own bus name, bridge and documentation plan: notifications (T-245), achievements (T-246), now-playing and paths (ADR-020, T-304/T-306), lifecycle (T-279), player slots (ADR-017, T-266). Without a charter the surface grows by accident, and a private service becomes public by a bus-policy edit.

**Proposal.** (1) **Three tiers.** *A, shell-private:* Profiles, Store, Update, Devices admin, Telemetry configuration; never exposed, the bus policy stays "shell and root only". *B, the Platform API:* a new narrow service `ruya-platform` (`org.ruyaos.Platform1`, system bus, one `--system-talk-name` per app) is the only door a sandboxed app has; it identifies the caller (Flatpak app id, profile), checks a per-app permission table the player controls in Settings > Privacy (T-220), rate-limits, sanitises, answers per profile and forwards to the internal services, which stay private. *C, data-only formats* (no code, safest): the save-data layout (03 §4.5a), AppStream `x-ruya-*` keys, `.play` packages, sound/theme/wallpaper packs, icon conventions. (2) **The candidate Tier B list, approved once** (anything else needs a new ADR line): lifecycle (suspend/resume/stop, "save now"), achievements, play statistics and rich presence/now-playing, notifications, controller input extras (player slots, rumble, battery), text input (on-screen keyboard), display information (read-only), theme accent (read-only), age-rating and parental respect (read-only flag), a portal-style storage picker. **Never public:** profiles, PINs and admin, update, install/uninstall, system settings writes, telemetry. (3) **Process.** A task header field `Developer surface: none | internal | public-API | public-format` set at planning; a public task's Definition of done adds a documented XML contract with a stability tag, a developer-guide paragraph, a runnable sample, mock support for off-device testing and a conformance test; a read-only `ruya-api-reviewer` agent checks every diff that touches a public surface; a `ruya-devdocs-auditor` agent follows the guide as a newcomer before each release. (4) **Versioning.** `RUYA_API_LEVEL` in os-release; apps declare the minimum in AppStream; the Store hides apps the console cannot serve; everything is *experimental* (no promise) until the first release, then additions only within a level and a two-level deprecation window. (5) **Dogfooding.** A first-party app may use only the public surface.

**Options.** (a) The charter above (recommended). (b) One bus name per feature (`GameData1`, `Achievements1`, ...) reachable from the sandbox: least new code, but Flatpak grants a bus name all-or-nothing, so the per-app permissions of T-220 cannot be enforced by the platform, every service must be hardened against hostile callers, and identity, rate limits and versioning are done N times. (c) Nothing public in v1: apps get Wayland, PipeWire and evdev only; no achievements, notifications or hub, so no "console" features for third parties.

**Decided (owner, 2026-11-08):** option (a) **approved as drafted**: the Tier B capability list is approved (a new capability needs a new ADR line first), the "never public" list stays, and stability promises start only at the first release. The design of the proxy and the level numbers are the lead's. **Risk to prove first (T-352, step one of that task):** that a caller behind `xdg-dbus-proxy` on the system bus can be mapped to its Flatpak app id the way the session-bus portals do it; if not, the per-app permission falls back to a per-app session-bus portal in front of the same service.
**Risk proved (RUY-157 step 1, VM 0.0.104, lead 2026-11-22): the system-bus door holds; no fallback.** A proxied caller's peer is its `xdg-dbus-proxy`, which carries the app's identity. The recipe: take `ProcessFD` (a pidfd) from `GetConnectionCredentials` and check it is alive; read `/proc/<pid>/root/.flatpak-info` (name, instance-id) and `/proc/<pid>/cgroup`, and require the scope `app-flatpak-<name>-<instance-id>.scope` under `user@<UnixUserID>.service`; re-check the pidfd after the reads (pid reuse shows as `Pid: -1`); the profile is `UnixUserID` through ruya-profiles; no `.flatpak-info` or any mismatch means "not an app" and is refused. An argument naming another app is ignored, and a sandbox cannot change its `.flatpak-info` (read-only bind), its cgroup or its namespaces. **Trust boundary:** identity is unforgeable only for *sandboxed* callers. Code running unsandboxed as the profile's uid can create a matching scope and a fake `.flatpak-info` (shown), as with the portals. So nothing third-party runs unsandboxed as a profile, and the Store treats the permissions that escape the sandbox (`--socket=session-bus`, `--talk-name=org.freedesktop.Flatpak`, talk to systemd1) as "trusted as the profile".

**Build decisions (lead, 2026-11-23, RUY-157 review; split into RUY-1098, RUY-1099):**
1. **Permission store.** Platform capabilities are granted per (profile, app, capability) in root-owned files, one per profile, `/var/lib/ruyaos/platform/profiles/<profile-id>.json` (directory 0700, file 0600, atomic writes), removed when the profile is deleted. Never in the home: an app with home access could grant itself. The store holds Platform capabilities only, never the per-console Flatpak overrides of 03 §4.4 (RUY-744).
2. **Lifecycle shape.** An app opts in with `Register()`; the events are unicast to that instance's connections, never broadcast (a broadcast would tell every app about the others). `Background()`: the app left the front and keeps running (a hold, ADR-042 point 3, ADR-046). `Resume(frozen_ms)`: it is in front again, with how long it was frozen (0 if it was not). `Stopping(deadline_ms)`: the OS will stop it; it saves and answers `SaveDone()`, and the OS waits up to 5 s before the stop's SIGTERM and its 30 s grace. There is **no notice before a freeze**: the freeze is instant (the Hub must open at once), and a frozen app could not act on a notice; the app learns of it from `Resume`. ruya-session, which decides freeze, thaw and stop, tells ruya-platform through a root-only method; ruya-platform alone talks to apps.
3. **Who changes a profile's Platform permissions (lead-45, RUY-1104).** A profile changes its own, an admin any profile's, a guest nobody's (a temporary guest's choices would die with it: it has the defaults only). Per profile and about the player's own data, so unlike RUY-744's console-wide Flatpak overrides (admin only). The service cannot tell people apart (Manage callers are root or ruya-shell), so the shell enforces the rule in one function, `Platform.mayChange`; the service keeps its uid check. `Manage.ListCapabilities` lists every capability with its default for the pane. Parental controls (T-212) may later lock them for a managed profile: not now.
4. **Caller identity is read by a bus-less helper; the door holds no capability (Accepted (architect, 2026-11-23); measured by the lead on the Dell, 0.0.106).** *Context:* `.flatpak-info` in a sandbox is 0600 and owned by the profile user. Reading it through `/proc/<pid>/root` needs `CAP_SYS_PTRACE` plus a DAC capability; on the most exposed root service that pair means "read every file" if the door is compromised (`/proc/1/root` defeats namespace hiding). The "Risk proved" note above was measured without the unit's sandbox. *Decision:* a separate crate, `ruya-platform-identify`, holds the reads. Its lib is pure, tested on every host, and holds the wire codec. Its bin is `/usr/libexec/ruya-platform-identify`, socket-activated: `ruya-platform-identify.socket` (`ListenSequentialPacket=/run/ruya-platform-identify.sock`, `SocketUser=root`, `SocketMode=0600`, `Accept=yes`, `MaxConnections=8`) and `ruya-platform-identify@.service` (`StandardInput=socket`). Request: the caller's pidfd (SCM_RIGHTS) and the bus's `UnixUserID`; the helper refuses a peer whose `SO_PEERCRED` uid is not 0. The helper takes the pid from its own fdinfo of the passed pidfd, never from the door. It opens `/proc/<pid>/root/.flatpak-info` (`O_NOFOLLOW`, regular file, `st_uid` == uid, else `not-owned` and nothing is read) and `/proc/<pid>/cgroup`, and returns {pid, info bytes or error code, cgroup bytes or error code}; it parses nothing. The rules stay in `identity.rs`, in the door: the pidfd checks run on the door's own `/proc/self/fdinfo` (no privilege), then the parse, the scope rule and the re-check; `Procfs::flatpak_info`/`cgroup` become one call `caller_files(pidfd, uid)`, implemented by `HelperProcfs`. The helper has no bus (`InaccessiblePaths=/run/dbus`), no network, one task, a short `RuntimeMaxSec`, and `CapabilityBoundingSet=CAP_SYS_PTRACE CAP_DAC_READ_SEARCH`; the door gets `CapabilityBoundingSet=` (empty) and `ProtectProc=invisible`. *Consequences:* a compromised door can only obtain a uid's own `/.flatpak-info` and a cgroup line, nothing else; the helper's only attacker-shaped input is a kernel pidfd and it parses no attacker data; the proxy case works unchanged (the proxy's pidfd); ADR-023 holds (no root service reaches into homes or `/run/user`). The door drops to about the notifications exposure (around 1.1); the helper gets its own baseline row. The `st_uid` check also closes a confused deputy: code running unsandboxed as a profile uid could bind-mount any file it can see onto `/.flatpak-info` in a matching scope, and `O_NOFOLLOW` does not stop a bind mount. *Rejected:* (a) a DAC capability on the door: reads everything if compromised. (c) `setfsuid`: needs `CAP_SETUID`/`SETGID`, so a compromised door becomes any non-root uid (profile homes, ruya-shell's state), it is per-thread fragile under tokio, and it keeps PTRACE. The host copy `/run/user/<uid>/.flatpak/<id>/info`: a directory the user can write, and it needs a `ProtectHome` hole (against ADR-023). `setns` or a pidfd mount namespace: needs `CAP_SYS_ADMIN`. The scope name alone: needs no privilege, but loses the cross-check against a process moved into another app's scope; keep both facts. A reader as the profile user (ADR-045 style): would need per-profile sockets in `/run/user`. Whether the door also stops being root is ADR-047 (Proposed). **Built (RUY-1129):** `services/ruya-platform-identify` (the wire in `wire.rs`, the helper's steps in `serve.rs`), `HelperProcfs` in `ruya-platform`'s `procfs.rs`, the units as above (the helper instance also `CollectMode=inactive-or-failed`, so a request the door gave up on leaves no failed unit); `vm-platform-check.sh` checks the capability sets, the real path and the confused deputy (`identity`, `deputy`). Measured on the Dell (0.0.106 with the branch's binaries and units, transient): the whole check passed those items, exposure door 1.1, helper 1.6.

**Consequences.** New service and bus policy (T-352); mock and sample harness for developers (T-353); API level (T-351); lint (T-350); the app-facing parts of T-245, T-246, T-279, T-304, T-306 and T-266 are re-seated behind `Platform1`, and `GameData1` becomes an internal service reached through it; ADR-015 (Accepted with this ADR, owner, 2026-11-08) puts the client bindings in the `org.ruyaos.Platform` runtime extension. Detail and the task audit: [`docs/developers/api-surface.md`](../developers/api-surface.md).

### ADR-023 — Per-profile Wayland sockets: made by the compositor, one per profile user, closed by mode and ACL; each client mapped to a profile by its peer uid — *Accepted (lead, 2026-11-09, T-164)*
**Question.** An app runs as its profile's Unix user (ADR-004), but the compositor (`ruya-shell`) listened only on `ruya-0` in its own 0700 runtime directory, so a profile's app found no display (Dell, 2026-11-08: SuperTuxKart ended with "No available video device"). Where does a profile's socket live, who makes it, how does the sandbox see it, and how does the compositor know whose window a client is?

**Decision.**
- **The compositor makes the sockets** (`shell/compositor/ProfileSockets`): for every profile it knows, a listening socket `/run/ruya-wayland/ruya-<id>`, owned by `ruya-shell`, mode 0600 plus one POSIX ACL entry `user:ruya-<id>:rw-`, so only that user can connect (connecting needs write permission). The directory is the compositor unit's `RuntimeDirectory` (0711: a profile user can open its own socket by name but cannot list the others), emptied at every start and stop of the shell. Each socket is bound in a private 0700 staging directory, given its mode and ACL there, then renamed into place, so no other user can connect at any moment. The fd goes to `QWaylandCompositor::addSocketDescriptor`. libwayland cannot drop a listening socket, so the socket of a deleted profile is unlinked (unreachable) and its fd stays idle until the shell restarts. `ruya-0` stays for the shell's own clients (VM test clients).
- **The spawner points the app at it:** `ruya-session` sets `WAYLAND_DISPLAY=/run/ruya-wayland/ruya-<id>` (an absolute path) for every app unit, and `SDL_VIDEODRIVER=wayland` (there is no X server). `flatpak run --socket=wayland` binds exactly that one socket into the sandbox as `$XDG_RUNTIME_DIR/wayland-0` and sets `WAYLAND_DISPLAY=wayland-0`; the sandbox never sees `/run/ruya-wayland` and so has no path to another profile's socket. An app without the `wayland` socket permission (X11-only) gets no display: there is no Xwayland.
- **Whose window it is** is decided per client by its peer uid (`WaylandClient.userId`, `AppGate.verdict`, C++ in the shell, tested on every host): the signed-in profile's user is that profile's; the shell's own user is the shell's (shown to whoever is signed in); everyone else (another profile, root, any other uid), and every client but the shell's while nobody is signed in, is closed when it makes its first surface, before anything is drawn. `Shell.addApp(item, profile)` shows a window only to its own profile and hides every window while nobody is signed in (the picker and the wizard are never covered); a hidden window gets no focus and no keys. T-165 decides what a profile switch does to the hidden apps.
- **Input for profile apps (minimal):** apps get keyboard and pointer events through the compositor (`wl_seat`), which already carries what `ruya-inputd` makes of the pads (arrows, Return, Escape, ...). Profile users get **no** access to `/dev/input/event*` (the `uaccess` ACL stays with the seat session, the shell's), so a game cannot read a pad directly yet; real pad access for games (and the double input of B-006 once they can) is T-217/T-266's.
- **GL clients:** Fedora's `qt6-qtwayland` ships only the `wayland-egl` client-buffer integration (no `linux-dmabuf-unstable-v1` plugin), and `wayland-egl` needs `EGL_WL_bind_wayland_display`, which the image's Mesa does not offer (the shell logs its absence on the Dell and in the VM). On the Dell (T-355) STK through the shell rendered on llvmpipe at 563 % CPU. **T-358 (Accepted (lead, 2026-11-09)):** the image builds Qt's own `linux-dmabuf-unstable-v1` compositor plugin from the source RPM of the installed qt6-qtwayland (stage `qt-dmabuf` in `image/Containerfile`) with our patch `image/qt/0001-linux-dmabuf-v4-feedback.patch`: protocol v4 with default and surface feedback (`main_device` = the EGL device's render node, one tranche); `ruya-compositor@.service` sets `QT_WAYLAND_CLIENT_BUFFER_INTEGRATION=linux-dmabuf-unstable-v1;wayland-egl`. On the Dell STK then renders on the UHD 630 at about 15 % CPU, 1080p60, with the Guide overlay over it. The plugin uses private Qt API: the build refuses an image whose Qt differs from the one it was built against. Open: explicit sync (NVIDIA proprietary), `external_only` modifiers in the tranche, multi-GPU, direct scanout (B-003). Worth upstreaming.

**Rejected.** (a) *`ruya-session` (root) makes the socket in the profile's runtime directory and hands the fd to the shell over `Session1`* (the planner's first idea): the root service would need `CAP_CHOWN`/`CAP_DAC_OVERRIDE` and a hole in `ProtectHome=yes` (which hides `/run/user`), it would put fds on the system bus, and the socket's life would follow the service while its listener (libwayland cannot remove one) follows the compositor; a restart of either leaves the other with dead sockets. Same tightness, more privilege and more moving parts. (b) *One shared socket for all profile users, filtered by peer uid only:* any profile's process could connect while another profile plays and talk to the compositor's globals before it is refused; the per-user socket keeps them out at `connect()`. (c) *A socket in each profile's `$XDG_RUNTIME_DIR` made by the profile's own user manager (a socket unit):* the listener would be a process of the profile, not the compositor; only a proxy could bridge it. (d) *`--filesystem=/run/ruya-wayland` for the sandbox:* would show every profile's socket path to every app.

**Consequences.** `ruya-compositor@.service` gets `RuntimeDirectory=ruya-wayland` (0711). The display an app gets (an absolute `WAYLAND_DISPLAY`, `wayland-0` inside Flatpak, `SDL_VIDEODRIVER=wayland`) is something apps rely on: *experimental* until the first release (ADR-022). The same "path into the profile" question for `ruya-library` (Steam libraries in the profile's home, `ProtectHome`) is answered the same way, by running the per-profile part as the profile: see `03` §4.1.

### ADR-024 — Ruya Input: one input service owns the pads; apps get virtual devices of their profile only; the shell keeps a path that cannot be taken away — *Accepted (lead, 2026-11-09; target set by the owner's requirements, `06-input-requirements.md`)*
**Owner decision, 2026-11-12 (lead-15): the virtual pad matches the controller.** A game sees a virtual pad of the physical pad's family:
- a DualSense or DualShock as a virtual DualSense: PlayStation prompts, gyro, touchpad, lightbar and triggers where the family has them;
- a Nintendo pad as a Switch Pro;
- anything else as the Xbox 360 pad RUY-3 built.
A per-game switch forces Xbox 360 for a game that handles the other families badly (RUY-43's Controller page). Isolation, take-away and mapping stay as below: only the identity of the virtual device changes. Today only the Xbox 360 type is built. The spike (RUY-449) decides the mechanism (uhid with the vendor's report format, so the kernel's own driver binds, or uinput with the right ids) and writes the build ticket.
**Question.** The owner's requirements for the input subsystem (`06-input-requirements.md`: device discovery and capabilities, normalisation, mapping, layers, routing and ownership modes, virtual pads/keyboard/mouse, haptics, gyro and touchpad, profiles, an SDK, settings UI, Quick Resume, community profiles) meet a console where games run as the profile's Unix user and see **no** controller today: the physical pads' nodes carry an ACL for `ruya-shell` only (Dell, 2026-11-09: SuperTuxKart's Controls list shows the keyboard alone), and `ruya-inputd` (ADR-003's stopgap) turns every pad into navigation keys that reach the focused game through `wl_seat`. How do the requirements fit ADR-003, ADR-004, ADR-017, ADR-022 and ADR-023, and in which order are they built?

**Decision.**
- **One input service** owns the physical controllers (discovery, identity, capabilities, normalisation, mapping, routing, virtual-device lifecycle) and is the only reader of physical pads apart from the shell's emergency path. Which engine it is stays ADR-003's question and is answered by the spike **T-366** with evidence: InputPlumber (not packaged in Fedora 44, so built in the image; GPL-3.0; runs as root) or our `ruya-inputd` grown into it (ADR-003's named fallback). Either way the processing runs with the least privilege the spike shows to be enough (the requirement "not the whole engine as root").
- **Apps see only virtual devices of their own profile.** Physical nodes keep their shell-only ACL (unchanged from ADR-023). The service creates the virtual devices (uinput: an Xbox-style pad per player, later keyboard and mouse) and gives each node one ACL entry for the signed-in profile's user (`ruya-<id>`), removed at lock and switch, the same "closed by ACL, one user" rule as ADR-023's sockets and ADR-010's pulse sockets. A Flatpak game needs `--device=input` (or `all`) to see them.
- **Routing follows the focus.** While an app has the focus the service sends it pad input only through its virtual devices and stops the navigation keys (no double input); Guide always goes to the shell (the compositor's `KeyRouter`), and the shell's overlays take the pad back. If the service dies, the shell must still navigate (a fallback reader for the shell, decided in T-366).
- **Ownership modes** (requirements §6): *Ruya-managed* (default), *direct passthrough* and *Steam-managed* (the profile's user gets the physical nodes for that run, no virtual pad from us) are per-app settings stored by the service, never by editing Steam's files. *Amended by RUY-2 (lead, 2026-11-12):* hidraw only in Steam-managed; outside the app route the service grabs those pads (`06-input.md` §5.3).
- **Profiles** (requirements §9) are versioned JSON with a schema, validated on load and import, inheriting game → platform → global → built-in; per controller identity and per console profile. No scripts in profiles; macros are data with limits.
- **Apps reach the semantic API only through `Platform1`** (ADR-022): actions, glyphs, haptics requests. The raw evdev surface (virtual pads) is public too and documented in `docs/developers/controller-input.md`.
- **Order** (each a task, smallest useful slice first): T-366 spike, engine decision and `06-input.md` (design: model, schema v1, `Input1` contract draft) → T-367 *a game sees the pad* (virtual pad per pad, profile ACL, focus routing) → T-368 controllers pane, capabilities and button test → T-369 mapping v1 (layout swap, dead zones, curves, global profiles, import/export) → T-370 game and platform profiles → T-371 ownership modes (passthrough, Steam) → T-372 keyboard/mouse output, layers, chords, shortcuts → T-373 gyro, touchpad, rumble/haptics back to the pad → T-374 semantic actions and glyphs for apps. ADR-017's slots (T-264, T-266) use T-367's layer. T-217 is split into these tasks.

**Spike result (T-366 / RUY-2, lead, 2026-11-12; design `06-input.md`).** Engine: `ruya-inputd` grown (ADR-003), running as the system user `ruya-input`, not root. Reach: proven on the Dell: a uinput Xbox 360-style pad with one ACL entry for `ruya-p1` is SuperTuxKart's "Xbox 360 Controller" in p1's sandbox and refused to p2; a sandbox without `--device` has no `/dev/input`. Two corrections to the decision above: logind's `uaccess` flushes foreign ACL entries on every udev event of a tagged node, so virtual nodes are owned by the service through a phys-prefix udev rule and it re-asserts the ACL after each event; and removing an ACL does not close an open descriptor, so at lock, switch, run end and Freeze the service **destroys** the profile's virtual pads and makes new ones. Shell safety: fast restart (measured 2.2-2.4 s today, target 0.5 s) **and** a compositor emergency reader after 3 s without the service (06 §8). Contract draft `api/dbus/org.ruyaos.Input1.xml`, profile schema `docs/specs/schemas/input-profile-v1.json`.

**Amendment: `/dev/uinput` for the signed-in profile (owner decision RUY-1061 a, 2026-11-22; details lead, RUY-1063; built RUY-1063, host-tested, vm and hw pending).** Steam Input makes its own virtual pad through `/dev/uinput` for every game it manages, so "only root and `ruya-input` create input devices" (`06-input.md` §3 rule 1) gives way: `/dev/uinput` belongs to `ruya-input` (mode 0600) and `ruya-inputd` gives it one ACL entry, for the signed-in profile's user, at sign-in and switch, none while locked or when the shell leaves the bus, set again after each udev event on the node. What that opens is closed in the same change: a uinput device's `phys` is whatever its creator wrote and nothing in sysfs or udev names the creator, so a **parentless** input device (`/devices/virtual/input/inputN`) is **foreign until marked**: `ruya-inputd` writes `/run/ruya-input/own/inputN` right after it makes a device and removes it before it destroys it (all of them at start), root may vouch for its own (`/run/ruya-input-trusted/inputN`: the checks' stand-in pads and keyboards, then treated as hardware), and the udev rules test the markers at every event, so an own device can be briefly foreign, never the reverse. A foreign node is `ruya-input`'s, mode 0600, without `uaccess` and `power-switch`, with `LIBINPUT_IGNORE_DEVICE=1`: the shell's libinput, logind's power key and `ruya-inputd`'s pad reader never take it (the shell cannot filter per device: Qt merges every keyboard). It carries one ACL entry, for the profile that held `/dev/uinput` when it appeared, while that profile is signed in; one that appears within 2 s of a profile change is nobody's. The phys prefix `ruya-input/` is a label, no longer a trust check. Foreign keyboards and mice into the game are RUY-1090. Never `/dev/uhid`.

**Rejected.** (a) *Give the profile user the physical pads* (simplest, and what a desktop does): no remapping, double input with the navigation keys, the shell's Guide path depends on the game, and a pad of player 2 would be readable by whoever is signed in. (b) *Building the requirements as one subsystem in one go:* the document itself asks for small stages; the first useful result is a game that sees a pad.

**Consequences.** New contract `org.ruyaos.Input1` (T-366 drafts, T-367/T-368 build), a udev rule and an ACL owner for virtual nodes, the shell's focus reaches the input service, B-006 is replaced by these tasks. Owner-level and later: a community profile repository (hosting, moderation, publishing), glyph licences (T-199), anything that needs Sony/Microsoft/Nintendo terms (adaptive triggers through hidraw are technical, no terms question known).

### ADR-025 — Windows runners: a set of them, GE-Proton preinstalled and the default — *Accepted (owner, 2026-11-09: "we should ship proton ge default", "also wine, Wine-GE etc."), details open (lead, 2026-11-09)*
**Question.** ADR-014 (D3, owner 2026-11-06) made Wine the only system runner and shipped no Proton or Steam runtime. The owner now wants GE-Proton (the community Proton build with extra game fixes and media support) shipped and used by default.

**Decision (direction, owner).** The image preinstalls **GE-Proton** and it is the default runner for Windows games: `.play` packages with `runner: proton-ge` or `source: system` of the Windows kind, first-party launchers (the Epic app of ADR-018 if accepted) and, when the player installs Steam, Steam's default compatibility tool. It updates through the Store, independently of the OS, pinned to tested releases *(amended by the owner, 2026-11-19, RUY-897: it is always in the OS image and updates with the OS, ADR-038)*. This amends ADR-014 D3 ("only Wine"). **More runners, the player's choice (owner):** plain Wine (stable and staging), Wine-GE, Valve's Proton as UMU-Proton and other open builds are offered as further runner extensions in the Store, installed on demand, one branch per major *(amended by the owner, 2026-11-19: "ship them all in the default image. an app can decide what to use"; every runner is in the OS image, ADR-038, RUY-37; **narrowed by the owner, 2026-11-20, RUY-915:** the image ships two families, GE-Proton (the current major and the previous one, so a major bump doesn't break installed games) and plain Wine stable. Wine staging, Wine-GE (upstream archived in 2024) and UMU-Proton (its umu and Steam Linux Runtime path doesn't run in the sandbox, RUY-91) are not shipped: they overlap GE-Proton and each costs size and upkeep. A package that needs one bundles it; a runner joins the image only when a real package or compatibility report needs it)*; a game's Compatibility setting picks the runner and version per game (`05` §6.2's per-game override, now for every Windows game). Only GE-Proton is preinstalled. Wine-GE's upstream stopped in 2024 (its author points to GE-Proton with umu): T-381 confirms, and if so it is offered only as a frozen legacy branch for games that need it. *(Superseded by RUY-915, 2026-11-20: the image carries GE-Proton and Wine stable; Wine-GE is not offered.)*

**Lead decisions inside it.**
- **Form** *(superseded by ADR-038: `org.ruyaos.Play.Runner.ProtonGE<major>//1`, files on /usr in the image)*: a Flatpak extension, one branch per GE-Proton major (`org.ruyaos.Runner.GEProton//<major>`, name fixed by T-381), built from the upstream release tarball with a pinned checksum, never downloaded at run time by the OS. It runs through **umu-launcher** and the Steam Linux Runtime the way Heroic and Lutris run it; the spike (T-381) decides whether those come as extensions too. **Found by RUY-91 (2026-11-16):** inside a Flatpak sandbox on Flatpak 1.18.4, umu and the Steam Linux Runtime do not start. The portal's `--usr-path` sub-sandbox fails, and without the portal pressure-vessel exits 125. Without the runtime, GE-Proton runs, so `.play` uses GE-Proton directly (ADR-014, "Spike result"). The same portal may also break Proton in the Steam Flatpak; T-381 and the Steam default (T-383) re-test it first.
- **Display:** Wine's Wayland driver if GE-Proton's works on the per-profile socket (ADR-023); otherwise Xwayland in the compositor becomes its own task. No X server is added silently.
- **Developer surface (ADR-022):** **no D-Bus call** runs a Windows program for an app (that would launch code outside the caller's sandbox). An app or package *uses* the runner by declaring the extension in its own Flatpak manifest and reading its `runner.json`; that is a **tier-C data format** (extension name, branch, `runner.json`, the umu entry), experimental until the first release, documented in `docs/developers/windows-games.md` with the sample `samples/hello-runner/` (T-384, built as RUY-36; `lint-dev-docs.ps1` checks the sample's extension point against `commit.rs` and `image/play/runners/`; the ids are `org.ruyaos.Play.Runner.<Family><major>//1` since ADR-038, and the umu entry is gone with ADR-038/RUY-91). Which runner and version the shell shows (About, a game's Compatibility screen) is internal (tier A).

### ADR-026 — Downloads: one job record in Store1 and Update1, one manager in the shell, no new service — *Accepted (lead, 2026-11-09; owner request: "a download manager: current downloads, speeds, actions, stats")*
**Question.** The console downloads through two root services: `ruya-store` (Flatpak installs and updates, later runner extensions and `.play` imports) and `ruya-update` (the OS image through bootc). Both report only a percent; nothing can be cancelled, paused or reordered, and nothing is counted. The owner wants one place to see and act on all of it.

**Decision.**
- **No new service.** Each service keeps owning its own downloads (they run as root, with their own queues and policies); a new aggregator daemon would only proxy them. The shell's C++ `Downloads` facade merges both into one model, as the Library merges its sources.
- **One job record, v2, in both contracts** (`Store1.ListJobs`/`JobProgress`, `Update1` gains the same for its one image job): `job`, `source` ("store" | "update"), `kind` ("install" | "update" | "remove" | "runner" | "os"), `app_id`, `title`, `state` ("queued" | "running" | "paused" | "finished" | "failed" | "cancelled"), `phase`, `bytes_done`, `bytes_total` (0 = unknown), `rate_bps` (a smoothed rate), `eta_s` (0 = unknown), `position` (queue order), `started`, `finished`, `error`. Unknown values say so (0 plus a flag); the UI never invents a number.
- **Actions** (shell and root only, as every Store1/Update1 call): `CancelJob`, `PauseJob`, `ResumeJob`, `MoveJob(job, position)` on Store1; `CancelDownload`, `PauseDownload`, `ResumeDownload` on Update1. *Pause* is "stop and keep what is fetched": OSTree and the OCI pull keep fetched objects, so Resume continues; a source that cannot resume says `unsupported`. Installing and removing stay admin-gated as today.
- **Stats** live where the bytes are counted: each service appends finished jobs and per-day byte totals to a small root-only ledger (90 days), read through `GetDownloadStats(days)`; the shell shows the sum.
- **Policy** (Settings > Downloads, stored by the services): pause downloads while a game is in front (default on), download updates in standby (only where T-166's wake works), a bandwidth limit only if the spike finds a real mechanism (otherwise not offered).
- **Developer surface:** tier A (shell-private). Installing and updating are on ADR-022's never-public list. Apps' own downloads (a game patching itself) stay in the app; letting an app report one to the manager would need a new tier-B line (owner) and is not planned.

**Consequences.** T-388 (lead: spike and contract drafts), T-389 (Store1 jobs v2 and actions), T-390 (Update1 the same), T-391 (the Downloads page and a status-cluster pill), T-392 (stats and policy).

**Spike findings and amendments (RUY-27, lead, 2026-11-23; measured on the Dell, Flatpak 1.18.4, bootc 1.17.1; the drafts are `api/dbus/drafts/`).**
- **Store bytes come from libflatpak, not the CLI.** The `flatpak` CLI prints no byte counts; with `--noninteractive` (as `ruya-store` runs it) it prints no progress at all, so today's percent never moves on real hardware. Without it, it draws a terminal progress bar (percent, rate, ETA). libflatpak's `FlatpakTransactionProgress` reports bytes transferred (within 7 % of the NIC's count), each operation's download size before the first byte, and a cancel through its `GCancellable` (1.2 s). `ruya-store` runs its transactions through libflatpak (the `libflatpak` crate, MIT, over the LGPL library); the image gains `flatpak-libs` (1.1 MB). Its listing calls stay on the CLI until they move too (one adapter in the end; RUY-28 files it).
- **Update bytes come from `bootc --progress-fd`.** bootc 1.17.1 writes JSON lines to a pipe: `ProgressBytes` (bytes, bytes still to fetch, bytes already present, one subtask per layer) about ten times a second while layers arrive, then `ProgressSteps` for the import and the deploy, which carry no bytes. 0.0.105 to 0.0.106 on the Dell: 21 s silent, 114 s of bytes, about 80 s of import, 12 s deploy. Pause is SIGTERM: fully fetched layers are kept as repository commits (9 of 19 after 40 s) and reused by the next run, also after a reboot; once the import has started, Pause and Cancel answer `unsupported`.
- **The record** (amends the field list above): the job is named `id`, as in Store1 and Play1 today (RUY-799); `state` is "queued" | "running" | "paused" | "finished", with the outcome in `status` ("ok", "failed", "cancelled", ...) as JobFinished has it, so there is one terminal state; new keys `resumable` (Pause offered) and the `reason` values "playing" (paused by the policy) and "restarted"; `bytes_done` counts network bytes of all the job's runs (what the stats add up) and `percent` is the source's own completion (libflatpak counts objects already fetched). `JobChanged(a{sv})` replaces `JobProgress`.
- **Pause is per boot.** A cancelled Flatpak transaction leaves its fetched objects in OSTree's staging directory, which is named by the boot id: a resumed install fetched 240 of 335 MB after 127 MB had arrived (objects in flight at the pause are fetched again). After a reboot they are not reused: the job stays paused with reason "restarted" and Resume starts over. Remove and rollback jobs are not resumable (`unsupported`). OSTree verifies every object's checksum as it commits, so a resumed download is verified before use by construction; RUY-28's VM check proves it with a corrupted staged object.
- **No bandwidth limit.** Flatpak and OSTree have only libcurl's low-speed abort, no rate limit; shaping incoming traffic would need `tc` with an `ifb` device for all of the console's traffic. Not offered (the policy bullet above).
- **Who owns which job.** Each service that does the work owns its job and uses this record: Store1 (Flatpak apps and runners, and moving them between drives, RUY-139), Update1 (the OS image), Play1 (`.play` imports, source "play"), and apps through Platform1 (RUY-454, source "app"). The last replaces "not planned" above: the owner made the app integration APIs public on 2026-11-12 (ADR-018). The Downloads page shows Store1, Update1, Play1 and app jobs. Save operations (RUY-148 and the saves manager) and ROM uploads use the same record in their own service and are shown where saves and ROMs are, not on the Downloads page (they download nothing).

### ADR-028 — Games and saves: the OS indexes and protects, it does not own other launchers' files — *Accepted (lead, 2026-11-10; input: the owner's "Universal Game & Save Management System" proposal, `docs/archive/research/universal-game-and-save-management-proposal.md`); inside ADR-005, ADR-014, ADR-020, ADR-023, ADR-025*
**Question.** The proposal asks for one authoritative game library and one universal save manager across emulators, Proton/Wine, native, Steam, Heroic and Lutris, with ~20 services, emulator adapters that launch and configure emulators, access leases on canonical game files, cloud sync and save conversion. How much of it fits RuyaOS?

**Decision (what we take).**
- **One library index, many installations.** A *game* is a logical entry; Flatpak, Steam, Heroic/Lutris, `.play` and ROM files are its *installations* (each with its source, location, runner, preferred flag). Never merge two installations by title alone: ids (Steam app id, Flatpak id, a content hash from `GameData1.Identify`) or the player's confirmation, with the confidence recorded. The Library (`ruya-library`) holds this; no second database.
- **The save rules are ours:** local-first; snapshots are immutable, have a manifest with checksums and are marked good only after verification; every restore first takes a safety snapshot and restores through staging; never while the game runs; never delete the only valid backup; long operations are journaled and resumable and use ADR-026's job record; events notify, `Get*` calls are the truth.
- **Where saves are found** (in this order): what the app declares through the hub (T-311); our own runner prefixes, where we know the layout (one prefix per game per profile, ADR-025/05 §6: back up the prefix's `drive_c/users/<user>` minus caches, so a recreated prefix gets its saves back); a known-locations data file (Ludusavi's manifest is the candidate: its licence is an owner question); the player's manual choice. Confidence levels as in the proposal (verified, high, probable, unverified); nothing is moved or deleted on an uncertain find.
- **Discovery runs as the profile user**, never as root: ADR-023 keeps root services out of profile homes. A small per-profile agent (or the hub's per-profile half) reads `~/.var/app/*` and Steam's `compatdata`; the root side sees only what it hands over.
- **Storage locations by volume id**, not mount path; a missing drive leaves its games listed as "unavailable"; moving a game to another drive is a job with verify-then-delete. Saves stay on the console (owner, ADR-020); drives hold games, ROMs, captures and backups.
- **The proposal's edge-case table and test list** become the acceptance matrix of the epic spec (T-302's `08-games-and-saves.md`).

**Rejected.** The OS as owner of canonical game files with access leases and copy-on-write working copies (Steam, Heroic and Flatpak own their installs; Flatpak permissions already scope access). OS-side emulator adapters that launch and configure RPCS3, PCSX2, Dolphin (emulators are Store apps, ADR-014 ships none; they tell the hub what they need, T-311). Per-game "save profiles" beside console profiles (a console profile is the save owner; slots are the game's own). Registry-backed save backup, save conversion and cross-emulator migration (not now). Cloud sync and cross-device conflict resolution (out of the MVP, 00 §2; owner-level when it comes). Managing firmware or licence files (RAP, BIOS): the OS only says where they go and explains a missing one. Twenty services: it is `ruya-library` + the hub of ADR-020 + the saves manager of T-309.

**Consequences.** T-302 (epic spec) writes `08-games-and-saves.md` from this ADR and the proposal's good parts; T-215, T-309, T-310 take the snapshot rules; new T-400 (lead spike: the per-profile agent, Ludusavi, prefixes), T-401 (Library: installations of one game), T-402 (Windows saves in prefixes), T-403 (games on other drives).

### ADR-029 — Ruya Web: a local-network admin page, paired on the TV, off by default — *Accepted (owner, 2026-11-10: the invariant change as proposed; browser actions = what Settings can do minus profiles, PINs and update/rollback in v1; Avahi and nftables join the image); it changes the security invariant "D-Bus policies stay restrictive: the shell and root only" (input: the owner's "Ruya Web" document, `docs/archive/research/ruya-web-proposal.md`)*
**Question.** The owner wants a browser interface on the home network to manage the console: library and artwork, ROM upload and import, BIOS files, saves and backups, storage, downloads, apps, system information, logs and settings. Today only the shell (`ruya-shell`) and root may call the system services; there is no network-facing service, no mDNS, no Companion app and no web toolchain.

**Proposal.**
- **One network gateway for every remote client** (lead, 2026-11-10, after the owner's Companion document, ADR-030): a new service `ruya-link` (Rust, like the other services) serves the Ruya Web page **and** the Companion app with the same device identities, pairing, per-device permissions and event stream; the web page is static files it serves. Below, `ruya-web` means this service. A new system user. Each system service's bus policy gets an **allow-list of methods** for `ruya-web` (reads, and the admin actions the owner approves), not "everything the shell may do": that is the invariant change. `ruya-web` holds no business logic: every action is a call to the service that owns it (Library, Store, Update, Devices, the hub, the saves manager, Downloads of ADR-026), so a missing capability is built there, never in the web layer (the proposal's own rule).
- **Off by default**; turned on by an admin in Settings > Web management, which shows the address and a QR code.
- **Pairing on the TV, not "being on the Wi-Fi":** a new browser shows a code that must be confirmed on the TV with the admin PIN; the browser then holds a revocable device token (Settings lists paired browsers). Admin actions in the browser still ask for the admin PIN. No passwords, no second user database: profiles and PINs stay in `ruya-profiles` (the PIN hash never leaves it).
- **Local only, enforced three ways:** it listens on loopback and the LAN interfaces only, an nftables rule drops its port from non-private sources, and every request is checked (source address, `Host` header against the console's names and addresses: DNS-rebinding protection, `Origin`, CSRF token). No relay, no remote access, ever.
- **HTTPS with a console-made certificate:** generated on first enable, its fingerprint shown on the TV during pairing (the browser's warning is explained, TLS is never weakened, no HTTP fallback). mDNS (`ruya.local`, Avahi in the image) is a convenience; the IP address always works.
- **Front end:** the 04 design tokens exported from `Theme.qml` to CSS so the page looks like the console; the framework is the spike's choice (the proposal suggests React + TypeScript + Vite; the host has no JS toolchain: it runs in WSL, never installed on Windows).
- **Scope order:** (1) foundation, pairing, read-only dashboard; (2) library and artwork; (3) ROM upload and import through the hub (ADR-020) and its archive safety; (4) BIOS and firmware files the player owns (hash-checked, never shipped); (5) downloads, apps, storage, saves through their services; (6) diagnostics with redaction. Logs and settings come last because they are the most sensitive.
- **Taken from the proposal:** upload and import as separate stages, duplicate detection by hash, never trust a BIOS by its file name, events notify and state is read back, capability-driven navigation, no placeholder controls, security tests for every boundary. **Left out:** Companion (does not exist; nothing here depends on it), REST plus OpenAPI as a second source of truth (the D-Bus XML stays the contract; the web API is a thin, generated mapping), AI agents (a later client of the same allow-list).

**Owner questions.** (1) May a network-facing service call the system services, under a method allow-list, off by default and paired on the TV (the invariant change)? (2) Which admin actions may the browser do at all (install, uninstall, delete files, change settings, see logs)? Recommended: everything the Settings app can do except profiles, PINs and updates/rollback in v1. (3) Avahi (mDNS) and nftables join the image.

**Consequences if accepted.** T-404 (lead: threat model and the bus allow-list), T-405 (lead spike: stack, TLS, pairing, tokens export), T-406..T-410 (builders), each with its security tests.

### ADR-032 — Stores: one default store, and anyone can run their own as a signed Flatpak repository that an admin adds — *Accepted (owner, 2026-11-10: "the OS will ship with a default store, but developers could create their own stores and users can use them"); details lead, 2026-11-10; owner answers 2026-11-10, hosting of the default store still open*

**Context.** `03` §4.2 already had three kinds of Flatpak remote (official, Flathub, "developer remotes" an admin enables) and `ruya-store` has `AddRemote`, but there was no screen, no removal, no rule for what a foreign remote may do, and "developer remote" read as a test feature. The owner wants other stores to be a normal thing a player can use.

**Decision** (the whole design is `docs/specs/10-stores.md`):
1. **A store is a signed Flatpak repository and its `.flatpakrepo` file.** No RuyaOS store format, no account, no server of ours in the path; inside ADR-005 (Flatpak only) and ADR-011.
2. **Three trust levels:** `official` (the `ruyaos` remote, in the image, not removable), `community` (Flathub, in the image, can be turned off), `third-party` (added by an admin with the PIN after a preview that shows host and key fingerprint; removable; at most 16).
3. **A third-party store cannot replace anything:** never an app, runtime or id that a trusted store offers or that is installed from another store; no reserved names; runtimes come from trusted stores; its metadata is hostile input; a broken store breaks only itself. Its apps run in the Flatpak sandbox like every other app, so the invariant "third-party apps run only in Flatpak sandboxes" is unchanged, and so is the bus policy (stores are shell-private, tier A).
4. **Who installs:** admins directly; a Standard profile needs an admin's PIN for a third-party store unless the admin opened that store to everyone; hidden for child profiles unless allowed (T-211).
5. **A key that changes is never accepted silently; removing a store keeps its apps by default; a blocklist ships in the image** and changes only with OS updates.
6. **`.play` packages are a second shelf of the same store** (`10-stores.md` section 11): a signed index of `.play` files next to, or instead of, the Flatpak repository. The console downloads the file and its own importer turns it into an app; a store never ships a ready-made `play.<id>` Flatpak (that prefix is reserved), so ADR-014's rules (closed permissions, vetted art, developer key continuity) hold for every store. This replaces `05` section 11 way 1; `05` section 18 lists the other corrections to that draft.
7. **What is public:** the format a store author follows (the store file, the repository, the `.play` index, the well-known address, the AppStream keys) joins `docs/developers/api-surface.md` as tier C (`public-format`); the D-Bus calls stay private.

**Rejected:** a RuyaOS-specific store protocol or catalogue server (a second format to secure, nothing gained over Flatpak); adding a store without an admin; letting stores carry runtimes (a hijack path for every app); a store reputation service (needs a server and a policy we do not have).

**Owner answers (2026-11-10):** (1) the signing key of the default store, and by the same rule the OS image key, is held by the owner, offline (a hardware token or an offline machine; releases are signed by hand; no key in CI); only first-party content goes into the default store at the start (our apps, runners, curated entries for Flathub apps; everyone else uses Flathub or their own store); **hosting is not decided yet**. (2) Yes, a blocklist, empty at first; only the owner adds an entry (malware, a stolen key), each with a written reason an admin can read on the console. (3) The warning text of `10-stores.md` section 8 is approved as written. **The questions were:** (1) the default store's hosting, signing-key custody and who may submit (T-444; also T-381, T-426); (2) the blocklist: do we keep one at all, and who decides an entry; (3) the wording of the warning (`10-stores.md` §8) is a liability statement.

**Consequences.** T-440 (contract and service: preview, add, remove, states), T-441 (isolation rules, blocklist, hostile fixture store), T-442 (Settings > Stores), T-443 (badges, the install gate and store states in the Store), T-445 (the "your own store" chapter and sample), T-444 (the default store, waits for the owner), T-446 (`.play` in stores, after the `.play` epic). `03` §4.2's "developer remotes" row is replaced by this ADR.

### ADR-033 — Ruya Hub: the quick menu grows into the in-game control centre, inside the shell, with no Hub service — *Accepted (owner, 2026-11-10: "plan them", with the lead's recommendations for the open questions); details lead, 2026-11-10*

**Context.** The owner's requirements (`07-hub-requirements.md`, 2026-11-09) ask for a Guide-button overlay with a compact control centre (status, quick settings, running and recent games) and panels (Games, Quick Settings, Performance, Audio, Controllers, Notifications, Power). They assume gamescope, a separate "Ruya Hub Service" and a Ruya Input service that already exists. Here the shell is the compositor (ADR-002 A), the quick menu over a running app is built (T-147, `02` §1.4/§1.5) and Ruya Input is still a spike (ADR-024, T-366).

**Decision.**
1. **Ruya Hub is the quick menu (`QuickMenu.qml`), grown in three levels:** the Quick Hub (what opens on Guide), expanded panels (one level deeper, still over the game) and the full Ruya interface (Settings, Library: leaving the Hub). It never becomes a second desktop. The name "Ruya Hub" is the overlay's; the game data service is `ruya-gamedata` (ADR-020).
2. **No Hub service and no second process.** The Hub is shell UI and reads the existing services (`Session1`, `Devices1.*`, `Library1`, `Notifications`, the power page); every gap is a method or property on the service that owns it, contract first (`CLAUDE.md`). Overlay state (open, panel, focus) is shell state.
3. **Above the game by construction.** The shell composites every app (ADR-002 A), so the Hub is a layer above the app layer, not a layer-shell client; an app cannot draw above it or impersonate it. **Opening the Hub pauses the game; closing it returns to gameplay (owner, 2026-11-10, replacing "the game keeps running"):** the app in front is frozen with the cgroup freezer (all its scopes, ADR-019's mechanism) when the Hub opens over it and thawed when the Hub closes to it (Resume, B, Guide); its last frame stays on screen under the Hub and its sound stops. Home, Switch to and Close from the Hub keep their meaning (the app stays frozen behind Home as ADR-019 wants; Close thaws before it stops the app). A Settings switch "Pause games when Ruya Hub opens" (on by default) turns it off for online games, which can drop a connection while frozen. Built by T-457.
4. **Performance data without a new daemon:** FPS and frame time of the app in front come from the compositor (the app surface's commits and the shell's own frame timing); CPU, RAM, temperatures, GPU busy, VRAM and power come from the kernel through `Devices1.System`/`Devices1.Thermal`, each metric with a state (supported, unsupported, unavailable, temporarily unavailable), never an estimate; sampled only while the Performance panel is open.
5. **Activation through semantic input actions.** Today the shell's key router maps Guide (`KEY_HOMEPAGE`, `Super`); per-pad routing, long-press and "Guide never reaches the game" come with Ruya Input (T-367, ADR-027); configurable shortcuts after that.
6. **Owner answers (2026-11-10, the lead's recommendations accepted):** (a) the V1 exclusions in `07` §10 mean "not in the overlay", not "never in RuyaOS"; (b) a game surviving a shell crash is not in V1 (it would reopen ADR-002: the shell is the compositor, so its crash ends the session); (c) Quick Resume across reboots is later, after research; suspended, hibernated and restorable session states are not shown until a session can be in them (ADR-019). Test hardware (a spare low-tier PC) stays an owner spending question.

**Rejected:** a `ruya-hub` service between the shell and the services (a second owner of the same state, more bus surface, no gain while the shell is the only client); a separate overlay process or a layer-shell client (only needed under gamescope, which we do not run); a performance daemon that samples all the time (cost while nobody looks).

**Consequences.** T-447 (lead: the Hub's design, `02` §1.6 and `04`), T-448 (the Quick Hub: status row, tiles, running and recent games), T-449 (microphone in `Devices1.Audio`), T-450 (Audio panel), T-451 (performance metrics in `Devices1` and the compositor), T-452 (Performance panel), T-453 (Controllers panel), T-454 (display and brightness tiles), T-455 (activation latency and idle cost measured on the Dell), T-456 (Guide on every pad: long press, never reaching the game, after T-367). Notifications in the Hub are T-245's (its ruling); captures are T-305's. `07-hub-requirements.md` stays the owner's input; where it differs, this ADR wins.

### ADR-034 — XWayland as a compatibility layer for X11-only apps, never a display path of its own — *Accepted (owner, 2026-11-10: "treat it as a compatibility layer rather than a primary display technology"); details lead, 2026-11-10; mechanism decided by the spike T-461*

**Context.** ADR-004/ADR-023 run every app on the profile's Wayland socket with no X server. The Dell launch test (lead-10, 0.0.63) found X11-only Flatpaks that cannot start: AAAAXY (ebiten/GLFW: no X) and Alien Arena (sockets `x11` only). Many older and Windows-adjacent games are X11-only.

**Decision.**
1. **Wayland stays the only display path.** The shell, the compositor and every app that offers Wayland use it; `SDL_VIDEODRIVER=wayland` and `XDG_SESSION_TYPE=wayland` stay. X11 exists only to run apps that cannot do Wayland.
2. **On demand, per app instance, rootless** (lead, 2026-11-12, from the RUY-1 spike; was "per profile"). An X server is started only when an app that needs it is launched (its Flatpak metadata `sockets` has `x11` or `fallback-x11` and not `wayland`, or a per-app override says so). There is one per app instance, inside that instance's own unit, as a Wayland client of the profile's socket, and it stops with the instance. X11 has no isolation between clients, so it is never shared, not even between two apps of one profile. A per-profile server would also put every X window behind one Wayland client, and the shell could no longer tell instances apart. No X server at boot, none for the shell.
3. **X11 windows are ordinary app windows:** they reach the shell's app layer as xdg toplevels, so focus, the Hub, the pause, Close and the window ↔ instance match (T-459, by pid) work unchanged.
4. **Mechanism (decided by the spike T-461/RUY-1 on the Dell, lead, 2026-11-12): `xwayland-satellite` (Fedora 44 ships 0.8.3, with Xwayland 24.1.14).** A helper is the main process of the app's unit. It starts the satellite, which runs Xwayland rootless and acts as its X window manager, then runs `flatpak run` with `DISPLAY` and `XAUTHORITY`.
   - The satellite is the X window manager, so X windows reach the app layer as xdg toplevels. It lives in the app's cgroup, so the window ↔ instance match by pid (T-459), the Hub's freeze, Close and Stop all work unchanged.
   - **Readiness (RUY-472, VM-measured on image 0.0.73):** the satellite writes no `/tmp/.X<n>-lock` (Xwayland's own lock is not created under it), and listens on the display socket itself. The helper gives it a private `NOTIFY_SOCKET` (an `AF_UNIX` datagram socket in the 0700 instance directory, `SO_PASSCRED`); the display is up when the satellite's `READY=1` arrives from the satellite's own pid and the socket exists. A READY from another pid, a satellite that ends, or no READY within 10 s fails the launch. A file that another server could write is never the proof.
   - Xwayland renders on the GPU (glamor).
   - Measured cost on the Dell: idle about 35 MB private and 0 % CPU; SuperTuxKart had the same frame rate through it as on Wayland.
   - Qt's compositor offers `xdg_wm_base` v1 and `wl_output` v2 (hard-coded in qtwayland), and Fedora's satellite panics on both. Our build carries two small satellite patches until upstream or Qt changes.
   - No compositor protocol had to be added. Relative-pointer and pointer-constraints (X11 mouse-look) are not measured yet.
   - Rejected: an X window manager in the shell; rootful Xwayland (a 640x480 screen, never full screen).
5. **Security (as tested on the Dell):** the X server runs as the profile user inside the app's unit. It listens only on its path socket (`-nolisten local`: no abstract socket, no TCP), mode 0700, in a 0700 directory, and it requires a per-instance MIT cookie (`-auth`) that only that app gets (`XAUTHORITY`).
   - With the defaults, a sandbox of the same profile that has network access but no `x11` permission could connect over the abstract socket. With these settings, other profiles and the profile's other sandboxes are refused.
   - The VM check repeats that negative test, and the security baseline (T-424) asserts that no abstract X11 socket exists. Bus policies are unchanged.

**Rejected:** a permanent X server (cost and attack surface for every profile); X11 for the shell; one X server shared by all profiles (X11 lets clients read each other's input).

**Consequences.** T-461 (spike: mechanism, package, per-profile start/stop, AAAAXY and Alien Arena on the Dell), then a build task from its result; ADR-023 point "otherwise Xwayland becomes its own task" is this ADR.

### ADR-035 — Game settings in the Ruya Hub: the game declares them as a file, the shell draws them, changes reach the game on Resume — *Accepted (owner, 2026-11-12) for game settings; "show a system page" Proposed*
**Question.** The owner's input "Ruya System Dialogs & Game Settings Integration" (refined and reviewed by the lead in `docs/archive/research/system-dialogs-and-game-settings-proposal.md`) asks that games hand their settings to the console, which shows them natively, and that apps can ask for trusted system dialogs. Neither is on ADR-022's tier-B list, and the input assumed a separate dialog service, live apply and an OS settings store.

**Decision.**
1. **New tier-B capability: game settings** (ADR-022 line, owner 2026-11-12). A game ships `/app/share/ruya/settings.json` (tier C: a versioned, validated schema of `bool`, `enum`, `int`, `float`, `action`, `info` rows, fixed categories, one-condition `visibleWhen`, a `restart` flag, length and count limits) and publishes its current values through `org.ruyaos.Platform1.GameSettings`. No runtime schema registration.
2. **The shell draws them in the Ruya Hub:** a **Game** icon, first in the panel icon row, only for a game whose schema is valid and whose values arrived; the panel uses the existing rows (ToggleRow, ChoiceRow, SliderRow). Games without settings see no change.
3. **Changes are staged and reach the game once on Resume** (thaw), because the Hub freezes the game (ADR-033 point 3); the game answers what it applied and what it refused, with a reason the Hub toasts. Close game drops staged changes. No live preview in V1.
4. **The OS stores no game values:** the game keeps them in its own `config/` (tier C, `saves-and-data.md`).
5. **No new service:** the delivery is an interface on `Platform1` (ADR-022), the drawing is shell UI (ADR-033 point 2). An app never writes a system setting (ADR-022 "never public").
6. **Proposed, not decided:** "show a system page", where an app asks the shell to open a system panel (Audio, Controllers, Display & motion, Accessibility) over itself and learns only that it closed. Not added: app-requested confirmation and device-picker dialogs (no security gain; RuyaKit covers confirmation). The storage picker stays the tier-B line it already is.

**Rejected:** a Ruya Dialog Service (a second door next to `Platform1`); runtime registration of schemas (an abuse surface with no gain over a file); live apply to a frozen game; an OS settings database for game values.

**Amendment (owner, 2026-11-14, lead-18: "those game settings should also be available in the OS per app/game settings, so you can change the settings from there without running the app"; the lead's option B, accepted).** It replaces point 4 and adds a second place where the settings appear:
1. **A cache and a queue, never the values.** Per profile and per app, the console keeps (a) the values the game last published (`PublishValues`) and its unavailable rows, and (b) the changes the player staged since. The game stays the owner: it keeps its values in its own `config/`, and the cache is only "what the game last said". The cache and queue live with the service that serves `Platform1.GameSettings`, root-only under `/var/lib`, and the shell reaches them over its own side of that service. They are deleted with the app or the profile, and are not part of a game's data.
2. **The game page** (03, RUY-524) gets a **Game settings** row under Manage, for a game whose file is valid. It opens the same panel the Hub draws (the same rows, the same component), titled with the game's name and icon, while the game is not running or is frozen behind Home.
3. **Values on the page:** the cached values; for a game that has not published yet, the file's `default`s. A changed row says "Changes the next time you play" and can be discarded. `action` rows are disabled with a note, because only a running game can act.
4. **Delivery:** the queued changes reach the game **once**, by the same `ChangesRequested` as on Resume: at its next start, right after its first `PublishValues`, or at the thaw if it was frozen. The game answers with `ChangesResult` as it does on Resume; a refusal is a toast and the page then shows the game's real value. A `restart` row applies before the game's first frame, so no restart is needed.
5. **An update** that changes the file drops the queued changes that no longer fit it (unknown id, wrong type or range), and the page says so once.
6. Only games that ship the file take part (Ruya-aware Flatpaks). Steam and Proton games have no Game settings row.
Consequences: RUY-408 builds the cache, the queue and the delivery at start. A new ticket builds the game page row after RUY-408 and RUY-524, with a Claude Design canvas first. The goal is formation RUY-566 ("Game settings in the console").

**Consequences.** RUY-406 (schema, loader, mock game), RUY-407 (the Hub Game panel against the mock), RUY-408 (`Platform1.GameSettings`, after RUY-157 and RUY-158); `ruya-platform` and its prerequisites (T-351, T-352, T-353: RUY-156..158) move from phase 7 to phase 3 (owner, 2026-11-12).

### ADR-036 — A local SELinux module lets PID 1 read package files on removable drives for ruya-play's helper — *Accepted (lead, 2026-11-18, lead-34; for the architect's next audit)*
**Context.** ruya-play's unprivileged helper gets its package as `OpenFile=<path>:...:read-only`, which PID 1 opens in its pre-exec child (`init_t`). Fedora's policy denies `init_t` reading `dosfs_t` (FAT, exFAT, ntfs3) and `fusefs_t` (ntfs-3g) files, and `graceful` turns the denial into "missing", so every USB install failed in the VM on 0.0.92 (RUY-100). The `--pipe` route was ruled out in RUY-839.
**Decision.** The image ships one CIL module, `image/rootfs/usr/share/selinux/packages/ruyaos/ruya_play_openfile.cil`, loaded by `semodule -i` in the Containerfile: `allow init_t dosfs_t:file {getattr open read}` and the same for `fusefs_t`. Nothing else: no write, exec or directory rights, no optical media (`iso9660_t`, `udf`) until packages from discs are in scope. *Amended (lead, 2026-11-21, lead-40, RUY-999):* one module per concern; the second, `ruya_play_runners.cil`, holds only a file context: the runner trees under `/usr/lib/ruyaos/play/runners` are `textrel_shlib_t` (as Fedora labels `/usr/lib/wine`), because Wine relocates the runners' 32-bit DLLs (execmod), which `lib_t` denies. It grants no rule.
**Alternatives tested in the VM (lead-34 spike).** (b) Binding the file into the unit (`BindReadOnlyPaths=`): it works on USB without policy, but `incoming/` (root 0600) fails, it depends on the drive's mount mode, and a bind re-resolves the path (no fd-level guarantee). (c1) FDSTORE, or `OpenFile=` on a service socket: denied. (c2) The helper connects to a root-only socket bound into its unit, and the service sends the fd it opened with SCM_RIGHTS: it works with stock policy and gives the strongest TOCTOU guarantee, but it is new protocol code (socket server, peer check, fd receive).
**Consequences.** Any unit's `StandardInput=file:` or `OpenFile=` can now read files on USB drives through PID 1, not only ruya-play's. PID 1 is already trusted, and only root defines units, so the extra reach is small. ruya-play's own checks stay the gate (a candidate path under `/run/media`, noexec, `lstat`, the helper's dev/ino check). `vm-play-check.sh` checks that the module is loaded and that no `init_t` denial happened during the run. When RUY-20 confines the ruya services, option c2 replaces this module if the architect prefers stock policy.

### ADR-037 — `runner.json` v1 and the `.play` launch protocol — *Accepted (architect, 2026-11-19, RUY-101)*
**Context.** 05 §6.2 names `runner.json` but never defines it; packagers write it, our runners carry it, and RUY-36 makes it tier C. Today ruya-pack reads only `family`, leniently.
**Decision.**
- **Format.** One UTF-8 JSON object of at most 64 KiB, strict keys (an unknown key is `runner.unknown_key`): `format` 1 (else `runner.format_too_new` / `runner.format_invalid`); `family` `[a-z0-9][a-z0-9.-]{0,63}`; `kind` `wine`, `proton`, `emulator` or `engine`, equal to the component's `type` (`runner.kind_mismatch`); `version` at most 32 characters holding a number (so `compare_versions` and `major_of` apply); `arch` `"x86_64"`; `entry`, plain relative paths without `..`, each a regular file in the runner tree: wine `{"wine":"bin/wine","wineserver":"bin/wineserver"}`, proton `{"proton":"proton"}`, none for emulator and engine (`run.command` names `${component:<id>}` itself); optional `capabilities` (closed list `multiarch`, `dxvk`, `vkd3d`, `ntsync`; informational in v1); optional `licence` (SPDX) and `source_url` (https).
- **Missing file.** A bundled copy without `runner.json` keeps lead-29's defaults (the type's own family, the entry paths above). A present but invalid file is refused at validate (`runner.*`, `invalid-package`), never defaulted.
- **Home.** One parser, `ruya_play_format::runner`, used by ruya-pack, the importer and the launcher, next to `api/play/runner.schema.json` and a schema test. The runner hash line format of 05 §7.3 moves there too. A system runner's hash is the same formula over its tree minus one root file, `.ruya-runner-hash`, which the image build writes and the launcher reports; nothing hashes a runner at launch. A bundled runner's hash is the one the importer computed, stored in the deployment.
- **Argv** (`S()` is `run.command` after placeholder substitution): native, emulator, engine `S(run.command)`; wine `[root/entry.wine] + S(...)` with `WINEPREFIX=${prefix}`, `WINESERVER` and `WINELOADER` from `entry`, and `WINEARCH` only when the prefix is created; proton `[root/entry.proton, "waitforexitandrun"] + S(...)` with `STEAM_COMPAT_DATA_PATH=${data}/proton` and `STEAM_COMPAT_CLIENT_INSTALL_PATH=${data}/proton/client` (the entry runs through its shebang; the Platform has python3). `setup[]` steps run through the same wrapper (`proton run`, or `wine` then `wineserver -w`).
- **Prefix.** `${prefix}` is per kind: wine `${data}/prefix`, proton `${data}/proton/pfx`. One function, `runner::prefix_dir(kind, data)`, resolves `${prefix}` and the `prefix:` save roots for the launcher, ruya-library and T-402.
- **Environment.** The base environment, then `run.env` (the deny table of 05 §6.3), then the launcher's own variables. `RUYA_` joins the deny prefixes.
- **Override.** The player's choice reaches the launcher as `--runner=package|bundled|system`, which ruya-session adds from ruya-library's per-profile choice. The launcher never reads files outside the sandbox.
- **Epoch and setup.** The launcher does the epoch migration and the setup-once record inside the sandbox, as the profile user, copying without following links into `${data}/.ruya-play/` (a state file and `epoch-<n>-backup/`), so a planted link reaches only what the sandbox shows.
**Consequences.** Changing the format is a `runner.json` major. RUY-36 documents this text. The proton prefix path is what packagers write in `data.saves` (`prefix:` stays the root name). The plan audit's "T-402 engine" for epochs is superseded.

### ADR-038 — The Play platform on the image: launcher and system runners from `/usr` — *Accepted (architect, 2026-11-19, RUY-101); runner delivery with the OS confirmed by the owner (2026-11-19, RUY-897); premise proven in the VM (RUY-899)*
**Context.** The `ruyaos` remote does not exist (RUY-65, owner). bootc never updates `/var/lib/flatpak`, but the launcher must follow the booted OS, offline. The device key's meaning ("this console's importer accepted this package", 05 §7.1) should not be stretched.
**Decision.**
- **Where they live.** The launcher and the image's system runners are files in the signed image: `/usr/lib/ruyaos/play/launcher/` (`bin/ruya-play-launch`, a static binary (glibc with `crt-static`; *amended by the lead, 2026-11-20: was musl, but Fedora ships no musl Rust std, found by the 0.0.97 build*) built in the `services-build` stage, so the Platform branch does not matter) and `/usr/lib/ruyaos/play/runners/<Name>/`.
- **How Flatpak sees them.** As unmaintained extensions: `tmpfiles.d/ruya-play-platform.conf` `L+` lines recreate at every boot `/var/lib/flatpak/extension/org.ruyaos.Play.Launcher/x86_64/1` and `.../org.ruyaos.Play.Runner.<Name>/x86_64/1` as links into `/usr`. Not committed to any remote, not signed by the device key. An OS update or rollback changes them at the next boot; installed apps need nothing, since Flatpak resolves the mount at each run.
- **Runner ids.** Family and major are in the id, the branch is the ABI: `org.ruyaos.Play.Runner.ProtonGE10//1`. This replaces ADR-025's `org.ruyaos.Runner.GEProton//<major>` and 05 §6.4's `//<major>` (Flatpak mounts one branch per id, fixed in each app's metadata, so a branch per major would hide all majors but one). Every major is visible at once; `runner.json`, not the folder name, gives family and version.
- **Generated metadata.** `[Extension org.ruyaos.Play.Runner]` with `directory=runners`, `subdirectories=true`, `version=1`, `no-autodownload=true`, `autodelete=false`; the launcher point keeps `version=1` and gets `no-autodownload=true`. Windows runners also get the Compat.i386 and GL32 points. The launcher scans `/app/runners/*/runner.json` (at most 32 folders, no links followed).
- **Steam.** It shares the same tree through one more link under Steam's `com.valvesoftware.Steam.CompatibilityTool` point (`com.valvesoftware.Steam.CompatibilityTool.<Name>//stable`, from the Steam Flathub manifest: `subdirectories: true`, `directory: share/steam/compatibilitytools.d`): one copy on disk, never a second build. One `L+` line per Proton runner folder (`services/ruya-play/tests/platform.rs` holds folders and lines together); GE-Proton's own `compatibilitytool.vdf` in the tree is what Steam reads. `ruya-session` makes the tool Steam's default once per profile (`03` Steam row; RUY-35).
- **ABI change.** The image ships launcher branches 1 and 2 side by side until reconcile has moved every app to 2. The importer stamps a metadata generation into `installed.json`; at start, reconcile re-generates and re-commits our apps whose generation is older.
- **A generation bump never widens a grant** *(Accepted (lead, 2026-11-20), RUY-909)*. A re-commit runs without the admin gate and the update diff (05 §8), so it may only keep or narrow what an installed app has. (1) **Rule:** a row of 05 §8's permission table never gains a Flatpak grant; a broader grant is a new vocabulary word, which reaches an app only through a package update (update diff, admin gate). (2) **Enforced at run time:** the re-commit compares the new metadata's permission sections (`[Context]`, `[Session Bus Policy]`) with the deployed app's; if anything is added it leaves the app as deployed (fail closed), logs `recommit.widens` and keeps the app's older generation, so the image keeps that launcher branch. (3) **Caught at build time:** a golden of each word's grants in `ruya-play-trust`'s tests; a row that is not a subset of its golden fails, new words pass. A re-approval path in the shell is not built: under (1) it never has anything to ask.
- **Fallback** if the VM check shows Flatpak will not mount unmaintained extensions from the system installation: a boot-time commit of the `/usr` trees into `ruyaos-play-local`, signed by the device key, with the same ids. The ADR is amended only on that point.
**Consequences.** Nothing reaches the sandbox that is not in the signed image. A profile user can shadow an extension in their own user installation, but only for their own runs (no escalation). The preinstalled runners and the launcher are always in the OS image and update with it (owner, 2026-11-19, RUY-897); a packager who needs another version bundles it. Every runner RuyaOS offers ships this way (owner, 2026-11-20, RUY-915, narrowing 2026-11-19: GE-Proton, current and previous major, and Wine stable; RUY-37), one id per family and major; there is no Store channel for runners.

### ADR-039 — A game asks the OS for the player's own ROM: `requires.rom` in play.json and one read-only file through `Platform1` — *Accepted (owner, 2026-11-21, RUY-1012; proposed by the lead in lead-40). Open: disc sets and BIOS files the same way*
**Question.** The owner asked (2026-11-21) whether a recompiled port (a `.play`, or a Flatpak, that contains no game data, e.g. an N64 recomp) can ask the ROM manager to import the game's ROM and run it. ADR-020 gives emulators ROM folders (`RomRoots`) and content ids (`Identify`), but nothing hands one specific file, chosen by hash, to a game that needs exactly that file.
**Proposal.** (1) `play.json` gains an optional `requires.rom` list: `system` (ADR-020's ids), the accepted `sha1` values (one per known good dump), a display name and an optional size; `ruya-play-format` validates it and the package page and the Library show "Needs your copy of <name>" until a match is in the profile's (or the shared) ROM library. (2) A `Platform1` call (tier B, experimental first, ADR-022) `RequestRom(system, hashes)`: `ruya-gamedata` looks up a file whose content hash matches; when none is there, the shell offers Import from USB by controller (the hub's import, ADR-020 (6): only after a player action), checks the hash and stores it. The app receives a read-only fd for that one file (or a read-only bind of it into its next sandbox), never the folder or another ROM; the answer is per profile and per app, revocable in the app's permissions. (3) AppImages are not a way in: third-party code runs only in Flatpak sandboxes (`CLAUDE.md`); a recomp ships as a `.play` or a Flatpak and both use the same call. (4) RuyaOS ships, downloads and suggests no ROMs, BIOS or game data (ADR-020 (6), 05 §1); only the player's own dumps are used, and the hash list is the packager's, never a download source.
**Alternatives.** (a) The game reads `RomRoots` itself and scans: it sees every ROM of the system and duplicates the hub's identification. (b) The packager bundles the data: excluded by 05 §12 for copyrighted game data. (c) A file picker portal with no hash: the player can hand over the wrong file and the game has to explain why.
**Consequences.** A new public format field and a new public call (owner-level under ADR-022), after ADR-020's service exists (epic T-302); a developer-guide section, a sample (a "hello-recomp" that needs a tiny public-domain ROM), mock and conformance case. Open: whether a recomp may also ask for a disc image set (several files) and BIOS files the same way.

### ADR-040 — `run.writable`: a per-profile game tree for games that write next to their exe — *Accepted (architect, 2026-11-21, RUY-1015); inside ADR-014 and ADR-037*
**Context.** UT GOTY (RUY-1007, Dell) writes its ini, log and saves into `System/` and `Save/`, but `/app/payload` is read-only. An overlay is not possible: the sandbox gives no user namespace with mount rights and no `/dev/fuse`. Flatpak cannot bind anything over `/app`. Hard links do not work either (the files are root-owned, `protected_hardlinks`, and they sit on another mount).
**Decision.**
- **Format (tier C, additive).** `run.writable[]` is optional: at most 16 payload-relative folders, with the table's path rules. It may not be the root and may not overlap another entry (`run.writable_overlap`). A folder may be missing from the table, in which case it is created empty. The table bytes under these folders are capped at 2 GiB (`run.writable_too_large`) and 16384 files (`run.writable_too_many_files`; initial values, kept in `limits.rs`). `${game}` is a new placeholder, valid only with `writable` (`run.game_placeholder_without_writable`). With `writable`, `run.command[0]` and `run.cwd` must start with `${game}` (`run.writable_needs_game`). `${payload}` keeps meaning the read-only original. `data.saves` gains the root `game:`. Without `writable`, nothing changes.
- **Tree.** `${game}` = `${data}/.ruya-play/game/`. Every folder is a real folder. Outside the writable folders, folders are 0500 and files are links to `/app/payload/...`, so writes fail there exactly as they do today and no change is silently lost. Inside the writable folders, folders are 0700 and files are copies: 0700 when the table marks the file executable, else 0600. **The file `run.command[0]` names is always a copy**, even outside the writable folders. The working folder is a real folder, so `getcwd` stays in the tree.
- **Why not links all the way down.** Wine maps a Unix path to `Z:` lexically (`find_drive_rootA` matches prefixes against drive roots and does not use `realpath`), so `GetModuleFileName` should give the link path. `/proc/self/exe`, however, resolves links (native games, `SDL_GetBasePath`), and so does `getcwd`. Copying the entry file covers both, and the design works whichever way Wine resolves the path; the launcher ticket's VM check confirms the module path for Wine and GE-Proton.
- **Why not a full copy.** It would double the disk for every profile. Copies use FICLONE (reflink) when the filesystem allows it, else a byte copy (`ruya-fs`).
- **Record.** `state.json` gains `game_build`, the package `build` the tree was made from. `${data}/.ruya-play/game-base.json` (`format`, `build`, at most 16384 entries, at most 4 MiB) holds the play.files SHA-256 of each file copied into a writable folder (known from the table: nothing is hashed when a copy is made). The game can write both files, so both are read as untrusted. A missing or unreadable base counts as "every file changed": player data is kept, never deleted.
- **Update and rebuild.** The launcher acts when the tree is missing or `game_build` differs from `/app/play.json`'s `build`. It builds `game.new/` from the new table and walks the writable files: a file whose current hash equals its base hash is replaced by the new build's copy; a file the game changed or made is moved over with `renameat`, never copied; changed or made files in a folder the new build no longer lists go to `.ruya-play/game-kept/<old build>/` with a log line (only the newest such set is kept, as with the epoch backups, RUY-911). Then it writes `game-base.json` and `state.json` and renames `game.new` into place; an interrupted rebuild starts again from `game.new`. The current files are hashed only during an update. Every step goes through `ruya-fs` (no-follow, links kept as links), which gains `rename` and the reflink copy. An epoch rebuild of the prefix leaves the tree alone.
- **Trust.** The tree is game-writable data. The game can swap its own executable, but only inside its own sandbox and profile, which is no more than the code it already runs can do. The tree adds no Flatpak grant, so ADR-038's generation rule is untouched.
**Consequences.** One tree walk per new build at launch, plus hashing of the writable files at an update; the per-profile disk cost is the writable bytes (zero with reflink). Packagers declare folders instead of game switches (`INI=` remains an option, windows-games.md). Not owner-level under ADR-022 (additive, optional, writes only into `${data}`); ADR-022 (3) still applies: developer-guide paragraph, sample, conformance test, `ruya-api-reviewer`.

### ADR-041 — Steam games are child instances in Session1 — *Accepted (architect, 2026-11-22, RUY-815)*
**Context.** A Steam game runs in Steam's own portal subsandbox scope(s) (pressure-vessel's `steam-runtime-launch-client --bus-name=org.freedesktop.portal.Flatpak`), under Steam's Flatpak id, beside the scope ruya-session attached and the client's scope (Dell 0.0.102, RUY-813). The owner wants the game in the Hub and with play time as its own item (RUY-815). The shell keys running apps by Flatpak id (`Library.sessionAppId`), so without an item key a second mapping would be bolted on beside the first.
**Decision.**
1. Every running record gets `item` (the Library1 item id: `flatpak:<id>` or `steam:<appid>`) and `parent` (an instance name, or ""). A Steam game is a child instance of the profile's Steam instance; its instance name is opaque and set by the service.
2. A scope belongs to a child when its processes carry `SteamGameId` (else `SteamAppId`), digits only, read as the profile user by a helper (`ruya-session steam-probe <scope>`, the x11-run and steam-default-tool pattern). Every other Steam scope belongs to the parent. **Amended by spike RUY-1047 (Dell, 2026-11-22; Half-Life 70 native, BioShock 7670 and Bionic Commando 21670 on GE-Proton):** "any process" is wrong. While a game runs, the parent's scopes also carry the id: the reaper (`reaper SteamLaunch AppId=N`) and `_v2-entry-point` in the attached scope, and `steam-runtime-launch-client --alongside-steam` in the client's. Pre-launch steps get short scopes of their own: UpdatingDRM carries `SteamGameId` without `SteamAppId`, and an install script carries only `STEAM_COMPAT_APP_ID`. The rule is therefore: a scope, other than the instance's attached one, belongs to child G when its sandbox's **top process**, the oldest process in the scope whose environ carries `FLATPAK_ID` (pv-adverb), carries **both** `SteamAppId` and `SteamGameId`, digits only; G = `SteamGameId`. ("Oldest with a non-empty environ", the spike's first wording, is wrong: RUY-1052 found on the Dell that each scope's xdg-dbus-proxy and its bwrap are older than pv-adverb and carry an environ without the ids.) Every other scope, the pre-launch ones included, belongs to the parent. The environ is readable as the profile user. Each game made exactly one such scope, which ends within 0.5 s of the game's exit. The X `STEAM_GAME` property matched in every case. Not yet observed: non-Steam shortcuts (`SteamAppId` may be 0), and a launcher handing over to a game in a new scope. Rejected: parsing console_log (log text, not an interface), wrappers or edited launch options (they change the player's settings), and the X `STEAM_GAME` property (a window fact, overlay-dependent, needs an X client; a spike cross-check only).
3. New method `LaunchItem(item, profile) -> (status, instance)`. Session builds `steam://rungameid/N` itself from the digits and never takes Library's opaque `launch` string. If Steam is not running, its unit starts with that URL as its argument; if it is, a short profile-user unit forwards the URL. The child stays `starting` until its scope appears, and becomes `launch-failed` after 120 s. `Launch(app_id)` stays.
4. Games started inside Steam's own UI become children the same way. The shell re-reads ListRunning when AppStarted names an instance it does not know. AppStarted and AppExited keep their signature, with the parent's app_id.
5. A child ends when none of its scopes has existed for 3 s (a launcher handing over to the game). Stop, Freeze, Thaw and Kill on a child touch only its scopes; Stop on the parent stops the children first, then Steam. InstanceOfPid answers the child for any pid in its scopes.
6. The ledger's session and day rows get `item`. While Steam's instance is in front and has a running child, the shell's front instance is the child: ReportPresence reports it and the Hub shows it, with "Close game" and "Close Steam".
7. **Parent and children (lead, 2026-11-22, RUY-1051 review; inside this ADR and ADR-042):**
   - Stop and Kill on a parent end its children first, then the parent.
   - Freeze and Thaw on a parent apply to every child, and to the parent's own scopes only as far as its app-table `freeze` rule allows (Steam is `never`).
   - Each record's `frozen` describes that record alone.
   - `LaunchItem` for a Steam item whose child is already running answers `already-running` with that child's instance.
   The Session1 XML carries the same text.
**Consequences.** Session1 XML, mock, D-Bus client and contract tests change together; the shell keys its running model by `item`; Library, Home, the game page and play time stay unchanged. Spike RUY-1047 proves point 2 first.

### ADR-042 — Freeze what is a game, never a client — *Accepted (architect, 2026-11-22, RUY-817)*
**Decision.**
1. Freeze on a Steam child freezes only the child's scopes.
2. Audio is parked per instance: a stream belongs to an instance when its kernel-verified peer pid (`pipewire.sec.pid`) is in one of the instance's cgroups. Matching by Flatpak id, or by the pid a client reports about itself, is gone. **Amended by the owner (2026-11-22, RUY-1081 option a):** not buildable as written. In the console's PipeWire every profile stream's `pipewire.sec.pid` is the profile's pulse server (`ruya-pulse@<user>`), never the app; pipewire-pulse reads the real peer pid but does not export it (Dell 0.0.104). Parking stays per profile (park.rs: a profile's streams are parked only while every running app of it is frozen or held, RUY-1054); a frozen game's stream goes idle and `pulse.idle.timeout` suspends the card anyway. No patched pipewire-pulse.
3. The image app table (ADR-043) gives each app `freeze = always | never`; Steam is `never`. For a `never` app, the Hub's pause and ADR-019's background freezing park its audio and keep its input neutral (the shell route), but never touch the cgroup freezer. A child is frozen anyway.
4. For third-party apps, ADR-019's `X-Ruya-Background` is the only public door (planned with T-279, RUY-133; not built: nothing reads it yet, lead-43). This ADR adds no public capability; whether apps get more is an owner question (RUY-1060). **Superseded by the owner (2026-11-22, RUY-1060 option b):** third-party apps get a public "do not freeze me" declaration. Its format, what the player sees, the player's override and the limits that keep ADR-019's memory and battery model go into their own ADR under ADR-022 (RUY-1062) before anything is built: ADR-046.
Rejected: SIGSTOP of a subtree, and child cgroups inside a Flatpak scope (we do not own that tree, and it races with fork).
**Consequences.** Before it is built, the Dell study RUY-1049 proves that freezing only the game is safe for Steam. Built (RUY-1054): Steam's row says `never`; a Freeze that reaches a `never` instance marks it held, and its sound is parked with the profile's frozen apps. Parking is per profile and app id until RUY-1081 decides per-instance parking (point 2). A profile that leaves freezes a `never` app's own unit too (RUY-1063, as ADR-046 point 2 has it for `client`): its open `/dev/uinput` descriptor must not make devices in the next profile's time; whether a long-frozen Steam client reconnects after the Thaw is a Dell check (hw pending).

### ADR-044 — Steam's display: nested gamescope with Steam integration, within ADR-034 — *Accepted (architect, 2026-11-22), conditional on spike RUY-1048*
**Decision.** ADR-034 points 1, 2, 3 and 5 are kept. Gamescope runs as a Wayland client of the profile's socket, one per instance, inside the instance's unit, and its Xwayland is reachable only by that instance. ADR-034 point 4 (xwayland-satellite) stays the mechanism for every other X11 app. Steam gets `display = gamescope`: a helper like x11-run starts `gamescope -e` (Steam integration) around `steam -gamepadui`.
**Reasons.** Steam reads the focused game from gamescope (the `GAMESCOPE_FOCUSED_APP` family of root properties), which is the input RUY-812 lacks under the satellite. The shell sees a single toplevel owned by Steam's instance, and ADR-041 point 6 needs nothing more from the window side. Pad identity (RUY-820) is out of the display path's reach; RUY-449 is its structural answer. Gamescope never gets the physical pads.
**If the spike fails,** Steam stays on the satellite and RUY-812 goes back to tracing what Steam reads.
**Spike result (RUY-1048, Dell 0.0.104, lead 2026-11-22): not accepted for now; Steam stays on the satellite.** Stock gamescope 3.16 does not start on the compositor (it needs wp_presentation, relative-pointer and pointer-constraints, and binds wl_seat v8 / wl_output v4 / wl_data_device_manager v3 where Qt offers v4 / v2 / v1). A patched build gave one toplevel and the right `GAMESCOPE_FOCUSED_APP`, but its Xwayland listens on an abstract socket with no cookie, so a sandbox with `--nosocket=x11` connected unauthenticated (ADR-034 point 5), and wlroots has no option to turn that off. Accepting would mean two permanent patches against a package we don't control, for a benefit (Steam applying a game's controller config) not yet shown. The one-toplevel gain was solved in the shell (RUY-1089). By the owner's rule (2026-11-22) the Steam goal pauses here. Revisit when upstream gamescope can run without an abstract or unauthenticated X socket, or when the compositor has the protocols for its own reasons (RUY-437, RUY-778).

### ADR-045 — Per-profile readers — *Accepted (architect, 2026-11-22)*
**Context.** Library's Steam discovery (RUY-958), saves (RUY-136) and Steam game identity (ADR-041) all need a route into profile homes, which spec 03 decided on 2026-11-09 and nobody built. Library1 has no profile dimension, although Steam items are per profile.
**Decision.** Root and system services stay out of profile homes. ruya-session runs a short-lived reader as the profile user, in the profile's manager, with the hardening of app units: `ruya-library profile-scan` for Steam items and art, the saves lister later. The reader reads through `ruya-fs` (links refused) and prints bounded JSON, art included, to stdout. ruya-session passes it to ruya-library through a root-only method `Library1.PutProfileItems(profile, data)`, under a per-method policy for root alone. ruya-library checks and decodes everything again, because the data comes from a sandbox. Library1 serves the active profile's view: it follows ActiveProfile, and ItemsChanged fires on a switch. Steam's VDF and safe_file code move into one shared crate (RUY-960). No profile process gets bus access. **The reader's sandbox (RUY-1102):** the properties are only ones a transient unit in a user manager accepts and their effect is measured, not assumed: the home and `/run/user/<uid>` are read-only through `ProtectHome=read-only` (`ProtectSystem=strict` leaves them to it), and sockets are closed by the system-call filter (`~@network-io`), not by `RestrictAddressFamilies=`; 03 §5 (the Library row) lists them.
**How Library1 learns the active profile (lead, 2026-11-22, RUY-1056 review; inside this ADR):** ruya-library may not call or receive Profiles1 (its policy allows the shell and root only). ruya-session, which already follows ActiveProfile, tells it through a second root-only method, `Library1.SetActiveProfile(profile)`, sent before any scan on every change; Library1 mirrors it as the property `ActiveProfile`. The service checks the caller's uid itself (0 only) as well as the policy. ruya-session runs the reader when the active profile changes, when ruya-library's bus name gets a new owner, when the profile's Steam instance ends, and on `Library1.ProfileScanWanted(profile)`, which `Rescan` sends.

### ADR-046 — "Keep me running": a declared background reason `client` — *Accepted (owner direction 2026-11-22, RUY-1060 b; details lead, 2026-11-22, RUY-1062)*
**Context.** ADR-019 freezes every app that is not in front, unless it declares a background reason (`audio`, `download`) that currently holds. Some apps are useless frozen: a launcher or store client whose games it starts must keep talking to it, a chat or voice client, a remote-play host. The image covers the apps it knows with the app table's `freeze = never` (ADR-042, ADR-043: Steam). The owner decided that third-party apps get a public declaration too (RUY-1060, option b, against the architect's and lead's recommendation a).
**Decision.**
1. **One declaration, one place.** The background reasons of ADR-019 are declared in the app's **Flatpak metadata**, group `[X-Ruya]`, key `Background`, a `;`-separated list of `audio`, `download`, `client` (`flatpak build-finish --metadata=X-Ruya=Background=client`). The metadata is signed with the commit, readable before install (`flatpak remote-info --show-metadata`, the Store's install sheet) and after (ruya-session already reads `/var/lib/flatpak/app/<id>/current/active/metadata` through `ruya-keyfile`). This replaces T-279's "AppStream metadata" wording: AppStream stays for the catalogue, not for behaviour. A `.play` package declares it in `play.json` (`background`, the same list) and `ruya-pack` writes the group; unknown reasons are ignored, a malformed value counts as none (logged). The old desktop-entry spelling `X-Ruya-Background` is not read. The declaration is read from the installed commit at launch. **Consent follows the commit:** when an update adds or changes a reason, the Store's update sheet shows the same row as the install sheet, and until the player accepts it the app is treated as declaring the reasons it had before. "Signed" means the publisher's signature, not a vetting by RuyaOS; a local bundle shows the row on its install sheet the same way. How `download` *holds* (ADR-019) is a separate question owned by RUY-133; this ADR settles only where reasons are declared.
2. **What `client` means.** A `client` app is never frozen by ADR-019's background rule (behind Home, after Switch to) and never by the Hub's pause: it gets exactly the treatment of the app table's `freeze = never` (ADR-042 point 3): audio parked, input neutral (the shell route) and no cgroup freeze. `client` does not keep its sound: an app that must be heard behind Home declares `audio` too, which holds only while it plays (ADR-019). The app table and the declaration feed **one** freeze policy in ruya-session; a table row decides over a declaration for the same app. Children of an instance (ADR-041) are frozen whatever their parent declares, and end with their parent. `client` is the one reason with no hold condition (ADR-019 said "only while the reason holds"; the owner overrode that for this reason, RUY-1060 b). **Only for the active profile:** the declaration exempts an app from the behind-Home rule and the Hub's pause while its own profile is the active one. A profile switch, a lock, sleep and "Who's playing?" freeze or stop a `client` app exactly like any other (T-165); it thaws when its profile is active again, and nothing of one profile's `client` app is shown to another profile. A voice client declares `audio` as well; microphone capture is protected by neither reason.
3. **Limits that keep ADR-019's model.**
   - **CPU and I/O:** while not in front, a `client` app's unit and scopes run with `CPUWeight=20`, `CPUQuota=50%` (half of one core) and `IOWeight=20`, so it cannot take frames from the game in front. It occupies one of ADR-019's open-app slots like any app.
   - **What the limits do not stop:** a game that declares `client` can stay online and use spare CPU, and GPU use is not limited (a follow-up: no frame callbacks for hidden windows, 03 §4.6). The player's override and the Hub's "Running in the background" line are the real control; curated-remote review is advice, not enforcement. The developer guide says so.
   - **Memory:** it is closed under memory pressure like any background app (ADR-019 point 3, least recently used first, toast and relaunch card); freezing frees no memory, so the declaration changes nothing here.
   - **Battery:** on battery power it is frozen after 10 minutes behind Home (a console on mains power never does this).
   - **Not a channel:** the declaration grants no bus name, permission or device; it is Tier C (a data-only format, ADR-022), `experimental` until the first release.
4. **What the player sees.** The Store's install sheet lists "Keeps running in the background" with the permission rows; the game page and the Hub say "Running in the background" instead of "Paused" for a `client` app. The player can turn it off per app and profile ("Allow to run in the background", on by default for a declared app) in the per-app permission table that Settings > Privacy owns (ADR-022, T-220), kept per profile in ruya-platform's root-owned store (amended, lead 2026-11-23, RUY-157: a file in the home would let an app with home access grant itself; see ADR-022 "Permission store") and keyed by app id so it survives updates (per profile, so a guest or child profile cannot change another profile's choice); turned off, the app is treated as declaring nothing. The global "Pause games when Ruya Hub opens" setting keeps its meaning.
5. **Developer surface.** The developer guide's lifecycle chapter replaces rule 7 ("there is no call to say do not freeze me") with the declaration, its limits and the advice to use it only for clients, never for a game; `api-surface.md` lists it; the sample gets a declared variant and the mock shows "Running in the background" for it; `api-surface.md` (tier C, experimental) says why behaviour lives in Flatpak metadata and catalogue text in AppStream, and `play.json`'s schema gets `background`. The conformance runner checks that a declared app stays unfrozen behind Home with the limits above, and the abuse cases: an unknown reason is ignored, a malformed value counts as none, a reason added by an update stays off until accepted, a profile switch or lock freezes it, the memory-pressure close reaches it, the player's override freezes it, and a table `freeze = always` wins. The guide keeps "do not try to prevent the pause" for games. Store review on the curated remotes flags a `Game` app that declares `client`.
**Rejected.** A runtime call (`Platform1.SetBackgroundReason` for `client`): a promise made at install is visible to the player before install, a call is not. AppStream as the place: it is catalogue data, not what the installed app is. A per-player setting alone (option c): the owner chose a developer declaration.
**Consequences.** Build tickets: the parser and the one freeze policy in ruya-session (with the table), the CPU weight and battery rule, the Store sheet row, the Hub and game-page copy, the per-app override, `ruya-pack`'s `background` field, docs, sample and conformance. RUY-133 (T-279) reads its background reasons from the same group.

### ADR-047 — ruya-platform runs as its own system user — *Proposed (architect, 2026-11-23; owner question)*
**Question.** The app-facing door `ruya-platform` (ADR-022) runs as uid 0. Every internal bus policy allows root, so a compromised door can call Profiles1, Store1 and Update1 admin methods; with no capability at all, uid 0 reads root-owned 0600 files as their owner (`ProtectSystem=strict` leaves `/var` readable), today including the PIN hashes in `/var/lib/ruyaos/profiles.toml`, and it can read `/proc/<pid>/root` of capability-less root services such as ruya-session. ADR-022 decision 4 removes its capabilities; this ADR asks whether it should stop being root.
**Proposal.** The door runs as the sysusers user `ruya-platform`, which owns `org.ruyaos.Platform1` and its 0700 `StateDirectory`. It reaches internal services only under a per-method allow-list, as ADR-029 does for `ruya-link`: today Profiles1's read members used by `ruya-profiles-client`, later each internal service it forwards to. The identity helper's socket becomes `SocketUser=ruya-platform`.
**Options.** (a) keep root, hide the other state directories and drop the capabilities (ADR-022 decision 4 and the PIN-directory ticket); (b) this proposal; (c) as (b) with `DynamicUser=` (rejected: the state needs a stable owner). **Recommendation: (b).** Root is equivalent to every tier-A API (ADR-022's "never public" list), and the door is the one service every sandbox talks to. Decision 4 and the PIN-directory move come first either way; they do not depend on the answer.
**Consequences if accepted.** It changes the invariant "D-Bus policies stay restrictive: the shell and root only" by one more per-method caller, as ADR-029 did. A compromised door can then no longer read root-owned files, call any admin method, or ptrace-read other root services.
